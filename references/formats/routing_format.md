# Routing format

> Format-Version: 1

Model routing gives each Purlin skill a tier and each tier a model, so a skill that runs a script
and reads its output does not spend what a skill that writes rules spends. Each skill names its
tier in its own front matter; the project gives each tier a model in `.purlin/routing.json`;
`purlin:route on` writes one project skill per Purlin skill that runs it on that model. No script
decides. This page is the one home of the tables, the file, the project skills, the hand-off and
the hand-off message.

## The two tables

Each skill's tier is the `tier:` line of its front matter, `skills/<name>/SKILL.md`:

| Skill | Tier |
|-------|------|
| `status` | `fast` |
| `drift` | `fast` |
| `test` | `balanced` |
| `build` | `balanced` |
| `init` | `balanced` |
| `anchor` | `balanced` |
| `audit` | `balanced` |
| `spec` | `performance` |
| `spec-from-code` | `performance` |
| `sign` | `performance` |

`route` names no tier. `test` is `balanced`, the session's own model, because a switch to
another model and back rewrites the conversation into each model's cache, which on a measured
three-part feature cost more than running the tests on `haiku` saved. `audit` is `balanced` because its session starts a script and reads the
result; the judgement is in the planted bugs, written on the `performance` model, as "The audit's
planted bugs" below says.

Each tier's default model, the name Claude Code gives the slot:

| Tier | Model |
|------|-------|
| `fast` | `haiku` |
| `balanced` | `sonnet` |
| `performance` | `opus` |

The tier names say the size of the work, not the provider. In Claude Code `haiku`, `sonnet` and
`opus` are slots a gateway may fill with another provider's models; another harness names its own
models in `tiers`.

## The file

`.purlin/routing.json` is committed and the team's:

```json
{
  "schema": "purlin-routing/1",
  "enabled": true,
  "tiers": { "fast": "haiku", "balanced": "sonnet", "performance": "opus" },
  "skills": { "sign": "fast" }
}
```

| Field | Required | What it holds |
|-------|----------|---------------|
| `schema` | yes | `purlin-routing/1` |
| `enabled` | yes | `true` routes; `false` runs every skill on the session's model |
| `tiers` | yes | Each tier's model. A tier left out takes its default |
| `skills` | no | A skill whose tier in this project differs from its front matter, and that tier |

`.purlin/routing.local.json` holds `tiers` alone and is one person's: a person whose models differ
writes theirs there, and git ignores it.

## The project skills

`purlin:route on` writes `.claude/skills/<skill>/SKILL.md` in the project for each skill that
names a tier, and no project skill for `init`, which runs before routing is set up and whose
name Claude Code's own `/init` takes.

The tier is the `skills` entry of `.purlin/routing.json` for that skill where there is one, before
the skill's own `tier:`. The model is the tier's entry in the `tiers` of
`.purlin/routing.local.json` where there is one, before the `tiers` of `.purlin/routing.json`,
before the default.

For `spec`, `spec-from-code` and `sign`, which stop to ask the person, the project skill runs the
skill in the session where the session is on its model, and otherwise hands the whole skill to a
`purlin:runner` subagent on that model, as "The hand-off" below says:

```markdown
---
name: <skill>
description: Generated by purlin:route. Runs purlin:<skill> on this project's model for it
---

Say `<skill>: <tier> (<model>)`. If you already run on `<model>`, run purlin:<skill> here with
these arguments, $ARGUMENTS, and stop reading. Otherwise start a `purlin:runner` subagent on the
model `<model>` with this message, and do none of the work yourself:

<the hand-off message, "The hand-off message" below, filled in: Command: purlin:<skill> $ARGUMENTS>

Show the person what the subagent returns, word for word. When the person answers, send the
answer word for word to that same subagent with SendMessage, and show its reply. Go on until the
subagent says the work is done.
```

For each other skill, the project skill names the model, and Claude Code runs the command on it:

```markdown
---
name: <skill>
description: Generated by purlin:route. Runs purlin:<skill> on this project's model for it
model: <model>
---

Say `<skill>: <tier> (<model>)`, then run purlin:<skill> with these arguments: $ARGUMENTS
```

A command the person types, `/<skill> <arguments>`, runs on that model; the turn after it is back
on the session's model. A request in plain words, or `/purlin:<skill>` typed whole, runs on the
session's model. The description marks the file as written by `purlin:route`; `purlin:route on` never writes
over a file there without that mark.

## The hand-off

Where the session already runs on the skill's model, the skill runs in the session and no
subagent starts. Otherwise a skill that asks the person runs whole on a `purlin:runner` subagent
on its model, because
Claude Code keeps a typed command's model for one turn alone and the person's answer is a turn of
its own. Each answer is sent to the same subagent with `SendMessage`, so the subagent keeps its
conversation and every turn of the skill runs on that model; the session only shows what it
returns and passes on what the person says.

A skill another skill runs, such as the `purlin:test` that `purlin:build` runs, takes the model
already running: Claude Code applies a skill's model only to a command the person types.

## The hand-off message

The whole message the subagent starts with, filled in by the project skill. It holds no conversation: what it needs is in the
files it names.

```
Purlin hand-off
Command:  purlin:<skill> <arguments>
Goal:     <the rule's own sentence from the spec, or the person's request in one line>
Model:    <model> (<tier>)
Context:  <one or two lines: what the person asked and what was decided>
Previous: <the skill that ran this one>: <its result in one line>, or none
Read:     <the spec>; <the test file>; <the evidence file>; any other file, by path
Rules:    The model is chosen; do not route again. If the person must answer, stop and return the question.
Return:   Up to 5 lines: result, files changed, commits, left to do, and the paths that hold the detail.
          Where the person must answer: return what they must read, such as the draft, and the
          questions, word for word.
```

The session shows the person the subagent's reply word for word, so a draft is read and answered
in the same conversation; showing it costs the session about $0.05 more than a summary would.

`agents/runner.md` is the subagent: it has the tools `Skill`, `Read`, `Write`, `Edit`, `Bash` and
`PowerShell` alone, so it starts with a small context, and a platform's harness drops the shell it
does not have.

## The session

The session reads requests in plain words, passes messages for the hand-off and runs the skills
other skills run, so it runs on the `balanced` model. `purlin:route on` writes this into the project's Claude Code settings,
keeping every other setting:

```json
{ "agent": "purlin:purlin", "model": "sonnet" }
```

It writes `.claude/settings.json`, or `.claude/settings.local.json` where the models are one
person's. `purlin:route off` takes the two out. A `--model` given when a session starts, or
`/model` in it, wins for that session.

## The audit's planted bugs

Where `.purlin/routing.json` is on, the audit writes its planted bugs on the `performance` model,
which its own call to the model is given as `--model`; with no file, or with `"enabled": false`,
it names no model and the harness's default answers. The model in an `@ai(...)` tag is not
routed: it is the model that proof's test runs on.

## Limits

- A model the harness does not know fails at the first command that names it;
  `purlin:route on` starts no model to check.
- The hand-off is a step the session follows, not code: nothing forces it.
- The subagent starts with its own instructions and the hand-off message, about 14,000 tokens, and
  the session spends on passing messages; a spec handed off cost $0.72 where a whole session on
  `opus` spent $0.40, measured on one small feature.
