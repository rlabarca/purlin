# Feature: skill_init

> Scope: skills/init/SKILL.md, scripts/init/scaffold.py
> Stack: markdown (skill definition)
> Description: The `purlin:init` skill initializes a project for spec-driven development. The skill asks the questions; `scripts/init/scaffold.py` writes the files: `.purlin/`, `specs/`, the config, the proof plugins, the runner wiring, the gitignore block, the dashboard and both git hooks.

## Rules

- RULE-1: Skill file has YAML frontmatter with `name` and `description` fields
- RULE-2: Skill file contains a `## Usage` section documenting command syntax
- RULE-3: The `name` field in frontmatter is `init`, matching the directory name
- RULE-4: Skill includes commit instructions or git operations for file modifications
- RULE-5: `--add-plugin` validates plugin files against language-specific patterns (Python: `proofs`+`json`, JS: `proofs`+`JSON`, Shell: `purlin_proof`, Java: `proofs`+`Proof`) and warns if validation fails
- RULE-6: `--add-plugin` supports both local file paths and git URL sources with distinct handling for each
- RULE-7: `--list-plugins` identifies built-in plugins (`pytest_purlin`, `jest_purlin`, `purlin-proof`) by framework name and labels all others as `custom`
- RULE-8: Running `scripts/init/scaffold.py` in a git repository that holds none of them creates `.purlin/`, `.purlin/plugins/`, `specs/` and `specs/_anchors/`
- RULE-9: `config.json` is valid JSON containing all 8 required fields: version, test_framework, spec_dir, pre_push, remote_verification, mutation_checks, report, digest
- RULE-10: The version field in config.json matches the contents of the VERSION file
- RULE-11: Default config values are test_framework: auto, spec_dir: specs, pre_push: warn, remote_verification: off, mutation_checks: false, report: true, digest: auto. `mutation_checks` defaults to `false` because the check costs roughly twice the tokens and minutes per proof, so it is a decision the project makes rather than a cost it inherits (RULE-57). `remote_verification` defaults to `off` because setup is offered on discovery rather than at init (`skill_test` RULE-11): a project with no runner-gated proofs has no runner to configure, so init writes the field and declines to ask about it
- RULE-12: When conftest.py exists at project root, auto-detection selects pytest
- RULE-13: When pyproject.toml contains [tool.pytest], auto-detection selects pytest
- RULE-14: When package.json contains jest, auto-detection selects jest
- RULE-15: `--test-framework vitest` scaffolds `.purlin/plugins/vitest_purlin.ts` (Vitest's reporter API differs from Jest's — Vitest never calls onTestResult/onRunComplete — so the native TypeScript reporter is used for both JS and TS Vitest projects; Vitest loads .ts reporters natively via Vite)
- RULE-16: `--test-framework pytest,jest` scaffolds both `.purlin/plugins/pytest_purlin.py` and `.purlin/plugins/jest_purlin.js` and writes `test_framework` as the list it was given
- RULE-17: `--test-framework shell` scaffolds `.purlin/plugins/purlin-proof.sh`. Shell is scaffolded because it was selected and never as a fallback: it carries no detection heuristic in `references/supported_frameworks.md`, and a project where detection finds nothing gets no plugin rather than a silent shell default (RULE-71)
- RULE-18: Scaffolded pytest_purlin.py in .purlin/plugins/ is byte-identical to scripts/proof/pytest_purlin.py
- RULE-19: Scaffolded jest_purlin.js in .purlin/plugins/ is byte-identical to scripts/proof/jest_purlin.js
- RULE-20: Scaffolded purlin-proof.sh in .purlin/plugins/ is byte-identical to scripts/proof/shell_purlin.sh
- RULE-21: Scaffolded pytest_purlin.py produces valid .proofs-unit.json when run with @pytest.mark.proof markers
- RULE-22: Scaffolded jest_purlin.js produces valid .proofs-unit.json when invoked as reporter with [proof:...] markers
- RULE-23: Scaffolded purlin-proof.sh produces valid .proofs-unit.json when purlin_proof + purlin_proof_finish are called
- RULE-24: After init with empty specs dir, sync_status returns No specs found without errors
- RULE-25: Status progression: no proofs reports UNTESTED, all passing reports PASSING, one failing reports FAILING
- RULE-26: When report: true in config, sync_status generates .purlin/report-data.js containing valid PURLIN_DATA
- RULE-27: .gitignore contains all required purlin entries and does NOT contain `.purlin/report-data.js` (the digest is committed)
- RULE-28: Running init twice (re-init) does not create duplicate entries in .gitignore
- RULE-29: After init, .git/hooks/pre-push exists, is executable, and contains purlin
- RULE-30: When a non-purlin pre-push hook exists before init, the existing hook is preserved
- RULE-31: When report: true, purlin-report.html exists at project root; when report: false, it does not
- RULE-32: Full lifecycle works end-to-end: init creates structure, spec created, proof plugin runs, proofs emitted, sync_status reports PASSING, pre-push hook allows push
- RULE-33: Init prints DETECTING CODEBASE before scanning for test frameworks
- RULE-34: Init always presents the full framework selection list to the user, even when auto-detection succeeds, with detected frameworks pre-selected
- RULE-35: When a single framework is detected, the selection list shows it pre-selected with [x] and all others unselected with [ ]
- RULE-36: When multiple frameworks are detected, all detected frameworks are pre-selected in the list
- RULE-37: When no frameworks are detected, the selection list shows all options unselected
- RULE-38: The Purlin MCP server is bundled with the plugin — `.claude-plugin/plugin.json` declares a `purlin` entry under `mcpServers`; init does NOT write a `purlin` entry into the project's `.mcp.json` (a project-scope entry would shadow the plugin server with a version-pinned path that breaks on every plugin update)
- RULE-39: The bundled MCP server entry uses the `python3` command with `args` pointing to `${CLAUDE_PLUGIN_ROOT}/scripts/mcp/purlin_server.py`, so the path always resolves to the currently installed plugin version
- RULE-40: Init migrates legacy MCP config: when the project's `.mcp.json` has a `purlin` entry under `mcpServers` (pre-0.9.4 version-pinned path), init removes that entry, preserves all other server entries, deletes the file only when nothing else remains in it, and tells the user to reload plugins or restart the session
- RULE-41: Config has `"digest"` field with value `"auto"`, `"warn"`, or `"off"`
- RULE-42: After init, `.git/hooks/pre-commit` exists, is executable, and contains `purlin`
- RULE-43: When a non-purlin pre-commit hook exists before init, the existing hook is preserved
- RULE-44: In digest `auto` mode, running `git commit` triggers the pre-commit hook which regenerates `.purlin/report-data.js` and stages it into the commit
- RULE-45: After digest generation, `report-data.js` contains a `timestamp` field with a recent ISO timestamp and a `git_sha` field
- RULE-46: Digest generation does NOT trigger a new audit — `audit_summary` reflects only cached data (null when no cache exists)
- RULE-47: Scaffolded vitest_purlin.ts in .purlin/plugins/ is byte-identical to scripts/proof/vitest_purlin.ts
- RULE-48: The framework selection list is built dynamically from the framework registry (`references/supported_frameworks.md`) and presents an option for every proof plugin shipped in `scripts/proof/`; the skill does not hardcode framework names, so a newly shipped plugin (e.g. xUnit) appears in the selection once it is registered
- RULE-49: `purlin:init --update` decides what is pending from the project's contents and never from its `version` field, and every check names the files it counted. A project may have been initialized by any plugin version, edited by hand, or half-migrated already, so a version comparison would both miss real work and invent work that is already done; a count with no filename is not something a user can consent to. The seven ids are `legacy-tier-windows`, `legacy-proof-file`, `legacy-marker`, `plugin-copies-stale`, `config-fields-missing`, `receipt-v1` and `legacy-mcp`
- RULE-50: The marker rewrite covers every proof-marker syntax Purlin ships a plugin for, not only the one the project's `test_framework` names: pytest (`tier="windows"`), jest and vitest (`[proof:...:windows]`), shell (`PURLIN_PROOF_TIER=windows`), C (the `purlin_proof()` tier argument), phpunit and sql (`@purlin ... windows`) and xunit (the `PurlinProof` trait). Each becomes tier `unit` plus the platform in that plugin's own syntax. A project with two frameworks would otherwise have half its markers rewritten and half left writing files that satisfy nothing
- RULE-51: Nothing is written before consent, and the delta is shown first: the step prints KEEPING, UPDATING, RENAMING and ASKING per file in the shape `skills/spec/SKILL.md` Step 7c uses, then asks through `AskUserQuestion`. `--update --check` reports and writes nothing at all, which is also what a CI preflight runs
- RULE-52: The update never writes a proof entry and never writes a receipt. A proof entry is a claim that a test ran and a receipt is a claim that a suite passed, and a migration ran neither; renaming a proof file through `git mv` moves an existing record and keeps its history, which is a different act. `receipt-v1` and `legacy-mcp` therefore print directives (`purlin:verify` and `purlin:init --mcp`) and change nothing, and a feature whose markers were rewritten is re-run through `purlin:test` so its plugin writes the scoped file itself
- RULE-53: After the update, every `.purlin/plugins/` copy that has a counterpart in the installed plugin's `scripts/proof/` is byte-identical to it (extending RULE-18, RULE-19, RULE-20 and RULE-47 from the copies init scaffolds to every copy a project already holds). A copy with no counterpart is a plugin the project installed itself and is left alone
- RULE-54: The update is idempotent: a second `--check` reports nothing pending apart from the two directives the script does not apply, and a second `--apply` of the same ids changes no file. A migration that is not idempotent cannot be re-run after a partial failure, which is when it is most needed
- RULE-55: The provenance loss a renamed platform proof file suffers is stated to the user before consent: the commit that carried the old name still exists, but the report reads provenance per current filename, so the file reports `runner not recorded` until the runner next commits it under the new name. The rename does not delete evidence, and saying so is what stops the gap being read as one
- RULE-56: `purlin:init --mcp` is the MCP step of `--update` under its own name: `--update` runs it as the `legacy-mcp` migration and `--mcp` runs that one step alone. Two commands that both migrate `.mcp.json` by different rules is how a project ends up half-migrated
- RULE-57: `mutation_checks` is asked, never backfilled. `purlin:init` prints the value statement from `references/spec_quality_guide.md` (what it catches, what it costs, who should turn it on) before the question, `purlin:init --mutation-checks on|off` changes it later exactly as `--pre-push` changes its mode, and `--update` asks the same question when the field is absent and passes the answer as `--mutation-checks on|off` rather than writing the template's default. Every other missing config field is filled from the template; this one doubles the cost of writing a proof, which makes it a decision and not a default
- RULE-58: `purlin:init`'s file-writing half is `scripts/init/scaffold.py`, which takes the answers as flags and decides nothing that was asked. The skill asks the questions, runs the script with the answers and prints its plan; it keeps `--update` (which is `scripts/update/migrate.py`) and `--mcp` for itself, and every flag the skill's invocation names is one the script accepts. A skill that also wrote the files would be a second implementation of the same mechanics, which is exactly how the shell simulation and the real init drifted apart
- RULE-59: In a directory that is not a git repository, `scaffold.py` prints `Purlin requires git. Run 'git init' first.`, exits 2 and creates nothing: no `.purlin/`, no `specs/`, no `.gitignore`. Proofs, receipts, manual stamps, drift detection and both hooks all read git, so a project without it cannot be initialized at all rather than half-initialized
- RULE-60: With `.purlin/config.json` already present and no `--force`, `scaffold.py` exits 1, names `--force` in its message and leaves every file byte-identical. Re-running init over a configured project is how an answered setting gets silently reverted to a default
- RULE-61: With `--force` the existing `.purlin/config.json` is the base: keys no flag on the command line answers keep their values (`platforms`, `audit_criteria`, `audit_llm` among them), answered keys take the new answer, missing template keys are filled and `version` is restamped from `VERSION`. Every artifact already on disk is kept and reported as `kept`, so a re-init changes what was re-answered and nothing else
- RULE-62: `.purlin/config.json` is the template `templates/config.json` with the answered values written over it and `version` stamped from `${CLAUDE_PLUGIN_ROOT}/VERSION`; no field is a literal in the script, so a field added to the template reaches new projects without the script being edited
- RULE-63: Each selected framework's plugin is copied byte-identical from the installed plugin's `scripts/proof/` into `.purlin/plugins/` under the name `references/supported_frameworks.md` registers, a comma-separated list copies every one of them, `other` copies nothing and names `purlin:init --add-plugin`, and an id the registry does not list exits 2 rather than installing a file nobody shipped
- RULE-64: The runner wiring of Step 4 is written by the script when the project has no such file and left alone when it has one: `conftest.py` for pytest, `jest.config.js` for jest, `vitest.config.ts` for vitest. The pytest wiring puts `.purlin/plugins` on `sys.path` and names the plugin as a module, because `.purlin` is not an importable package name and a dotted `.purlin.plugins.pytest_purlin` raises before any test runs
- RULE-65: The gitignore block is `templates/gitignore.purlin`, entry by entry, and that file is the one source for it: it carries `.purlin/config.local.json` (the per-user overlay every doc calls gitignored) and `/purlin-report.html`, it never carries `.purlin/report-data.js` because the digest is committed, and an entry the project already has is not added a second time
- RULE-66: With `report` on, `purlin-report.html` at the project root is a symlink whose target is the installed plugin's `scripts/report/purlin-report.html`, so the dashboard tracks plugin updates instead of going stale as a copy; when the target cannot be linked it is copied and the plan says `copied`. With `report` off no dashboard is created and an existing one is never deleted
- RULE-67: Both hooks are installed into the repository's `hooks/` directory the same way: a symlink to the installed plugin's `scripts/hooks/` script, copied when the symlink cannot be made. A hook file that already exists is kept whether or not it is Purlin's. With `digest` `off` no pre-commit hook is installed at all and the plan says so, because the mode that disables the digest should not leave a hook behind to read it
- RULE-68: The script prints one line per path, each beginning `wrote`, `kept`, `copied`, `linked` or `skipped`, so the skill can print what init did without inspecting the tree, and `--dry-run` prints exactly that plan while leaving the project byte-identical
- RULE-69: Two runs with the same answers and `--force` leave every file byte-identical, including `.gitignore`. A scaffolder whose second run differs from its first cannot be re-run after a partial failure, which is when it is most needed
- RULE-70: Every answered mode is written verbatim, not only the defaults: `--pre-push strict` and `off`, `--digest warn` and `off`, `--mutation-checks on`, `--report off` and `--remote-verification required` each land in `.purlin/config.json` as the value that was answered
- RULE-71: `--test-framework auto` records `auto` in the config and scaffolds the plugin for every framework the registry's detection heuristics match, so the hook resolves the framework at run time from what is on disk. A project with `conftest.py` and a jest `package.json` gets both plugins; a project with no indicator gets no plugin and a plan line saying so, and `shell` is never written on the user's behalf
- RULE-72: `purlin:init --update` on a project with nothing pending is a no-op that says so: `--check` prints `"pending": []` and exits 0, the skill prints `Project is up to date with Purlin <VERSION>.` and stops, and `--apply` of every scripted id prints `nothing to do` and leaves every file byte-identical. A project that was never migrated has to be told it is current rather than have a migration run over it, because an update that rewrites a clean project cannot be told apart from one that corrupts it
- RULE-73: `--platform-id` defaults to `windows`, the OS family id, and the default the flag's own help text names is that same value. With the flag absent a legacy `@windows` proof tag becomes `@unit @on(windows)`, `<feature>.proofs-windows.json` becomes `<feature>.proofs-unit@windows.json` carrying `"platform": "windows"` on the payload and on every entry, and each marker syntax takes `windows` as its platform. A default that guessed a runner-specific id would stamp a platform no project registered
