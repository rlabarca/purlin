# Feature: skill_init

> Scope: skills/init/SKILL.md, scripts/init/scaffold.py
> Stack: markdown (skill definition)
> Description: The `purlin:init` skill initializes a project for spec-driven development. The skill asks the questions; `scripts/init/scaffold.py` writes the files: `.purlin/`, `specs/`, the config, the proof plugins, the runner wiring, the gitignore block, the dashboard and both git hooks.

## Rules

- RULE-5: `--add-plugin` validates a copied plugin file against the per-extension patterns `references/proof_plugin_contract.md` § C lists under **What a plugin file must contain**, and warns without refusing when the file does not match. The skill carries the citation and the warning text, never a second copy of the table: a plugin the user named is installed either way, and two tables are how the `.java` row outlived the fact that no shipped plugin is written in Java
- RULE-6: `--add-plugin` supports both local file paths and git URL sources with distinct handling for each
- RULE-8: Running `scripts/init/scaffold.py` in a git repository that holds none of them creates `.purlin/`, `.purlin/plugins/`, `specs/` and `specs/_anchors/`
- RULE-9: `config.json` is valid JSON containing all 7 required fields: version, test_framework, pre_push, remote_verification, mutation_checks, report, digest
- RULE-10: The version field in config.json matches the contents of the VERSION file
- RULE-11: Default config values are test_framework: auto, pre_push: warn, remote_verification: off, mutation_checks: false, report: true, digest: auto. `mutation_checks` defaults to `false` because the check costs roughly twice the tokens and minutes per proof, so it is a decision the project makes rather than a cost it inherits (RULE-57). `remote_verification` defaults to `off` because setup is offered on discovery rather than at init (`skill_test` RULE-11): a project with no runner-gated proofs has no runner to configure, so init writes the field and declines to ask about it
- RULE-12: Auto-detection reads its heuristics from the framework registry `references/supported_frameworks.md` and from no second list: a `conftest.py` at the project root or a `pyproject.toml` carrying `[tool.pytest]` selects pytest, a `package.json` declaring `jest` under `dependencies` or `devDependencies` or a `jest.config.*` file beside it selects jest, and the same two questions asked of `vitest` select vitest, each of them a row of the registry's **Detection** table. One rule per heuristic froze the list at the frameworks those rules happened to name, so a plugin shipped later was detectable only once someone wrote a rule for it; the registry is the one home, the same one the selection list is built from (RULE-48), and a heuristic added there is a heuristic init runs. A manifest is parsed as JSON and the key looked up rather than the file searched as text, because a substring search called every project whose manifest merely says the word a project of that framework: a vitest project whose `description` reads `migrated off jest` was handed the jest plugin as well
- RULE-15: `--test-framework vitest` scaffolds `.purlin/plugins/vitest_purlin.ts` (Vitest's reporter API differs from Jest's — Vitest never calls onTestResult/onRunComplete — so the native TypeScript reporter is used for both JS and TS Vitest projects; Vitest loads .ts reporters natively via Vite)
- RULE-16: `--test-framework pytest,jest` scaffolds both `.purlin/plugins/pytest_purlin.py` and `.purlin/plugins/jest_purlin.js` and writes `test_framework` as the list it was given
- RULE-17: `--test-framework shell` scaffolds `.purlin/plugins/purlin-proof.sh`. Shell is scaffolded because it was selected and never as a fallback: it carries no detection heuristic in `references/supported_frameworks.md`, and a project where detection finds nothing gets no plugin rather than a silent shell default (RULE-71)
- RULE-21: Scaffolded pytest_purlin.py produces valid .proofs-unit.json when run with @pytest.mark.proof markers
- RULE-22: Scaffolded jest_purlin.js produces valid .proofs-unit.json when invoked as reporter with [proof:...] markers
- RULE-23: Scaffolded purlin-proof.sh produces valid .proofs-unit.json when purlin_proof + purlin_proof_finish are called
- RULE-24: After init with empty specs dir, sync_status returns No specs found without errors
- RULE-25: Status progression: no proofs reports UNTESTED, all passing reports PASSING, one failing reports FAILING
- RULE-26: When report: true in config, sync_status generates .purlin/report-data.js containing valid PURLIN_DATA
- RULE-27: .gitignore contains all required purlin entries and does NOT contain `.purlin/report-data.js` (the digest is committed)
- RULE-28: Running init twice (re-init) does not create duplicate entries in .gitignore
- RULE-29: After init, .git/hooks/pre-push exists, is executable, and contains purlin
- RULE-30: When a non-purlin pre-push hook exists before init, the existing hook is preserved
- RULE-31: When report: true, purlin-report.html exists at project root; when report: false, it does not
- RULE-32: Full lifecycle works end-to-end: init creates structure, spec created, proof plugin runs, proofs emitted, sync_status reports PASSING, pre-push hook allows push
- RULE-33: Init prints DETECTING CODEBASE before scanning for test frameworks
- RULE-34: Init always presents the full framework selection list to the user, even when auto-detection succeeds, with detected frameworks pre-selected
- RULE-35: When a single framework is detected, the selection list shows it pre-selected with [x] and all others unselected with [ ]
- RULE-36: When multiple frameworks are detected, all detected frameworks are pre-selected in the list
- RULE-37: When no frameworks are detected, the selection list shows all options unselected
- RULE-38: The Purlin MCP server is bundled with the plugin — `.claude-plugin/plugin.json` declares a `purlin` entry under `mcpServers`; init does NOT write a `purlin` entry into the project's `.mcp.json` (a project-scope entry would shadow the plugin server with a version-pinned path that breaks on every plugin update)
- RULE-40: Init migrates legacy MCP config: when the project's `.mcp.json` has a `purlin` entry under `mcpServers` (pre-0.9.4 version-pinned path), init removes that entry, preserves all other server entries, deletes the file only when nothing else remains in it, and tells the user to reload plugins or restart the session
- RULE-41: Config has `"digest"` field with value `"auto"`, `"warn"`, or `"off"`
- RULE-42: After init, `.git/hooks/pre-commit` exists, is executable, and contains `purlin`
- RULE-43: When a non-purlin pre-commit hook exists before init, the existing hook is preserved
- RULE-44: In digest `auto` mode, running `git commit` triggers the pre-commit hook which regenerates `.purlin/report-data.js` and stages it into the commit
- RULE-45: After digest generation, `report-data.js` contains a `timestamp` field with a recent ISO timestamp and a `git_sha` field
- RULE-46: Digest generation does NOT trigger a new audit — `audit_summary` reflects only cached data (null when no cache exists)
- RULE-48: The framework selection list is built dynamically from the framework registry (`references/supported_frameworks.md`) and presents an option for every proof plugin shipped in `scripts/proof/`; the skill does not hardcode framework names, so a newly shipped plugin (e.g. xUnit) appears in the selection once it is registered. The name each plugin file takes inside `.purlin/plugins/` comes from the same registry, its **Installed as** column, and from no table in the scaffolder: the shell harness is installed as `purlin-proof.sh` and every other plugin under its own basename, and a scaffolder holding that fact privately is one `purlin:init --update` cannot resolve a copy back through
- RULE-49: `purlin:init --update` decides what is pending from the project's contents and never from its `version` field, and every check names the files it counted. A project may have been initialized by any plugin version, edited by hand, or half-migrated already, so a version comparison would both miss real work and invent work that is already done; a count with no filename is not something a user can consent to. The ten ids are `legacy-tier-windows`, `legacy-proof-file`, `legacy-marker`, `plugin-copies-stale`, `config-fields-missing`, `hooks-stale`, `dashboard-stale`, `digest-schema-old`, `receipt-v1` and `legacy-mcp`. Every id is a detector in the server paired with an applier in the script, so the advisory a reader consents to and the work the script does cannot describe different sets, and `docs/installation-guide.md` carries one table row per id saying what it does, because an id a user is asked to consent to and cannot look up is one they have to take on trust
- RULE-50: The marker rewrite covers every proof-marker syntax Purlin ships a plugin for, not only the one the project's `test_framework` names: pytest (`tier="windows"`), jest and vitest (`[proof:...:windows]`), shell (`PURLIN_PROOF_TIER=windows`), C (the `purlin_proof()` tier argument), phpunit and sql (`@purlin ... windows`) and xunit (the `PurlinProof` trait). Each becomes tier `unit` plus the platform in that plugin's own syntax. A project with two frameworks would otherwise have half its markers rewritten and half left writing files that satisfy nothing
- RULE-51: Nothing is written before consent, and the delta is shown first: the step prints KEEPING, UPDATING, RENAMING and ASKING per file in the shape `skills/spec/SKILL.md` Step 7c uses, then asks through `AskUserQuestion`. `--update --check` reports and writes nothing at all, which is also what a CI preflight runs
- RULE-52: The update never writes a proof entry and never writes a receipt. A proof entry is a claim that a test ran and a receipt is a claim that a suite passed, and a migration ran neither; renaming a proof file through `git mv` moves an existing record and keeps its history, which is a different act. `receipt-v1` and `legacy-mcp` therefore print directives (`purlin:verify` and `purlin:init --update`, the command whose Step 5c owns the MCP entry) and change nothing, and a feature whose markers were rewritten is re-run through `purlin:test` so its plugin writes the scoped file itself
- RULE-53: After the update, every `.purlin/plugins/` copy the registry can resolve to a file in the installed plugin's `scripts/proof/` is byte-identical to it (extending RULE-18, RULE-19, RULE-20 and RULE-47 from the copies init scaffolds to every copy a project already holds). Resolution runs through the registry in both directions: a copy under the name the **Installed as** column gives it, `purlin-proof.sh` among them, and a copy under a name an older plugin gave it, `shell_purlin.sh` among them, both resolve to the shipped file behind them. Keying a copy by its own basename against `scripts/proof/` reported neither as stale, so a project's shell harness was never refreshed by any update. A resolved copy is refreshed in place under the name it already has and is never renamed, because the project's own tests source that path. A copy the registry cannot resolve is a plugin the project installed itself and is left alone
- RULE-54: The update is idempotent: a second `--check` reports nothing pending apart from the two directives the script does not apply, and a second `--apply` of the same ids changes no file. A migration that is not idempotent cannot be re-run after a partial failure, which is when it is most needed
- RULE-55: The provenance loss a renamed platform proof file suffers is stated to the user before consent: the commit that carried the old name still exists, but the report reads provenance per current filename, so the file reports `runner not recorded` until the runner next commits it under the new name. The rename does not delete evidence, and saying so is what stops the gap being read as one
- RULE-57: `mutation_checks` is asked, never backfilled. `purlin:init` prints the value statement from `references/spec_quality_guide.md` (what it catches, what it costs, who should turn it on) before the question, `purlin:init --set mutation_checks on|off` changes it later exactly as `--set pre_push` changes its mode (RULE-74), and `--update` asks the same question when the field is absent and passes the answer as `--mutation-checks on|off` rather than writing the template's default. Every other missing config field is filled from the template; this one doubles the cost of writing a proof, which makes it a decision and not a default
- RULE-58: `purlin:init`'s file-writing half is `scripts/init/scaffold.py`, which takes the answers as flags and decides nothing that was asked. The skill asks the questions, runs the script with the answers and prints its plan; it keeps `--update` (which is `scripts/update/migrate.py`) for itself, and every flag the skill's invocation names is one the script accepts. A skill that also wrote the files would be a second implementation of the same mechanics, which is exactly how the shell simulation and the real init drifted apart. Two steps are exempt, and only for the four audit fields: Step 7b writes `audit_criteria` and `audit_criteria_pinned`, Step 7c writes `audit_llm` and `audit_llm_name`, because the scaffolder takes no flag for any of them and the answers exist only once those steps have asked. No other step writes `.purlin/config.json` by hand, and every other key of it is the scaffolder's
- RULE-59: In a directory that is not a git repository, `scaffold.py` prints `Purlin requires git. Run 'git init' first.`, exits 2 and creates nothing: no `.purlin/`, no `specs/`, no `.gitignore`. Proofs, receipts, manual stamps, drift detection and both hooks all read git, so a project without it cannot be initialized at all rather than half-initialized
- RULE-60: With `.purlin/config.json` already present and no `--force`, `scaffold.py` exits 1, names `--force` in its message and leaves every file byte-identical. Re-running init over a configured project is how an answered setting gets silently reverted to a default
- RULE-61: With `--force` the existing `.purlin/config.json` is the base: keys no flag on the command line answers keep their values (`platforms`, `audit_criteria`, `audit_llm` among them), answered keys take the new answer, missing template keys are filled and `version` is restamped from `VERSION`. Every artifact already on disk is kept and reported as `kept`, so a re-init changes what was re-answered and nothing else
- RULE-62: `.purlin/config.json` is the template `templates/config.json` with the answered values written over it and `version` stamped from `${CLAUDE_PLUGIN_ROOT}/VERSION`; no field is a literal in the script, so a field added to the template reaches new projects without the script being edited
- RULE-63: Each selected framework's plugin is copied byte-identical from the installed plugin's `scripts/proof/` into `.purlin/plugins/` under the name `references/supported_frameworks.md` registers, a comma-separated list copies every one of them, `other` copies nothing and names `purlin:init --add-plugin`, and an id the registry does not list exits 2 rather than installing a file nobody shipped
- RULE-64: The runner wiring of Step 4 is written by the script when the project has no such file and left alone when it has one: `conftest.py` for pytest, `jest.config.js` for jest, `vitest.config.ts` for vitest. The pytest wiring puts `.purlin/plugins` on `sys.path` and names the plugin as a module, because `.purlin` is not an importable package name and a dotted `.purlin.plugins.pytest_purlin` raises before any test runs
- RULE-65: The gitignore block is `templates/gitignore.purlin`, entry by entry, and that file is the one source for it: it carries `.purlin/config.local.json` (the per-user overlay every doc calls gitignored) and `/purlin-report.html`, it never carries `.purlin/report-data.js` because the digest is committed, and an entry the project already has is not added a second time
- RULE-66: With `report` on, `purlin-report.html` at the project root is a copy of the installed plugin's `scripts/report/purlin-report.html`, byte-identical to it, and the plan line reads `copied scripts/report/purlin-report.html -> purlin-report.html`. It is a copy on every host and a symlink on none, because the only target a plugin install can offer is version-pinned (`~/.claude/plugins/cache/purlin/purlin/<version>/`): the link dangles on the next update and the dashboard stops opening at all, which is worse than a copy one release behind, and `purlin:init --update` refreshes the copy. With `report` off no dashboard is created and an existing one is never deleted
- RULE-67: The hooks directory is the one git reads: `core.hooksPath` when the repository sets it, absolute or relative to the top level, and otherwise `git rev-parse --git-common-dir`/hooks, which is the main repository's for a linked worktree. `--absolute-git-dir` would name `.git/worktrees/<name>` there, a directory git never reads hooks from. Into that directory, and only when the slot is free, goes a short delegator carrying the marker `purlin-delegator`, the missing-shim guard RULE-78 requires, and an `exec` of `"$(git rev-parse --show-toplevel)/.purlin/hooks/<name>"` with its arguments, mode `0755`. Every hook path therefore has one of five outcomes, each a plan line: the shim is `wrote` or `kept` (RULE-77), the delegator is `wrote` into a free slot, `kept` when the slot already holds one carrying the marker, and `skipped` when it holds anything else (RULE-78). With `digest` `off` neither the pre-commit shim nor its delegator is written and both lines say so, because the mode that disables the digest should not leave a hook behind to read it. Nothing in the install is a symlink, so a host where `os.symlink` raises gets the same working hooks as every other host
- RULE-68: The script prints one line per path, each beginning `wrote`, `kept`, `copied` or `skipped`, so the skill can print what init did without inspecting the tree, and `--dry-run` prints exactly that plan while leaving the project byte-identical
- RULE-69: Two runs with the same answers and `--force` leave every file byte-identical, including `.gitignore`. A scaffolder whose second run differs from its first cannot be re-run after a partial failure, which is when it is most needed
- RULE-70: Every answered mode is written verbatim, not only the defaults: `--pre-push strict` and `off`, `--digest warn` and `off`, `--mutation-checks on`, `--report off`, `--remote-verification required` and `--quality-gate deterministic` each land in `.purlin/config.json` as the value that was answered
- RULE-71: `--test-framework auto` records `auto` in the config and scaffolds the plugin for every framework the registry's detection heuristics match, so the hook resolves the framework at run time from what is on disk. A project with `conftest.py` and a jest `package.json` gets both plugins; a project with no indicator gets no plugin and a plan line saying so, and `shell` is never written on the user's behalf. Each heuristic names a fact only a project of that framework has, because a plugin scaffolded for a framework the project does not use is a plugin nobody wired and a `test_framework` answer the hook cannot run: `c` requires a `Makefile` or `CMakeLists.txt` AND at least one `*.c` file, since a Makefile is how a Python or a Go project spells its task runner just as often as it is how a C project builds; `sql` requires a test-shaped name (`test_*.sql`, `*_test.sql` or `*.test.sql`) under `tests/`, since `tests/fixtures.sql` is seed data; and `jest` and `vitest` are read out of the parsed dependency maps (RULE-14). Detection reads the project root and the package directories under it, the two levels below the root that `packages/*`, `apps/*` and `services/*` lay down, in sorted order, so a monorepo whose `conftest.py` lives in `packages/api/` is seen rather than reported as a project with no framework. Dot directories and `node_modules` are never searched
- RULE-72: `purlin:init --update` on a project with nothing pending is a no-op that says so: `--check` prints `"pending": []` and exits 0, the skill prints `Project is up to date with Purlin <VERSION>.` and stops, and `--apply` of every scripted id prints `nothing to do` and leaves every file byte-identical. A project that was never migrated has to be told it is current rather than have a migration run over it, because an update that rewrites a clean project cannot be told apart from one that corrupts it
- RULE-73: `--platform-id` defaults to `windows`, the OS family id, and the default the flag's own help text names is that same value. With the flag absent a legacy `@windows` proof tag becomes `@unit @on(windows)`, `<feature>.proofs-windows.json` becomes `<feature>.proofs-unit@windows.json` carrying `"platform": "windows"` on the payload and on every entry, and each marker syntax takes `windows` as its platform. A default that guessed a runner-specific id would stamp a platform no project registered
- RULE-74: A single-step re-answer is a single config write, and `purlin:init --set <key> <value>` is its one spelling. `skills/init/SKILL.md` maps the five keys `pre_push`, `report`, `digest`, `mutation_checks` and `quality_gate` to `scaffold.py --force` with that key's single flag, in one five-row table in Step 2, and such a run rewrites exactly that key of `.purlin/config.json` and leaves every other key, and every other file in the project, byte-identical. The mapping is stated once: no step restates the `--force` invocation for its own setting, because five copies of one procedure are five things to keep in step, and the `## Usage` block documents `--set` rather than any of the five. The five old flag spellings keep working as aliases, each printing one line naming its `--set` replacement, and go away in 0.12.0; `scripts/init/scaffold.py` keeps its long flags, because the script's interface is not the skill's. `--set` replaces the agent hand-editing the config, which is how a key gets dropped, reordered or written in the wrong type. `--test-framework` therefore keeps rather than defaulting to `auto`: left off it is the value the project already recorded, and `auto` only in a project with no config yet, where it is the template's own value. A flag defaulting to `auto` would re-detect the frameworks on every such run and write `auto` over the recorded answer (RULE-71's `auto` is an answer a user gave, not the absence of one), so a step that changed one setting could not be told from one that changed the framework too
- RULE-75: `quality_gate` is the one answer `templates/config.json` does not carry, and `scaffold.py` writes it only when `--quality-gate` answers it. A run without the flag leaves the written key set equal to the template's eight keys; a `--force` run without the flag keeps a mode the project already recorded and still adds no key to a project that never recorded one; a value outside `off` and `deterministic` exits 2 and writes nothing. Because it is not a template key, `scripts/update/migrate.py --check` reports no pending entry for it on a project that lacks it, so `purlin:init --update` neither backfills nor asks about it. The quality gate is project policy a project opts into and not a default every project inherits, and a field backfilled as `off` would read as a declaration nobody made
- RULE-76: A template key that no longer has a reader is retired rather than left to sit in every project's config: the key leaves `templates/config.json`, and `purlin:init --update` removes it from an existing config under the `config-fields-missing` migration, which names the key in its delta line (`<key> removed (retired)`) so the user reads what left before consenting. It gets no migration id of its own because it is the same question that migration already asks, from the other side: does this config hold what the template says it should. `spec_dir` is the first: `scripts/hooks/refresh_digest.py` was its last reader, and every other reader of the spec directory, this repository's own tooling and all twelve skills included, has always hardcoded `specs`, so the field was a setting a user could change with no effect
- RULE-77: `purlin:init` writes the two hook shims `.purlin/hooks/pre-commit` and `.purlin/hooks/pre-push`, mode `0755`, and they are tracked in git: a shim names no machine, no plugin version and no checkout, so the copy in the repository is correct for every clone of it. Each shim resolves the installed plugin at run time and `exec`s that plugin's own `scripts/hooks/<name>.sh` with its arguments and its stdin, so the hook body is the plugin's and never a copy of it. The plugin root is the first of five candidates carrying that script, and a candidate that does not carry it is stepped over rather than ending the search: `$PURLIN_PLUGIN_ROOT`; the absolute path on the first line of `.purlin/plugin-root`, which this script writes and `scripts/update/migrate.py` repoints when the plugin has moved, and which `templates/gitignore.purlin` excludes because it is true of one machine only; `$CLAUDE_PLUGIN_ROOT`; the `installPath` Claude Code recorded for this project under `plugins["purlin@purlin"]` in `~/.claude/plugins/installed_plugins.json`, the entry whose `projectPath` is this project or else the one with the newest `lastUpdated`; and the project root, for a dev checkout of the framework itself. The registry is the candidate that survives a plugin update: a symlink or a recorded path into `~/.claude/plugins/cache/purlin/purlin/<version>/` dangles the moment the version changes, while the registry entry moves to the new directory. When no candidate carries the script the shim prints a WARNING naming every path it searched and the two ways to fix it, and then keeps its own hook's contract: `pre-commit` exits 0, and `pre-push` exits 0 in `warn` and `off` and 1 in any other mode, rather than passing a push it could not check
- RULE-78: A hook slot Purlin does not own is never written to. A slot holding a hook without the `purlin-delegator` marker keeps its bytes, and the plan line names the exact line to add to it. A repository whose hooks a manager owns is left alone the same way and the manager is named: `core.hooksPath` pointing into `.husky` is husky and the line belongs in `.husky/<name>`, one naming `lefthook` is lefthook and the line belongs in `lefthook.yml`, and a `.pre-commit-config.yaml` at the project root is the pre-commit framework and the line belongs in that file. The shims are written in every one of these cases, because they are the project's file and the manager's hook only has to reach them. The delegator does not `exec` the shim blind: it resolves the path, and when nothing executable is there it prints one line naming that path and `purlin:init --update` and exits 0. A checkout that predates the shims, an older branch and a git worktree sharing the repository's hooks directory all carry no `.purlin/hooks/`, and an `exec` onto a path that is not there fails the hook, which blocks every commit made on that checkout over a file the commit has nothing to do with. Writing into a managed slot either loses the project's hooks or has Purlin's overwritten on the manager's next install, and silently replacing a check somebody else put there is the worst thing an initializer can do to a repository
- RULE-79: `scripts/init/scaffold.py --ci github` writes exactly one file, `.github/workflows/purlin-verify-gate.yml`, and writes it only when that flag is on the command line. Its body is this plugin's own `.github/workflows/verify-gate.yml` under the four consumer adaptations `consumer_ci` RULE-1 states, whose two inserted steps are lifted verbatim from the runner-workflow template in `references/remote_verification.md`, and two further operations and no others: every trigger `paths:` filter becomes `specs/**`, `.purlin/config.json` and `.github/workflows/**`, and the job gains an `env:` block holding `PURLIN_REF`, stamped `v` followed by the installed `VERSION`, which the tooling clone reads in place of the template's `--branch v<VERSION>`. The plugin's own filters name `scripts/ci/verify_gate.py` and `scripts/mcp/purlin_server.py`, two paths no consumer checkout holds, so a workflow that kept them would skip the run a spec or config change should have triggered; the pin is a literal and not a runner expression, so it is legal in a job `env:` block where `runner.temp` is not, and it moves the job to another release in one line. A file already at that path is `kept` with its bytes untouched whatever it holds, because a workflow is the file a team is likeliest to have written itself and the worst one to replace. `github` is the only provider the flag accepts. The skill asks and the scaffolder writes: the `--ci` section of `skills/init/SKILL.md` puts the question through `AskUserQuestion` and states in two lines what lands before it runs anything, and every other run of `purlin:init` passes no `--ci` at all, so a project never finds a workflow it did not agree to spending its CI minutes on
- RULE-80: `hooks-stale` is pending when the project's hook install is not the one the installed plugin writes, and `purlin:init --update` rewrites it. Two files per hook are checked. The generated shim `.purlin/hooks/<name>` is stale when its bytes differ from what `scripts/init/scaffold.py` would generate for it, because the plugin owns those bytes and a shim from an older plugin resolves the plugin by rules that plugin no longer uses. The slot the hook git runs occupies, resolved by RULE-67, is stale when it holds a hook Purlin put there in a shape the plugin stopped writing: a symlink that does not resolve, a symlink into the plugin (which dangles on the next update), a copy of the plugin's own hook body (which resolves the plugin from `.git/hooks`, where it is nowhere, so it warns on every commit and blocks every strict push), or a delegator written before the missing-shim guard. A free slot and a foreign hook are never stale, because RULE-78 owns them and an update that installed a hook into a project that declined one would be changing an answer rather than carrying it forward. A shim that is simply absent is reported only when the slot holds one of those defective Purlin hooks, for the same reason. The applier removes Purlin's own defective slot file first, so the delegator writer sees a free slot rather than an occupied one it must refuse, and then runs the same shim and delegator writer `purlin:init` runs. It is not blocking: a hook is a surface the developer reads, not evidence a test run writes
- RULE-81: `dashboard-stale` is pending when the project's root `purlin-report.html` is not the installed plugin's `scripts/report/purlin-report.html`, and `purlin:init --update` copies over it. Two shapes count: a symlink that does not resolve, which is what every project initialized before RULE-66 became a copy holds once the version-pinned plugin cache it pointed at goes away, and a path whose bytes differ from the installed dashboard, which is a copy from an older plugin or a resolving symlink into an older one. A project with no `purlin-report.html` at all is not repaired, because the dashboard is an answer `purlin:init` asks for and a project that turned it off is not one an update hands it back to. It is not blocking, for RULE-80's reason
- RULE-82: `digest-schema-old` is pending when `.purlin/report-data.js` carries a `schema_version` lower than the one this plugin writes, or carries none at all, which is what every digest written before the field holds and is read as schema 1 (`report_data` RULE-48). `purlin:init --update` rebuilds the digest rather than editing it: the old payload is missing whole fields, and reading the project again is the only honest way to produce them. The rebuild is the offline one and is stamped `update`, so a reader can tell a digest the update rebuilt from one a commit or a status call wrote. A digest whose `schema_version` is higher than this plugin's is never reported: the dashboard's own banner says a newer Purlin wrote it (`purlin_report` RULE-51), and a rebuild here would throw away a payload this plugin cannot produce. A project with no digest at all is not given one, because the digest follows the `report` answer `purlin:init` asked for. It is not blocking, for RULE-80's reason
- RULE-83: A `.purlin/plugins/` copy is never overwritten without its previous bytes being kept first. Before `plugin-copies-stale` writes the installed plugin's file over a copy, the bytes that were there are written to `.purlin/plugins/<name>.local-<sha8>.bak`, where `<sha8>` is the first eight hex digits of their sha256, and the path is named in the action line the script prints and in the delta the skill shows before asking. The script cannot tell an old plugin's bytes from a change the project made on purpose, and one of the two consumer projects this was found on had a locally modified reporter: both look alike on disk, and overwriting either without a copy destroys work that exists nowhere else. Naming the backup for its own content means re-applying the same migration writes the same path rather than accumulating a file per run, and `templates/gitignore.purlin` excludes the pattern because a backup is one machine's working state and not the project's record
- RULE-84: `purlin:init --update` closes by re-running the `--sync-audit-criteria` step when `.purlin/config.json` has `audit_criteria` set, before the commit, and says in one line that it skipped when the field is unset. The cached criteria at `.purlin/cache/additional_criteria.md` and the sha in `audit_criteria_pinned` are what `purlin:audit` grades against and what it refuses to grade with when the two disagree, so a project that pinned external criteria and then let its plugin move is a project whose next audit refuses or grades against a copy nobody has looked at since. The update is the one moment the project's pinned state is already being brought forward, and it is the step that knows the criteria were pinned
