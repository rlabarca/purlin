# Feature: skill_test

> Scope: skills/test/SKILL.md
> Stack: markdown (skill definition)
> Description: The `purlin:test` skill runs tests (unit tier unless `--all`), emits proof files via write-scoped overwrite, and reports coverage per feature. It is the single owner of test execution: `purlin:build` and `purlin:verify` delegate to it rather than invoking runners themselves. That ownership is also why remote execution of platform-declared proofs lives here: pushing a branch and pulling a runner's proof commits is writing, and `purlin:verify` is a read-only gate.

## Rules

- RULE-1: Skill file has YAML frontmatter with `name` and `description` fields
- RULE-2: Skill file contains a `## Usage` section documenting command syntax
- RULE-3: The `name` field in frontmatter is `test`, matching the directory name
- RULE-4: Skill includes commit instructions or git operations for file modifications
- RULE-5: Skill requires calling `sync_status` after tests and states it is not optional
- RULE-6: The freshness check distinguishes "no tests were collected" from "the proof plugin failed to emit". Zero collected tests reports that the plugin is fine and routes to `purlin:build`; only a run that executed tests without refreshing proof files reports a plugin problem and suggests `purlin:init --force`
- RULE-7: Step 1.5 classifies the platforms in scope and prints the `Platforms:` block `sync_status` renders **before the first test runs**, rather than recomputing the split itself. It names the platform registry in `.purlin/config.json` and the family ids (`windows`, `macos`, `linux`) as what an `@on(...)` id resolves against, and it states three invariants: there is no local substitute for a platform, a platform with no runner warns and never blocks, and the local run sets `PURLIN_PLATFORM` so the plugins write the scoped file rather than falling back to the OS family. Its samples name concrete ids such as `macos-14` and `windows-2022`, never the host the skill happens to run on, and never `windows` as a tier
- RULE-8: Remote execution is documented as a step of this skill and nowhere else, as one round over every remote platform at once: push the branch once (every runner proves the same commit), one `gh workflow run` dispatch per remote platform, all of them awaited together with `gh run watch`, then a single `git pull --ff-only` after every run has completed, retried once when a late commit-back lands mid-pull. One pull, not one per runner, because a pull while another runner is still committing races it. The reason the path lives here rather than in `purlin:verify` is stated, not implied: those operations write, and verify's contract forbids writing
- RULE-9: Step 3 reports the platform lines as `sync_status` prints them, distinguishing a remotely-proved platform from a locally-proved one, and sources the runner identity and time per scoped proof file from that file's own commit trailers (`Purlin-Runner:` for the runner, `Purlin-Platform:` cross-checked against the platform in the filename) rather than from the proof entry, because the entry records that a test passed and only the commit records where. The freshness check is confined to the local run, since a proof file a runner wrote arrived by `git pull` and its mtime says when it was fetched
- RULE-10: The remote loop is bounded at 3 rounds, matching `skills/audit/SKILL.md` and `skills/verify/SKILL.md`, and the bound is stated as a number rather than as "a few". The not-converging report names both the platform that is still failing and the runner it failed on, because a project with several platform runners cannot act on "remote still failing". A fourth round spends another CI run on a failure that is not converging
- RULE-11: Remote setup is offered per platform on discovery and never at init: when a platform's proofs are awaiting and no dispatchable workflow proves it, the skill offers to scaffold `.github/workflows/purlin-<id>-proofs.yml` from `references/remote_verification.md` **and** to write the `runner` block into `platforms.<id>` of `.purlin/config.json`, writing both or neither and neither without consent, because a workflow the config does not name is one this skill will never dispatch. The skill states that this consent path is the one place a skill other than `purlin:init` writes the config, matching the `platforms` row of `references/drift_criteria.md`. `purlin:init` is not the place, because a project with no platform-declared proofs has no runner to configure
