# Feature: skill_audit

> Scope: skills/audit/SKILL.md
> Stack: markdown (skill definition)
> Description: The `purlin:audit` skill evaluates proof quality with STRONG/WEAK/HOLLOW assessments. It is read-only — it never modifies code or test files.

## Rules

- RULE-1: Skill file has YAML frontmatter with `name` and `description` fields
- RULE-2: Skill file contains a `## Usage` section documenting command syntax
- RULE-3: The `name` field in frontmatter is `audit`, matching the directory name
- RULE-4: Independent auditor mode documents instructions to read audit criteria and assess proofs as STRONG/WEAK/HOLLOW
- RULE-5: Independent auditor mode documents routing HOLLOW/WEAK findings to `purlin:build` for remediation, and states that no fixer agent is spawned because the audit is read-only
- RULE-6: Independent auditor mode documents re-auditing the affected proofs after the fixes land
- RULE-7: Independent auditor mode terminates after all findings addressed or after 3 rounds on any single proof
- RULE-8: Anchor rule handling documents reporting to the lead for ambiguous anchor rules
- RULE-9: External LLM detects deliberately hollow tests (assert True, assert None) as non-STRONG
- RULE-10: External LLM rates well-structured tests with real assertions as STRONG or WEAK (never HOLLOW)
- RULE-11: Response parsing extracts all required fields (PROOF-ID, ASSESSMENT, CRITERION, WHY, FIX) from external LLM output
- RULE-12: External LLM mode is the same two-pass flow with the second pass shelled out. `static_checks` catches HOLLOW in Pass 1 and only the survivors reach Pass 2, and the `## External LLM Mode` section of `skills/audit/SKILL.md` documents that flow in one place: it states that Pass 1 still runs first, names the `audit_llm` and `audit_llm_name` config fields the mode is switched on by, names the five response fields a parser must find with the note that parsing is keyword-based because different LLMs format slightly differently, and carries the `### External LLM with Independent Audit` subsection for the relay loop. It reprints neither the Pass 2 prompt nor the report header: both are pointers back to Step 2 and Step 3, because a second copy of a prompt is a second prompt the day one of them is edited
- RULE-14: Criteria are loaded via the single `load_criteria()` function (`--load-criteria` CLI); built-in criteria always apply, additional team criteria are appended — never replaced. When `audit_criteria` is configured the cached copy must carry a `<!-- purlin-criteria-sha: <sha> -->` first line equal to `audit_criteria_pinned`; a mismatch, a missing header or a missing cache stops the load with exit 2 instead of quietly returning the built-in criteria alone, because an audit that graded against the wrong standard reports a number indistinguishable from one that graded against the right one
- RULE-15: The skill documents a portable Python interpreter for invoking static_checks.py — falling back from `python3` to `python` to `py -3` — rather than assuming `python3` is always on PATH (it is not on stock Windows)
- RULE-16: When a proof's `test_file` is empty (e.g. C#/xUnit, where `dotnet test` leaves `TestCase.CodeFilePath` null), the skill resolves the source file from the fully-qualified `test_name` via `static_checks.py --resolve-source` before Pass 1 and Pass 2, so C# Pass-1/Pass-2 is reachable through purlin:audit without a populated path. The skill also documents that populating it natively requires source info (`RunConfiguration.CollectSourceInformation=true` with full PDBs)
- RULE-17: The skill carries a lever table naming which lever moves which assessment: HOLLOW and EXCLUDED are decided by test code and no spec edit moves them, WEAK is fixed by strengthening the test rather than narrowing the proof description (never for anchor rules), and the Proof Design levels are the ones prose is meant to move. The reasoning behind the table, the warning that reclassifying only shrinks the denominator, and the arithmetic for reaching a target Integrity score live once in `references/audit_criteria.md` § Scoring, which the skill points at, because that is the file the dashboard's own formulas are documented in and two copies of a formula are two formulas the day one is edited
- RULE-18: Writing the audit cache is a numbered step of its own, marked mandatory, naming the literal `--write-cache` command with an explicit `--project-root`. The skill states that an audit which does not write the cache has produced no measurement, and that pruning against an empty live-keys set would delete the entries just written. The live-keys file the prune step reads is `.purlin/cache/live_keys.txt`, beside the cache it prunes and inside the already-gitignored cache directory, never a path under `/tmp`: a fixed `/tmp` name is world-readable, shared by every checkout on the machine and absent on Windows, so two projects auditing at once would prune each other's keys. It also states who writes what: each auditor subagent writes its own assessments through `--write-cache`, whose exclusive lock is what makes parallel writers safe, while the lead writes only the grades it made in the main context and reads the cache back to verify the subagents' entries landed. The skill and `agents/purlin-auditor.md` say the same thing, because they used to say opposite things and one of them was always wrong. Neither file lists the nine entry fields: both name `references/audit_criteria.md` § Required entry fields, which is where the list is written down, and the skill prints the entry shape once, in the cache-load step, rather than twice
- RULE-19: The skill derives its mode from observable project state rather than asking or assuming: a Step 0 runs `--audit-scope` and maps the result to design-only or both, treats explicit user intent and `--design`/`--integrity` as overrides, and requires the chosen mode and the state behind it to be announced. It states that Pass 0.5 and Pass 1 must not run without proof files because they exit 2
- RULE-20: The skill documents the Proof Design pass — deterministic `--check-proof-design` followed by an LLM pass — with the four Design levels, the instruction never to use STRONG/WEAK/HOLLOW for a description, and remediation routed to `purlin:spec` because the description is the artifact at fault
- RULE-21: When the project sets `mutation_checks: true`, Pass 2 may ask the author to name the mutation that was run for a proof (which behaviour was broken, and that the proof failed while it was broken) and grades a proof whose author cannot name one no higher than WEAK. Naming a plausible mutation lifts the cap; it does not raise the grade by itself. When the project leaves `mutation_checks` at `false` the criterion does not apply and caps nothing, because the project never claimed the practice
- RULE-22: The skill never computes a cache key and never pastes the key's inputs in. It names `--cache-key --feature <name> --proof-id PROOF-N` as the only way to obtain one, states that `--write-cache` discards the key the caller supplies and re-keys every entry from the project, and states that an unresolvable `(feature, proof_id)` is rejected with exit 2. There is no `--criteria` flag: a criteria file named on the command line is not the file `audit_criteria_pinned` names, so the flag was a way to bypass the sha pin and report a number indistinguishable from a correctly graded one. Its criteria step states that `--load-criteria` exiting 2 stops the audit and that there is no fall back to the built-in criteria, because a project graded against a standard it did not pin reads exactly like one graded correctly
