# Feature: scaffold

> Description: `purlin:init`, which sets a project up. It asks one question,
>   "what must be true before CI lets a change merge?", derives everything
>   else from that answer or reads it from the tree, writes each file in turn
>   and names every one of them in the summary. Two honest exceptions ask a
>   second question: a tree with nothing to detect is asked which framework
>   its tests use, and `signed` is asked who may sign. It also writes the
>   pre-push hook, whose one contract is that it blocks a push only when the
>   project asked for that and a tagged test failed.
> Scope: scripts/init/scaffold.py, scripts/hooks/pre-push.sh, templates/config.json, templates/gitignore.purlin
> Stack: python3 (stdlib only, 3.9 floor), shell/sh for the hook and the shim

## Rules

- RULE-1: A project with code to detect is asked the gate question and no other question [risk: medium] [origin: eng]
- RULE-2: Each gate answer derives its own settings, and the three pairs are `passed` no minimum and never, `strong` 70 and high, `signed` 80 and medium [risk: high] [origin: eng]
- RULE-3: `--gate` answers the question without asking it, and a later run with no flag keeps the gate the config already names [risk: medium] [origin: eng]
- RULE-4: An answer that is not one of the three gates is read as `passed` and the fallback is printed, so a typo lowers what CI enforces loudly rather than raising it silently [risk: high] [origin: eng]
- RULE-5: The config init writes carries exactly `ai_review_at`, `ci`, `gate`, `min_strength`, `mutation_engine`, `sql_engine`, `test_framework` and `version`, plus `signers` under `signed`, and no key this release stopped reading; `templates/config.json` carries the same eight keys [risk: medium] [origin: eng]
- RULE-6: A tree with nothing to detect is asked which framework its tests use, that answer is the one installed, and a name this release ships no plugin for is reported and read as `shell` [risk: medium] [origin: eng]
- RULE-7: The framework detected in the tree gets its proof plugin copied into `.purlin/plugins/` byte for byte, under the file name the framework registry gives it [risk: high] [origin: eng]
- RULE-8: The test runner's own configuration is written for pytest, jest and vitest, naming that framework's plugin, and a configuration the project wrote itself is kept rather than replaced [risk: high] [origin: eng]
- RULE-9: A framework whose tooling init cannot wire is told what to do instead: an xunit project that its logger needs a `*.TestLogger.dll` assembly and `dotnet test --logger purlin`, and a node project that Stryker is what measures the breaks [risk: low] [origin: eng]
- RULE-10: Only `signed` asks who may sign; the emails are lower-cased into `signers` and the one-time commit-signing setup is printed for each of them [risk: high] [origin: eng]
- RULE-11: Under `signed`, init prints what the gate will otherwise fail on: the missing signer list with the command that writes it, and every rule carrying no risk tag named by feature and rule id [risk: high] [origin: eng]
- RULE-12: Raising the gate adds what the higher level needs and keeps every file an earlier run wrote; lowering it writes the setting and deletes nothing, the signer list included [risk: high] [origin: eng]
- RULE-13: Under `passed` no CI workflow is written and the summary says `--ci` writes it anyway; `--ci` under `passed` writes it [risk: medium] [origin: eng]
- RULE-14: The git host is read from the remote URL as `github`, `azure` or nothing at all, and `--ci` overrides what the remote said [risk: medium] [origin: eng]
- RULE-15: The workflow carries one job per operating system the `@env` tags in `specs/` name, one linux job when they name none, and the Purlin release pinned as `v<version>` [risk: medium] [origin: eng]
- RULE-16: `--upstream-check` adds the scheduled job that watches the pins, and without the flag that job is absent [risk: low] [origin: eng]
- RULE-17: The branch rules the git host has to enforce are printed: under `passed` the force-push and deletion rule alone, and above it the restrictions on `.purlin/records/**` and `.purlin/briefs/**` as well [risk: medium] [origin: eng]
- RULE-18: The summary names every path init wrote, kept, copied or skipped, and each path it says it wrote is on disk afterwards [risk: medium] [origin: eng]
- RULE-19: A block init appends to a file the project also owns is appended once and never twice, whatever else that file already held [risk: medium] [origin: eng]
- RULE-20: A second run at the same gate writes no file [risk: medium] [origin: eng]
- RULE-21: `.purlin/plugin-root` holds the directory the run came out of, and is the only file in the project that names that directory [risk: high] [origin: eng]
- RULE-22: A copy of the plugin installed from the marketplace sets a project up the same way this checkout does [risk: high] [origin: eng]
- RULE-23: No file init writes into a project points at this repository's own development folder, which a consumer's checkout does not carry [risk: medium] [origin: eng]
- RULE-24: init writes the tracked shim `.purlin/hooks/pre-push` and the delegator git runs, both executable, the delegator reaching the shim and saying so rather than failing when the shim is absent; no pre-commit hook is installed and the plugin ships no pre-commit script [risk: medium] [origin: eng]
- RULE-25: The shim names no machine, no checkout and no release, so the file is right for every clone and everything machine-specific is resolved when it runs [risk: high] [origin: eng]
- RULE-26: A pre-push hook someone else wrote, or a repository whose hooks another tool manages, is named in the summary with the line to add rather than written over [risk: medium] [origin: eng]
- RULE-27: The hook runs `purlin_run.py --all --quick` and no test runner of its own, and blocks a push only when `pre_push` is `on` and a tagged test failed; every other outcome exits 0 and prints one line saying why [risk: high] [origin: eng]
- RULE-28: The hook exits 0 and prints nothing when there is no project to check: no specs, no `.purlin/`, or no git repository [risk: medium] [origin: eng]
- RULE-29: The shim takes the first plugin root that carries `scripts/hooks/pre-push.sh` out of `PURLIN_PLUGIN_ROOT`, `.purlin/plugin-root`, `CLAUDE_PLUGIN_ROOT` and a marketplace copy under the home directory, in that order, and warns and exits 0 when none of them does [risk: high] [origin: eng]
- RULE-30: `--dry-run` prints the plan and writes nothing, inside a git repository or outside one [risk: medium] [origin: eng]
- RULE-31: A real run outside a git repository exits 2 saying to run git init and leaves the directory empty, and a project root that does not exist exits 2 [risk: medium] [origin: eng]
- RULE-32: `--add <framework>` keeps what was detected and records the framework once however many times it is added [risk: low] [origin: eng]
- RULE-33: `--update` hands the project to `scripts/init/update.py`, and `--update --dry-run` asks it what is pending instead of applying anything [risk: medium] [origin: eng]
- RULE-34: The last line of a run is the next step, computed from the state the project is now in [risk: low] [origin: eng]
- RULE-35: Nothing init prints, and nothing in the hook script it installs, carries an emoji or a term this release retired [risk: low] [origin: eng]
- RULE-36: A project init set up walks the three gates: the quick run passes, a record the developer commits meets `passed`, raising to `strong` refuses that record and accepts one the build identity committed, and `signed` refuses first an empty signer list and then a high-risk rule with no signature, until a signature is written in a signed commit [risk: high] [origin: eng]
- RULE-37: Each language init supports is wired the same way in a real project, and an install from the marketplace leaves `.purlin/plugin-root` as the only file naming the install [risk: high] [origin: eng]
- RULE-38: A `test_framework` name the config carries that detection does not find and the tree carries no wiring for is dropped and the drop is printed, so no runner is wired for a language the project does not have; a name the tree does carry is kept [risk: medium] [origin: eng]
- RULE-39: The mutmut block names as source every top-level directory holding a `.py` file at any depth and no test file at its top level, and names as the test selection the directories that do hold one, with `src`, `lib` and `app` preferred as source and `tests` and `test` as the selection; a project with no such directory names each non-test `.py` module at its root, and names `.` only when there is none [risk: medium] [origin: eng]
- RULE-40: Writing the mutmut block also appends `mutants/` to the project's `.gitignore`, once and never twice, so the copy mutmut breaks is never committed [risk: medium] [origin: eng]
- RULE-41: The `.gitignore` block init writes names `.purlin/briefs/**/*.brief.txt`, so the text rendering written beside a committed brief is never committed [risk: low] [origin: eng]
