# Feature: update

> Description: `purlin:init --update`, which brings a project an older Purlin
>   set up onto this release. The skill asks and this script edits, so the
>   edits are deterministic: `pending()` returns the migrations a project
>   still needs, the run prints that list before it asks, and `sync_status`
>   reads the same function, so the advisory a developer sees and the work
>   the script does cannot disagree. Every migration asks before it writes,
>   every file it rewrites is copied beside itself first, and one commit
>   carries the whole run.
> Scope: scripts/init/update.py
> Stack: python3 (stdlib only, 3.9 floor)

## Rules

- RULE-1: `pending()` returns one entry per migration a project still needs, each carrying an id, one line saying what it does and the files it touches; it returns nothing for a root with no `.purlin/`
- RULE-2: The detectors read the layout v0.9.5 left, and what that layout leaves behind is what they report; a project that carries a hook v0.9.5 installed has the hook migration reported too
- RULE-4: A project root with no `.purlin/` exits 2 saying there is nothing to update and naming the command that sets a project up
- RULE-5: `--yes` answers yes to every question and applies every pending migration, and a second run finds nothing left to do and changes neither the commit nor the tree
- RULE-6: Every migration asks before it writes; a declined one is reported as skipped and left pending, and declining one never stops the others
- RULE-7: Every file a migration rewrites is copied beside itself as `<name>.local-<sha8>.bak` holding the bytes it had before, and a second run does not write the copy again
- RULE-8: No proof file and no run file is left beside a spec, on disk or tracked; the dashboard data is untracked, left on disk, and named in `.gitignore`; the `.purlin/cache/` folder 0.9.5 kept is deleted, from git and from disk
- RULE-9: The pre-commit and pre-push hooks v0.9.5 installed under `.git/hooks/` are deleted, and a hook another tool wrote is left alone: this release runs nothing at commit time and nothing at push time
- RULE-10: The config the run leaves carries exactly `version`, `gate`, `mutation_engine`, `min_strength`, `audit_parallel`, `tests` and `ci` at every gate, with `audit_parallel` 4 and none of the keys this release stopped reading; `ci` keeps `github`, `azure` or `none` where the project already named one, and otherwise names the host of the `origin` remote, `github` or `azure`, or `none` with no remote or another host
- RULE-11: The rewritten config carries no key this release does not read: the dashboard switch 0.9.5 wrote is not written back, whether it was on or off
- RULE-12: The gate question `purlin:init` asks is asked once more on an update, defaulting to the gate the project already named, then to `strong` when the old pre-push setting was the blocking one and to `passed` otherwise, taking the answer typed when it is one of the three gates and leaving the default when it is not
- RULE-13: The retired Windows tag at the end of a proof line becomes `@env(windows)`, and the same spelling in the middle of a line is left alone
- RULE-15: The workflow v0.9.5 wrote, which committed proof files back beside the specs, is removed; one runner file is offered in its place, where `purlin:init` writes it for the project's git host, `.github/workflows/purlin.yml` for GitHub and `purlin.azure-pipelines.yml` at the root for Azure DevOps, carrying the matrix the `@env` tags name, the pinned release and the triggers on run branches and signing tags; declining it leaves the file unwritten and says to run `purlin:init` again; the same prerequisites init checks are checked first, and a missing one leaves the workflow unwritten
- RULE-16: The plugin copies v0.9.5 put in the plugin folder under `.purlin/` are removed, and a file there of any other name is left alone; the wiring its init wrote is removed from each file that carries it, each backed up first and named in one line: the `pytest_plugins` entry naming the pytest plugin in `conftest.py`, which is removed when nothing else is left in it, and the reporter naming the Jest or Vitest plugin in `jest.config.*`, `vitest.config.*` or `package.json`; a `.csproj` that compiles the xUnit logger is named with what to remove by hand and left as it was
- RULE-18: One commit carries the whole run, its subject naming the release and every migration id applied; a run that applies nothing writes no commit; nothing is left uncommitted afterwards but the backup copies
- RULE-19: `sync_status` prints the directive to run the update while anything is pending, including when the config alone is already clean, and stops printing it once nothing is
- RULE-20: What the run prints carries no emoji, and a run that had migrations to ask about ends on a line naming the next step: `purlin:init --update` again for the migrations still pending, otherwise `purlin:status`
- RULE-21: The `tests` setting is written from the frameworks the old config named, xunit read as dotnet, one suite per framework init writes a command for; a framework detection does not find in the tree is dropped and the drop is printed, `dropped <name> from the tests: nothing in the tree runs it`, and `auto`, or no value, writes what detection finds
- RULE-23: A proof line that ends with the tag naming the kind of test it is, the tag v0.9.5 wrote, loses that tag, an `@env` tag after it is kept, and the rest of the line is untouched
- RULE-24: The design reference 0.9.5 let a spec carry is removed: a `> Visual-Reference:` line, a `> Visual-Hash:` line, a `> Source:` naming Figma and the `> Pinned:` that goes with that source; the spec is backed up first, the rest of it is untouched, a git `> Source:` and its `> Pinned:` stay, and one line per spec names the fields removed
- RULE-25: The config step prints one line naming every key it dropped, the retired ones and the ones 0.9.5 wrote that this release does not read, `report` and `audit_criteria_pinned` among them
- RULE-26: An update of a config with no `mutation_engine` asks, after the gate question and only at the gate `strong` or `signed`, the mutation question init asks, where an engine exists for the project's frameworks, defaulting to no: no writes `none` and `min_strength` null, yes writes `auto` with the gate's minimum and says to run `purlin:init` to wire the engine; at those gates a project with no engine is asked nothing, gets `none` and is told in one line; at `passed` nothing is asked or said and `none` is written; a config that already carries `mutation_engine` keeps it
- RULE-27: A feature spec with no `> Scope:` line is reported as advice naming it, `<n> specs have no > Scope: line: <names>. Run purlin:spec <name> to add one.`, with the line optional below `signed` and required at `signed`; the spec is not changed, nothing stays pending for it, and anchors are not named
- RULE-28: A project with no `.purlin/evidence/README.md` gets `.purlin/evidence/` with that README, the same bytes `purlin:init` writes, while the run files and proof files 0.9.5 committed beside the specs are still removed
- RULE-29: Each marker v0.9.5's plugins read becomes the comment `purlin: <feature> PROOF-<n>` above the same test, in the file's own comment syntax: the pytest `proof` mark with whatever follows its first two arguments, the Jest and Vitest tag, which leaves the title, the xUnit trait naming the proof and the SQL `@purlin` comment; a shell script's calls to the harness naming a proof become one comment each at its top, and each call, the line loading the harness and the closing call become a no-op; each file is backed up first, and one line per file names how many markers it rewrote, adding for a shell or SQL script that the file is one test now and passes when it exits 0
- RULE-30: A marker the upgrade cannot place above one test, such as a module-wide `pytestmark`, is named by file and line with what to do, and left as it was
- RULE-31: A `purlin-report.html` at the project root that is a link, as 0.9.5 left it, or whose bytes are not the page the plugin ships is replaced with a copy of that page, the bytes `purlin:init` writes; a project with no page there is left without one
