# Feature: update

> Description: `purlin:init --update`, which brings a project an older Purlin
>   set up onto this release. The skill asks and this script edits, so the
>   edits are deterministic: `pending()` returns the migrations a project
>   still needs, `--check` prints that list and exits 1 while anything is
>   pending, and `sync_status` reads the same function, so the advisory a
>   developer sees and the work the script does cannot disagree. Every
>   migration asks before it writes, every file it rewrites is copied beside
>   itself first, and one commit carries the whole run.
> Scope: scripts/init/update.py
> Stack: python3 (stdlib only, 3.9 floor)

## Rules

- RULE-1: `pending()` returns one entry per migration a project still needs, each carrying an id, one line saying what it does and the files it touches; it returns nothing for a root with no `.purlin/`, and `--json` prints that same list [risk: high] [origin: eng]
- RULE-2: The detectors read the layout v0.9.5 left, and what that layout leaves behind is what they report; a project that carries a retired hook has the hook migration reported too [risk: high] [origin: eng]
- RULE-3: `--check` prints the pending list with the command that applies it, exits 1 while anything is pending, writes nothing at all, and exits 0 saying nothing is pending once nothing is [risk: high] [origin: eng]
- RULE-4: A project root with no `.purlin/` exits 2 saying there is nothing to update and naming the command that sets a project up [risk: low] [origin: eng]
- RULE-5: `--yes` answers yes to every question and applies every pending migration, and a second run finds nothing left to do and changes neither the commit nor the tree [risk: high] [origin: eng]
- RULE-6: Every migration asks before it writes; a declined one is reported as skipped and left pending, and declining one never stops the others [risk: high] [origin: eng]
- RULE-7: Every file a migration rewrites is copied beside itself as `<name>.local-<sha8>.bak` holding the bytes it had before, and a second run does not write the copy again [risk: high] [origin: eng]
- RULE-8: No proof file and no run file is left beside a spec, on disk or tracked; the dashboard data and the cache are untracked, left on disk, and named in `.gitignore` [risk: high] [origin: eng]
- RULE-9: The pre-commit shim and the delegator git ran for it are deleted and untracked, a delegator another tool wrote is left alone, and a pre-push shim pointing at an older script is repointed at `scripts/hooks/pre-push.sh` with the rest of the shim untouched [risk: high] [origin: eng]
- RULE-10: The config the run leaves is the gate and what the gate derives, carrying `version`, `gate`, `ai_review_at`, `ci`, `min_strength`, `sql_engine`, `mutation_engine`, `test_framework`, `digest` and `pre_push`, plus `signers` under `signed`, and none of the keys this release stopped reading [risk: high] [origin: eng]
- RULE-11: The rewritten config carries no key nothing reads: the dashboard switch an older release carried is not written back [risk: medium] [origin: eng]
- RULE-12: The gate question is asked once more on an update, defaulting to the gate the project already named read in this release's words, then to `strong` when the old pre-push setting was the blocking one and to `passed` otherwise, taking the answer typed when it is one of the three gates and leaving the default when it is not [risk: high] [origin: eng]
- RULE-13: A proof's retired operating-system tag becomes `@env(<os>)` when the person confirms the system it names, is dropped when they decline or when it names no operating system, and the retired tier tag becomes `@unit @env(windows)`; text that only looks like a tag is left alone [risk: high] [origin: eng]
- RULE-14: A design source that named a design tool becomes `designs/<feature>/`, the retired visual fields and their continuation lines are dropped, and the rest of the spec is untouched [risk: medium] [origin: eng]
- RULE-15: The workflows this release replaced are removed and one `purlin.yml` is offered in their place, carrying the matrix the `@env` tags name and the pinned release; declining it leaves the file unwritten and names `purlin:init --ci` [risk: medium] [origin: eng]
- RULE-16: Every copy under `.purlin/plugins/` matches the plugin this release ships again, keeping the file name the project gave it, and a copy this release does not ship is left alone [risk: medium] [origin: eng]
- RULE-17: `.purlin/records/` is created with the README saying what an audit writes there, and that README is tracked [risk: low] [origin: eng]
- RULE-18: One commit carries the whole run, its subject naming the release and every migration id applied; a run that applies nothing writes no commit; nothing is left uncommitted afterwards but the backup copies [risk: high] [origin: eng]
- RULE-19: `sync_status` prints the directive to run the update while anything is pending, including when the config alone is already clean, and stops printing it once nothing is [risk: high] [origin: eng]
- RULE-20: What the run prints carries no emoji, and its last line names the next step: the update again while something is left, otherwise `purlin:status` [risk: low] [origin: eng]
- RULE-21: A `test_framework` name the config carries that detection does not find and the tree carries no wiring for is dropped and the drop is printed, while a name the tree does carry is kept [risk: medium] [origin: eng]
- RULE-22: A project whose `.gitignore` does not name `.purlin/briefs/**/*.brief.txt` has `untracked-files` pending, and applying it appends the line exactly once [risk: low] [origin: eng]
