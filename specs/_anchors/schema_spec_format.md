# Anchor: schema_spec_format

> Description: The spec format: the two sections every spec carries, the rule and proof
>   grammar, the metadata fields, the rule tags, the `@manual` tag and the `@env` tag, and
>   the values this release refuses rather than reads. Every surface that reads a spec
>   reads it through one parser, so a spec means the same thing to the status table, the
>   dashboard and the evidence file. The `specs` feature, which is that parser, requires
>   this anchor.
> Type: schema
> Scope: scripts/mcp/purlin/specs.py, references/formats/spec_format.md, references/formats/anchor_format.md
> Stack: python/stdlib, one regex parser in scripts/mcp/purlin/specs.py

## Rules

- RULE-1: A spec carries two sections, `## Rules` and `## Proof`, and the format names no third; a spec carrying a heading the format does not name still parses, its rules are still read, and nothing is reported about the extra heading
- RULE-2: Rule ids read `RULE-N`, are assigned in increasing order and are never reused, so a retired rule leaves its number vacant and a gap in the sequence is reported as nothing; a line under `## Rules` carrying no id is reported as a warning saying it is not numbered
- RULE-3: A proof line reads `PROOF-N (RULE-N)`, and names several rules as `PROOF-N (RULE-A, RULE-B)` when one flow drives all of them
- RULE-4: A rule that no proof line names carries an empty proof list and reads `no test` in its passed cell with the reason `no proof written`, so a spec cannot claim evidence it does not have
- RULE-5: `> Requires:` is a comma-separated list of spec names whose rules are counted with this spec's own and carry the label `required`
- RULE-6: `> Scope:` is a comma-separated list of file paths, parsed into a list in the order written, because the fingerprint hashes exactly those files to tell a code change from a rule change
- RULE-7: A first-level heading reads `# Feature: <name>` for a feature spec and `# Anchor: <name>` for an anchor [level: passed]
- RULE-8: `> Description:` takes continuation lines that begin with `>` and are not themselves a `> Field:` line, so the next field's value never reaches the description [level: passed]
- RULE-9: A proof line carries at most one `@manual` tag and at most one `@env` tag, in either order, read off the end of the line; any other trailing at-word is not a tag and stops the reading, and a tag that follows a list connector (a comma, `and`, `or`) is not a tag either, so a description whose prose ends in an at-word is left whole
- RULE-10: `@env` takes `windows`, `macos` or `linux` and nothing else; any other value, and any tag this release stopped reading, is returned in the unknown list and sets no environment, so a proof is never treated as owned by an operating system the release cannot name
- RULE-11: `> Note:` is free text addressed to whoever reads the spec; the parser ignores it, it never reaches the description or displaces `> Source:`, and a spec may carry more than one [level: passed]
- RULE-12: The two section headings are matched without regard to case, so `## rules` and `## PROOF` are read as `## Rules` and `## Proof`

## Proof

- PROOF-1 (RULE-1): The spec format reference, under its heading `## Required sections`, names exactly two sections, `## Rules` and `## Proof`, and no third. A spec carrying a heading `## What it does` between its metadata and its `## Rules` is still read: the status report names the spec, carries no `WARNING` and never mentions `What it does`, and the spec's rules read exactly `RULE-1`
- PROOF-2 (RULE-2): A spec at `specs/test/test_feat.md` whose rules hold `RULE-1` and the line `- some constraint without RULE-N prefix` is reported with the warning `WARNING: 1 lines under ## Rules in specs/test/test_feat.md are not numbered`. A spec whose rules are `RULE-1`, `RULE-3` and `RULE-20`, each with a proof, is reported with no `WARNING` at all, and its rules read exactly `RULE-1`, `RULE-3` and `RULE-20`, in that order
- PROOF-3 (RULE-3): Every list item under `## Proof` in every spec this project carries under `specs/` begins `PROOF-<n> (RULE-<n>)`, a proof id followed by one rule id in brackets. In a spec holding `RULE-1`, `RULE-2` and `RULE-3`, the line `PROOF-1 (RULE-1): One rule` is read as the one proof of `RULE-1`, the line `PROOF-2 (RULE-2, RULE-3): One flow drives both` as a proof of both `RULE-2` and `RULE-3`, and the line `PROOF-3: No rule named`, which names no rule, is not read as a proof
- PROOF-4 (RULE-4): A spec holding `RULE-1` and an empty `## Proof` section is read: `RULE-1` carries no proof, and its passed cell reads `no test` with the one reason `no proof written`. The same rule given the line `PROOF-1 (RULE-1)` and still no test carries the one proof `PROOF-1`, and its passed cell reads `no test` without the reason `no proof written`
- PROOF-5 (RULE-5): A feature carrying `> Requires: base` and one rule of its own is read beside an anchor `base` that holds `RULE-1`; among the feature's rules, those labelled `required` are exactly `RULE-1` of `base`. With `> Requires: other, base, ghost`, where `other` holds `RULE-1` and `RULE-2` and no spec is named `ghost`, the feature's rules read, in this order, its own `RULE-1` labelled `own`, `RULE-1` and `RULE-2` of `other` labelled `required`, and `RULE-1` of `base` labelled `required`; `ghost` adds no rule
- PROOF-6 (RULE-6): A spec carrying `> Scope: scripts/mcp/purlin/specs.py, src/app.py` is read with a scope of exactly two paths in the order written, `scripts/mcp/purlin/specs.py` then `src/app.py`, and the same two written the other way round read `src/app.py` then `scripts/mcp/purlin/specs.py`; beside an anchor whose scope is `scripts/`, the status report names both the spec and the anchor. In a project tracking `src/app.py` and `src/other.py`, a spec scoped `src/app.py` keeps the code part of its fingerprint unchanged when `src/other.py` is edited, and the code part changes when `src/app.py` is edited
- PROOF-7 (RULE-7): Read every file under `specs/` and verify each first-level heading begins `# Feature: ` or `# Anchor: `; a heading matching neither fails, naming the file and the heading
- PROOF-8 (RULE-8): Write a spec whose description is `First line` with the continuation `second line`, followed by `> Scope: src/`; scan the specs and verify the description carries both lines and that `src/` is absent from it, while the scope parses as the one-item list `["src/"]`
- PROOF-9 (RULE-9): Each proof description below is read into four values, its text, whether it is manual, its environment and its unknown tags. `Check it by hand @manual` reads manual with no environment; `Lock the file @manual @env(windows)` reads manual on `windows`, and `Lock the file @env(macos) @manual` manual on `macos`; `Lock the file @env(linux)` reads not manual on `linux`; each keeps its text before the tags and has no unknown tag. `Grep the file; verify present @smoke`, and prose whose last at-words follow a comma, `and` or `or`, such as `Check the documented tags @manual, @env` and `Accepts either @env or @manual`, each read whole, not manual, with no environment and no unknown tag. A second tag of a kind is limited: `Lock the file @env(linux) @env(macos)` reads `Lock the file` on `macos`, not manual, with the one unknown tag `@env(linux)`, and `Lock the file @manual @manual` reads `Lock the file`, manual, with no unknown tag. An at-word that is not a tag stops the reading: `Lock the file @manual @smoke` reads whole, not manual, with no environment and no unknown tag. A spec proof ending in prose with commas and then `@env(linux)` reads `linux`, not manual, with all its prose kept; this proof, which quotes tags inside its text, reads not manual with no environment and its last words kept. The two orders of the same pair of tags give the same four values, identical tuples
- PROOF-10 (RULE-10): The descriptions `Lock the file @env(windows)`, `Lock the file @env(macos)` and `Lock the file @env(linux)` each read `Lock the file`, not manual, on that system, with no unknown tag. `Lock the file @env(windows-2022)`, `Lock the file @env(ubuntu-24.04)` and `Lock the file @env(Windows)` each read `Lock the file`, not manual, with no environment and exactly one unknown tag, the tag as written. `Lock the file @windows` reads `Lock the file`, not manual, with no environment and the one unknown tag `@windows`. A tag carrying a value in brackets other than `@env` is one this release stopped reading: `Lock the file @manual(2024-01-01)` reads `Lock the file`, manual, with no environment and the one unknown tag `@manual(...)`, and `Lock the file @smoke(x)` reads `Lock the file`, not manual, with the one unknown tag `@smoke(...)`
- PROOF-11 (RULE-11): Write an anchor carrying `> Description: Local policy`, two `> Note:` lines and `> Source: ./dev/external-refs/policy.git`; scan the specs and verify the description equals `Local policy`, the source equals that path, the text of either note is absent from every parsed value of the spec, and `RULE-1` still parses
- PROOF-12 (RULE-12): A spec whose headings read `## rules` and `## PROOF`, holding `RULE-1` and `PROOF-1 (RULE-1)`, is read as a spec with a rules section: its rules read exactly `RULE-1`, and the proofs of `RULE-1` read exactly `PROOF-1`. A spec whose headings read `## Rule` and `## Proofs`, each one letter off, is read with no rules section, no rules and no proofs
