# Feature: package

> Description: The evidence package `purlin:export` writes: one data file for one version,
>   holding every rule's words, proofs, tests, results, audit, signatures and statuses, for a
>   reviewer who cannot open the repository. It is built from what git holds, says first
>   whether the version is signed or work in progress, gives the same bytes for the same tag,
>   and carries a fingerprint of itself. It is evidence handed to a regulated system of
>   record; Purlin makes no claim of compliance.
> Scope: scripts/export/package.py
> Stack: python/stdlib (json, hashlib, subprocess), git worktree

## Rules

- RULE-1: Run with no argument, the command writes `.purlin/evidence/package/<version>.json`, taking the version from the `VERSION` file, prints `Evidence package written to <path>. State: <state>, <m> of <n> rules meet the gate <gate>.` followed by `Not for approval.` for every state but `signed`, commits nothing and leaves no checkout behind
- RULE-2: `--release <name>` names the version, the file and the tag the package names in place of the `VERSION` file's value
- RULE-3: The package's top-level keys are, in this order, `schema` (`purlin-package/1`), `state`, `not_for_approval`, `rules_meeting_gate`, `rules_short_of_gate`, `purlin_version`, `project`, `version`, `tag`, `commit`, `gate`, `trust`, `mutation_engine`, `min_strength`, `features`, `warnings` and `fingerprint`, and `commit` is the commit the evidence was taken at
- RULE-4: While any rule does not meet the gate the state is `work in progress`, `not_for_approval` is true and the two counts say how many rules do and do not meet it; a project with no evidence, a rule with no test, a rule no audit has read and an unsigned rule at the gate `signed` each hold it there
- RULE-5: When every rule meets the gate and the version is not signed and tagged, the state is `gate <gate> met` and `not_for_approval` is still true; at the gate `passed` or `strong` the state is never `signed`, even where a `signed/<version>` tag names the commit, because only a project at `signed` is tagged
- RULE-6: Each rule carries its words exactly as the spec has them, its level and whether it was marked, its proofs, its tests, each result with its operating system, source, time, commit and runner, what the audit found with the model and the fingerprint of its instructions, each current signature with its signer, time, machine, operating system, note, whether its commit verifies and the hashes it locked, the statuses its level asks for and whether it meets the gate; nothing names who last changed a test. `statuses` carries `passed` always, `strong` where the rule's level is `strong` or `signed`, and `signed` where it is `signed`, and has no key at all for a status the level does not ask for
- RULE-7: Evidence written and not committed is left out of the package and named, one line per file, in its `warnings` and on the terminal as `<path> is written and not committed; the package leaves it out.`
- RULE-8: The same commit gives the same bytes: exporting twice, or from a second clone at the tag, writes identical files, with `\n` line ends, a trailing newline, and every time in UTC ending in `Z`
- RULE-9: `fingerprint` is the sha256 of the package's canonical bytes with that field empty; `--check <file>` prints `The package matches its fingerprint.` and exits 0 for a package as written, and for one edited afterwards names the mismatch and exits 1
- RULE-10: `--commit` commits the package alone with the subject `purlin: evidence at <sha7>`, naming the commit the evidence was taken at, and a second `--commit` over the same evidence prints `Package unchanged.` and leaves that commit named

## Proof

- PROOF-1 (RULE-1): In a project at the gate `signed` whose `VERSION` file reads `2.1.0` and whose one rule needing a signature has none, the command is run with no argument; it exits 0, its first line reads `Evidence package written to .purlin/evidence/package/2.1.0.json. State: work in progress, 1 of 2 rules meet the gate signed. Not for approval.`, `HEAD` has not moved, `git status` lists that one file as untracked and nothing else, and `git worktree list` shows one worktree
- PROOF-2 (RULE-2): In a project whose `VERSION` file reads `2.1.0`, the command is run with `--release beta`; it exits 0, its first line begins `Evidence package written to .purlin/evidence/package/beta.json.`, that package reads `version` `beta` and `tag` `signed/beta`, and no `.purlin/evidence/package/2.1.0.json` is written
- PROOF-3 (RULE-3): A project whose settings name it `proj`, at the gate `signed` with a minimum strength of 50 and no trust or mutation engine set, is exported; the package's top-level keys read exactly the seventeen the rule names, in that order, so a key added, missing or out of place fails, `schema` reads `purlin-package/1`, `purlin_version` reads the installed Purlin's version, `project`, `gate`, `trust`, `mutation_engine` and `min_strength` read `proj`, `signed`, `local`, `none` and 50, and `commit` is the full 40-character sha of the commit the project stands at
- PROOF-4 (RULE-4): A project at the gate `passed` whose `VERSION` file reads `1.0.0` and which has no evidence at all is exported; it exits 0, its first line ends `State: work in progress, 0 of 2 rules meet the gate passed. Not for approval.`, the package reads `state` `work in progress`, `not_for_approval` true, `rules_meeting_gate` 0 and `rules_short_of_gate` 2, and `RULE-1` carries no result and a passed status reading `no test`
- PROOF-5 (RULE-4): In a project at the gate `signed` whose rule needing a signature is signed, a third rule reading `A locked account returns 423 (URS-042)` has no proof and no test; exported, the package carries that rule's words exactly so, no proofs and no tests, one result reading `no test` and `meets_gate` false, and reads `state` `work in progress` with `rules_short_of_gate` 1
- PROOF-6 (RULE-4): A project at the gate `strong` whose two tests pass and whose `RULE-2` no audit has read is exported; `RULE-2` carries `audit` null, a strong status reading `not audited`, so any other word fails, and `meets_gate` false, and the package reads `state` `work in progress` with `not_for_approval` true
- PROOF-7 (RULE-4): A project at the gate `signed` whose `RULE-2` passes and is audited `strong` but is not yet signed is exported; `RULE-2` carries no signatures and a signed status reading `unsigned`, and the package reads `state` `work in progress` with `rules_meeting_gate` 1 and `rules_short_of_gate` 1
- PROOF-8 (RULE-5): A project at the gate `passed` whose two rules pass is exported; its first line ends `State: gate passed met, 2 of 2 rules meet the gate passed. Not for approval.` and the package reads `state` `gate passed met` with `not_for_approval` true. A project at the gate `signed` whose every rule is signed and meets it, with no `signed/<version>` tag written, is exported; the package reads `state` `gate signed met`, not `signed`, with `not_for_approval` true
- PROOF-9 (RULE-6): A project at the gate `signed` is signed and tagged and its package read; `RULE-2` carries its words exactly as `Invalid credentials return 401 and the body "denied"`, the level `signed` and not marked, where `RULE-1` reads `passed` and marked; one proof, `PROOF-2`, with its words, not manual and with no operating system; one test naming `tests/test_login.py` and `test_a_bad_password_is_denied` under `PROOF-2`; one current result from `ci` reading `passed`, with the runner `ci`, the time `2026-09-13T12:00:00Z`, an operating system and the full sha of the commit the tests ran at; an audit reading `strong` with no findings, strength 90, the model's name, the fingerprint of the audit's instructions and the time `2026-09-13T12:05:00Z`; one signature by `jane@acme.com` whose commit verifies, with no note, an operating system, a machine, a time in UTC ending in `Z`, and six locked hashes that equal the rule's current rule, proof, test and audit hashes, the test hash's kind and the first 16 characters of its triple, so a signature locking any other value fails; a signed status reading `signed` with the reason `by jane@acme.com`; and `meets_gate` true
- PROOF-10 (RULE-10): In a project standing at a commit `<sha>`, the command is run with `--commit`; it exits 0, its last line reads `Package committed.`, the newest commit's subject reads `purlin: evidence at <the first 7 characters of sha>`, and `git status` is clean. Run with `--commit` a second time over the same evidence, its last line reads `Package unchanged.`, `HEAD` has not moved, and the package's `commit` still reads the full `<sha>`. With a change to another file staged first, `--commit` makes a commit that changes `.purlin/evidence/package/2.1.0.json` and nothing else, and the other change is still staged after it
- PROOF-11 (RULE-6): In a signed and tagged project whose test file was committed by `dev@example.com`, the package's text carries neither that address nor the word `author` anywhere
- PROOF-12 (RULE-7): In a project at the gate `signed` whose every rule is signed, the `ci` evidence is written again with the later time `2026-09-14T12:00:00Z` and not committed, and the project is exported; the terminal prints `.purlin/evidence/ci/login.json is written and not committed; the package leaves it out.`, `warnings` holds exactly that one line, and `RULE-2`'s one result carries the committed time `2026-09-13T12:00:00Z`, not the later one
- PROOF-13 (RULE-8): A project is exported twice with nothing changed between; the two files are the same byte for byte, the file ends in `}` and a newline, and it holds no carriage return
- PROOF-14 (RULE-8): A signed and tagged project is cloned into a second folder, `signed/2.1.0` is checked out there, and the project is exported there; it exits 0, its first line ends `State: signed, 2 of 2 rules meet the gate signed.`, so it carries no `Not for approval.`, and the file it writes holds exactly the bytes of `.purlin/evidence/package/2.1.0.json` as the tag holds it
- PROOF-15 (RULE-8): In a signed and tagged project's package, the times stored under `at` and `committed_at` that are not null number at least four, and each reads as a date, `T`, a time to the second and `Z`, as `2026-09-13T12:00:00Z` does; a time with an offset such as `+02:00` or with fractions of a second fails
- PROOF-16 (RULE-9): A package is exported and its file checked with `--check`; it exits 0 and prints exactly the one line `The package matches its fingerprint.`, and the package's `fingerprint` reads 64 lowercase hexadecimal characters that equal the sha256 taken separately over the file's bytes with that field's value emptied to `""`, so a fingerprint taken over any other bytes fails
- PROOF-17 (RULE-9): In an exported package the first `"unsigned"` is changed to `"signed"` and the file checked with `--check`; it exits 1 and its first line reads in full `The package does not match its fingerprint: the package records the fingerprint <the fingerprint as written> and its content gives <the sha256 of the edited bytes with that field emptied>.`, the two values differing. The package as written, with a carriage return put before each newline and nothing else changed, is checked; it exits 1 and its first line names `not in the canonical form`
- PROOF-18 (RULE-6): In a project at the gate `passed`, a rule with no proof, `RULE-3`, has one passing test marked with the rule's own id, and its evidence is committed; exported, `RULE-3` carries no proofs, one test naming `RULE-3` where a proof id would stand, the file `tests/test_login.py` and the name `test_a_locked_account_returns_423`, and one result reading `passed`, while `RULE-2`, which has a proof, lists its test under `PROOF-2`
- PROOF-20 (RULE-6): In a signed and tagged project whose `RULE-1` is marked `[level: passed]`, `RULE-1`'s `statuses` holds exactly the one key `passed`, reading `passed`, and `RULE-2`'s holds exactly `passed`, `strong` and `signed`. With `RULE-1` marked `[level: strong]` instead and the project exported, its `statuses` holds exactly `passed` and `strong`, neither of them null; a `signed` key or a null value there fails
- PROOF-19 (RULE-5): A project at the gate `strong` whose two rules meet it carries a `signed/2.1.0` tag, made by hand, on the commit it stands at, and is exported; it exits 0, its first line ends `State: gate strong met, 2 of 2 rules meet the gate strong. Not for approval.`, and the package reads `state` `gate strong met`, not `signed`, with `not_for_approval` true. The same project at the gate `passed` with the same hand-made tag exits 0, its first line ends `State: gate passed met, 2 of 2 rules meet the gate passed. Not for approval.`, and the package reads `state` `gate passed met` with `not_for_approval` true
