# Feature: pm_anchor_userstories

> Scope: tools/PM/purlin-anchor-userstories.md, tools/PM/purlin-anchor-userstories.skill
> Stack: markdown (packaged Claude skill)
> Description: The `purlin-anchor-userstories` skill under `tools/PM/`: a product manager writes user stories with it and the result has to be a file the Purlin plugin actually reads. These rules hold it to the one output path `sync_status` scans, to the vocabulary the rest of the project uses, to the authoring template `references/formats/anchor_format.md` owns, and to the commit prefix `references/commit_conventions.md` defines. The `.skill` file beside the markdown is a zip of that same markdown, so the rules that cover the text cover what a user installs.

## Rules

- RULE-1: The skill writes its output to `specs/_anchors/<name>.md` inside the user's project repo and to no other path, and `<name>` is a snake_case token that is both the file name and the name on the `# Anchor:` line. FORBIDDEN: the suffix `.anchor.md` anywhere in the file, and any instruction that lets the reader choose where the file lands. `sync_status` scans `specs/_anchors/*.md` and nothing else, so a spec written to a path the reader picked is invisible to every Purlin command the project runs, and the skill has produced a document rather than a spec
- RULE-2: FORBIDDEN: the terms `toolkit`, `anchor file` and `.anchor.md`. REQUIRED: `anchor spec` for the artifact and `the Purlin plugin` for what consumes it. Purlin is a Claude Code plugin, not a toolkit, and what the skill produces is a spec in the same 2-section format every other Purlin spec uses; a skill that calls it an "anchor file" at an arbitrary path teaches a product manager that the output is a document nobody parses
- RULE-3: The skill's authoring template is the one `references/formats/anchor_format.md` carries under Part 1: the same headings in the same order (`# Anchor: <name>`, `## Rules`, `## Proof`) and the same metadata field names (`Description`, `Scope`, `Type`). The format file is the versioned contract and this skill is a second copy of it, so the copy is held equal to the original rather than trusted to stay that way
- RULE-4: The skill commits with `anchor(<name>): create`, the row `references/commit_conventions.md` carries for creating an anchor spec, and it tells the reader not to use `chore:`. The prefix is what says a spec moved, to a human reading the log and to the project's own tooling; `chore:` says a file was tidied
- RULE-5: The `.skill` archive beside the markdown holds exactly one `SKILL.md` whose bytes equal `tools/PM/purlin-anchor-userstories.md`. The `.md` is what a reviewer reads and the `.skill` is what a user installs, so a zip regenerated from an older `.md` ships instructions the repository no longer contains. `dev/pack_tools.sh` regenerates it from the markdown (`qa_report` RULE-6 states the same for the QA pair)

## Proof

- PROOF-1 (RULE-1): Read `tools/PM/purlin-anchor-userstories.md` line by line and assert no line contains `.anchor.md`, reporting the line number and the line text of the first offender. Assert the literal `specs/_anchors/<name>.md` appears, that the fenced write block contains `cat > specs/_anchors/` and `git add specs/_anchors/`, and that the word `snake_case` appears. Restoring one `.anchor.md` mention fails the first assertion and names the line @unit
- PROOF-2 (RULE-2): Read the file and assert, one assertion per term so the failure names it, that no line carries `toolkit`, `anchor file` or `.anchor.md` (case-insensitive, reporting the offending line number), and that `anchor spec` and `the Purlin plugin` each appear at least once. Putting `Purlin toolkit` back into the opening paragraph fails the proof and names that line @unit
- PROOF-3 (RULE-3): Parse the fenced `markdown` block under `### Template` in `references/formats/anchor_format.md` and the fenced `markdown` block under `## Anchor Spec Template` in the skill. From each, collect the heading lines in order and the `> <Field>:` metadata field names. Assert the two heading lists are equal and the two field-name lists are equal, so neither file can gain, lose or reorder a section without the other. Dropping `> Scope:` from the skill's template, or renaming `## Proof` in either file, fails the proof @unit
- PROOF-4 (RULE-4): Assert `anchor(<name>): create` appears in the skill, that the commit fence contains `git commit -m "anchor(<name>): create"`, that the retired instruction `chore:` appears only in the sentence forbidding it, and that `references/commit_conventions.md` carries a table row naming `anchor(<name>): create`. Reverting the commit line to `chore: update anchor file ...` fails on the fence assertion @unit
- PROOF-5 (RULE-5): Open `tools/PM/purlin-anchor-userstories.skill` as a zip through the same helper `qa_report` PROOF-6 uses, assert its namelist is exactly `['purlin-anchor-userstories/SKILL.md']`, read that entry's bytes and assert they equal the bytes of the sibling `.md`. Appending a byte to the `.md` without rerunning `dev/pack_tools.sh` fails the proof @unit
