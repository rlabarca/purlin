# Feature: test_results

> Description: What `purlin:test` leaves behind. A run of the tagged tests writes one
>   `.purlin/tests/<feature>.json` per feature it covered and one `.purlin/tests.md` table for
>   the whole project, then commits both under the person's own git identity and never pushes.
>   Both files are tracked, because the point of them is that somebody who did not make the run
>   can read them on the git host. They are the `local` source: they count at the gate `passed`
>   and at nothing above it, where a record CI wrote is the evidence.
>   This feature covers the two files, the words a rule reads, the table, the commit, the run
>   that has nothing to commit, and the reader that hands the results to the payload.
> Scope: scripts/run/results.py, scripts/mcp/purlin/results.py, references/formats/tests_format.md
> Stack: python/stdlib (json, subprocess, datetime), git

## Rules

- RULE-1: A `--quick` run writes `.purlin/tests/<feature>.json` for every feature it covered, carrying `schema` `purlin-tests/1`, the full `commit` the working tree was on, the `at` time in ISO 8601 UTC, the `os` the run was on, a `rules` object and a `proofs` array [bar: strong] [origin: eng]
- RULE-2: `rules` holds one entry per rule the spec writes, reading the passed cell's own word for what this run saw: `passed` where every proof that could run here passed, `failed` where a test claiming one of them failed, `not run` where a proof is tagged `@env` for another operating system, and `no test` where nothing observed any of them; a rule whose proofs are all `@manual` reads `passed`, because no run was ever going to observe one [bar: strong] [origin: eng]
- RULE-3: `proofs` holds one entry per proof of those rules, each naming its `id`, its `rule`, a `result` of `pass`, `fail` or `missing`, its `tier`, its `env` and the `test` that observed it as `<file>::<name>` [bar: strong] [origin: eng]
- RULE-4: `.purlin/tests.md` is one table for the whole project, rendered from every file under `.purlin/tests/` rather than from the run, so a `--feature` run leaves the rows it did not run exactly as they were; it carries a heading naming the commit, the columns `Feature`, `Rules`, `Passed`, `Failing`, `No test` and `Last run`, and one sentence saying the numbers are the last local run and count only at `passed` [bar: strong] [origin: eng]
- RULE-5: `Passed` counts the rules reading `passed`, `Failing` those reading `failed` and `No test` every other rule, and `Last run` is `<sha7> · <time> · <os>` from that feature's own file [bar: strong] [origin: eng]
- RULE-6: The run commits both files itself, under the person's own git identity, with the subject `purlin: tests at <sha7>`, then prints `Test results committed.`; it never pushes and never prints a push command [bar: strong] [origin: eng]
- RULE-7: A run that saw the same thing about the same code writes neither file again and prints `Test results unchanged.`, where the same code means the two commits differ in nothing outside `.purlin/tests/` and `.purlin/tests.md`, so committing the results does not give the next run something to commit [bar: strong] [origin: eng]
- RULE-8: Outside a git repository the two files are still written and the run says there is no git repository to commit them to [bar: passed] [origin: eng]
- RULE-9: The reader hands the payload one `{proof_id: status}` map per feature, taking the committed results and this checkout's own runtime run and letting the newer of the two answer; a feature only one of them knows about is read from that one [bar: strong] [origin: eng]
- RULE-10: Neither file is gitignored: `templates/gitignore.purlin` names neither `.purlin/tests/` nor `.purlin/tests.md`, and neither does this repository's own `.gitignore` [bar: strong] [origin: eng]
- RULE-11: `references/formats/tests_format.md` is the wire format: it carries a `Format-Version` of at least 1, names both paths, the seven fields of the JSON file, the four words a rule may read, the six fields of a proof entry and the commit subject [bar: strong] [origin: eng]

## Proof

- PROOF-1 (RULE-1): Run `--all --quick` over a project with one spec and one tagged passing test; verify `.purlin/tests/feat.json` exists, that its `schema` is `purlin-tests/1`, that its `commit` is the 40-character sha HEAD names, that its `at` matches `YYYY-MM-DDTHH:MM:SSZ`, that its `os` is one of `windows`, `macos` and `linux`, and that its keys are exactly `schema`, `feature`, `commit`, `at`, `os`, `rules` and `proofs` @unit
- PROOF-2 (RULE-2): Call `rule_word()` with one proof observed `pass`; verify `passed`. With one observed `fail` beside one observed `pass`; verify `failed`. With a proof tagged `@env` for another operating system beside a passing one; verify `not run`. With a proof nothing observed; verify `no test`. With no proof at all; verify `no test`. With one proof whose tier is `manual`; verify `passed` @unit
- PROOF-3 (RULE-3): Run `--all --quick` over a spec whose `RULE-1` has a passing `PROOF-1` and whose `RULE-2` has an unobserved `PROOF-2`; verify the `proofs` array holds two entries with the keys `id`, `rule`, `result`, `tier`, `env` and `test`, that `PROOF-1` reads `pass` with a `test` of `tests/test_feat.py::test_ok`, and that `PROOF-2` reads `missing` with an empty `test` @unit
- PROOF-4 (RULE-4): Run `--feature one --quick` then `--feature two --quick` over a project with both specs; verify `.purlin/tests.md` holds a row for each, that the second run did not change the first row, that the file opens `# Test results at <sha7>`, that its header row names the six columns in order and that its last line is the sentence naming the gate `passed` @unit
- PROOF-5 (RULE-5): Render the table from two features, one with 3 rules reading `passed`, `failed` and `not run` and one with 1 rule reading `passed`; verify the first row reads `3 | 1 | 1 | 1` for rules, passed, failing and no test, that the second reads `1 | 1 | 0 | 0`, and that each `Last run` cell is that feature's own `<sha7> · <time> · <os>` @unit
- PROOF-6 (RULE-6): In a git checkout, run `--all --quick`; verify the output holds `Test results committed.` and no line holding `git push`, that `git log -1 --format=%s` reads `purlin: tests at <sha7>` for the commit the run observed, that the commit's author is the checkout's own git identity, and that the commit touches `.purlin/tests/feat.json` and `.purlin/tests.md` and nothing else @unit
- PROOF-7 (RULE-7): Run `--all --quick` three times in a git checkout with nothing else changing; verify the first prints `Test results committed.` and the next two print `Test results unchanged.`, that exactly one `purlin: tests at` commit was made, and that `.purlin/tests/feat.json` still names the commit the first run observed. Change a source file, commit it and run again; verify `Test results committed.` @unit
- PROOF-8 (RULE-8): Run `--all --quick` in a directory that is not a git repository; verify both files were written and that the output holds `there is no git repository to commit them to` @unit
- PROOF-9 (RULE-9): Write a results file saying `PROOF-1` passed at a time an hour ago, and a runtime proof file saying it failed; verify `local_status_map()` answers `fail` for that feature. Make the results file the newer of the two and remove the runtime file's newer timestamp; verify it answers `pass`. Remove the runtime file; verify the committed results answer. Remove the results file instead; verify the runtime run answers @unit
- PROOF-10 (RULE-10): Read `templates/gitignore.purlin` and this repository's `.gitignore`; verify neither names `.purlin/tests` in any spelling. Build the payload over a project whose only evidence is a committed results file; verify the rule's passed cell reads `passed` with the source `local` @unit
- PROOF-11 (RULE-11): Read `references/formats/tests_format.md`; verify its first line is a `Format-Version` of at least 1, that it names `.purlin/tests/<feature>.json` and `.purlin/tests.md`, that it lists the seven fields, the four words `passed`, `failed`, `no test` and `not run`, the six proof fields and the subject `purlin: tests at <sha7>` @unit
