# Feature: records

> Description: The evidence a verify run leaves behind. A record is one run's observations
>   for one feature, written into the tree as a file and committed: adding a file never
>   conflicts, so the log of what was verified is the git history of `.purlin/records/`.
>   This feature covers the file's name and retention, the validation tag that keeps a
>   record for ever, the two identities that commit one, the label git puts on it, the
>   workflow the git host runs, the pull request comment and the dashboard artifact a CI
>   run publishes, the `--remote` round trip, and the scan that reads another repository's
>   rollup without cloning it whole.
> Scope: scripts/run/records.py, scripts/run/ci.py, scripts/run/remote.py, scripts/run/workflow.py, scripts/report/scan.py, templates/purlin.yml, templates/purlin.azure-pipelines.yml, dev/fixtures/consumer-ci
> Stack: python/stdlib (json, subprocess, urllib), git, GitHub and Azure DevOps REST APIs

## Rules

- RULE-1: A record is written to `.purlin/records/<feature>/<timestamp>-<commit7>-<runner>[-<os>].json`, where `<runner>` is `ci` or the local part of the committer's email, and the `runner`, `os` and `timestamp` fields inside the file are set to match the name rather than left as the caller handed them over [risk: medium] [origin: eng]
- RULE-2: A feature keeps the three newest records for each operating system and a write prunes the rest as it goes, so a Windows job never deletes what a Linux job wrote [risk: medium] [origin: eng]
- RULE-3: `purlin:verify --tag <name>` writes the annotated tag `validated/<name>` listing one record path per line in its message, and retention never deletes a path any `validated/*` message names [risk: medium] [origin: eng]
- RULE-4: A developer's commit stages the records and the deletions retention made, commits under the developer's own git identity and pushes; with no remote, no upstream or nothing staged it prints the reason and exits 0 [risk: medium] [origin: eng]
- RULE-5: A CI commit on GitHub is made through the git host's REST API as one tree request, then commit, then ref update, where the single tree carries the text of every path the run handed over including the approvals and the briefs that sit beside a spec, only a path whose bytes are not UTF-8 costs a blob request of its own, and no `author` and no `committer` field is sent, so the git host signs the commit with its own key [risk: high] [origin: eng]
- RULE-6: A ref update refused because the branch moved is retried 3 times and then raised; a refusal that is not a moved branch is raised at once without a retry [risk: medium] [origin: eng]
- RULE-7: A pull request from a fork writes no commit, and so does a run with no repository name or no token; each prints the reason and the run carries on [risk: high] [origin: eng]
- RULE-8: On Azure DevOps the record is pushed through the Pushes API against the ref's current object id, retried when that id is stale, and the branch is the pull request's head branch when the run has one [risk: medium] [origin: eng]
- RULE-9: A record is labelled from the last commit that touched it: `ci` when the git host made it, which on GitHub is the committer email `noreply@github.com` with the author `github-actions[bot]` and on Azure DevOps the build service, and only when the signature does not contradict that identity; `developer` when a person did; `local` when it is not committed at all [risk: high] [origin: eng]
- RULE-10: A CI run posts the seven-state rollup as a comment on the pull request it belongs to; a run that is not a pull request, or is not on a git host, posts nothing and is not an error, and a refusal by the git host is printed rather than raised [risk: low] [origin: eng]
- RULE-11: A CI run copies the dashboard page and `.purlin/report-data.js` into the directory the runner's own temporary-directory variable names, which is the directory the upload step reads; off a runner it goes to `.purlin/runtime/report` in the project [risk: medium] [origin: eng]
- RULE-12: `purlin:verify --remote` pushes the current branch and waits for the workflow with the git host's CLI; on Azure DevOps it prints the pipeline URL and returns, and a detached head is refused before anything is pushed [risk: low] [origin: eng]
- RULE-13: `scan.py` fetches `specs/` and `.purlin/` alone by sparse checkout, so a repository's code is never read, and a ref that does not exist is refused by name [risk: low] [origin: eng]
- RULE-14: The rollup names the project, the gate and every one of the seven states that has a count, then the newest record with its path, label and timestamp, or says no record has been committed yet [risk: medium] [origin: eng]
- RULE-15: The rollup counts the commits between the commit the newest record observed and HEAD, leaving out commits that touch only `.purlin/records/`, and says the count is unknown when the fetched history stops short of that commit [risk: medium] [origin: eng]
- RULE-16: `scan.py` requires `--repo`, reads the branch or tag `--ref` names rather than the default branch, and removes its temporary directory before it returns [risk: low] [origin: eng]
- RULE-17: The workflow a consumer project runs is rendered from `templates/purlin.yml`, which carries a `<<MATRIX>>` and a `<<PURLIN_REF>>` placeholder for the two things a project decides [risk: medium] [origin: eng]
- RULE-18: The rendered workflow checks out the project, locates Purlin, runs `purlin_run.py --all --record --ci`, uploads the artifact `purlin-dashboard-<runner>`, one name per matrix job, from the directory the run publishes to, clones the Purlin release the project pins, tells a forked pull request that no record was committed, and carries the scheduled pin check only when it is asked for [risk: high] [origin: eng]
- RULE-19: The matrix always covers Linux first, then one job per other operating system the project's `@env` tags name, so a project that tags nothing and a project that tags only Windows both keep a Linux job [risk: medium] [origin: eng]
- RULE-20: A consumer project carries no Purlin `scripts/` and no `dev/`: the fixture is its own project of 9 tracked files, its config is the shape this release reads, its plugin is a byte-identical copy of `scripts/proof/pytest_purlin.py`, its spec carries `@env(linux)` and no retired tag, its own tests pass against its own module, and Purlin reads it as one feature with 2 rules [risk: medium] [origin: eng]
- RULE-21: The default branch is the one `origin/HEAD` points at; with no remote it is the branch `HEAD` names, and `main` only when neither can be read, so a repository whose only branch is `master` is never told its approval is not on the branch [risk: medium] [origin: eng]
- RULE-22: A REST call the git host refuses with 403 or 429 while naming how long to wait, in `Retry-After` seconds or the `x-ratelimit-reset` epoch, waits that long, no longer than 120 seconds, prints one line saying so and is sent again, up to 3 times before the refusal is raised; a refusal naming no wait is raised on the first answer [risk: medium] [origin: eng]
- RULE-23: Records read at a ref come out of git at that commit rather than off the disk, each labelled from git; a ref git cannot read gives no records, and a file under `.purlin/records/` that is not a JSON object is skipped [risk: medium] [origin: eng]
- RULE-24: A developer's record commit hands git the pathspec `.purlin/records` with `/` on every operating system, both to find the records retention deleted and to stage the records, so a record commit made on Windows stages the new record and the deletions [risk: medium] [origin: eng]
