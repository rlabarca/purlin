# Feature: records

> Description: The evidence a CI run leaves behind. A record is one run's observations
>   for one feature, written into the tree as a file and committed: adding a file never
>   conflicts, so the log of what ran is the git history of `.purlin/records/`. An audit
>   writes one, on a person's machine or on a runner, and the folder it sits in is its
>   source.
>   This feature covers the file's name and retention, the one identity that commits a
>   `ci` record, the source git gives it, the workflow the git host runs, where a CI run
>   commits and where it does not, the workspace check that keeps a fixture project from
>   speaking for the job it runs inside, and the `--remote` round trip.
> Scope: scripts/run/records.py, scripts/run/ci.py, scripts/run/remote.py, scripts/run/workflow.py, templates/purlin.yml, templates/purlin.azure-pipelines.yml, dev/fixtures/consumer-ci
> Stack: python/stdlib (json, subprocess, urllib), git, GitHub and Azure DevOps REST APIs

## Rules

- RULE-1: A record is written to `.purlin/records/<source>/<feature>/<timestamp>-<commit7>-<runner>[-<os>].json`, where `<source>` is `ci` or `local` and `<runner>` is `ci` or the local part of the committer's email, and the `source`, `runner`, `os` and `timestamp` fields inside the file are set to match the name and the folder rather than left as the caller handed them over [bar: strong] [origin: eng]
- RULE-2: A feature keeps the three newest records for each operating system in each source folder and a write prunes the rest as it goes, so a Windows job never deletes what a Linux job wrote and a local audit never deletes what CI wrote [bar: strong] [origin: eng]
- RULE-5: A CI commit on GitHub is made through the git host's REST API as one tree request, then commit, then ref update, where the single tree carries the text of every path the run handed over including the briefs under `.purlin/briefs/`, only a path whose bytes are not UTF-8 costs a blob request of its own, and no `author` and no `committer` field is sent, so the git host signs the commit with its own key [bar: strong] [origin: eng]
- RULE-6: A ref update refused because the branch moved is retried 3 times and then raised; a refusal that is not a moved branch is raised at once without a retry [bar: strong] [origin: eng]
- RULE-7: A run with no repository name or no token writes no commit, prints the reason, and carries on [bar: strong] [origin: eng]
- RULE-8: On Azure DevOps the record is pushed through the Pushes API against the ref's current object id, retried when that id is stale, and the branch is the one the run was started for [bar: strong] [origin: eng]
- RULE-9: A record's source is the folder it sits in, and `record_label` reads the other answer, who committed the file, which `purlin:init --update` asks once when it moves a record written before the folders existed: `ci` when the git host made the commit, which on GitHub is the committer email `noreply@github.com` with the author `github-actions[bot]` and on Azure DevOps the build service, and only when the signature does not contradict that identity; `local` for everything else [bar: strong] [origin: eng]
- RULE-29: `purlin:audit` commits its record and its briefs through the same path `purlin:test` commits the test results, under the person's own identity and with no push, printing `Record committed.` or `Record unchanged.`; it stages `.purlin/records/local` and `.purlin/briefs/local` and nothing else [bar: strong] [origin: eng]
- RULE-12: `purlin:test --remote` is the one push Purlin makes: it creates the run branch `run/<branch>-<sha7>` on the remote, looks the run up by that branch with `gh run list --branch`, retried while the run registers and reported by name when none ever does, watches that one run, pulls the commit the runner made back onto the local branch with `git pull --ff-only origin <run branch>` at every gate, then deletes the run branch; a detached head and a tree with uncommitted changes are both refused before anything is pushed; on Azure DevOps it pushes the run branch the same way, then prints the pipeline URL, the pull and the delete and returns [bar: strong] [origin: eng]
- RULE-17: The workflow a consumer project runs is rendered from `templates/purlin.yml`, which carries a `<<MATRIX>>` and a `<<PURLIN_REF>>` placeholder for the two things a project decides; a project has a workflow at all for two reasons and no others, a proof tagged `@env` for an operating system this machine is not and a project whose trust is `remote`, and a project with neither gets none [bar: strong] [origin: eng]
- RULE-18: The rendered workflow triggers on a push to a `run/**` branch and on a push of a `signed/**` tag and on nothing else, and its one job is named `purlin`; it checks out the project, locates Purlin, runs `purlin_run.py --all --ci`, uploads nothing, and ends with a `Check the gate` step running `scripts/ci/gate_check.py --check --verify`; it clones the Purlin release the project pins [bar: strong] [origin: eng]
- RULE-19: The matrix always covers Linux first, then one job per other operating system the project's `@env` tags name, so a project that tags nothing and a project that tags only Windows both keep a Linux job [bar: strong] [origin: eng]
- RULE-20: A consumer project carries no Purlin `scripts/` and no `dev/`: the fixture is its own project of 9 tracked files, its config names the gate `strong`, its plugin is a byte-identical copy of `scripts/proof/pytest_purlin.py`, its spec carries `@env(linux)` and no retired tag, its own tests pass against its own module, and Purlin reads it as one feature with 2 rules [bar: strong] [origin: eng]
- RULE-21: The default branch is the one `origin/HEAD` points at; with no remote it is the branch `HEAD` names, and `main` only when neither can be read, so a repository whose only branch is `master` is never told its signature is not on the branch [bar: strong] [origin: eng]
- RULE-22: A REST call the git host refuses with 403 or 429 while naming how long to wait, in `Retry-After` seconds or the `x-ratelimit-reset` epoch, waits that long, no longer than 120 seconds, prints one line saying so and is sent again, up to 3 times before the refusal is raised; a refusal naming no wait is raised on the first answer [bar: strong] [origin: eng]
- RULE-23: Records read at a ref come out of git at that commit rather than off the disk, each carrying the source of its folder; a ref git cannot read gives no records, and a file under `.purlin/records/` that is not a JSON object is skipped [bar: strong] [origin: eng]
- RULE-24: `deleted_records()` hands git the pathspec `.purlin/records` with `/` on every operating system, so a run on Windows still finds the records retention deleted and the CI commit carries those deletions [bar: strong] [origin: eng]
- RULE-26: A run whose project root is not the directory the job checked out, named by `GITHUB_WORKSPACE` or `BUILD_SOURCESDIRECTORY`, speaks for nothing that job owns; with neither variable set every project is its own and nothing changes [bar: strong] [origin: eng]
- RULE-27: A CI commit through the git host's API is refused the same way when the project root is not the job's workspace, so a fixture project a test suite drives cannot land its records on the branch under review [bar: strong] [origin: eng]
- RULE-28: A CI run commits where its evidence is kept and nowhere else: `commits_here()` is true on a branch under `run/` and true off a runner altogether, where no rule is being spoken for, and false on a tag run, which writes nothing and says `Tag run: nothing is written.`; an Azure DevOps ref is read from `BUILD_SOURCEBRANCH` before `BUILD_SOURCEBRANCHNAME`, which carries only a ref's last part [bar: strong] [origin: eng]
