# Feature: run_script

> Description: The one command that runs a project's tagged tests, writes what they saw and,
>   on CI, writes the record. `purlin:test` runs it as `--quick`, `purlin:audit` as `--audit`,
>   and the CI job as `--ci`. It
>   resolves the configuration and the frameworks, scans the specs, runs one arm per
>   framework into `.purlin/runtime/proofs/`, and then checks the two things no test
>   framework reports on its own: an arm that ran and wrote nothing, and a marker in a test
>   source that this run produced no entry for. The contract every proof plugin implements
>   is the `proof_common` anchor this spec requires, written and proved once there rather
>   than restated here.
> Requires: proof_common
> Scope: scripts/run/purlin_run.py, scripts/proof/pytest_purlin.py, scripts/proof/jest_purlin.js, scripts/proof/vitest_purlin.ts, scripts/proof/xunit_purlin.cs, scripts/proof/shell_purlin.sh, scripts/proof/sql_purlin.sh, references/formats/proofs_format.md, references/proof_plugin_contract.md, references/supported_frameworks.md
> Stack: python/stdlib (subprocess, re, hashlib), pytest, jest, vitest, xunit, bash, sqlite3

## Rules

- RULE-1: The command line names exactly one of `--quick`, `--audit` and `--ci`, and either `--all` or at least one `--feature`; `--remote` belongs to `--quick`; `--tier` is `unit` or `all`. Any other shape exits 2 and prints the usage line, and `--audit --remote` exits 2 naming `purlin:test --remote` [bar: strong] [origin: eng]
- RULE-2: A `--feature` name with no spec under `specs/` exits 2 naming it, and a `--project-root` that is not a directory exits 2 saying so [bar: strong] [origin: eng]
- RULE-3: `--quick` runs one arm per resolved framework and the evidence lands in `.purlin/runtime/proofs/<feature>.<tier>.json`; nothing is written under `specs/` [bar: strong] [origin: eng]
- RULE-4: The shell arm runs each `*.test.sh` at the project root, and the sql arm runs each `.sql` file under `tests/` through the sql harness with the engine `sql_engine` names, defaulting to `sqlite3` [bar: strong] [origin: eng]
- RULE-5: A test that fails exits the run 1, names the runner that exited non-zero, and its proof entry carries `status: "fail"` [bar: strong] [origin: eng]
- RULE-6: The runtime proof directory is emptied before the arms run, so a file from an earlier run is never read as this run's evidence [bar: strong] [origin: eng]
- RULE-7: An arm that ran while its framework's markers sit in the tree, and whose plugin appended no entry at all, exits the run 1 and names that framework and how many marked tests were found; an arm with no markers is silent and not a failure [bar: strong] [origin: eng]
- RULE-8: A marker in a test source that produced no proof entry in this run exits the run 1 and is named; at most 5 are listed and the rest are counted [bar: strong] [origin: eng]
- RULE-9: A marker naming a feature this run did not select is not reported as missing [bar: strong] [origin: eng]
- RULE-10: A proof the spec tags `@env` for another operating system is not run here and is never reported missing; the run prints one sentence for it, `<feature> PROOF-N needs <os>; this machine is <os>. A remote runner runs it: purlin:init adds one.`, and a proof tagged for this one runs like any other [bar: strong] [origin: eng]
- RULE-11: Every run prints the status table and one line naming the next step; a `--quick` run then prints `gate passed: <n> of <rules>` or `gate not met: <n> of <rules>` as its last line, counting every rule under `specs/` rather than only the features it ran, and exits 1 when the passed level is not met; a project with no specs says so and exits 1 [bar: passed] [origin: eng]
- RULE-12: `--audit` and `--ci` each build one `purlin-record/3` record per feature carrying the commit, whether the tree was dirty, the runner, the timestamp, the environment, the plugins that ran, the operating system, the scope tree hash and the log [bar: strong] [origin: eng]
- RULE-13: Each rule of a record carries its proof ids, the tests that observed them, the result `pass`, `fail` or `missing`, and the test strength; a rule with no evidence is listed under `missing` [bar: strong] [origin: eng]
- RULE-14: A capture a test wrote under `.purlin/runtime/attachments/<feature>/<PROOF-N>.<ext>` is hashed into the record beside the rule its proof belongs to [bar: strong] [origin: eng]
- RULE-15: The run's console log is written to `.purlin/runtime/run.log` and the record carries that path with the log's sha256 [bar: strong] [origin: eng]
- RULE-16: The breaks are asked for each feature's scope files, the tests of each rule and the tier the run covered [bar: strong] [origin: eng]
- RULE-17: `--ci` on a run branch at `strong` and above commits the records it wrote through the git host with the message `purlin: record for <commit7>`, writes the briefs and says how many; `--audit` commits the same message through the local commit path under the person's own identity and never through the git host's API; at `passed` neither writes a record at all and each says so; `--quick` commits no record ever [bar: strong] [origin: eng]
- RULE-47: A `--ci` run writes only where the evidence it writes is kept, which is a `run/*` branch. On a tag run it writes no record and no brief at all and prints `Tag run: nothing is written.`, because what a tag run is for is the rerun and the gate check over the evidence already committed [bar: strong] [origin: eng]
- RULE-18: A checkout whose break engines are not importable still writes its record under `--ci`, prints that test strength was not measured, and exits 0 [bar: strong] [origin: eng]
- RULE-19: The marker scan reads the marker of each of the six shipped frameworks out of that framework's own file extensions, and never descends into `node_modules`, `bin`, `obj` or a dotted directory [bar: strong] [origin: eng]
- RULE-20: A record carries the git tree hash of its feature's scoped files, so a rule's passed cell reads `passed` while only other files change and reads `code changed` once a scoped file changes [bar: strong] [origin: eng]
- RULE-21: The operating system this run is on is reported as `windows`, `macos` or `linux` and never as anything else [bar: strong] [origin: eng]
- RULE-22: The run script's source carries none of the words this release retired and no emoji, and reads the operating system only through `sys.platform` [bar: passed] [origin: eng]
- RULE-36: `references/formats/proofs_format.md` is the wire format: it names the runtime location, the seven fields, one marker section per shipped framework and the retired fields, and carries no run-marker section [bar: strong] [origin: eng]
- RULE-37: The release ships a plugin for six frameworks, each with a runner-setup line in `references/supported_frameworks.md`, and shell is the one of them whose tests the scans read without extracting a test body [bar: passed] [origin: eng]
- RULE-38: The shell harness buffers what `purlin_proof` records and writes it when `purlin_proof_finish` runs, which clears the buffer, so a second finish with nothing buffered writes nothing [bar: strong] [origin: eng]
- RULE-39: The run script reconfigures stdout and stderr to UTF-8 before it prints anything, so a console whose codec is cp1252 prints the state table's glyphs instead of ending the run with an encoding error [bar: strong] [origin: eng]
- RULE-40: An arm that exits non-zero or is killed has the last 60 lines of its own output printed to stdout under `--- <arm> output (last 60 lines) ---` before the missing-evidence lines, and under `--ci` every arm's whole output is published as `logs/<arm>.log` in the dashboard directory [bar: strong] [origin: eng]
- RULE-41: `--project-root` with an empty value exits 2 naming the flag, rather than resolving to the working directory and running there [bar: strong] [origin: eng]
- RULE-42: `--ci` writes the briefs before the commit and hands their paths to it, so the one commit that carries the record carries the `.brief.json` files under `.purlin/briefs/ci/` too; `--audit` writes its record into `.purlin/records/local/` and its briefs into `.purlin/briefs/local/` and commits both; no run of any kind writes a signature file [bar: strong] [origin: eng]
- RULE-43: The pytest arm never collects `mutants/`, the copy mutmut leaves of the project, so a test mutmut copied is not collected twice and does not stop the run [bar: strong] [origin: eng]
- RULE-45: The gate decides the breaks and only `--audit` ever runs them: under `passed` an `--audit` run makes none, prints `Strength n/a: the gate is passed.` and writes no record, and under `strong` and `signed` the breaks run and the audit prints each feature's test strength beside the minimum, then each rule's observations; a `--ci` run makes none at any gate and prints `Strength n/a: no breaks run on CI.` [bar: strong] [origin: eng]
- RULE-48: `--audit` ends with `gate strong: <n> of <rules>` or `gate not met: <n> of <rules>`, counting the rules whose strong cell is met over every rule under `specs/`, and exits 1 when the gate is not met; under `passed`, where no strong cell exists, it names `passed` and counts that cell instead [bar: strong] [origin: eng]
- RULE-46: The briefs a `--ci` run writes are for the rules whose bar is `strong` and whose every tagged test passed in this run, named from the records the run just built rather than left to the brief writer to read off a passed cell, because the record is still uncommitted while the briefs are written and its source reads `local`, which `signed` does not count [bar: strong] [origin: eng]
- RULE-44: The shell arm also runs each `*.test.sh` in a subdirectory, from the project root by its relative path in sorted order, and steps over hidden directories, `node_modules`, `bin`, `obj` and `mutants/`, so a consumer's shell tests under `tests/` prove what they record [bar: strong] [origin: eng]
