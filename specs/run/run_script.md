# Feature: run_script

> Description: The one command that runs a project's tests and writes what they saw.
>   `purlin:test` runs it as `--test`, `purlin:audit` as `--audit`, and the CI job as
>   `--ci`. It resolves the configuration and the suites the settings name, scans the specs
>   and the markers, runs each suite's own command, ties each result in its report to the
>   markers above its test, and then checks the two things no test framework reports on its
>   own: a suite that left no report, and a marker of a feature it covers that has no result.
>   It hands what it saw to the evidence writer, whose own spec covers the file. How a report
>   is read and a result tied to its marker is the `reports` spec. Before any test it checks that
>   the settings file is there, that no older Purlin set the project up without an upgrade, and
>   that a test command is set, suggesting one from the test tools it knows.
> Scope: scripts/run/purlin_run.py, scripts/mcp/purlin/frameworks.py, references/supported_frameworks.md
> Stack: python/stdlib (subprocess, re, hashlib), bash, pytest, sqlite3

## Rules

- RULE-1: The command line names exactly one of `--test`, `--audit` and `--ci`, and at most one of `--all` and `--feature`; `--remote` belongs to `--test`, and `--commit` belongs to `--test` and `--audit` without `--remote`. Any other shape exits 2 and prints the usage line, and `--audit --remote` exits 2 naming `purlin:test --remote`
- RULE-2: A `--feature` name with no spec under `specs/` exits 2 naming it, and a `--project-root` that is not a directory exits 2 saying so
- RULE-3: `--test` runs each suite the `tests` setting names and writes what they saw into `.purlin/evidence/local/<feature>.json`, and writes nothing under `specs/`
- RULE-4: A SQL script in an `exit` suite run through `sqlite3 -bail` is one test: it passes when every statement succeeds and fails when one raises an error
- RULE-5: A test that fails exits the run 1 and its proof reads `fail` in the evidence; a failing test is a result, so the run does not call it missing evidence
- RULE-7: A project whose tests carry no marker is not missing evidence: the run names nothing missing, and the table is what says a rule has no test
- RULE-8: A marker of a feature the run covers whose test has no passing or failing result, because it was skipped, the report does not hold it, or no test follows the marker, exits the run 1 and is named with its file and line; at most 5 are listed and the rest are counted; on a remote runner only the markers of the proofs tagged `@env` for its system count
- RULE-9: A marker naming a feature this run did not select is not reported as missing
- RULE-10: A proof the spec tags `@env` for another operating system is not counted here and is never reported missing; the run prints `<feature> PROOF-N needs <system>; this machine is <system>. Run purlin:test --remote.`, each system as `Windows`, `macOS` or `Linux/Unix`, and a proof tagged for this one is counted like any other
- RULE-11: Every run ends on the status table, then the summary sentence and `Left to do`, which count every rule under `specs/` rather than only the features it ran; `--test` exits on the tests alone: 1 where a test failed, evidence is missing or a marker names nothing a spec has, 0 otherwise, and `--audit` and `--ci` exit as RULE-48 and RULE-12 say. A project with no specs says so and exits 1
- RULE-12: `--ci` on a run branch covers only the features that have a proof tagged `@env` for the runner's system and writes, for each, this runner's section of `.purlin/evidence/ci/<feature>.json`, listing those proofs alone and the rules they prove, with the runner `ci` and the machine `remote runner, <system>`, hands every path to the git host's commit with the subject `purlin: evidence at <sha7>` and the merge that puts its section into what the branch holds, at every gate, and prints `Evidence committed.`; it exits 1 when a test tied to one of those proofs failed or could not run and 0 otherwise, whatever else it found, a test tied to no such proof included
- RULE-15: `--audit` and `--ci` write the run's console log to `.purlin/runtime/run.log`, except a `--ci` run on a tag, which writes none
- RULE-16: The breaks are asked for each feature's scope files
- RULE-17: `--test` and `--audit` never commit through the git host's API, even with `--commit`, and write nothing under `.purlin/evidence/ci/`; only `--ci` commits through the API; no run of any kind writes a signature file
- RULE-47: A `--ci` run writes only where the evidence it writes is kept, which is a `run/*` branch. On a tag run it runs the tests tied to the proofs tagged `@env` for its system, writes no evidence and no `.purlin/runtime/run.log`, commits nothing, and prints a line beginning `Tag run: nothing is written.`
- RULE-20: The evidence a run wrote makes a rule's passed cell read `passed` while its fingerprint is the one taken now, committed or not; changing a scoped file makes the cell read `out of date` with the reason `code changed since <sha7>`, editing the spec `spec changed since <sha7>`, and editing a test file `tests changed since <sha7>`, where the sha is the commit the run started on; the next run clears it
- RULE-21: The run reads the operating system it is on as `windows`, `macos` or `linux`, and a system that is neither Windows nor macOS as `linux`
- RULE-22: The run script's source carries no emoji
- RULE-39: The run script reconfigures stdout and stderr to UTF-8 before it prints anything, so a console whose codec is cp1252 prints the state table's glyphs instead of ending the run with an encoding error
- RULE-40: A suite that exits non-zero or is killed has the last 60 lines of its own output printed to stdout under `--- <suite> output (last 60 lines) ---` before the status table, and `--audit` and `--ci` keep the whole of every suite's output in `.purlin/runtime/run.log`
- RULE-41: `--project-root` with an empty value exits 2 naming the flag, rather than resolving to the working directory and running there
- RULE-43: No marker is read from `mutants/`, the copy mutmut leaves of the project, so a test mutmut copied is never counted twice
- RULE-45: Mutation testing decides the breaks and only `--audit` ever runs them: under the gate `passed` an `--audit` run makes none and leaves `audit.mutation` null; with `mutation_engine` `none` it makes none, and a rule the AI audit found nothing against reads `strong` with the reason `no mutation score measured`; otherwise the breaks run for each feature with a rule the audit reads and for no other, the score lands in `audit.mutation`, and a score under `min_strength` leaves the strong cell `weak`; a `--ci` run makes no breaks, calls no model and writes no `audit` at any gate
- RULE-48: `--audit` exits 1 at every gate when a test it ran failed or did not run. Above the gate `passed` it also exits 1 when a rule it read is weak or could not be audited; a rule waiting only on a signature does not make it exit 1, and at the gate `passed` nothing the audit found makes it exit 1
- RULE-49: `--audit` reads each rule of the features it runs that is the feature's own, has a proof with a test, whose passed cell reads `passed` and that has no audit entry for its current rule, proof and test; a rule a feature takes from an anchor it requires is read once, as the anchor's, and never as the feature's. With no feature named and no `--all` it reads the rules of every feature, whichever features its tests ran, and `--all` reads every such rule again whatever entry it has
- RULE-50: Before its first model call `--audit` prints `AI audit: <n> rules to read, <k> at a time.`, where `<k>` is the lower of `audit_parallel` and `<n>`, and carries on without asking; with nothing to read it prints `AI audit: nothing to read; every rule matches its last audit.` and calls nothing
- RULE-51: `--audit` makes one model call per rule it reads, `audit_parallel` of them at once, 4 when the setting is absent, and 4 when it is not a whole number from 1 to 16, a fraction or a word included, with the run's first line reading `"audit_parallel" is <value>, which is not a whole number from 1 to 16; reading it as 4`, and writes each answer into that rule's `audit.rules` entry in `.purlin/evidence/local/<feature>.json` with its `verdict`, its `findings`, the `model` that answered and the sha256 of the `criteria` it was sent
- RULE-52: A rule the model could not be reached for gets nothing written into the evidence, its strong cell reads `not audited` with the reason `the AI audit could not run: <why>`, the run prints one line per cause with its count, `<n> rules could not be audited: <why>.` followed by what to do, and above the gate `passed` it exits 1; the next audit reads the rule again
- RULE-55: With no feature named and no `--all`, `--test` and `--audit` run a feature when no section for this operating system exists in either source of its evidence, when the newest such section's fingerprint differs from the one taken now on its spec, its code or its tests, when an untracked file git does not ignore sits under its `> Scope:` or beside one of its marker files, or when its spec names no files; an anchor's rules count in the spec of every feature that requires it, so an anchor edit runs the anchor and those features; every other feature is not run and its evidence is left as it was
- RULE-56: Before it runs anything, such a run prints `Selected <n> of <m> features: <feature> (<reasons>), ...` with the reasons `no run on <os> yet`, `<part> changed since <sha7>`, `a file is not tracked` and `names no files, so every run includes it`, then `Skipped <k> features whose spec, code and tests match their evidence: <names>. purlin:test --all runs them too.`, naming ten and counting the rest, then one line for each untracked file that selected a feature, `<path> is under <feature>'s scope and is not tracked, so its content is not part of the evidence until you git add it.`
- RULE-57: When such a run selects nothing it prints `Nothing to run: every feature's spec, code and tests match its evidence. purlin:test --all runs them anyway.`, runs no test, writes no evidence, ends on the status table, the summary sentence and `Left to do`, and exits 1 where a rule's tests fail in the evidence it stands on and 0 otherwise; with `--commit` it still commits the evidence an earlier run wrote
- RULE-58: A run over fewer features than the project has gives each suite's `{files}` only the test files that carry a marker of a feature it runs, and starts no suite that has none; a run over every feature runs every suite whole
- RULE-59: `--all` runs every feature whatever its evidence says, and `--ci` with no feature named runs every feature that has a proof tagged for this runner's system
- RULE-60: With no feature named, `--audit` runs its tests on the selection RULE-55 makes and then reads the rules RULE-49 names; with nothing selected it runs no test and still reads each rule that has no audit entry for its current text, proof and test
- RULE-54: `--audit` keeps one line before its ending: after the lines naming the evidence it wrote and committed, it prints `AI audit: <n> rules read, <s> strong, <w> weak.` and, on the same line, the rules it skipped, `<k> rules skipped; their text, proof and test match their last audit. purlin:audit --all reads them again.`, then one line per cause the model could not be reached, then the status table, the summary sentence and `Left to do`
- RULE-61: With the `tests` setting empty and a test tool Purlin knows found in the project, the run prints `No test command is set in .purlin/config.json, so nothing ran.`, then `Suggested for <name>: <run>`, then `Suggested entry: ` and the entry as one line of JSON, writes nothing and exits 1
- RULE-62: With the `tests` setting empty and no test tool Purlin knows found, the run prints `No test command is set in .purlin/config.json, and no test tool Purlin knows was found, so nothing ran. Run purlin:test to have one proposed.`, writes nothing and exits 1
- RULE-63: The entry suggested is that of the first tool found, in the order pytest, vitest, jest, dotnet, go, sql and shell: the tool's own command with the flag that writes the report Purlin reads, the report's path under `.purlin/runtime/reports/`, its format and the globs its test files live under; the supported-frameworks page shows the same seven entries
- RULE-64: A suggested tool that needs something added before it can write its report is told so in one more line: jest that it needs the package `jest-junit`, and sql that each test file runs through the `sqlite3` command and fails by raising an error
- RULE-65: With no `.purlin/config.json` in the project, the run prints `No .purlin/config.json here, so nothing ran. Run purlin:init to write it.`, writes nothing and exits 1
- RULE-66: In a project Purlin 0.9.5 set up and nobody upgraded, as the `update` spec tells one, the run prints `This project was set up by an older Purlin and not upgraded, so nothing ran. Run purlin:init --update.`, writes nothing and exits 1
- RULE-67: Before the status, the run prints one line for each rule of the features it ran that fails here, `<feature> <RULE-N> fails: <file>::<test>. Run purlin:build <feature>.`, naming each of its tests that failed, and for each that has no test, `<feature> <RULE-N> has no test. Run purlin:build <feature>.`
- RULE-68: `--commit` makes two commits: first `purlin: specs, tests and settings for <features>`, holding the spec of each feature it ran, the test files carrying their markers and `.purlin/config.json` where any changed, printed as `Committed <sha7>, the work these results describe:` and each path on a line of its own; then the evidence and the table, whose subject `purlin: evidence at <sha7>` names the first, or HEAD where the first had nothing to commit
