# Feature: run_script

> Description: The one command that runs a project's tagged tests and, on request, writes
>   the record. `purlin:test` runs it as `--quick`, `purlin:verify` as `--record`. It
>   resolves the configuration and the frameworks, scans the specs, runs one arm per
>   framework into `.purlin/runtime/proofs/`, and then checks the two things no test
>   framework reports on its own: an arm that ran and wrote nothing, and a marker in a test
>   source that this run produced no entry for. This feature also carries the contract every
>   proof plugin implements, because the run script is what executes them and what reports
>   the evidence they went missing.
> Scope: scripts/run/purlin_run.py, scripts/proof/pytest_purlin.py, scripts/proof/jest_purlin.js, scripts/proof/vitest_purlin.ts, scripts/proof/xunit_purlin.cs, scripts/proof/shell_purlin.sh, scripts/proof/sql_purlin.sh, references/formats/proofs_format.md, references/proof_plugin_contract.md, references/supported_frameworks.md
> Stack: python/stdlib (subprocess, re, hashlib), pytest, jest, vitest, xunit, bash, sqlite3

## Rules

- RULE-1: The command line names exactly one of `--quick`, `--record` and `--remote`, and either `--all` or at least one `--feature`; `--commit`, `--ci` and `--tag` belong to `--record`; `--tier` is `unit` or `all`. Any other shape exits 2 and prints the usage line [risk: medium] [origin: eng]
- RULE-2: A `--feature` name with no spec under `specs/` exits 2 naming it, and a `--project-root` that is not a directory exits 2 saying so [risk: medium] [origin: eng]
- RULE-3: `--quick` runs one arm per resolved framework and the evidence lands in `.purlin/runtime/proofs/<feature>.<tier>.json`; nothing is written under `specs/` [risk: high] [origin: eng]
- RULE-4: The shell arm runs each `*.test.sh` at the project root, and the sql arm runs each `.sql` file under `tests/` through the sql harness with the engine `sql_engine` names, defaulting to `sqlite3` [risk: medium] [origin: eng]
- RULE-5: A test that fails exits the run 1, names the runner that exited non-zero, and its proof entry carries `status: "fail"` [risk: high] [origin: eng]
- RULE-6: The runtime proof directory is emptied before the arms run, so a file from an earlier run is never read as this run's evidence [risk: high] [origin: eng]
- RULE-7: An arm that ran while its framework's markers sit in the tree, and whose plugin appended no entry at all, exits the run 1 and names that framework and how many marked tests were found; an arm with no markers is silent and not a failure [risk: high] [origin: eng]
- RULE-8: A marker in a test source that produced no proof entry in this run exits the run 1 and is named; at most 5 are listed and the rest are counted [risk: high] [origin: eng]
- RULE-9: A marker naming a feature this run did not select is not reported as missing [risk: medium] [origin: eng]
- RULE-10: A proof the spec tags `@env` for another operating system is listed as needing that system, is not run here, and is never reported missing; a proof tagged for this one runs like any other [risk: high] [origin: eng]
- RULE-11: Every run ends with the state table and one line naming the next step; a project with no specs says so and exits 1 [risk: low] [origin: eng]
- RULE-12: `--record` builds one `purlin-record/1` record per feature carrying the commit, whether the tree was dirty, the runner, the timestamp, the environment, the plugins that ran, the operating system, the scope tree hash and the log [risk: high] [origin: eng]
- RULE-13: Each rule of a record carries its proof ids, the tests that observed them, the result `pass`, `fail` or `missing`, and the test strength; a rule with no evidence is listed under `missing` [risk: high] [origin: eng]
- RULE-14: A capture a test wrote under `.purlin/runtime/attachments/<feature>/<PROOF-N>.<ext>` is hashed into the record beside the rule its proof belongs to [risk: medium] [origin: eng]
- RULE-15: The run's console log is written to `.purlin/runtime/run.log` and the record carries that path with the log's sha256 [risk: medium] [origin: eng]
- RULE-16: The breaks are asked for each feature's scope files, the tests of each rule and the tier the run covered [risk: medium] [origin: eng]
- RULE-17: `--commit` commits the records under the developer's identity and `--ci` under the git host's, both with the message `purlin: record for <commit7>`; `--tag <name>` names the records the validation tag vouches for; with neither flag nothing is committed, and `--ci` also auto-approves, writes the briefs and says how many of each [risk: high] [origin: eng]
- RULE-18: A checkout whose break engines are not importable still writes its record, prints that test strength was not measured, and exits 0 [risk: medium] [origin: eng]
- RULE-19: The marker scan reads the marker of each of the six shipped frameworks out of that framework's own file extensions, and never descends into `node_modules`, `bin`, `obj` or a dotted directory [risk: medium] [origin: eng]
- RULE-20: A record carries the git tree hash of its feature's scoped files, so a rule stays Recorded while only other files change and falls back to Tested when a scoped file changes [risk: high] [origin: eng]
- RULE-21: The operating system this run is on is reported as `windows`, `macos` or `linux` and never as anything else [risk: medium] [origin: eng]
- RULE-22: The run script's source carries none of the words this release retired and no emoji, and reads the operating system only through `sys.platform` [risk: low] [origin: eng]
- RULE-23: Every proof plugin writes `.purlin/runtime/proofs/<feature>.<tier>.json`, creating the directory when it is absent, and every entry carries the seven fields `feature`, `id`, `rule`, `test_file`, `test_name`, `status` and `tier` and no eighth, with `status` either `pass` or `fail` [risk: high] [origin: eng]
- RULE-24: Every proof plugin finds the project root by walking up from the working directory: the nearest ancestor, that directory included, holding `specs/` or `.purlin/`, and the working directory itself when none does [risk: high] [origin: eng]
- RULE-25: Every recorded `test_file` is relative to that root with `/` separators, and is the same string however the test was invoked; a file outside the root keeps an absolute path rather than gaining `../` segments [risk: high] [origin: eng]
- RULE-26: A run that collected no marker writes no proof file and leaves the files on disk exactly as it found them [risk: medium] [origin: eng]
- RULE-27: A write replaces only this feature's entries from the test files this run executed: another feature's entries stay, another file's entries stay, and an entry whose test file no longer exists is reaped [risk: high] [origin: eng]
- RULE-28: A written file's entries are sorted by `(id, test_file, test_name)` under ordinal comparison after the merge, so two runs of the same tests in any order write byte-identical files [risk: medium] [origin: eng]
- RULE-29: A test the framework skipped writes no entry and keeps the entry it already had; a test that did execute replaces its own entry even when a skipped test in the same file carries the same proof id [risk: high] [origin: eng]
- RULE-30: A plugin that saw markers and wrote no entry at all prints one line naming the features whose evidence went missing and exits non-zero [risk: high] [origin: eng]
- RULE-31: A marker carrying a retired operating-system keyword is refused by name, with a line saying to write `@env(windows)`, `@env(macos)` or `@env(linux)` on the proof line instead, and the run fails [risk: high] [origin: eng]
- RULE-32: Every write goes to a temporary file beside the target whose name carries the writing process's own id, and is then moved onto the target in one operation [risk: medium] [origin: eng]
- RULE-33: A proof plugin imports its language's standard library and its test framework and nothing else [risk: medium] [origin: eng]
- RULE-34: Each framework's marker is read exactly and nothing else is one: the pytest `proof` marker, the `[proof:...]` segment of a jest or vitest title, the xUnit trait named `PurlinProof`, the shell `purlin_proof` function and the SQL `-- @purlin` comment. A marker with too few arguments, a title with no marker, a trait with another name or another casing produces no entry [risk: high] [origin: eng]
- RULE-35: The tier the marker names picks the file the entry lands in, and a marker that names no tier lands in the `unit` file [risk: medium] [origin: eng]
- RULE-36: `references/formats/proofs_format.md` is the wire format: it names the runtime location, the seven fields, one marker section per shipped framework and the retired fields, and carries no run-marker section [risk: medium] [origin: eng]
- RULE-37: The release ships a plugin for six frameworks, each with a runner-setup line in `references/supported_frameworks.md`, and shell is the one of them whose tests the free checks grade without extracting a test body [risk: low] [origin: eng]
- RULE-38: The shell harness buffers what `purlin_proof` records and writes it when `purlin_proof_finish` runs, which clears the buffer, so a second finish with nothing buffered writes nothing [risk: medium] [origin: eng]
