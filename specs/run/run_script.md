# Feature: run_script

> Description: The one command that runs a project's tagged tests and writes what they saw.
>   `purlin:test` runs it as `--test`, `purlin:audit` as `--audit`, and the CI job as
>   `--ci`. It resolves the configuration and the frameworks, scans the specs, runs one arm per
>   framework into `.purlin/runtime/proofs/`, and then checks the two things no test
>   framework reports on its own: an arm that ran and wrote nothing, and a marker in a test
>   source that this run produced no entry for. It hands what the arms saw to the evidence
>   writer, whose own spec covers the file. The contract every proof plugin implements is the
>   `proof_common` anchor this spec requires, written and proved once there rather than
>   restated here.
> Requires: proof_common
> Scope: scripts/run/purlin_run.py, scripts/proof/pytest_purlin.py, scripts/proof/jest_purlin.js, scripts/proof/vitest_purlin.ts, scripts/proof/xunit_purlin.cs, scripts/proof/shell_purlin.sh, scripts/proof/sql_purlin.sh, references/formats/proofs_format.md, references/proof_plugin_contract.md, references/supported_frameworks.md
> Stack: python/stdlib (subprocess, re, hashlib), pytest, jest, vitest, xunit, bash, sqlite3

## Rules

- RULE-1: The command line names exactly one of `--test`, `--audit` and `--ci`, and either `--all` or at least one `--feature`; `--remote` belongs to `--test`, and `--commit` belongs to `--test` and `--audit` without `--remote`. Any other shape exits 2 and prints the usage line, and `--audit --remote` exits 2 naming `purlin:test --remote` [bar: strong]
- RULE-2: A `--feature` name with no spec under `specs/` exits 2 naming it, and a `--project-root` that is not a directory exits 2 saying so [bar: strong]
- RULE-3: `--test` runs one arm per resolved framework and the evidence lands in `.purlin/runtime/proofs/<feature>.json`; nothing is written under `specs/` [bar: strong]
- RULE-4: The shell arm runs each `*.test.sh` at the project root, and the sql arm runs each `.sql` file under `tests/` through the sql harness with the engine `sql_engine` names, defaulting to `sqlite3` [bar: strong]
- RULE-5: A test that fails exits the run 1, names the runner that exited non-zero, and its proof entry carries `status: "fail"` [bar: strong]
- RULE-6: The runtime proof directory is emptied before the arms run, so a file from an earlier run is never read as this run's evidence [bar: strong]
- RULE-7: An arm that ran while its framework's markers sit in the tree, and whose plugin appended no entry at all, exits the run 1 and names that framework and how many marked tests were found; an arm with no markers is silent and not a failure [bar: strong]
- RULE-8: A marker in a test source that produced no proof entry in this run exits the run 1 and is named; at most 5 are listed and the rest are counted [bar: strong]
- RULE-9: A marker naming a feature this run did not select is not reported as missing [bar: strong]
- RULE-10: A proof the spec tags `@env` for another operating system is not run here and is never reported missing; the run prints one sentence for it, `<feature> PROOF-N needs <os>; this machine is <os>. A remote runner runs it: purlin:init adds one.`, and a proof tagged for this one runs like any other [bar: strong]
- RULE-11: Every run prints the status table and one line naming the next step; a `--test` run then prints `gate passed: <n> of <rules>` or `gate not met: <n> of <rules>` as its last line, counting every rule under `specs/` rather than only the features it ran, and exits 1 when the passed level is not met; a project with no specs says so and exits 1 [bar: passed]
- RULE-12: `--ci` on a run branch writes this runner's section of `.purlin/evidence/ci/<feature>.json` for every feature it covered, with the runner `ci`, and hands every path to the git host's commit with the subject `purlin: evidence at <sha7>` and the merge that puts its section into what the branch holds, at every gate, then prints `Evidence committed.` [bar: strong]
- RULE-15: `--audit` and `--ci` write the run's console log to `.purlin/runtime/run.log` [bar: strong]
- RULE-16: The breaks are asked for each feature's scope files and the tests of each rule [bar: strong]
- RULE-17: `--test` and `--audit` never commit through the git host's API, even with `--commit`, and write nothing under `.purlin/evidence/ci/`; only `--ci` commits through the API; no run of any kind writes a signature file [bar: strong]
- RULE-47: A `--ci` run writes only where the evidence it writes is kept, which is a `run/*` branch. On a tag run it writes nothing at all and prints `Tag run: nothing is written.`, because what a tag run is for is the rerun and the gate check over the evidence already committed [bar: strong]
- RULE-18: A checkout whose break engines are not importable still writes its evidence under `--audit`, prints that test strength was not measured, and exits 0 or 1 on the tests alone [bar: strong]
- RULE-19: The marker scan reads the marker of each of the six shipped frameworks out of that framework's own file extensions, and never descends into `node_modules`, `bin`, `obj` or a dotted directory [bar: strong]
- RULE-20: The evidence a run wrote makes a rule's passed cell read `passed` while its fingerprint is the one taken now, committed or not; changing a scoped file makes the cell read `out of date` with the reason `code changed since <sha7>`, editing the spec `spec changed since <sha7>`, and editing a test file `tests changed since <sha7>`, where the sha is the commit the run started on; the next run clears it [bar: strong]
- RULE-21: The operating system this run is on is reported as `windows`, `macos` or `linux` and never as anything else [bar: strong]
- RULE-22: The run script's source carries none of the words this release retired and no emoji, and reads the operating system only through `sys.platform` [bar: passed]
- RULE-36: `references/formats/proofs_format.md` is the wire format: it names the runtime location, the six fields, one marker section per shipped framework and the retired fields, and carries no run-marker section [bar: strong]
- RULE-37: The release ships a plugin for six frameworks, each with a runner-setup line in `references/supported_frameworks.md`, and shell is the one of them whose test source the brief does not read, because a shell proof has no body [bar: passed]
- RULE-38: The shell harness buffers what `purlin_proof` records and writes it when `purlin_proof_finish` runs, which clears the buffer, so a second finish with nothing buffered writes nothing [bar: strong]
- RULE-39: The run script reconfigures stdout and stderr to UTF-8 before it prints anything, so a console whose codec is cp1252 prints the state table's glyphs instead of ending the run with an encoding error [bar: strong]
- RULE-40: An arm that exits non-zero or is killed has the last 60 lines of its own output printed to stdout under `--- <arm> output (last 60 lines) ---` before the missing-evidence lines, and under `--ci` every arm's whole output is published as `logs/<arm>.log` in the dashboard directory [bar: strong]
- RULE-41: `--project-root` with an empty value exits 2 naming the flag, rather than resolving to the working directory and running there [bar: strong]
- RULE-43: The pytest arm never collects `mutants/`, the copy mutmut leaves of the project, so a test mutmut copied is not collected twice and does not stop the run [bar: strong]
- RULE-45: The gate decides the breaks and only `--audit` ever runs them: under `passed` an `--audit` run makes none, prints `Strength n/a: the gate is passed.` and writes a null `audit.mutation`, and under `strong` and `signed` the breaks run, the audit prints each feature's test strength beside the minimum and then each rule's observations, and the score lands in `audit.mutation`; a `--ci` run makes no breaks and writes no `audit` at any gate [bar: strong]
- RULE-48: `--audit` ends with `gate strong: <n> of <rules>` or `gate not met: <n> of <rules>`, counting the rules whose strong cell is met over every rule under `specs/`, and exits 1 when the gate is not met; under `passed`, where no strong cell exists, it names `passed` and counts that cell instead [bar: strong]
- RULE-44: The shell arm also runs each `*.test.sh` in a subdirectory, from the project root by its relative path in sorted order, and steps over hidden directories, `node_modules`, `bin`, `obj` and `mutants/`, so a consumer's shell tests under `tests/` prove what they record [bar: strong]
