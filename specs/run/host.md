# Feature: host

> Description: What a remote runner does with the evidence it writes, and how a run reaches
>   one. A runner runs the tests of the proofs tagged `@env` for its own operating system; a
>   proof with no tag is proven on a person's own machine. A run branch's runner writes its
>   own operating system's section of `.purlin/evidence/ci/<feature>.json` and always commits
>   it, through the git host's REST API, because that evidence exists nowhere else.
>   This feature covers that commit on GitHub and Azure DevOps, the merge that keeps two
>   runners from overwriting each other, the workflow the git host runs, where a CI run
>   commits and where it does not, the workspace check that keeps a fixture project from
>   speaking for the job it runs inside, and the `--remote` round trip.
> Scope: scripts/run/host.py, scripts/run/ci.py, scripts/run/remote.py, scripts/run/workflow.py, templates/purlin.yml, templates/purlin.azure-pipelines.yml, dev/fixtures/consumer-ci
> Stack: python/stdlib (json, subprocess, urllib), git, GitHub and Azure DevOps REST APIs

## Rules

- RULE-5: A CI commit on GitHub is made through the git host's REST API as one tree request, then commit, then ref update, where the single tree carries the text of every path the run handed over, only a path whose bytes are not UTF-8 costs a blob request of its own, and no `author` and no `committer` field is sent, so the git host signs the commit with its own key
- RULE-6: A ref update refused because the branch moved is sent again, at most 3 times in all, and then raised; a refusal that is not a moved branch is raised at once without a retry
- RULE-7: A run with no repository name or no token writes no commit, prints the reason, and carries on
- RULE-8: On Azure DevOps the evidence is pushed through the Pushes API against the ref's current object id, retried when that id is stale, and the branch is the one the run was started for; a file the branch already holds is sent as `changeType: edit` and one it does not hold as `add`
- RULE-12: `purlin:test --remote` is the one push Purlin makes: it creates the run branch `run/<branch>-<sha7>` on the remote, finds the run started for that branch, retried while the run registers and reported by name when none ever does, waits on that one run, then pulls the commit the runner made back onto the local branch with `git pull --ff-only origin <run branch>` at every gate, deletes the run branch and prints the table, after a red run as after a green one, on both git hosts; on GitHub the run is found with `gh run list --branch` and waited on with `gh run watch <id> --exit-status`
- RULE-36: `purlin:test --remote` refuses a detached head and a tree with uncommitted changes before anything is pushed
- RULE-30: On Azure DevOps the organisation and project the run is looked up in are read from `origin`, which takes one of three forms, `https://dev.azure.com/<org>/<project>/_git/<repo>`, `git@ssh.dev.azure.com:v3/<org>/<project>/<repo>` and `https://<org>.visualstudio.com/<project>/_git/<repo>`, where a user part before the host is ignored and a percent-encoded name is decoded; a URL in no such form is refused in one sentence naming what to set, before anything is pushed, and the run exits 1
- RULE-31: On Azure DevOps the run is found with `az pipelines runs list --organization https://dev.azure.com/<org> --project <project> --branch refs/heads/<run branch> --top 1 --query "[0].id" --output tsv`, asked every 3 seconds for up to 60, then waited on with `az pipelines runs show --id <id> --organization https://dev.azure.com/<org> --project <project> --query "[status,result]" --output tsv`, asked every 15 seconds for up to 90 minutes until the status is `completed`; the result `succeeded` exits 0 and `failed`, `canceled` and `partiallySucceeded` exit 1, each after the pull, the delete and the table of RULE-12; with no `az` on PATH, with no run registered and at the 90-minute limit it says so in one sentence naming what to do and exits 1, and it deletes the run branch only when no run registered
- RULE-38: On Azure DevOps every `git` and `az` process `purlin:test --remote` starts has a time limit, and none can prompt for a credential
- RULE-17: The workflow a consumer project runs is rendered from `templates/purlin.yml`, which carries a `<<MATRIX>>` and a `<<PURLIN_REF>>` placeholder for the two things a project decides
- RULE-39: A project has a workflow for one reason, a proof tagged `@env` for an operating system this machine is not, and a project with no such proof gets none
- RULE-18: The rendered workflow triggers on a push to a `run/**` branch and on a push of a `signed/**` tag and on nothing else, and its one job is named `purlin`; it checks out the project, locates Purlin, uploads nothing, and ends with the step that runs `purlin_run.py --all --ci`, so the job's result is that step's; it clones the Purlin release the project pins; the Azure DevOps pipeline has the same triggers and ends with the same step
- RULE-19: The matrix is one job per operating system it is handed, in the order Linux, macOS, Windows, and no other
- RULE-20: A consumer project carries no Purlin `scripts/` and no `dev/`: the fixture is its own project of 6 tracked files and carries nothing of Purlin in its tests, its config names the gate `strong` and one pytest suite and holds exactly the keys `purlin:init` writes, its test of the greeting passes against its own module and its test scoped to Linux passes on Linux alone, and Purlin reads it as one feature with 2 rules
- RULE-22: A REST call the git host refuses with 403 or 429 while naming how long to wait, in `Retry-After` seconds or the `x-ratelimit-reset` epoch, waits that long, no longer than 120 seconds, prints one line saying so and is sent again, up to 3 times before the refusal is raised; a refusal naming no wait is raised on the first answer
- RULE-24: When a run looks for the evidence files it removed, it hands git the path `.purlin/evidence` spelled with `/` on every operating system, so a run on Windows still finds them and the CI commit carries those deletions
- RULE-27: A CI commit through the git host's API from a project root that is not the directory the job checked out, named by `GITHUB_WORKSPACE` or `BUILD_SOURCESDIRECTORY`, is refused, so a fixture project a test suite drives cannot land its evidence on the branch under review; with neither variable set every project commits
- RULE-32: On every attempt of a CI commit each file is read again at the branch's current head and this runner's own operating system's section is merged into what the head holds, so a section another runner committed in between is kept
- RULE-40: The merge of a CI commit drops the rules the spec no longer carries from every section
- RULE-28: A CI run commits where its evidence is kept and nowhere else: it commits on a branch under `run/` and off a runner altogether, where no rule is being spoken for; a tag run writes nothing and says `Tag run: nothing is written.`, and a run on any other ref writes nothing and says that ref is neither a run branch nor a signed tag
- RULE-37: On Azure DevOps the run's branch is read from `BUILD_SOURCEBRANCH`, with `refs/heads/` taken off, before `BUILD_SOURCEBRANCHNAME`, which carries only a ref's last part, and that one reading decides both whether the run commits and the branch its commit is pushed to
- RULE-33: `purlin:test --remote` in a project whose `.purlin/config.json` says `ci: none` prints `purlin:test --remote needs a GitHub or Azure DevOps remote, and .purlin/config.json says ci: none.`, starts no process, so nothing is pushed, and exits 1
- RULE-34: A CI commit through the git host's API when neither the git host's variables nor git name a branch, as on a detached head, sends nothing and prints `No branch could be read from the git host or from git, so the results were not committed.`
- RULE-35: `purlin:test --remote` in a project whose `.purlin/config.json` cannot be read prints the sentence saying why, starts no process, so nothing is pushed, and exits 1
