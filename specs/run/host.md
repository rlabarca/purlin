# Feature: host

> Description: What a remote runner does with the evidence it writes, and how a run reaches
>   one. A runner runs the tests of the proofs tagged `@env` for its own operating system; a
>   proof with no tag is proven on a person's own machine. A run branch's runner writes its
>   own operating system's section of `.purlin/evidence/ci/<feature>.json` and always commits
>   it, through the git host's REST API, because that evidence exists nowhere else.
>   This feature covers that commit on GitHub and Azure DevOps, the merge that keeps two
>   runners from overwriting each other, where a CI run commits and where it does not, the
>   project root check that keeps a fixture project from speaking for the job it runs inside,
>   the runner file the first `--remote` writes for the git host the remote names, and the
>   `--remote` round trip.
> Scope: scripts/run/host.py, scripts/run/ci.py, scripts/run/remote.py, scripts/run/workflow.py, templates/purlin.yml, templates/purlin.azure-pipelines.yml
> Stack: python/stdlib (json, subprocess, urllib), git, GitHub and Azure DevOps REST APIs
> Highest-Rule: 56
> Highest-Proof: 143

## Rules

- RULE-55: A CI commit on GitHub goes through the git host's REST API as one tree, one commit and one move of the branch; the tree carries every file the run handed over and, as a deletion, every evidence file the run removed, on every operating system, and the commit carries no `author` and no `committer`, so the git host signs it with its own key
- RULE-8: On Azure DevOps the evidence is pushed through the Pushes API against the ref's current object id, to the branch the run was started for; a file the branch already holds is sent as `changeType: edit` and one it does not hold as `add`
- RULE-49: A CI commit refused because the branch moved is sent again, at most 3 times in all, and each attempt reads every file again at the branch's current head and merges this runner's own operating system's section into what the head holds, so a section another runner committed in between is kept
- RULE-40: The merge of a CI commit drops the rules the spec no longer carries from every section
- RULE-50: A CI commit with no repository name, no token, or no branch it can read from the git host or from git sends nothing, raises no error and prints why no evidence was committed
- RULE-27: A CI commit through the git host's API from a project root that is not the directory the job checked out, named by `GITHUB_WORKSPACE` or `BUILD_SOURCESDIRECTORY`, is refused, so a fixture project a test suite drives cannot land its evidence on the branch under review; with neither variable set every project commits
- RULE-56: A CI run commits where its evidence is kept and nowhere else: on a branch under `run/`, and off a runner altogether; a run on any other ref writes nothing and says that ref is not a run branch. On Azure DevOps the ref is read whole from `BUILD_SOURCEBRANCH`, never from `BUILD_SOURCEBRANCHNAME`, which carries only its last part
- RULE-22: A REST call the git host refuses with 403 or 429 while naming how long to wait, in `Retry-After` seconds or the `x-ratelimit-reset` epoch, waits that long, no longer than 120 seconds, prints one line saying so and is sent again, up to 3 times before the refusal is raised; a refusal naming no wait is raised on the first answer
- RULE-12: `purlin:test --remote` is the one push Purlin makes: it pushes the run branch `run/<branch>-<sha7>`, waits on the run the git host starts for that branch, on GitHub the `purlin.yml` workflow's run alone, then pulls the commit the runner made with `git pull --ff-only`, deletes the run branch and prints the table, after a red run as after a green one, and exits 1 when the run failed
- RULE-51: `purlin:test --remote` refuses before anything is pushed, says what is wrong and how to fix it, and exits 1, when the checkout is on no branch or holds uncommitted changes, when `origin` is neither GitHub nor Azure DevOps or is an Azure DevOps URL it cannot read, when `.purlin/config.json` cannot be read, and when the program it waits with, `gh` or `az`, is not installed
- RULE-30: On Azure DevOps the organisation and project the run is looked up in are read from `origin` in any of its three forms, `https://dev.azure.com/<org>/<project>/_git/<repo>`, `git@ssh.dev.azure.com:v3/<org>/<project>/<repo>` and `https://<org>.visualstudio.com/<project>/_git/<repo>`, with a percent-encoded name decoded
- RULE-31: On Azure DevOps the run is found with `az pipelines runs list` for the run branch and waited on with `az pipelines runs show` every 15 seconds for up to 90 minutes; `succeeded` exits 0, and `failed`, `canceled` and `partiallySucceeded` exit 1, each after the pull, the delete and the table of RULE-12; at the 90-minute limit it names the pull and delete commands, pulls nothing and exits 1
- RULE-52: Every `git`, `gh` and `az` process `purlin:test --remote` starts has its input closed and runs with `GIT_TERMINAL_PROMPT=0`, so none can prompt for a credential, and on Azure DevOps each has a time limit
- RULE-53: The runner file Purlin renders for each git host starts a run on a push to a `run/` branch and on nothing else, holds one job for each operating system it is handed, and ends with the step that runs `purlin_run.py --all --ci`, so the job's result is that step's
- RULE-54: The first `purlin:test --remote` in a project with no runner file for its remote's git host writes it, `.github/workflows/purlin.yml` for GitHub and `purlin.azure-pipelines.yml` for Azure DevOps, names the systems it runs for, pushes nothing and exits 0; `purlin:test --remote --commit-runner` then commits that file alone as `ci: the Purlin runner for <host>` and runs
