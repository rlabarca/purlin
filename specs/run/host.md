# Feature: host

> Description: What a remote runner does with the evidence it writes, and how a run reaches
>   one. A run branch's runner writes its own operating system's section of
>   `.purlin/evidence/ci/<feature>.json` and always commits it, through the git host's REST
>   API, because that evidence exists nowhere else.
>   This feature covers that commit on GitHub and Azure DevOps, the merge that keeps two
>   runners from overwriting each other, the workflow the git host runs, where a CI run
>   commits and where it does not, the workspace check that keeps a fixture project from
>   speaking for the job it runs inside, and the `--remote` round trip.
> Scope: scripts/run/host.py, scripts/run/ci.py, scripts/run/remote.py, scripts/run/workflow.py, templates/purlin.yml, templates/purlin.azure-pipelines.yml, dev/fixtures/consumer-ci
> Stack: python/stdlib (json, subprocess, urllib), git, GitHub and Azure DevOps REST APIs

## Rules

- RULE-5: A CI commit on GitHub is made through the git host's REST API as one tree request, then commit, then ref update, where the single tree carries the text of every path the run handed over, only a path whose bytes are not UTF-8 costs a blob request of its own, and no `author` and no `committer` field is sent, so the git host signs the commit with its own key
- RULE-6: A ref update refused because the branch moved is retried 3 times and then raised; a refusal that is not a moved branch is raised at once without a retry
- RULE-7: A run with no repository name or no token writes no commit, prints the reason, and carries on
- RULE-8: On Azure DevOps the evidence is pushed through the Pushes API against the ref's current object id, retried when that id is stale, and the branch is the one the run was started for; a file the branch already holds is sent as `changeType: edit` and one it does not hold as `add`
- RULE-12: `purlin:test --remote` is the one push Purlin makes: it creates the run branch `run/<branch>-<sha7>` on the remote, finds the run started for that branch, retried while the run registers and reported by name when none ever does, waits on that one run, then pulls the commit the runner made back onto the local branch with `git pull --ff-only origin <run branch>` at every gate, deletes the run branch and prints the table, after a red run as after a green one and on both git hosts through the same code; on GitHub the run is found with `gh run list --branch` and waited on with `gh run watch <id> --exit-status`; a detached head and a tree with uncommitted changes are both refused before anything is pushed
- RULE-30: On Azure DevOps the organisation, project and repository are read from `origin` in three forms, `https://dev.azure.com/<org>/<project>/_git/<repo>`, `git@ssh.dev.azure.com:v3/<org>/<project>/<repo>` and `https://<org>.visualstudio.com/<project>/_git/<repo>`, where a user part before the host is ignored and a percent-encoded name is decoded; a URL in no such form is refused in one sentence naming what to set, before anything is pushed, and the run exits 1
- RULE-31: On Azure DevOps the run is found with `az pipelines runs list --organization https://dev.azure.com/<org> --project <project> --branch refs/heads/<run branch> --top 1 --query "[0].id" --output tsv`, asked every 3 seconds for up to 60, then waited on with `az pipelines runs show --id <id> --organization https://dev.azure.com/<org> --project <project> --query "[status,result]" --output tsv`, asked every 15 seconds for up to 90 minutes until the status is `completed`; the result `succeeded` exits 0 and `failed`, `canceled` and `partiallySucceeded` exit 1, each after the pull, the delete and the table of RULE-12; with no `az` on PATH, with no run registered and at the 90-minute limit it says so in one sentence naming what to do and exits 1, and it deletes the run branch only when no run registered; the intervals and limits are module constants, every `git` and `az` process it starts has a time limit, and none can prompt for a credential
- RULE-17: The workflow a consumer project runs is rendered from `templates/purlin.yml`, which carries a `<<MATRIX>>` and a `<<PURLIN_REF>>` placeholder for the two things a project decides; a project has a workflow for one reason, a proof tagged `@env` for an operating system this machine is not, and a project with no such proof gets none
- RULE-18: The rendered workflow triggers on a push to a `run/**` branch and on a push of a `signed/**` tag and on nothing else, and its one job is named `purlin`; it checks out the project, locates Purlin, uploads nothing, and ends with the step that runs `purlin_run.py --all --ci`, so the job's result is that step's; it clones the Purlin release the project pins; the Azure DevOps pipeline has the same triggers and ends with the same step
- RULE-19: The matrix is one job per operating system the project's `@env` tags name, in the order Linux, macOS, Windows, and no other, so a project that tags only Windows gets one Windows job and a name that is not an operating system adds none
- RULE-20: A consumer project carries no Purlin `scripts/` and no `dev/`: the fixture is its own project of 6 tracked files and carries nothing of Purlin in its tests, its config names the gate `strong` and one pytest suite and holds exactly the keys `purlin:init` writes, its own tests pass against its own module, and Purlin reads it as one feature with 2 rules
- RULE-21: The default branch is the one `origin/HEAD` points at; with no remote it is the branch `HEAD` names, and `main` only when neither can be read, so a repository whose only branch is `master` is never told its signature is not on the branch
- RULE-22: A REST call the git host refuses with 403 or 429 while naming how long to wait, in `Retry-After` seconds or the `x-ratelimit-reset` epoch, waits that long, no longer than 120 seconds, prints one line saying so and is sent again, up to 3 times before the refusal is raised; a refusal naming no wait is raised on the first answer
- RULE-24: `deleted_files()` hands git the pathspec `.purlin/evidence` with `/` on every operating system, so a run on Windows still finds the evidence files it removed and the CI commit carries those deletions
- RULE-26: A run whose project root is not the directory the job checked out, named by `GITHUB_WORKSPACE` or `BUILD_SOURCESDIRECTORY`, speaks for nothing that job owns; with neither variable set every project is its own and nothing changes
- RULE-27: A CI commit through the git host's API is refused the same way when the project root is not the job's workspace, so a fixture project a test suite drives cannot land its evidence on the branch under review
- RULE-32: On every attempt of a CI commit each file is read again at the branch's current head and this runner's own operating system's section is merged into what the head holds, so a section another runner committed in between is kept, and the rules the spec no longer carries are dropped from every section in the merge
- RULE-28: A CI run commits where its evidence is kept and nowhere else: `commits_here()` is true on a branch under `run/` and true off a runner altogether, where no rule is being spoken for, and false on a tag run, which writes nothing and says `Tag run: nothing is written.`; an Azure DevOps ref is read from `BUILD_SOURCEBRANCH` before `BUILD_SOURCEBRANCHNAME`, which carries only a ref's last part

## Proof

- PROOF-5 (RULE-5): With the GitHub variables set, a CI commit of one evidence file sends exactly five requests to GitHub, in this order: read the branch `main`, read its head commit, create one tree, create the commit, move `main`; it creates no blob and the commit's sha comes back. The commit request carries `message`, `tree` and `parents` and nothing else, so no `author` and no `committer`, and the tree's one entry carries the file's path, the file permission `100644` and the file's text inline, byte for byte the text of the file on disk, whose `feature` reads `greeting`, with no blob id. A CI commit of the evidence files of two features, `greeting` then `farewell`, sends one tree listing both in that order, each with its own text, and still creates no blob. A CI commit of an evidence file and a second file holding the bytes `89 50 4e 47 0d 0a 1a 0a ff fe`, which are not UTF-8, creates exactly one blob, sent as `base64` and decoding to those bytes; that file's tree entry carries the blob's id and no text, and the evidence file's entry still carries its text and no blob id
- PROOF-6 (RULE-6): With the GitHub variables set, GitHub refuses the first move of the branch with HTTP 422, its answer for a branch that moved; the run reads the branch again, sends the move a second time, and the commit's sha comes back. When GitHub refuses every move with 422, the run sends exactly 3 moves and then stops with the error 422. When GitHub refuses the move with HTTP 403, which is not a moved branch, the run stops with the error 403 after sending the move once
- PROOF-7 (RULE-7): With `GITHUB_REPOSITORY` set to `acme/widgets` and `GITHUB_TOKEN` not set, a CI commit of one evidence file makes no commit and raises no error: no request reaches GitHub, no commit sha comes back, and the run prints a line naming `GITHUB_TOKEN`. With `GITHUB_TOKEN` set and `GITHUB_REPOSITORY` not set, the same commit also sends no request to GitHub, raises no error and returns no commit sha, and the printed line names `GITHUB_REPOSITORY`
- PROOF-8 (RULE-8): With the Azure DevOps build variables set, naming the branch `main`, the git host is read as Azure DevOps.
