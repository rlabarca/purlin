# Feature: reports

> Description: How a test's result reaches its proof. A test is any test in the project's own
>   suite that carries one comment naming the proof, `purlin: <feature> PROOF-<n>`, or the
>   rule where a rule has no proof. The settings file names each suite's own command, where
>   its report lands, the report's format and the globs its test files live under. Purlin
>   runs the command, reads the report, finds each result's test in its file by name, and
>   gives the result to every marker above that test. A marker it cannot tie to exactly one
>   test is reported by file and line; it never guesses.
> Scope: scripts/run/reports.py, scripts/mcp/purlin/markers.py, references/formats/marker_format.md
> Stack: python/stdlib (xml.etree, json, tokenize, ast, re, shlex), pytest, jest, vitest, dotnet, go, bash, sqlite3

## Rules

- RULE-1: A marker is one whole-line comment, `purlin: <feature> PROOF-<n>` or `purlin: <feature> RULE-<n>`, after any of `#`, `//`, `--`, `;`, `%` and `'`, or inside a one-line `/* */` or `<!-- -->`; a `purlin:` comment of any other shape is reported as `purlin: <file>:<line> is not a marker; write purlin: <feature> PROOF-<n>` and ties nothing
- RULE-2: A marker-shaped line inside a Python string or inside a shell here document is not a marker
- RULE-3: Only a file one suite's `files` globs match is read for markers; `*` and `?` match within one path segment, `**` matches any number of segments, a glob with no `/` matches that file name in any directory, and a file two suites match belongs to the first
- RULE-4: A marker belongs to the next test declared after it in its file: blank lines, decorators, attributes and other comments may sit between them, every marker between the previous test's declaration and this one belongs to this one, and the test's result counts for each of them
- RULE-5: A marker no test follows is reported as `purlin: <feature> <id> at <file>:<line> is tied to no test` and its result is `not run`
- RULE-6: A test is declared by a Python function whose name starts with `test`, at module level or in a class; a JavaScript or TypeScript `it` or `test` call with a literal title, inside any number of `describe` calls; a C# method carrying `[Fact]`, `[Theory]`, `[Test]`, `[TestCase]` or `[TestMethod]`; a Go `func TestX(t *testing.T)`
- RULE-7: A `junit` report is read case by case: a case with a `failure` or `error` child fails, one with a `skipped` child is skipped, and any other passes; its `classname`, `name` and `file` are what the tie reads
- RULE-8: A `trx` report is read result by result, each joined through its `testId` to the class and method it ran: `Passed` passes, `Failed`, `Error`, `Timeout` and `Aborted` fail, and any other outcome is skipped
- RULE-9: A `gotest` report is the JSON stream a Go test run prints on its standard output, read event by event: an event naming a test whose action is `pass`, `fail` or `skip` is that test's result, and every other event is left alone
- RULE-10: A case's file is its `file` attribute where the report writes one, else its class name where that is a path, else the Python module its dotted class name names among the suite's marked files; a `trx` case is found by its class chain, narrowed by namespace, and a `gotest` case by its package, read against the module line of `go.mod`
- RULE-11: The cases of one parametrised test, `test_x[a]` and `test_x[b]`, `TestX/a`, `Method(x: 1)`, or the rows of an `it.each` table, all belong to that one test, and the test passes only when every one of them passes
- RULE-12: A nested title, `outer > inner > title`, is matched by its last part and, where two tests in the file share that part, narrowed by the outer parts; a Python class and a C# class narrow the same way
- RULE-13: A case that matches more than one test is counted for none of them, and the run prints `purlin: the report's <name> matches <n> tests in <file>, so its result is not counted`
- RULE-14: A test whose cases all passed reads `pass`; one with any failed or errored case reads `fail`; one whose cases were all skipped, or that no case in the report is, reads `not run`
- RULE-15: In an `exit` suite each test file is one test: the command runs once per file, with `{files}` that one file, and the file passes when the command exits 0; every marker in the file takes the file's result
- RULE-16: `{files}` in a suite's command becomes the test files that carry a marker of a feature the run covers, each quoted, on a run over some features, and nothing on a run over every feature; `{report}` becomes the report path; the command runs through bash from the project root
- RULE-17: A suite's report is deleted before the suite runs, file or folder, so a report from an earlier run is never read; a report path that is a folder is read file by file, and a report path of `-` is read from the command's standard output
- RULE-18: A suite that leaves no report to read makes the run say `Evidence is missing: the <name> suite wrote no report at <path>.` and exit 1
- RULE-19: A marker naming a feature no spec has, a proof or a rule its feature's spec does not have, or a rule that has proofs, is printed by file and line as `purlin: <feature> <id> at <file>:<line> names a feature no spec has`, `... names a proof no spec has`, `... names a rule no spec has` or `... names a rule that has proofs; name one of them`, followed by one line naming what to do, `Remove the comment, or write the proof it names.`, and the run exits 1 whatever its tests did; a run whose markers all name what a spec has prints neither and exits 0 when its tests pass
- RULE-20: A `tests` entry with no `run`, a `format` other than `junit`, `trx`, `gotest` and `exit`, or no `files` is left out with one line naming the suite and why

## Proof

- PROOF-1 (RULE-1): A file holds eight marker lines, one after each of `#`, `//`, `--`, `;`, `%`, `'`, inside `/* */` and inside `<!-- -->`, and one line reading `# purlin: login`; the eight read as markers, each with its feature and id, and the ninth is reported as `is not a marker` with its line number, 9
- PROOF-2 (RULE-2): A Python test file holds `# purlin: login PROOF-1` inside a triple-quoted string and the same line as a real comment further down; only the real comment is read, at its own line. A shell script writes `# purlin: login PROOF-1` into another file through a here document and carries `# purlin: login PROOF-2` after it; only `PROOF-2` is read
- PROOF-3 (RULE-3): Of `dev/test_a.py`, `dev/sub/test_b.py` and `a/b/c.test.ts`, the glob `dev/test_*.py` matches the first alone, `**/*.test.ts` matches the third, and `test_*.py` matches the first two; a marked file matched by no suite's glob is not read, and one matched by two suites is run by the first
- PROOF-4 (RULE-4): Real pytest runs a file where one marker sits above a decorator above a passing test, and two markers, `PROOF-1` and `PROOF-2`, sit one above the other over a second passing test; each of the three markers reads `pass`, and the second test's name is listed once under each of its two proofs
- PROOF-5 (RULE-5): A marker on the last line of a test file, with no test after it, is printed as `purlin: login PROOF-3 at tests/test_login.py:<its line> is tied to no test`, the run exits 1, and the proof reads `missing` in the evidence
- PROOF-6 (RULE-6): The tests read from a Python file are its module-level `test_` functions and the `test_` methods of its classes, and a helper function in the same file is not a test; from a TypeScript file, the `it` and `test` calls with their `describe` titles as scopes; from a C# file, the methods under `[Fact]` and `[Theory]` with their class, nested class and namespace; from a Go file, each `TestX` function
- PROOF-7 (RULE-7): The JUnit report real pytest writes for one passing, one failing, one skipped and one erroring test reads as `pass`, `fail`, `skip` and `fail`, each with its dotted class name
- PROOF-8 (RULE-8): The report `dotnet test --logger trx` wrote for a passing, a failing, a skipped and a nested-class test reads `pass`, `fail`, `skip` and `pass`, each with its class name, `App.Tests.GreetingTests+Nested` for the nested one, and its method name without arguments
- PROOF-9 (RULE-9): The stream `go test -json` printed for a module of two packages, one holding a passing test, a table-driven test whose subtest `TestParse/empty` failed beside `TestParse/one` that passed, a skipped test and a failing test, the other a passing test, a test that panics and a test after it, with one line that is not JSON added, reads as exactly eight cases: `TestRate` `pass`, `TestLookupPanics` `fail`, `TestTotal` `pass`, `TestParse/empty` `fail`, `TestParse/one` `pass`, `TestParse` `fail`, `TestDiscount` `skip` and `TestTotalIsWrong` `fail`, each with its package, and none for the test after the panic, which never ran
- PROOF-10 (RULE-10): A pytest case whose class is `tests.test_login.TestGroup` is tied to the method in `tests/test_login.py`; a Vitest case whose class is `tests/login.test.ts` and a Jest case whose file attribute is `tests/login.test.ts` are tied to that file; a TRX case `App.Tests.GreetingTests` is tied to the file declaring that class in that namespace; a Go case in package `example.com/shop/cart` is tied to the test in `cart/cart_test.go` under a `go.mod` reading `module example.com/shop`
- PROOF-11 (RULE-11): Real pytest runs a marked test parametrised over two values where both pass, and the marker reads `pass`; with one value failing it reads `fail`. A TRX theory with one passing and one failing row reads `fail`, a Go test whose subtest failed reads `fail`, and a Vitest `test.each` table of two passing rows reads `pass`
- PROOF-12 (RULE-12): A file declares `same name` inside `describe('outer', describe('inner'))` with a marker, and `same name` directly inside `outer` without one, which fails; from the Vitest report and from the Jest report alike the marker reads `pass`. Two Python classes each declare `test_same`, the marked one passing and the other failing; the marker reads `pass`
- PROOF-13 (RULE-13): A report case `test_x` in a file declaring `test_x` twice at module level is counted for neither, the run prints `the report's test_x matches 2 tests in tests/test_login.py, so its result is not counted`, and the marker above the first reads `not run`
- PROOF-14 (RULE-14): Real pytest runs four marked tests, one passing, one failing, one skipped and one whose fixture raises; their markers read `pass`, `fail`, `not run` and `fail`; a marked test that the report does not mention at all reads `not run`
- PROOF-15 (RULE-15): An `exit` suite of two shell scripts, one exiting 0 and carrying two markers at its top, one exiting 3 and carrying one marker; both markers of the first read `pass` and the marker of the second reads `fail`, and the run exits 1 with no line reading `Evidence is missing`
- PROOF-16 (RULE-16): A suite whose command writes down the arguments it was given receives only the quoted test file of the one feature a run over one of two features covers, and no test file at all on a run over every feature; the report path it is given reads `.purlin/runtime/reports/pytest.xml`
- PROOF-17 (RULE-17): A report left from an earlier run at the suite's report path is deleted before the suite runs, so a suite whose command writes nothing reports `wrote no report` rather than reading the old one; a folder of two TRX files is read as the cases of both; a Go suite whose report is `-` reads its cases from what the command printed
- PROOF-18 (RULE-18): A suite whose command exits 0 and writes no report ends the run with `Evidence is missing: the pytest suite wrote no report at .purlin/runtime/reports/pytest.xml.` and exit code 1
- PROOF-19 (RULE-19): Every rule of `login` has a passing test, and one more passing test is marked `purlin: nosuch PROOF-1`; the run prints `purlin: nosuch PROOF-1 at tests/test_login.py:<its line> names a feature no spec has` and then `Remove the comment, or write the proof it names.`, and exits 1. With a second such marker added, both are printed and the line after them reads `Remove each comment, or write the proof it names.`
- PROOF-20 (RULE-20): A `tests` setting of four entries, one with no `run`, one with the format `tap`, one with no `files` and one complete, gives one suite, and three lines naming the other three and what each lacks
- PROOF-21 (RULE-19): Every rule of `login`, which has `PROOF-1` to `PROOF-3`, has a passing test, and one more passing test is marked `purlin: login PROOF-9`; the run prints `purlin: login PROOF-9 at tests/test_login.py:<its line> names a proof no spec has` and `Remove the comment, or write the proof it names.`, and exits 1
- PROOF-22 (RULE-19): Every rule of `login`, which has `RULE-1` to `RULE-3`, has a passing test, and one more passing test is marked `purlin: login RULE-9`; the run prints `purlin: login RULE-9 at tests/test_login.py:<its line> names a rule no spec has` and `Remove the comment, or write the proof it names.`, and exits 1
- PROOF-23 (RULE-19): Every rule of `login` has a passing test, and one more passing test is marked `purlin: login RULE-1`, a rule that has `PROOF-1`; the run prints `purlin: login RULE-1 at tests/test_login.py:<its line> names a rule that has proofs; name one of them` and `Remove the comment, or write the proof it names.`, and exits 1
- PROOF-24 (RULE-19): The same project with only the three markers `login PROOF-1`, `PROOF-2` and `PROOF-3`, each above a passing test, exits 0 and prints no line containing `names a` and no line reading `Remove the comment, or write the proof it names.`
