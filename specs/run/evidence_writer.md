# Feature: evidence_writer

> Description: What a run leaves behind. `purlin:test` and `purlin:audit` write this
>   operating system's section of `.purlin/evidence/local/<feature>.json` for every feature
>   they covered, merged into the file already on disk, and render `.purlin/tests.md` from
>   every evidence file. They write and do not commit; `--commit` commits the files under the
>   person's own identity, and nothing ever pushes. Every file is tracked, because the point
>   of them is that somebody who did not make the run can read them.
>   This feature covers the section a run writes, the words a rule reads, the merge, the files
>   a run removes, the table, the lines the run prints, the commit, and the audit's entries.
> Scope: scripts/run/evidence.py, references/formats/evidence_format.md, templates/gitignore.purlin
> Stack: python/stdlib (json, subprocess, datetime), git

## Rules

- RULE-1: A `--test` run writes `.purlin/evidence/local/<feature>.json` for every feature it covered, carrying `schema` `purlin-evidence/1`, the `feature`, the `source` `local` and the `spec` path, and one section keyed by the operating system the run is on, which carries the full `commit` the working tree was on, `dirty`, the `at` time in ISO 8601 UTC, the `runner` slug of the person's email, the `fingerprint` taken over the tree the run saw, a `rules` object and a `proofs` array
- RULE-2: `rules` holds one entry per rule the spec writes, reading `passed` where every proof that could run here passed, `failed` where a test claiming one of them failed, `not run` where a proof is tagged `@env` for another operating system, and `no test` where nothing observed any of them; a rule whose proofs are all `@manual` reads `passed`, because no run was ever going to observe one
- RULE-3: `proofs` holds one entry per proof and test that observed it, each naming its `id`, its `rule`, a `result` of `pass` or `fail`, its `env`, whether it is `manual`, and the `test` as `<file>::<name>`; a proof nothing observed has one entry whose `result` is `missing`, or `not run` when it is tagged for another operating system, and whose `test` is empty
- RULE-4: A run reads the file on disk and replaces only its own operating system's section: a section another operating system wrote and the `audit` object stay byte for byte as they were
- RULE-5: Every write drops the `rules` entries and the `audit.rules` entries of rules the spec no longer carries
- RULE-6: Every run deletes the evidence files under `local/` and `ci/` whose feature no spec defines, and prints `Removed <path>: no spec defines <feature>.` for each
- RULE-7: A run that sees the same thing over the same fingerprint as the section on disk leaves the file byte for byte as it was, `at` and `commit` included, so a second run finds nothing new to commit
- RULE-8: `.purlin/tests.md` is rendered from every evidence file on disk rather than from the run, one row per feature from its newest section in either source, so a `--feature` run leaves every other row as it was; it opens `# Tests at <sha7>`, carries the columns `Feature`, `Rules`, `Passed`, `Failing`, `No test` and `Last run`, counts `No test` as every rule neither passed nor failed, and fills `Last run` with `<sha7> · <at> · <os> · <source>`
- RULE-9: `--test` and `--audit` write the evidence and the table and commit nothing, and print `Evidence written to .purlin/evidence/local/<feature>.json.` when one feature ran and `Evidence written to .purlin/evidence/local/ for <n> features.` when several did
- RULE-10: With `--commit` the run commits the files under `.purlin/evidence/local/`, the table and any file it removed, under the person's own git identity, with the subject `purlin: evidence at <sha7>`, and prints `Evidence committed.`; a run with nothing new prints `Evidence unchanged.` and makes no commit; neither ever pushes or prints a push command
- RULE-11: Outside a git repository the files are still written, and `--commit` says there is no git repository to commit them to
- RULE-12: `--audit` writes one `audit.rules` entry for each rule the AI audit read, carrying the rule, proof and test hashes it read, its `verdict`, its `findings`, the `model` that answered, the sha256 of the `criteria` it was sent, `at` and `commit`, and leaves every other rule's entry as it was; it writes `audit.mutation` when mutation testing ran, and null into a file that had no `audit` yet when it did not
- RULE-13: Neither the evidence nor the table is gitignored: `templates/gitignore.purlin` names neither `.purlin/evidence` nor `.purlin/tests.md` as a pattern, and neither does this repository's own `.gitignore`
- RULE-14: An audit entry that repeats the one already there, with the same hashes, `verdict`, `findings`, `model` and `criteria`, is left as it was, `at` and `commit` included; an entry that differs in any of them, the model that answered included, replaces it
- RULE-15: A rule with no proof is answered by the tests marked with its own id: each is listed in `proofs` with that id as both its `id` and its `rule`, and the rule reads `passed` when every one passed, `failed` when one failed, and `no test` when none is marked

## Proof

- PROOF-1 (RULE-1): In a git checkout whose git email is `dev@example.com`, with one spec, `feat` at `specs/a/feat.md`, and one marked test that passes, a `--all --test` run writes `.purlin/evidence/local/feat.json` carrying `schema` `purlin-evidence/1`, `feature` `feat`, `source` `local` and `spec` `specs/a/feat.md`, and exactly one section, keyed by the operating system the run is on and by no other; that section carries exactly `commit`, `dirty`, `at`, `runner`, `fingerprint`, `rules` and `proofs`, its `commit` is the 40-character sha of HEAD, its `at` reads as `YYYY-MM-DDTHH:MM:SSZ`, its `runner` reads `dev`, its `fingerprint` is the one Purlin takes over that project as it stands, and its `rules` read `RULE-1` `passed`
- PROOF-2 (RULE-2): A rule whose one proof passed reads `passed`. A rule with one proof that passed and one that failed reads `failed`. A rule with one proof that passed and one tagged `@env` for another operating system reads `not run`. A rule whose one proof no test observed reads `no test`, and so does a rule with no proof and nothing observed. A rule whose one proof is `@manual`, which no test observed, reads `passed`
- PROOF-3 (RULE-3): A spec's `RULE-1` has `PROOF-1`, which the tests `tests/a.py::test_a` and `tests/b.py::test_b` both observed passing, and `PROOF-3`, tagged `@env` for another operating system; its `RULE-2` has `PROOF-2`, which no test observed. The section written for the run lists `PROOF-1` twice, reading `pass` with `tests/a.py::test_a` and `pass` with `tests/b.py::test_b`, lists `PROOF-2` once, reading `missing` with an empty `test`, and lists `PROOF-3` once, reading `not run` with the other operating system as its `env`; every entry carries exactly `id`, `rule`, `result`, `env`, `manual` and `test`
- PROOF-4 (RULE-4): An evidence file holds a `windows` section and an `audit` object with an entry for `RULE-1`, and a `linux` section is written into it; the `windows` section and the `audit` object read back exactly as they were, and the `linux` section reads as written. A second `linux` section, which saw the test fail, then replaces the first: the `linux` section reads the failure, and the `windows` section still reads exactly as it was
- PROOF-5 (RULE-5): An evidence file's `windows` section and its `audit.rules` both hold `RULE-1` and `RULE-9`, and a `linux` section is written for a spec that now carries only `RULE-1`; the `rules` of the `windows` section, the `rules` of the new `linux` section and `audit.rules` each hold `RULE-1` and nothing else
- PROOF-6 (RULE-6): A project whose only spec is `feat` also holds evidence for a feature `gone`, at `.purlin/evidence/local/gone.json` and `.purlin/evidence/ci/gone.json`, and a `--all --test` run is made; both `gone` files are deleted, `.purlin/evidence/local/feat.json` is written, and the output holds `Removed .purlin/evidence/local/gone.json: no spec defines gone.` and `Removed .purlin/evidence/ci/gone.json: no spec defines gone.`
- PROOF-7 (RULE-7): In a git checkout, a `--all --test` run is made twice with nothing changed between the two; `.purlin/evidence/local/feat.json` after the second run is byte for byte the file the first run wrote. A section that saw the same results over the same fingerprint, and differs only in its `at` (`2030-01-01T00:00:00Z`), its `commit` and its `dirty`, is then written into it; the file is still byte for byte the same
- PROOF-8 (RULE-8): The evidence holds, for the feature `one`, a `ci` file whose `linux` section, made at `2026-09-03T00:00:00Z` on a commit starting `ccccccc`, reads `passed`, `failed` and `not run` for its three rules, beside an older `local` `macos` section made at `2026-09-01T00:00:00Z` reading one rule `passed`; for the feature `two`, a `local` `macos` section made at `2026-09-02T00:00:00Z` on a commit starting `bbbbbbb` reads `passed` for its one rule. The table rendered from them opens `# Tests at ccccccc`, its header row reads `| Feature | Rules | Passed | Failing | No test | Last run |`, the row for `one` reads `| one | 3 | 1 | 1 | 1 | ccccccc · 2026-09-03T00:00:00Z · linux · ci |`, taken from the newer `ci` section with the rule that did not run counted under `No test`, and the row for `two` reads `| two | 1 | 1 | 0 | 0 | bbbbbbb · 2026-09-02T00:00:00Z · macos · local |`. In a project with the features `one` and `two`, a `--feature one --test` run and then a `--feature two --test` run leave the row for `one` exactly as the first run wrote it, and the table then holds a row for `two`
- PROOF-9 (RULE-9): In a git checkout with one spec, `feat`, a `--all --test` run prints `Evidence written to .purlin/evidence/local/feat.json.`, HEAD is still the commit it was before the run, and git status lists a file under `.purlin/evidence/` as not committed. With two specs, `one` and `two`, the same run prints `Evidence written to .purlin/evidence/local/ for 2 features.`
- PROOF-10 (RULE-10): In a git checkout whose git email is `dev@example.com`, a `--all --test --commit` run prints `Evidence committed.` and no line holding `git push`; the newest commit's subject reads `purlin: evidence at <sha7>`, naming the commit the run started on, its author email is `dev@example.com`, and it changes exactly `.purlin/evidence/local/feat.json` and `.purlin/tests.md`. The same run made again prints `Evidence unchanged.`, and the checkout still holds 2 commits
- PROOF-11 (RULE-11): In a folder that is not a git repository, holding one spec and its passing test, a `--all --test --commit` run still writes `.purlin/evidence/local/feat.json` and `.purlin/tests.md`, and its output holds `there is no git repository to commit it to`
- PROOF-12 (RULE-12): An evidence file's `audit.rules` holds a `weak` entry for `RULE-2`, and an audit that read `RULE-1` and ran mutation testing with the engine `mutmut` and a score of `71` is written into it; `audit.rules` holds the new `RULE-1` entry and the `RULE-2` entry exactly as it was, and `audit.mutation` reads the engine `mutmut` and the score `71`. An audit written next, with no entries and mutation testing not run, handed a score of `5`, leaves `audit.mutation` reading `71`. An audit with mutation testing not run, written into a file that had no `audit`, writes `audit.mutation` as null. At the gate `strong`, with the AI audit answered by a model named `claude-fake-1` that settles the rule, a `--all --audit` run over a spec whose `RULE-1` is `[level: strong]` prints `Evidence written to .purlin/evidence/local/feat.json.` and writes `audit.rules.RULE-1` carrying the rule, proof and test hashes Purlin's status gives that rule, the `verdict` `strong`, empty `findings`, the `model` `claude-fake-1`, as `criteria` the sha256 of the text of `references/review_criteria.md`, an `at` reading as `YYYY-MM-DDTHH:MM:SSZ` and the 40-character sha of HEAD as `commit`; the rule's strong cell names `.purlin/evidence/local/feat.json` as its evidence
- PROOF-13 (RULE-13): The ignore lines `purlin:init` gives a new project, and this repository's own `.gitignore`, hold no line, other than a comment, that names `.purlin/evidence` or `tests.md`
- PROOF-14 (RULE-14): An audit entry for `RULE-1` with the verdict `strong`, answered by `claude-a`, is written at the time `x`; the same entry, answered by the same model and written again at the time `later`, leaves the file reading `at` `x`. The same entry answered by `claude-b` at `later` replaces it: the file reads the `model` `claude-b` and the `at` `later`
- PROOF-15 (RULE-15): A spec has three rules and no proof, and the run saw a passing test marked with `RULE-1`, `tests/a.py::test_a`, a failing test marked with `RULE-2`, `tests/b.py::test_b`, and none marked with `RULE-3`; the section's `rules` read `RULE-1` `passed`, `RULE-2` `failed` and `RULE-3` `no test`, and its `proofs` list exactly two entries, one whose `id` and `rule` both read `RULE-1`, reading `pass` with the test `tests/a.py::test_a`, and one whose `id` and `rule` both read `RULE-2`, reading `fail` with the test `tests/b.py::test_b`
