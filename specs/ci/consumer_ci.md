# Feature: consumer_ci

> Requires: verify_gate
> Scope: dev/fixtures/consumer-ci, dev/consumer_ci_dryrun.sh, dev/test_consumer_ci.py
> Stack: python/stdlib (json, subprocess), bash, GitHub Actions, `gh`
> Description: The committed consumer-CI fixture and the dry run that drives it. Purlin's remote
>   verification loop is documented in `references/remote_verification.md` and proved inside this
>   repository, which is the one project that is also the plugin. `dev/fixtures/consumer-ci/` is
>   the other case: a complete minimal consumer project, built through `scripts/init/scaffold.py`
>   and completed by hand, that clones the tooling instead of containing it.
>   `dev/consumer_ci_dryrun.sh` pushes that fixture to a scratch GitHub repository, dispatches both
>   workflows, and asserts what came back. Two of the three rules are deterministic unit tests, so
>   the fixture cannot drift from the reference templates without a red test; only the live run,
>   which creates and deletes a real repository under a real account, is manual.

## Rules

- RULE-1: The fixture's `.github/workflows/purlin-ubuntu-24-proofs.yml` equals the runner-workflow template in `references/remote_verification.md` ("Workflow template") after four literal substitutions, and its `.github/workflows/verify-gate.yml` equals this repository's own `.github/workflows/verify-gate.yml` after the consumer adaptation that same reference states. The substitutions are `<platform-id>` to `ubuntu-24`, `<runs-on>` to `ubuntu-24.04`, `--branch v<VERSION>` to `--branch two-gauges-remote-verification`, and `<test files>` to `tests/test_greeting.py`. The consumer adaptation is four operations and no others: the template's `Locate Purlin tooling` step is inserted verbatim after `actions/checkout` and the job gains no `env` block at all (that step publishes `PURLIN_PLUGIN_ROOT` through `$GITHUB_ENV`, and `PURLIN_PLATFORM` is not carried because the gate writes no proof file), the template's `Install Purlin tooling` step is inserted verbatim after `actions/setup-python`, the gate is invoked as `python3 "$PURLIN_PLUGIN_ROOT/scripts/ci/verify_gate.py" --check --project-root .` under `shell: bash`, and the repo-only `Run the verify_gate proofs` step is dropped because `dev/test_verify_gate.py` is not in a consumer checkout. The tooling pin is temporary: `two-gauges-remote-verification` is a branch, not a release, because `main` has not been pushed and no tag exists yet. It becomes `--branch v<VERSION>` with `<VERSION>` read from this repository's `VERSION` file when `main` is pushed and the release is cut, and RULE-1 is the record of that exception rather than a silent pin in a fixture nobody reads
- RULE-2: The fixture is a complete minimal consumer project and every file of it is tracked, so a clone of this repository carries a project that runs. It holds exactly nine files: `.purlin/config.json`, `.purlin/plugins/pytest_purlin.py`, `conftest.py` and `.gitignore` written by `scripts/init/scaffold.py` with `--test-framework pytest`; `specs/core/greeting.md`, `greeting.py` and `tests/test_greeting.py` added by hand; and the two workflows of RULE-1. `.purlin/plugins/pytest_purlin.py` is a byte-identical copy of `scripts/proof/pytest_purlin.py`, which is what the workflow's `migrate.py --check` preflight checks. `.purlin/config.json` registers `ubuntu-24` as `os: linux`, `distro: ubuntu`, `version: "24.04"`, `arch: x86_64` with a `github` runner on `ubuntu-24.04` running the `purlin-ubuntu-24-proofs` workflow, and declares `remote_verification: "optional"` so the gate reports its findings and exits `0`. The spec declares one agnostic `@unit` proof and one `@unit @on(ubuntu-24)` proof over two rules, so Purlin reads the project as one feature with exactly one proof awaiting the `ubuntu-24` runner until that runner commits its scoped file back. No generated state is committed with it: `.purlin/runtime/`, `.purlin/cache/` and the `purlin-report.html` symlink are what the fixture's own `.gitignore` excludes, and a fixture that shipped them would ship a claim about a run that did not happen here
- RULE-3: `dev/consumer_ci_dryrun.sh` is the live dry run of the loop end to end, and it is the only thing about this feature that is not deterministic. It copies the fixture to a temporary directory, `git init`s and commits it, creates `<user>/purlin-consumer-ci-scratch` private with `gh repo create --source . --push`, then waits for GitHub to register the pushed workflows before dispatching anything: it polls `gh workflow list --repo <repo> --json name,state` every 5 seconds for up to 180 seconds until both `purlin-ubuntu-24-proofs` and `verify-gate` are listed `active`, and prints that listing and exits `1` on timeout, because `gh repo create --push` returns before GitHub has indexed the files and a dispatch inside that window fails with `HTTP 404: workflow not found on the default branch`. The `--push` fires both workflows on `push` as well, so the script waits for those push runs to finish first (two live runs of the commit-back workflow would race for one branch), then dispatches both workflows with `gh workflow run ... --ref main`, and watches by id the runs `gh run list --workflow <file> --event workflow_dispatch` returns, so every run it asserts on is one it named rather than whichever was latest. It waits with `gh run watch <id> --exit-status`, pulls with `git pull --ff-only`, and then asserts four things about what came back: the commit-back carries both the `Purlin-Runner:` and `Purlin-Platform:` trailers readable through `git log -1 --format='%(trailers:key=Purlin-Runner,valueonly)'`, the scoped proof file `specs/core/greeting.proofs-unit@ubuntu-24.json` exists with `"platform": "ubuntu-24"`, `verify_gate.py --check` exits `0` in the scratch checkout, and the scratch repository is deleted with `gh repo delete --yes` unless `--keep` was given. `--dry-run` prints every command and executes no `gh` call at all, so the driver can be read and checked without touching an account. Creating and deleting a repository under a real account is a human-initiated, money-adjacent action against a repository that does not persist, so the proof of this rule is a dated `@manual` stamp and never an `@on(github-actions)` proof: a scoped proof file written inside the scratch repository belongs to that repository and never travels here, so such a proof would read `AWAITING RUNNER` forever, which is the opposite of honest
