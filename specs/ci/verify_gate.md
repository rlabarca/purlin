# Feature: verify_gate

> Requires: security_no_dangerous_patterns
> Scope: scripts/ci/verify_gate.py, .github/workflows/verify-gate.yml, .github/workflows/*-proofs.yml
> Stack: python/stdlib (argparse, json), GitHub Actions
> Description: Purlin's CI side of remote verification. `scripts/ci/verify_gate.py --check` is a
>   deterministic gate that reads the structured status payload and decides whether the branch may
>   merge; the runner workflows prove platform-declared proofs and commit their scoped proof
>   files back with recorded provenance. The gate reads the project's declared `remote_verification` mode, but the
>   mode is a declaration the agent can edit, not the enforcement: enforcement is branch protection
>   marking this job a required check. The same gate carries an opt-in second verdict: a project that
>   declares `quality_gate: "deterministic"` has its proofs graded by the two model-free passes on
>   every run, and a HOLLOW proof or an UNPROVABLE description fails the branch.

## Rules

- RULE-1: `verify_gate.py --check` reads its input from the structured payload `_build_report_data` produces, never from the rendered Unicode summary table. The table's glyphs and column order are presentation and change with the dashboard; a gate that parses them is coupled to a layout and breaks silently when the layout moves
- RULE-2: Exit codes are `0` when the gate passes, `1` when it fails, and `2` for a bad invocation (unreadable project, unknown mode, missing payload), matching `dev/bump_version.sh`. A gate must fail closed: an error reading the payload exits non-zero, never `0`. The `verify-gate.yml` workflow that runs it triggers on pushes and pull requests touching `specs/**`, `.purlin/config.json`, the gate script, the server and `.github/workflows/**`, so a change to any runner workflow re-runs the gate that reads what that workflow commits
- RULE-3: The gate's verdict is keyed off the project's `remote_verification` mode. Under `"required"` an unverified feature or a feature awaiting a runner fails the gate. Under `"optional"` the same findings are reported and the gate exits `0`. Under `"off"` the gate exits `0` and reports only that it is disabled, so a project that has not opted in is never blocked by a job it did not ask for
- RULE-4: Under `"required"`, a feature with proofs declared `@on(<platform>)` that have no result satisfying that platform fails the gate, even when it is VERIFIED, naming the proof id and the platform. The gate reads the payload's live `awaiting_runner` triples rather than the receipt's, because the receipt records what was true when it was issued and the gate is deciding about now; the receipt's own `awaiting_runner` (`skill_verify` RULE-9) is the record of the same gap, not the gate's input. A VERIFIED feature awaiting a runner is a verified-here claim, not a verified-everywhere one, and `"required"` is the declaration that verified-everywhere is the bar. Locally this state warns and never blocks (`sync_status` RULE-47): the gate is where it becomes fatal, because the gate is the only layer that runs on every platform
- RULE-5: The gate never writes. It reads the payload, prints a verdict, and exits: no file is created or modified, no commit is made, no proof or receipt is touched. It is the CI counterpart of `purlin:verify`'s read-only contract, and the same reason applies: a gate that can edit the evidence it grades is not a gate
- RULE-6: The `remote_verification` mode the gate reports is named as a declaration and not as the enforcement, in the gate's own output and in its source header. Enforcement is branch protection marking the job a required check, which lives outside the repository where the agent cannot reach it (`docs/regulated-environments.md`, "Policy lives outside the repo")
- RULE-7: Every workflow that commits a proof file back to the branch stamps the commit with both a `Purlin-Runner: <runner-identity>` trailer and a `Purlin-Platform: <platform-id>` trailer, in a single `-m` argument. Git builds one paragraph per `-m` and parses trailers out of the last paragraph only, so a trailer given its own `-m` reads correctly in `git log` and is invisible to `git log --format=%(trailers:key=...)`, which is what the report actually asks: the commit is the only place the identity of the proving runner is recorded and the platform trailer is what lets sync_status cross-check the platform the filename claims against the one the runner was told (`sync_status` RULE-48). Proof entries carry no such field, by design. A commit-back with no runner trailer reports as `runner not recorded`, which is a gap, not a valid state; a platform trailer that disagrees with the filename reports as `trailer says <id>`
- RULE-8: Every workflow that commits a proof file back to the branch carries a loop guard, so its own commit cannot retrigger it: a `paths-ignore` entry for the proof files it writes, and `[skip ci]` in the commit subject. Both, because either alone fails on a different trigger path
- RULE-9: The gate exits `2` in every mode, with each error printed, when the payload's `platforms.errors` is non-empty: a malformed registry entry was dropped, so a proof naming it may be matching every host of its family or nothing at all, and evidence read through a broken registry is unreadable evidence, the same case as a missing payload. In every mode the gate also prints a `By platform` section from `platforms.summary`, one line per declared id with its proved, awaiting and failing proof counts, so the job log records what each platform proved and not only what blocked
- RULE-10: Every workflow that commits a proof file back to the branch pushes it through a pull-rebase-retry loop rather than a single `git push`: three attempts of `git pull --rebase origin "$GITHUB_REF_NAME"` followed by `git push origin "HEAD:$GITHUB_REF_NAME"`, exiting `1` after the third. Several platform runners may commit to one branch at once, so a plain push fails a race it did nothing wrong to lose and the job goes red over scheduling rather than over a proof; the bound keeps a genuinely broken push a failure. The loop and the two provenance trailers of RULE-7 are what make a multi-platform commit-back survivable, so they are required together
- RULE-11: Every workflow that commits a proof file back to the branch runs `scripts/update/migrate.py --check` as a step before the step that runs the proofs (the step whose `name` begins with `Run`). A runner checks out `.purlin/plugins/` as committed; copies that predate platform scoping write agnostic proof files from a platform runner, which satisfy no declared platform, so the job goes green and proves nothing. The preflight is the only place that gap is visible, because the runner is the machine nobody watches, and it fails the job naming `purlin:init --update` instead of committing evidence that counts toward nothing. The check's exit code is `1` only for the migrations that make the run's evidence unreliable (every `legacy-*` id and `plugin-copies-stale`): a missing config field and a version 1 receipt are reported and do not fail the job, or the preflight would block the CI of every project that has not verified since the vhash formula changed
- RULE-12: The By-platform section of `--check` marks an environment: a row whose `platform_kind` is `environment` (`report_data` RULE-42) prints `<id> (environment): <n> proved, <n> awaiting, <n> failing (<n> features)` and every other row prints that same line with no mark after the id. The word is read from the payload and never recomputed from the registry here, so the gate cannot disagree with the report that sent the reader to it. The gate's output is read by someone looking at a branch that will not merge and deciding who has to act; an environment row that reads exactly like an OS row sends them to wait for a runner that nothing dispatches, when what the id needs is a person running the suite with `PURLIN_PLATFORM` set
- RULE-13: Under `"required"` with no proof in the project declaring a platform (the payload's `platform_testing` is false), the gate prints `verify-gate: no proof declares a platform, so nothing in .purlin/config.json's "platforms" registry is being verified: 'required' is a verified-here bar only.` and leaves the verdict to RULE-3 and RULE-4: a clean tree still exits `0`, an unverified feature still exits `1`, and neither becomes a `2`. This is not the unreadable registry of RULE-9. There the gate cannot tell what a proof naming a dropped entry matched; here it knows exactly what the evidence means, which is that nothing is platform-scoped, and an empty `platforms` object is a configuration `references/remote_verification.md` blesses ("Family ids need no configuration"), so emptiness cannot itself be the error. Exiting `2` would redden a build no proof failed, and the repair would be to declare the weaker `optional` mode to get the gate back, which is the wrong direction for a project that has asked for the strictest one. The named line is what stops the real failure: a PASS under `"required"` with no `By platform` section, which reads as platform coverage checked when nothing was ever declared. The line is printed under `"required"` only, because it is about what that declaration claims
- RULE-14: The gate reads the project's declared quality gate from the payload's `quality_gate` field (`report_data` RULE-46), defaulting to `off` when the payload omits it, and the field is a closed set of two values, `off` and `deterministic`. A value outside the set exits `2` in every `remote_verification` mode, naming the value and both valid modes, for RULE-9's reason and RULE-3's: a typo must not disable a declaration invisibly, and a gate that cannot tell what bar it was asked to hold has not read the evidence. The declared mode is printed as `verify-gate: quality_gate = <mode>` on its own line after the remote-mode line, under `off` as well, so a job log distinguishes a project that declined the quality gate from a build old enough to predate it. Under `off`, and under a config with no such field, that one line is the entire difference from the output this gate produced before the field existed: no checker module is imported and nothing is graded. The field is optional on purpose, so a project that never opted in pays neither the sweep's cost nor a new line of noise in a section it did not ask for
- RULE-15: Under `deterministic` the gate calls `deterministic_sweep` from `scripts/audit/static_checks.py` once over the project root, after the remote findings and before the verdict, and prints a section headed `Quality gate (deterministic): <h> HOLLOW, <u> UNPROVABLE, <m> unmeasurable` with one indented line per finding: `<feature>: <proof id> HOLLOW (<check>) <test file>::<test name>`, `<feature>: <proof id> UNPROVABLE (<check>)`, and `<feature>: <proof id> unmeasurable (<reason>)` naming the extension no checker reads, the file that is not on disk or the marker that was not found. The gate fails, exit `1`, when the sweep reports any HOLLOW proof or any UNPROVABLE description, and never on an unmeasurable one, which the section says in a line of its own: an unmeasurable proof is a gap in coverage, not a defect, and failing a branch over a language the framework ships no checker for would make the gate unusable for exactly the projects that extended it. The remote verdict and the quality verdict are independent: either failing exits `1`, both FAIL lines are printed when both hold rather than the first one short-circuiting the second, and the PASS and FAIL lines RULE-3 and RULE-4 specify are unchanged byte for byte when only the remote gate applies. Both passes are recomputed from source on every run and no cache is read, so the grade a job prints is a grade of the checkout in front of it and editing a test changes the next run's verdict. A checker module that cannot be imported, or a sweep that raises, exits `2` naming `scripts/audit/static_checks.py`, never `0` and never `1`: a gate that cannot run the check it declares has not read the evidence, and reporting that as a clean sweep is the one failure this mode must not have
- RULE-16: The `quality_gate` mode the gate reports is named as a declaration and not as the enforcement, in the gate's own output under `deterministic` and in its source header, the same split RULE-6 states for `remote_verification` and for the same reason: the field is a file in the repository the agent can edit. The header carries the literal `` `quality_gate` field DECLARES ``, and neither the output nor the header says the field enforces anything. `references/hard_gates.md` still carries exactly one `## Gate N` heading (`purlin_references` RULE-6 owns that count): this mode is project policy layered on the framework's single gate, in the same relation to it as `remote_verification`, and a second framework gate is what the count exists to catch
- RULE-17: RULE-5 holds under `deterministic` unchanged. The sweep opens nothing for writing, so a `deterministic` run creates no `.purlin/cache/` directory, writes no audit cache, and leaves the project byte-identical: same files, same sizes, same `git status --porcelain`, same HEAD. The quality gate reads more of the project than the remote gate does, the test sources themselves, which is exactly why the read-only contract has to be restated for it: a gate that could write a cache into the tree it grades would be committing evidence about its own verdict
