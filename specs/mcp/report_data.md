# Feature: report_data

> Scope: scripts/mcp/purlin_server.py
> Stack: python/stdlib, json
> Description: When `"report": true` is set in `.purlin/config.json`, `sync_status` writes a JS data file (`.purlin/report-data.js`) containing structured coverage, rule, and verification data for the HTML dashboard.

## Rules

- RULE-1: When config has `"report": true`, sync_status writes `.purlin/report-data.js`
- RULE-2: When config lacks `"report"` or it is false, no report file is written
- RULE-3: Report file contains `const PURLIN_DATA = {...};` that parses as valid JavaScript
- RULE-4: PURLIN_DATA.summary counts match the feature list (verified + passing + partial + failing + untested == total_features). Beside those five it carries `verified_here`, the number of features that would read VERIFIED with no platform in the picture, and `held_by_platform`, exactly `verified_here - verified`. The five-count invariant is unchanged and the two new keys sit outside it, because a held feature is already counted once under `passing`: counting it again would break the sum, and leaving the drop unnamed would let a dashboard report a fall in Verified as a regression when it is a platform that has not run yet
- RULE-5: Every feature entry has fields: name, type, is_global, proved, total, deferred, status, vhash, receipt, rules, audit, design, platforms, platform_complete
- RULE-6: Features with all proofs passing (status "PASSING" or "VERIFIED") have a non-null vhash; others have null vhash
- RULE-7: Features with receipt files include commit, timestamp, and stale fields in receipt
- RULE-8: Each rule entry has fields: id, description, label, source, is_deferred, is_assumed, status, proofs (array of proof objects where each proof has id, description, test_file, test_name, tier, platform, status, audit). `platform` is the id of the scoped proof file the entry was read from and null for an agnostic one, and there is one object per executed entry, so a proof proved on two platforms appears twice rather than collapsing into a result a reader cannot attribute. The proofs array contains executed proofs plus planned proofs — spec `PROOF-N` entries from the rule's source `## Proof` section with no executed result — distinguished by status "planned" with empty test_file, test_name, and audit, and tier parsed from the proof description's @tag (default unit); a proof id with an executed result for a rule is never also emitted as planned for that rule. A proof that declares `@on(...)` is never emitted as planned at all: for each platform it declares with no result there the array carries one flat object of status "awaiting" naming that platform, with empty test_file, test_name and audit, because "nobody wrote it" and "it is written and waiting on a runner" are different states, and flattening them into the same array is what lets a consumer walk `proofs` once instead of joining a second list
- RULE-9: Rule status is one of PASS, FAIL, NONE, or DEFERRED
- RULE-10: Rule label is one of own, required, or global
- RULE-11: docs_url is dynamically derived from the Purlin plugin git remote
- RULE-12: Anchor features have type "anchor" and include source_url when `> Source:` is present in spec
- RULE-13: anchors_summary.total matches the count of features with type "anchor"
- RULE-14: sync_status output includes dashboard file URL when purlin-report.html exists at project root
- RULE-15: report-data.js includes an audit_summary object with integrity percentage, assessment counts, last audit timestamp, relative time, and stale boolean; null when no audit cache exists
- RULE-16: Per-feature audit data is populated from the audit cache when entries exist for that feature
- RULE-17: All proved rules count toward the coverage fraction (proved/total) regardless of proof type — grep-based and behavioral proofs are treated equally. Proof quality is assessed by the auditor (STRONG/WEAK/HOLLOW), not the coverage system
- RULE-18: Features with partial behavioral coverage have status "PARTIAL" in report data, not "PASSING", even if all existing proofs pass — PASSING requires every behavioral rule to have a passing proof
- RULE-19: Every feature entry includes a `category` field derived from the spec's parent directory under `specs/` (e.g., `specs/skills/skill_build.md` has category `skills`)
- RULE-20: Coverage invariant — for every feature in report data, status PASSING or VERIFIED implies proved == total (100% coverage fraction). No feature may show PASSING or VERIFIED with proved < total
- RULE-21: Every feature entry includes a `description` field containing the text of the spec's `> Description:` metadata field (with multi-line continuations joined), or null if the field is absent
- RULE-22: Planned proofs do not affect coverage — proved/total counts, vhash, and feature status are computed from executed proofs only; a rule whose only proofs are planned has status NONE
- RULE-23: report-data.js carries a `design_summary` object with the Proof Design percentage and per-level counts, or null when no design cache exists, so the dashboard can render the gauge alongside integrity
- RULE-24: Every entry point that writes `.purlin/report-data.js` populates BOTH gauges. `sync_status` and `generate_digest` (the pre-commit digest path) each read the audit cache and the design cache, so a digest refresh never blanks a gauge the other path had populated
- RULE-25: Per-feature design data is populated from the design cache when entries exist for that feature, computed as PROVABLE / (PROVABLE + LOOSE + UNPROVABLE) with STRUCTURAL excluded from both numerator and denominator
- RULE-26: A feature's `audit` and `design` are always objects, never null, each carrying a `state` of `measured`, `excluded` or `unmeasured`, so no quality cell can render blank. `measured` means a percentage is present. `excluded` means every one of the feature's proofs has been assessed and none is gradeable, so the denominator is legitimately zero: EXCLUDED proofs on the Integrity side, STRUCTURAL descriptions on the Design side. `unmeasured` means the cache holds no entries for that feature, or holds fewer than its population, because a partially assessed feature's answer is not known yet. `excluded` is a strong claim and must not be made from a subset: asserting it off 2 assessments while 18 other executed proofs were never looked at is false
- RULE-27: `audit_summary` and `design_summary` each carry a `coverage` object of `measured`, `total` and `complete`, where `total` is the project-wide population the gauge could measure: executed proofs for Integrity, declared proof descriptions for Design. Each also carries `weighted`, the coverage-weighted figure a surface reports (`sync_status` RULE-46), and `assessed`, the unweighted score it was computed from. A percentage is therefore never readable without its denominator, and the number on the card cannot claim more than was measured
- RULE-28: Each per-feature gauge carries its own `coverage` object of `measured`, `total` and `complete` over that feature's population, mirroring the project summaries. Without it a row can neither justify its state nor say how much of the feature was looked at, which is what allowed a false `excluded`
- RULE-29: Each feature carries an `awaiting_runner` list of `{id, tier, platform}` for every proof it declares `@on(<platform>)` with no result satisfying that platform (`sync_status` RULE-47), one entry per proof per unsatisfied platform, and beside it an `undeclared` list of `{id, tier, platform}` for every scoped result that satisfies none of its proof's declared platforms (`sync_status` RULE-53). The feature's `proved`/`total` already exclude the rules the awaiting proofs are the only cover for, so without the first list the payload reports a clean N/N with nothing to explain the exclusion, and without the second a file that was ignored looks like a file that was never produced. Both lists are empty, not absent, when nothing is awaiting or undeclared. Every entry of `awaiting_runner` also appears inside the rule's `proofs` array as a RULE-8 awaiting object, so a surface that renders proofs row by row reports the same gap as one that reads the feature-level list, and the two can no longer disagree
- RULE-30: The payload carries the project's declared `remote_verification` mode as a top-level `remote_verification` string, defaulting to `"off"` when the config omits it. It is a top-level field rather than a per-feature one because the mode is a project declaration, and it is present rather than conditional because `scripts/ci/verify_gate.py` reads its verdict from this payload: a gate that has to distinguish "mode absent" from "payload from an older build" cannot fail closed on the difference
- RULE-31: The payload carries a top-level `platforms` object of `registry` (the resolved registry of `sync_status` RULE-50 keyed by id, `_id` stripped), `host` (the RULE-51 host record), `local` and `remote` (the declared ids this host does and does not satisfy), `errors` (the registry entries dropped, verbatim), `host_id` (the one id this host reports itself as: `PURLIN_PLATFORM` when set, else a registry id the host satisfies preferring a project-registered id over its family, else the literal `unregistered`) and `summary` (the RULE-36 rows), plus a top-level `platform_testing` boolean that is true when any proof declares a platform. Every key is present, `{}` or `[]` when nothing is declared, for RULE-30's reason: `scripts/ci/verify_gate.py` exits 2 on a non-empty `errors`, and a gate that has to distinguish "no registry" from "payload from an older build" cannot fail closed on the difference
- RULE-32: Each feature carries a `platforms` object keyed by every platform id one of its proofs declares, `{}` when none does, each record holding `declared` (proofs declaring that id), `proved`, `failed` and `awaiting` (proof id lists), a `status` from the closed vocabulary `FAILING` (a proof failed there), `AWAITING` (a declared proof has no result there), `PASSING` (every declared proof passed there) or `VERIFIED` (every declared proof passed there and the feature holds a current receipt), a `receipted` boolean that is what separates the last two, and `provenance` (`{commit, when, runner, trailer_platform}` from the scoped file's last commit, `sync_status` RULE-48, or null when it has none). The vocabulary has four words and no PARTIAL, because a platform with some proofs proved and the rest awaiting is still waiting on a runner and waiting warns rather than demotes; `receipted` is carried rather than inferred so a reader can tell "proved here" from "claimed here" without re-reading the receipt. Each proof object under a rule additionally carries `platforms` (its declared ids) and `results` (its per-platform statuses) when the proof declares `@on`; an agnostic proof object carries neither key, so a consumer can tell "declared nowhere" from "declared and unproved"
- RULE-33: A feature with a receipt carries, beside `commit`, `timestamp` and `stale`, a `vhash_version` (the receipt's own, defaulting to `1` for a receipt written before the key existed), a `test_run_commit` (the commit of the run the receipt cites in `evidence.test_run`, or `null` when the receipt cites no run) and a `platform_stale` list naming every platform whose scoped proof file has been committed again since the commit the receipt recorded for it in `evidence.proof_files`. Without these three a stale receipt in the dashboard reads the same whether it went stale because the hash format changed, because the evidence was never tied to a run, or because a runner re-proved a platform after the receipt was written, and those need different answers. All three keys are present whenever `receipt` is, `platform_stale` empty rather than absent

- RULE-34: The payload carries a top-level `migrations` list, always present and empty when the project is current, holding one `{id, count, summary, files}` object per pending migration in the same order sync_status prints them. Present rather than conditional for the reason RULE-30 and RULE-31 give: the dashboard and the CI preflight both read it, and a key that is sometimes absent cannot be told from a payload an older plugin wrote, which is the exact state the list exists to report
- RULE-35: Each feature carries `platform_complete`, true when every platform its proofs declare has a result there and true for a feature that declares none, and its `status` is VERIFIED only when `platform_complete` is true. A feature proved here and holding a current receipt while one declared platform has never run reads PASSING, never PARTIAL and never FAILING: an awaiting platform warns and never blocks (`sync_status` RULE-47), so it may not demote the feature, and it may not let the feature claim it was verified everywhere it says it runs. The receipt is still issued platform-partial, so `platform_complete` false with a current receipt is a state the payload must be able to express rather than one it resolves by withholding the receipt
- RULE-36: `platforms.summary` carries one row per platform some proof declares and no row for any other registry id, each row holding `features` (features with a record for that id), the four record-word counts `verified`, `passing`, `failing` and `awaiting`, `proofs` (`{declared, proved, failed, awaiting}` summed over those records), `integrity`, `last_proved` (the newest provenance timestamp among them, or null) and `last_runner` (the `Purlin-Runner:` trailer of that same commit, or null), the two read together so a surface can say when a platform was proved and by what without a second git read. `integrity` carries `weighted`, `assessed`, `strong`, `weak`, `hollow`, `manual`, `behavioral_total` and `coverage` over that platform's own population, which is every executed proof entry scoped to it plus every agnostic entry when it is `host_id`, weighted by measurement coverage exactly as RULE-27 weights the project figure. A row for a platform nothing names would be a column of zeroes asserting a gap that does not exist, and a per-platform figure computed over the whole project would report the same number for every platform
- RULE-37: `platform_testing`, `platforms` with all seven of its keys, `summary.verified_here`, `summary.held_by_platform`, and every feature's `platforms` and `platform_complete` are present in every payload, including one from a project where no proof declares a platform, where `platforms.summary` is `{}`, each feature's `platforms` is `{}` and `platform_complete` is true. Present rather than conditional for the reason RULE-30 and RULE-31 give: `scripts/ci/verify_gate.py` and the dashboard both branch on these keys, and a key that is sometimes absent cannot be told from a payload an older plugin wrote
- RULE-38: Every feature in the payload carries `evidence_stale`, a boolean, true only when the feature is VERIFIED and the commits touching its `> Scope:` since the run behind its receipt are more than zero (`sync_status` RULE-60). Present on every feature rather than only on the stale ones, for the reason RULE-30, RULE-31 and RULE-37 give: a consumer that branches on the key cannot tell an absent key from a payload an older plugin wrote. It is advisory and changes nothing else in the payload: `status` stays VERIFIED, the summary counts are untouched, and no gate reads it
