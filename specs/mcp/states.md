# Feature: states

> Description: The spec status and the three evidence levels of a rule, the
>   flags beside them, the rollups over them, the structured payload every
>   surface reads, and the status table a person reads. One reader assembles
>   specs, runtime proofs, records, briefs and signatures into the cells of
>   every rule; the table, the dashboard, the gate check and the drift report
>   all render that one payload rather than parsing each other's output.
> Scope: scripts/mcp/purlin/states.py, scripts/mcp/purlin/payload.py, scripts/mcp/purlin/status.py
> Stack: python/stdlib, json, hashlib, subprocess (list-only)

## Rules

- RULE-1: A rule that no proof line names has the spec status `drafted` and an empty proof list [risk: high] [origin: eng]
- RULE-2: A rule whose proof text raises a blocking free check has the spec status `drafted`; a rule whose proofs raise none has the spec status `ready` [risk: high] [origin: eng]
- RULE-3: The passed cell reads `passed` when every proof of the rule has a passing test from a source that counts under the gate and that pass describes the current checkout, and it carries the source, whether the pass is current and whether it counts [risk: high] [origin: eng]
- RULE-4: Under the gate `passed` a record counts whether ci, a developer or this checkout wrote it; under `strong` and `signed` only a record labelled `ci` counts [risk: high] [origin: eng]
- RULE-5: A record the gate does not read leaves the passed cell at `not run` with the reason `<source> record does not count under <gate>`, and this checkout's own run leaves it at `not run` with the reason `local run does not count under <gate>`; in both the cell names the source and reads `counts` false [risk: high] [origin: eng]
- RULE-6: A proof carrying `@env` is proved only by a record from that operating system: the passed cell reads `not run`, names the operating system under `missing_env` and gives the reason `<os>: no record yet` rather than taking a word of its own [risk: high] [origin: eng]
- RULE-7: A passing record that describes neither the head commit nor the current scope tree leaves the passed cell at `code changed` with the reason `code changed since <commit7>` and raises the `code_changed` flag: only the code moved, and CI clears it on the next run [risk: high] [origin: eng]
- RULE-8: A rule no test backs reads `no test` with no source, not current and not counting [risk: medium] [origin: eng]
- RULE-9: The passed cell reads `failed` when a counting record observed a failing proof of the rule, reading a `@env` proof only from that operating system's record, or when this checkout's last run failed one; its reasons name where, as `failing: <os> record` or `failing: this checkout`, and the `failing` flag is raised [risk: high] [origin: eng]
- RULE-10: The strong cell exists only at the gate `strong` and above and the signed cell only at `signed`; a cell above the gate is absent from `cells` rather than present and empty [risk: high] [origin: eng]
- RULE-11: A rule whose passed cell is not met has a strong cell reading `weak` with the one reason `not passed`, and the feature's latest test strength beside it [risk: high] [origin: eng]
- RULE-12: A test strength under `min_strength` makes the strong cell read `weak` with the reason `strength <n>% under <m>%`, and every free-check finding on the proof text is named after it [risk: high] [origin: eng]
- RULE-13: Where nothing measured a test strength the strong cell carries the reason `no engine: free checks only` and reads `weak` only when a blocking finding stands against the proof text [risk: medium] [origin: eng]
- RULE-14: A finding the brief raised against a test body makes the strong cell read `weak` and is named among its findings [risk: medium] [origin: eng]
- RULE-15: A rule whose risk is at or above `ai_review_at` needs a brief for its current rule, proof and test hashes that settled and observed nothing; without one the strong cell reads `needs a person` with the reason `no brief for the current hashes`, `review not settled`, or the sentence the model observed, and with no break engine available the threshold drops one level [risk: high] [origin: eng]
- RULE-16: A rule proved by a `@manual` proof reads `needs a person` with the reason `manual proof` [risk: medium] [origin: eng]
- RULE-17: A current hold makes the strong cell read `needs a person` with the reason `held by <email>: <case>` whatever the rule's risk, makes the signed cell read `held`, raises the `held` flag and leaves `needs_person` false; a hold bound to other hashes does nothing [risk: high] [origin: eng]
- RULE-18: A signature for the current hashes clears every reason a person was needed for, the hold included, because what it settles there is a question the machine could not [risk: high] [origin: eng]
- RULE-19: A strong cell that reads `strong` where an engine measured the strength carries no reasons at all [risk: low] [origin: eng]
- RULE-20: The signed cell is computed from the signature files whatever the cells below it read: `signed` with the reason `by <email>`, `unsigned`, `stale` with the reason `hashes changed after the signature`, `held`, or `not required` [risk: high] [origin: eng]
- RULE-21: The signed cell's `required` is true when the rule's risk is at or above `sign_at`; below it the cell reads `not required` and meets its level with no signature at all [risk: high] [origin: eng]
- RULE-22: A signature the gate refuses leaves the signed cell at `unsigned` carrying the reason the check gave, one of `the signing commit is not signed`, `the signer is not on the list`, `the signer last touched the test` and `the signing commit is not on <branch>` [risk: high] [origin: eng]
- RULE-23: A rule's bucket is exactly one of `untested`, `failing`, `passed`, `strong` and `signed`: `untested` while the spec status is `drafted` or no counting run reads as passed, `failing` where one failed, and otherwise the deepest level the rule met up to the gate [risk: high] [origin: eng]
- RULE-24: `meets_gate` is true when the spec status is `ready` and every cell up to the gate is met, and `blocked_by` names the lowest cell that is not, in the order `spec`, `passed`, `strong`, `signed`, and is null when the rule meets the gate [risk: high] [origin: eng]
- RULE-25: A feature's rollup carries `rules`, `met`, one count per bucket the gate reaches, `stale`, `held`, `needs_person`, the test strength and the latest record [risk: medium] [origin: eng]
- RULE-26: The project summary counts each rule once, under the feature that owns it, so a global anchor's rule is counted once however many features have to prove it, and it adds `features` to the rollup's keys [risk: high] [origin: eng]
- RULE-27: The payload carries schema version 5 and the top-level keys `generated_at`, `generated_by`, `project`, `version`, `commit`, `dirty`, `gate`, `summary`, `features`, `review_list`, `records` and `warnings` [risk: high] [origin: eng]
- RULE-28: A feature entry carries its spec path, its category, the paths of the signature files beside its spec, and each of its rules with the risk, the origin and the criterion the spec tagged, and each proof with its tier and its operating system [risk: medium] [origin: eng]
- RULE-29: The review list holds exactly the rules blocked at the strong cell by `needs a person` and the rules blocked at the signed cell, each row naming the feature, the owner, the rule, the risk, the cell and why; a rule blocked at `spec` or `passed` is never on it and the list is empty under the gate `passed` [risk: high] [origin: eng]
- RULE-30: A review row's `why` is drawn from the closed set `unsigned`, `stale`, `held`, `needs a person` and `manual`, and `manual` replaces `needs a person` where a `@manual` proof is the cause [risk: medium] [origin: eng]
- RULE-31: The review list reads risk high first, stale and held before the rest within one risk, then feature and rule number, and names each rule once under the feature that owns it [risk: medium] [origin: eng]
- RULE-32: The dashboard's data file is written as `const PURLIN_DATA = ` followed by the payload and a trailing semicolon, and reads back as the payload that was written [risk: medium] [origin: eng]
- RULE-33: A rebuild whose payload differs from the file on disk only by the stamp on it touches that file instead of rewriting it, so a background refresh never churns the bytes [risk: medium] [origin: eng]
- RULE-34: Every record in the payload's `records` map carries the result of the run it names, `fail` where any proof it observed failed and `pass` otherwise, beside the label read from git [risk: medium] [origin: eng]
- RULE-35: The tests a rule's test hash binds for a proof are the ones its feature's latest counting records observed, on every operating system together, so every checkout and CI read the same hash; this checkout's runtime proofs name them only for a proof no counting record has observed, and a test this checkout ran or could not run changes nothing once a record exists [risk: high] [origin: eng]
- RULE-36: The status table is one row per feature under the columns Feature, Rules, Spec, Tests and Run, with Strength and Strong added at the gate `strong` and Signed added at `signed`, and a feature with no record shows its strength as `n/a` [risk: medium] [origin: eng]
- RULE-37: The status report's summary line reads `<met> of <rules> rules meet the gate <gate>`, and the line under it names a test strength, a risk threshold or a signature count only at the gate that asks for one [risk: medium] [origin: eng]
- RULE-38: The report ends with exactly one `Next:` line, computed from the lowest cell blocking the project rather than from what the caller asked for [risk: medium] [origin: eng]
- RULE-39: A project with no specs under `specs/` says what to run instead of printing an empty table [risk: low] [origin: eng]
- RULE-40: The report carries no emoji: the only characters above U+2000 it prints are the arrow, the two triangles and the horizontal rule the design system allows [risk: medium] [origin: eng]
- RULE-41: A config carrying a key this release no longer reads prints the line `Run: purlin:init --update` above the next step [risk: medium] [origin: eng]
