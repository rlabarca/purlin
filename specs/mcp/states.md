# Feature: states

> Description: The three evidence levels of a rule, the flags beside them,
>   the rollups over them, the structured payload every surface reads, and
>   the status table a person reads. One reader assembles specs, the evidence
>   and the signatures into the cells of every rule; the table, the dashboard,
>   the sign walk and the drift report all render that one payload rather than
>   parsing each other's output.
> Scope: scripts/mcp/purlin/states.py, scripts/mcp/purlin/payload.py, scripts/mcp/purlin/status.py
> Stack: python/stdlib, json, hashlib, subprocess (list-only)

## Rules

- RULE-1: A rule that no proof line names, and whose own id marks no test, has a passed cell reading `no test` with the one reason `no proof written`, an empty proof list and the `no_proof` flag raised
- RULE-3: The passed cell reads `passed` when every proof of the rule has a passing test in an evidence section that is current, whose spec, code and tests fingerprint equals the one taken now, and it carries the source, whether the pass is current and whether it counts
- RULE-4: An evidence file's source is the folder it sits in, `ci` or `local`, and a current section from either counts at every gate, `signed` included, because what a signature locks is the evidence rather than the machine that produced it
- RULE-5: A current section under either source, committed or not, leaves the passed cell reading `passed` with that source named, `counts` true and no reason at all, at every gate; the runtime proof files a run leaves under `.purlin/runtime/` are not read
- RULE-42: An evidence file whose own `source` field disagrees with the folder it sits in is left out of the reading, and one warning naming its path is added to the payload's warnings
- RULE-43: The passed cell carries `platforms`, one entry per operating system a current section covers, each carrying that platform's own word, its source and when it ran; a platform a proof is tagged for that no current section covers is listed with the word `not run` and no source
- RULE-57: A person's own section answers for its own platform at every gate, so a red local section beside a green `ci` one from another operating system reads `partial` wherever the gate is set
- RULE-44: Where the platforms disagree the passed cell reads `partial`, naming the platforms that passed and the word of each that did not; `partial` is not met, its bucket is `partial` and its flag is `partial`
- RULE-45: A section that is out of date decides nothing: where the newest section that speaks for the rule is current, an older out-of-date one beside it is left out of `platforms` and its failures are not read
- RULE-47: The signed cell carries `at` beside `signer`: the date of the commit that added the signature, and the file's own timestamp where git cannot answer; and `signer_name` and `key_fingerprint`, as the signature file records them, each null where the file records none
- RULE-6: A proof carrying `@env` is proved only by a current section from that operating system: the passed cell reads `not run`, names the operating system under `missing_env` and gives the reason `<os>: no run yet` rather than taking a word of its own
- RULE-7: Where the newest section that speaks for the rule is not current the passed cell reads `out of date`, not met and not current, with one reason per part that differs, `spec changed since <sha7>`, `code changed since <sha7>` or `tests changed since <sha7>` where the sha is the section's commit, and raises the `out_of_date` flag; a person's own section, committed or not, goes out of date like any other, and the next run clears it
- RULE-8: A rule no test backs reads `no test` with no source, not current and not counting
- RULE-9: The passed cell reads `failed` when a current section observed a failing proof of the rule, reading a `@env` proof only from that operating system's section; its reasons name where, as `failing: <os>, <source>`, and the `failing` flag is raised
- RULE-11: A rule whose passed cell is not met reads what its passed cell says; at the gate `strong` and above its strong cell reads `waiting` with the one reason `waiting for its tests to pass`, and the feature's test strength beside it; `waiting` is never met and is not `weak`
- RULE-12: Where mutation testing is on, a test strength under `min_strength` makes the strong cell read `weak` with the reason `strength <n>% under <m>%`
- RULE-13: Where the audit found nothing and no strength was measured, because `mutation_engine` is `none` or no engine measured one, the strong cell reads `strong` with the reason `no mutation score measured`, and a strength left in the evidence is not compared while mutation testing is off
- RULE-14: The strong cell reads the audit entry for the rule's current rule, proof and test hashes, its `verdict` and its `findings`, and no other field: a field the format does not name decides nothing, the cell carries the entry's findings under `findings`, an entry reading `weak` makes it read `weak` with each finding among its reasons, and the cell names the evidence file under `evidence`
- RULE-15: At the gate `strong` and above a rule needs an audit entry for its current rule, proof and test hashes; without one the strong cell reads `not audited` with the reason `no audit has run on this code`, or `the AI audit could not run: <why>` where the last audit could not reach the model for those hashes; an entry reading `undecided` reads `weak` with the reason `the AI audit could not decide: <its sentence>`, and the rule's `left` reads `to_strengthen`
- RULE-16: At the gate `strong` and above, a rule with a `@manual` proof that no person has checked by hand reads `manual test` in its strong cell with the reason `manual proof`, and raises the `manual` flag
- RULE-18: A signature that counts and binds the current hashes of a rule with a `@manual` proof is its hand check, with or without a note: `hand_checked` is true, the strong cell reads `strong` with the reason `hand check by <email>`, the signed cell reads `signed`, and the rule's `left` is null
- RULE-19: A strong cell that reads `strong` where an engine measured the strength carries no reasons at all
- RULE-20: The signed cell reads `signed` with the reason `by <email>` where a signature that counts binds the rule's current hashes, and `unsigned` otherwise; a signature that no longer binds them is read as none, so the cell names no signer and gives no reason, and the rule's `left` reads `to_sign`
- RULE-73: At the gate `signed`, where no signature binds a rule's current hashes and its strong cell is not met, the signed cell reads `waiting` with the one reason `waiting for the audit`; a strong cell reading `manual test` leaves it `unsigned` with no reason, because a person checks and signs that rule in one act
- RULE-21: At the gate `signed` every rule needs a signature: one whose tests pass and whose audit found nothing, and that no signature binds, reads `unsigned` in its signed cell, and its `left` reads `to_sign`
- RULE-22: A signature that binds a rule's current hashes and that the signature check does not count leaves the signed cell `unsigned`, carrying the one reason the check gave, such as `the commit that added it is not signed`
- RULE-23: A rule's bucket is exactly one of `untested`, `failing`, `partial`, `passed`, `strong` and `signed`: `untested` while no counting run reads as passed, a rule no proof line names included, `failing` where every platform that ran failed, `partial` where they disagree, and otherwise the deepest cell the rule met up to the gate
- RULE-24: `meets_gate` is true when no cell up to the gate blocks the rule, and `blocked_by` names the lowest one that does, in the order `passed`, `strong`, `signed`, and is null when the rule meets the gate
- RULE-25: A feature's rollup carries `rules`, `met`, one count per bucket the gate reaches, `stale`, `manual`, `not_audited`, `queue`, `hand_checks`, the test strength, `proofs`, `proofs_without_test` and `proofs_without_test_ids`; at the gate `strong` and above it adds `asks_strong`, how many of its rules carry a strong cell, and at `signed` `asks_signed`, how many carry a signed cell, and the summary carries both the same way
- RULE-48: `proofs` counts every proof line the rollup's rules write, once each, and `proofs_without_test` counts those of them that no marker tied to a test declaration names, read from the test files and not from the evidence, so a proof whose marked test has not run yet has a test; `proofs_without_test_ids` names them; a `@manual` proof is left out, because its spec already says no test is written for it
- RULE-26: The project summary counts each rule once, under the feature that owns it, so a global anchor's rule is counted once however many features have to prove it, and it adds `features` to the rollup's keys
- RULE-27: The payload carries schema version 10 and the top-level keys `generated_at`, `generated_by`, `project`, `version`, `commit`, `dirty`, `gate`, `summary`, `features`, `queue`, `left`, `finished`, `last_line`, `os_words`, `evidence`, `tag`, `remote_url` and `warnings`; `remote_url` is the `origin` remote, or null when the project has no remote; `summary` carries `steps` and `sentence`; `left` lists the work left, each entry with `kind`, `count`, `text` and `command`; `finished` is true when `left` is empty, and `last_line` is then the line said in its place, null otherwise; `os_words` gives each system its word and its short word
- RULE-28: A feature entry carries its spec path, its category, the paths of the signature files beside its spec, `current`, true when its newest section is current, and `evidence`, which per source is null or the file's path, whether it is committed as it stands and each section's commit, time and whether it is current, and each of its rules with the audit hash a signature binds, and each proof with whether it is `@manual`, its operating system and no findings key
- RULE-32: The dashboard's data file is written as `const PURLIN_DATA = ` followed by the payload and a trailing semicolon, and reads back as the payload that was written
- RULE-34: Every section in the payload's `evidence` map, keyed by feature, source and operating system, carries the result of the run it names, `fail` where any proof it observed failed and `pass` otherwise, beside its commit, its time, whether it is current and its path
- RULE-35: The tests a rule's test hash binds for a proof are the ones the feature's current sections list, every operating system and both sources together, so every checkout and CI read the same hash; where no section is current every section's list answers, so a code change alone does not move the hash, and a runtime proof file this checkout wrote moves nothing
- RULE-36: The status table is one row per spec under the columns Spec, Rules, Proofs and Tests, where a project at the gate `passed` that writes no proof line is shown neither the Proofs column nor a count of proof lines, with Strong added at the gate `strong` and Signed added at `signed`; `Proofs` reads `<n>` and appends `· <k> no test`, `Tests` reads `<passed> of <rules>` and appends `· <k> partial` and `· <k> failing`, `Strong` reads `<n> of <rules> · <strength>`, and a feature with no audit shows `n/a`, and `Signed` reads `<n> of <rules>`; for a spec with no rules both are empty
- RULE-49: The status table and the dashboard render one spec's row from one module, so a cell reads the same characters wherever it is printed
- RULE-39: A project with no specs under `specs/` says what to run instead of printing an empty table
- RULE-40: The report carries no emoji: the only characters above U+2000 it prints are the arrow, the two triangles and the horizontal rule the design system allows
- RULE-41: A config carrying a key 0.9.5 wrote that this release does not read prints the line `→ Run: purlin:init --update` directly above the summary sentence
- RULE-59: At the gate `signed`, `tag` names the `signed/*` tag pointing at HEAD as `{name, commit}`, and is null where none does, so a surface that shows one commit's standing can say whether that commit is marked; where several point at HEAD the newest version wins, read as numbers where the name is numeric. Below `signed` `tag` is null, even where such a tag points at HEAD, because only a project at `signed` is ever tagged
- RULE-61: Every rule carries `audit`, at every gate: the `verdict`, `findings` and `notes` of the audit entry for its current hashes, the feature's test strength, the `model` that answered or `unknown`, `at`, `commit` and the evidence file under `path`, or null where no entry answers
- RULE-62: A feature spec with no `> Scope:` line, or whose scope reaches no tracked file, carries `incomplete: true` and `incomplete_reason`, `no > Scope: line` or `> Scope: names nothing that exists`, its rollup carries `incomplete: true`, and `summary.incomplete` counts such specs; a spec whose scope reaches a file carries `incomplete: false` and a null reason; an anchor is never incomplete; its rules' passed and strong cells read as any other spec's
- RULE-63: At the gate `signed` only, a rule of an incomplete spec reads `unsigned` in its signed cell with the reason `the spec names no files in > Scope:, so a signature cannot be tied to the code it governs`, whatever signature it has; below `signed` its cells read as they would with its files named
- RULE-64: The status report prints `1 spec names no files, so its tests run every time: <name>.`, or `<n> specs name no files, so their tests run every time: <names>.`, at every gate, and nothing of the kind when every spec names its files
- RULE-65: A rule no proof line names whose test is marked with the rule's own id reads its passed cell from that test, as a proof's test is read: `passed` where it passed in a current section and `failed` where it failed
- RULE-66: Proofs are optional at the gate `passed` and required above it: at `strong` and `signed`, a rule whose passed cell reads `passed` and that has no proof reads `no proof` in its strong cell with the reason `the rule has a test and no proof`, and its `left` reads `no_proof`; at `passed` such a rule has only its passed cell and its `left` is null
- RULE-70: The three sample payloads the dashboard is built and photographed against, one per gate, carry together exactly the key paths the builder writes, at every depth, and no other
- RULE-71: Every proof in a rule's entry carries its own `result`: `hand check` for a `@manual` proof; otherwise, over the current sections from the operating system its `@env` names, or from every system where it names none, `failed` where one failed it and `passed` where one passed it; with no current answer, `not run` where a marker in the test files ties it to a test and `no test` where none does. Each test listed under a proof carries the `result` a current section gave it, `pass` or `fail`, and `not run` where no current section lists it
- RULE-72: The status table's `Rules` cell reads how many rules the spec owns, then ` (+<k> shared)` where it proves rules from an anchor it requires or from a global anchor, `<k>` counting those rules, and reads the owned count alone where it proves none; every cell of the table starts at its column's left edge
- RULE-74: Every rule entry carries `applies_to`, the feature it is listed under; `code_hash`, the code hash of that feature's `> Scope:`; `machines`, `{system: machine}` over the current sections that speak for it, empty where none names a machine; `hand_checked`, true when the rule has a `@manual` proof and a signature that counts binds its current hashes, with or without a note; and `left`, the one kind of work it waits for, or null
- RULE-75: At the gate `passed`, a rule with a `@manual` proof is not counted as passing its tests, and its `left` reads `to_test_by_hand`, until a signature that counts binds its current hashes; then it is counted as passing its tests and its `left` is null
- RULE-76: An anchor's rule is signed once in each feature it applies to: listed under a feature, its signed cell reads `signed` when a signature made for that feature counts and binds it; listed under the anchor itself, it reads `signed` only when every feature it applies to, every feature for a global anchor, has such a signature
