# Feature: states

> Description: The spec status and the three evidence levels of a rule, the
>   flags beside them, the rollups over them, the structured payload every
>   surface reads, and the status table a person reads. One reader assembles
>   specs, runtime proofs, records, briefs and signatures into the cells of
>   every rule; the table, the dashboard, the gate check and the drift report
>   all render that one payload rather than parsing each other's output.
> Scope: scripts/mcp/purlin/states.py, scripts/mcp/purlin/payload.py, scripts/mcp/purlin/status.py
> Stack: python/stdlib, json, hashlib, subprocess (list-only)

## Rules

- RULE-1: A rule that no proof line names has the spec status `drafted` and an empty proof list [bar: strong] [origin: eng]
- RULE-2: A rule whose proof text raises a blocking free check has the spec status `drafted`; a rule whose proofs raise none has the spec status `ready` [bar: strong] [origin: eng]
- RULE-3: The passed cell reads `passed` when every proof of the rule has a passing test from a source that counts under the gate and that pass describes the current checkout, and it carries the source, whether the pass is current and whether it counts [bar: strong] [origin: eng]
- RULE-4: A record's source is the folder it sits in, `ci` or `local`; under the gates `passed` and `strong` both sources count, and under `signed` only `ci` does [bar: strong] [origin: eng]
- RULE-5: A record the gate does not read leaves the passed cell at `not run` with the reason `<source> record does not count under <gate>`, and this checkout's own run leaves it at `not run` with the reason `local run does not count under <gate>`; in both the cell names the source and reads `counts` false [bar: strong] [origin: eng]
- RULE-42: A record whose own `source` field disagrees with the folder it sits in is left out of the reading, and one warning naming its path is added to the payload's warnings [bar: strong] [origin: eng]
- RULE-43: The passed cell carries `platforms`, one entry per operating system a counting run named, each carrying that platform's own word, its source and when it ran; a platform a proof is tagged for that nothing ran on is listed with the word `not run` and no source [bar: strong] [origin: eng]
- RULE-57: A source the gate does not read answers for no platform and names no failure: at the gate `signed` this checkout's own run is left out of `platforms` and out of the failure search, and the cell still reads `not run` with the reason `local run does not count under signed` where that run is all there is [bar: strong] [origin: eng]
- RULE-44: Where the platforms disagree the passed cell reads `partial`, naming the platforms that passed and the word of each that did not; `partial` is not met, its bucket is `partial` and its flag is `partial` [bar: strong] [origin: eng]
- RULE-45: Where no counting run named an operating system the platform map is empty and the records and this checkout's run answer as one, exactly as they did before any platform was named [bar: strong] [origin: eng]
- RULE-46: Where no counting record exists for a rule whose bar is `passed` the strong cell reads `weak` with the reason `no audit has run`, because only an audit measures how good the tests are [bar: strong] [origin: eng]
- RULE-47: The signed cell carries `at` beside `signer`: the date of the commit that added the signature, and the file's own timestamp where git cannot answer [bar: strong] [origin: eng]
- RULE-6: A proof carrying `@env` is proved only by a record from that operating system: the passed cell reads `not run`, names the operating system under `missing_env` and gives the reason `<os>: no record yet` rather than taking a word of its own [bar: strong] [origin: eng]
- RULE-7: A passing record that describes neither the head commit nor the current scope tree leaves the passed cell at `code changed` with the reason `code changed since <commit7>` and raises the `code_changed` flag: only the code moved, and CI clears it on the next run [bar: strong] [origin: eng]
- RULE-8: A rule no test backs reads `no test` with no source, not current and not counting [bar: strong] [origin: eng]
- RULE-9: The passed cell reads `failed` when a counting record observed a failing proof of the rule, reading a `@env` proof only from that operating system's record, or when this checkout's last run failed one; its reasons name where, as `failing: <os> record` or `failing: this checkout`, and the `failing` flag is raised [bar: strong] [origin: eng]
- RULE-10: The strong cell exists only at the gate `strong` and above and the signed cell only at `signed`; a cell above the gate is absent from `cells` rather than present and empty [bar: strong] [origin: eng]
- RULE-11: A rule whose passed cell is not met has a strong cell reading `weak` with the one reason `not passed`, and the feature's latest test strength beside it [bar: strong] [origin: eng]
- RULE-12: A test strength under `min_strength` makes the strong cell read `weak` with the reason `strength <n>% under <m>%`, and every free-check finding on the proof text is named after it [bar: strong] [origin: eng]
- RULE-13: Where nothing measured a test strength the strong cell carries the reason `no engine: free checks only` and reads `weak` only when a blocking finding stands against the proof text [bar: strong] [origin: eng]
- RULE-14: A finding the brief raised against a test body makes the strong cell read `weak` and is named among its findings, and a sentence a settled review observed makes it read `weak` with that sentence among its reasons [bar: strong] [origin: eng]
- RULE-15: A rule whose bar is `strong` needs a brief for its current rule, proof and test hashes that settled; without one the strong cell reads `not audited` with the reason `no audit has run on this code`, and a brief whose model answered and did not settle reads `unsettled` with the reason `the AI audit could not settle`; a brief that reached no model at all settles nothing and leaves the cell to the free checks, and a rule whose bar is `passed` reads neither word [bar: strong] [origin: eng]
- RULE-16: A rule proved by a `@manual` proof reads `manual test` with the reason `manual proof`, and raises the `manual` flag [bar: strong] [origin: eng]
- RULE-17: A current hold makes the strong cell read `held` with the reason `held by <email>: <case>` whatever the rule's bar, makes the signed cell read `held`, raises the `held` flag, leaves the `manual`, `unsettled` and `not_audited` flags false, and keeps the rule from meeting the gate at `strong` and at `signed`; a hold bound to other hashes does nothing [bar: strong] [origin: eng]
- RULE-18: A signature for the current hashes clears every reason a person was needed for, the hold included, because what it settles there is a question the machine could not [bar: strong] [origin: eng]
- RULE-19: A strong cell that reads `strong` where an engine measured the strength carries no reasons at all [bar: passed] [origin: eng]
- RULE-20: The signed cell is computed from the signature files whatever the cells below it read: `signed` with the reason `by <email>`, `unsigned`, `stale` with the reason `hashes changed after the signature`, or `held` [bar: strong] [origin: eng]
- RULE-21: The signed cell's `required` is true at the gate `signed` when `sign_at` is `all` or the rule's bar is `strong`; with `required` false the cell reads `signed` or `unsigned` as the files say and meets its level either way [bar: strong] [origin: eng]
- RULE-22: A signature the gate refuses leaves the signed cell at `unsigned` carrying the reason the check gave, one of `the signing commit is not signed`, `the signer is not on the list`, `the signer last touched the test` and `the signing commit is not on <branch>` [bar: strong] [origin: eng]
- RULE-23: A rule's bucket is exactly one of `untested`, `failing`, `partial`, `passed`, `strong` and `signed`: `untested` while the spec status is `drafted` or no counting run reads as passed, `failing` where every platform that ran failed, `partial` where they disagree, and otherwise the deepest level the rule met up to the gate [bar: strong] [origin: eng]
- RULE-24: `meets_gate` is true when the spec status is `ready` and no cell up to the gate blocks the rule, and `blocked_by` names the lowest one that does, in the order `spec`, `passed`, `strong`, `signed`, and is null when the rule meets the gate [bar: strong] [origin: eng]
- RULE-25: A feature's rollup carries `rules`, `met`, one count per bucket the gate reaches, `stale`, `held`, `manual`, `unsettled`, `not_audited`, `signable`, the test strength, the latest record, `proofs`, `proofs_without_test` and `proofs_without_test_ids` [bar: strong] [origin: eng]
- RULE-48: `proofs` counts every proof line the rollup's rules write, once each, and `proofs_without_test` counts those of them that no test backs, leaving out a `@manual` proof, whose spec already says no test is written for it [bar: strong] [origin: eng]
- RULE-26: The project summary counts each rule once, under the feature that owns it, so a global anchor's rule is counted once however many features have to prove it, and it adds `features` to the rollup's keys [bar: strong] [origin: eng]
- RULE-27: The payload carries schema version 7 and the top-level keys `generated_at`, `generated_by`, `project`, `version`, `commit`, `dirty`, `gate`, `summary`, `features`, `review_list`, `sign_list`, `records`, `remote_url` and `warnings`; `remote_url` is the `origin` remote, or null when the project has no remote [bar: strong] [origin: eng]
- RULE-28: A feature entry carries its spec path, its category, the paths of the signature files beside its spec, and each of its rules with the bar, the origin and the criterion the spec tagged, and each proof with its tier and its operating system [bar: strong] [origin: eng]
- RULE-29: The review list holds exactly the rules whose strong cell reads `manual test`, `unsettled` or `held`, each row naming the feature, the owner, the rule, the bar, the cell, the kind and why; a rule reading `not audited` is never on it and the list is empty under the gate `passed` [bar: strong] [origin: eng]
- RULE-30: A row's `kind` is the cell's own word, drawn from `manual test`, `unsettled` and `held` on the review list and from `unsigned`, `stale` and `held` on the sign list, and `why` carries that one word [bar: strong] [origin: eng]
- RULE-31: Both lists read the rules whose bar is `strong` first, then by feature and rule number, and name each rule once under the feature that owns it [bar: strong] [origin: eng]
- RULE-32: The dashboard's data file is written as `const PURLIN_DATA = ` followed by the payload and a trailing semicolon, and reads back as the payload that was written [bar: strong] [origin: eng]
- RULE-33: A rebuild whose payload differs from the file on disk only by the stamp on it touches that file instead of rewriting it, so a background refresh never churns the bytes [bar: strong] [origin: eng]
- RULE-34: Every record in the payload's `records` map carries the result of the run it names, `fail` where any proof it observed failed and `pass` otherwise, beside the label read from git [bar: strong] [origin: eng]
- RULE-35: The tests a rule's test hash binds for a proof are the ones its feature's latest counting records observed, on every operating system together, so every checkout and CI read the same hash; this checkout's runtime proofs name them only for a proof no counting record has observed, and a test this checkout ran or could not run changes nothing once a record exists [bar: strong] [origin: eng]
- RULE-36: The status table is one row per spec under the columns Spec, Rules, Proofs and Tests, with Strong added at the gate `strong` and Signable and Signed added at `signed`; `Proofs` reads `<n>` and appends `· <k> without a test`, `Tests` reads `<passed> of <rules>` and appends `· <k> partial` and `· <k> failing`, `Strong` reads `<n> of <rules> · <strength>` and a feature with no record shows `n/a`, and `Signable` and `Signed` each read `<n> of <rules>` [bar: strong] [origin: eng]
- RULE-49: The table, the pull request comment and the dashboard render one spec's row from one module, so a cell reads the same characters wherever it is printed [bar: strong] [origin: eng]
- RULE-37: The status report's summary opens `<met> of <rules> rules meet the gate <gate>`, then counts the buckets the gate reaches in the tiles' own words and order, then names a test strength or a signature rule only at the gate that asks for one [bar: strong] [origin: eng]
- RULE-38: The report ends with exactly one `Next:` line, computed from the lowest cell blocking the project rather than from what the caller asked for [bar: strong] [origin: eng]
- RULE-39: A project with no specs under `specs/` says what to run instead of printing an empty table [bar: passed] [origin: eng]
- RULE-40: The report carries no emoji: the only characters above U+2000 it prints are the arrow, the two triangles and the horizontal rule the design system allows [bar: strong] [origin: eng]
- RULE-41: A config carrying a key this release no longer reads prints the line `Run: purlin:init --update` above the next step [bar: strong] [origin: eng]
- RULE-50: A rule's bar is the one its `[bar: ...]` tag names, and the project's gate where it names none: `passed` at the gate `passed` and `strong` at `strong` and at `signed`; the rule entry carries `bar` and `bar_from`, which reads `tag` or `gate` [bar: strong] [origin: eng]
- RULE-51: A rule has `cleared` true when its spec status is `ready` and either its bar is `passed` and its passed cell is met, or its bar is `strong` and its strong cell is met [bar: strong] [origin: eng]
- RULE-52: A rule whose bar is `passed` meets the gate on its passed cell alone, whatever its strong cell reads, and a rule whose bar is `strong` does not meet the gate until its strong cell is met [bar: strong] [origin: eng]
- RULE-53: A rule is `signable` when it has cleared its bar, needs a signature and its signed cell does not read `signed`; the rollup and the summary carry `signable` as a count [bar: strong] [origin: eng]
- RULE-54: The sign list holds exactly the signable rules, exists only at the gate `signed`, and each row names the feature, the owner, the rule, the bar, the cell `signed`, the kind and why [bar: strong] [origin: eng]
- RULE-55: At the gate `strong` and above the status report prints `<n> rules to review`, and at `signed` it prints `<n> rules to sign` under it, each counting its own list [bar: passed] [origin: eng]
- RULE-56: `sign_at` decides which rules need a signature at the gate `signed`: `all` asks on every rule and `strong` asks on the rules whose bar is `strong` [bar: strong] [origin: eng]
