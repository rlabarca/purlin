# Feature: states

> Description: The level and the three evidence levels of a rule, the
>   flags beside them, the rollups over them, the structured payload every
>   surface reads, and the status table a person reads. One reader assembles
>   specs, the evidence and the signatures into the cells of
>   every rule; the table, the dashboard, the gate check and the drift report
>   all render that one payload rather than parsing each other's output.
> Scope: scripts/mcp/purlin/states.py, scripts/mcp/purlin/payload.py, scripts/mcp/purlin/status.py
> Stack: python/stdlib, json, hashlib, subprocess (list-only)

## Rules

- RULE-1: A rule that no proof line names, and whose own id marks no test, has a passed cell reading `no test` with the one reason `no proof written`, an empty proof list and the `no_proof` flag raised
- RULE-3: The passed cell reads `passed` when every proof of the rule has a passing test in an evidence section that is current, whose spec, code and tests fingerprint equals the one taken now, and it carries the source, whether the pass is current and whether it counts
- RULE-4: An evidence file's source is the folder it sits in, `ci` or `local`, and a current section from either counts at every gate, `signed` included, because what a signature locks is the evidence rather than the machine that produced it
- RULE-5: A current section under either source, committed or not, leaves the passed cell reading `passed` with that source named, `counts` true and no reason at all, at every gate; the runtime proof files a run leaves under `.purlin/runtime/` are not read
- RULE-42: An evidence file whose own `source` field disagrees with the folder it sits in is left out of the reading, and one warning naming its path is added to the payload's warnings
- RULE-43: The passed cell carries `platforms`, one entry per operating system a current section covers, each carrying that platform's own word, its source and when it ran; a platform a proof is tagged for that no current section covers is listed with the word `not run` and no source
- RULE-57: A person's own section answers for its own platform at every gate, so a red local section beside a green `ci` one from another operating system reads `partial` wherever the gate is set
- RULE-44: Where the platforms disagree the passed cell reads `partial`, naming the platforms that passed and the word of each that did not; `partial` is not met, its bucket is `partial` and its flag is `partial`
- RULE-45: A section that is out of date decides nothing: where the newest section that speaks for the rule is current, an older out-of-date one beside it is left out of `platforms` and its failures are not read
- RULE-46: Where the evidence holds no audit entry for its current hashes, a rule whose level is `passed` has a strong cell reading `weak` with the reason `no audit has run`, shown and not blocking, because the audit never reads such a rule under a higher gate
- RULE-47: The signed cell carries `at` beside `signer`: the date of the commit that added the signature, and the file's own timestamp where git cannot answer; and `machine` and `os`, the host's name and the operating system the signature file logs, each null where the file logs none
- RULE-6: A proof carrying `@env` is proved only by a current section from that operating system: the passed cell reads `not run`, names the operating system under `missing_env` and gives the reason `<os>: no run yet` rather than taking a word of its own
- RULE-7: Where the newest section that speaks for the rule is not current the passed cell reads `out of date`, not met and not current, with one reason per part that differs, `spec changed since <sha7>`, `code changed since <sha7>` or `tests changed since <sha7>` where the sha is the section's commit, and raises the `out_of_date` flag; a person's own section, committed or not, goes out of date like any other, and the next run clears it
- RULE-8: A rule no test backs reads `no test` with no source, not current and not counting
- RULE-9: The passed cell reads `failed` when a current section observed a failing proof of the rule, reading a `@env` proof only from that operating system's section; its reasons name where, as `failing: <os>, <source>`, and the `failing` flag is raised
- RULE-10: The strong cell exists only at the gate `strong` and above and the signed cell only at `signed`; a cell above the gate is absent from `cells` rather than present and empty
- RULE-11: A rule whose passed cell is not met has a strong cell reading `weak` with the one reason `not passed`, and the feature's test strength beside it
- RULE-12: Where mutation testing is on, a test strength under `min_strength` makes the strong cell read `weak` with the reason `strength <n>% under <m>%`
- RULE-13: Where the audit found nothing and no strength was measured, because `mutation_engine` is `none` or no engine measured one, the strong cell reads `strong` with the reason `no mutation score measured`, and a strength left in the evidence is not compared while mutation testing is off
- RULE-14: The strong cell reads the audit entry for the rule's current rule, proof and test hashes, its `verdict` and its `findings`, and no other field: a field the format does not name decides nothing, the cell carries the entry's findings under `findings`, an entry reading `weak` makes it read `weak` with each finding among its reasons, and the cell names the evidence file under `evidence`
- RULE-15: A rule whose level is `strong` or `signed` needs an audit entry for its current rule, proof and test hashes; without one the strong cell reads `not audited` with the reason `no audit has run on this code`, or `the AI audit could not run: <why>` where the last audit could not reach the model for those hashes; an entry reading `undecided` reads `weak` with the reason `the AI audit could not decide: <its sentence>`, which is build work and never a place in the queue
- RULE-16: A rule proved by a `@manual` proof reads `manual test` with the reason `manual proof`, and raises the `manual` flag
- RULE-18: A signature for the current hashes clears every reason a person was needed for, because what it settles there is a question the machine could not, and takes the rule out of the queue
- RULE-19: A strong cell that reads `strong` where an engine measured the strength carries no reasons at all [level: passed]
- RULE-20: The signed cell is computed from the signature files whatever the cells below it read: `signed` with the reason `by <email>`, `unsigned`, or `stale` with the reason `audit findings changed after the signature` where the rule, the proof and the test still match and only what the audit found moved, and `hashes changed after the signature` otherwise
- RULE-21: At the gate `signed` a rule needs a signature exactly when its level is `signed`; the signed cell of a rule whose level is lower is computed from the signature files and shown like any other, and does not keep the rule from meeting the gate
- RULE-22: A signature the gate refuses leaves the signed cell at `unsigned` carrying the reason the check gave, `the signing commit is not signed`, which is the one reason the gate `signed` refuses a committed signature for
- RULE-23: A rule's bucket is exactly one of `untested`, `failing`, `partial`, `passed`, `strong` and `signed`: `untested` while no counting run reads as passed, a rule no proof line names included, `failing` where every platform that ran failed, `partial` where they disagree, and otherwise the deepest level the rule met up to the gate
- RULE-24: `meets_gate` is true when no cell up to the gate blocks the rule, and `blocked_by` names the lowest one that does, in the order `passed`, `strong`, `signed`, and is null when the rule meets the gate
- RULE-25: A feature's rollup carries `rules`, `met`, one count per bucket the gate reaches, `stale`, `manual`, `not_audited`, `queue`, `hand_checks`, the test strength, `proofs`, `proofs_without_test` and `proofs_without_test_ids`
- RULE-48: `proofs` counts every proof line the rollup's rules write, once each, and `proofs_without_test` counts those of them that no test backs, leaving out a `@manual` proof, whose spec already says no test is written for it
- RULE-26: The project summary counts each rule once, under the feature that owns it, so a global anchor's rule is counted once however many features have to prove it, and it adds `features` to the rollup's keys
- RULE-27: The payload carries schema version 9 and the top-level keys `generated_at`, `generated_by`, `project`, `version`, `commit`, `dirty`, `gate`, `summary`, `features`, `queue`, `evidence`, `tag`, `remote_url` and `warnings`; `remote_url` is the `origin` remote, or null when the project has no remote
- RULE-28: A feature entry carries its spec path, its category, the paths of the signature files beside its spec, `current`, true when its newest section is current, and `evidence`, which per source is null or the file's path, whether it is committed as it stands and each section's commit, time and whether it is current, and each of its rules with its `level`, the `level_marked` the spec tagged and the audit hash a signature binds, and each proof with whether it is `@manual`, its operating system and no findings key
- RULE-29: The queue is the one list of the rules that wait on a person. At the gate `strong` and above it holds, with the need `hand check`, every rule whose level is `strong` or `signed` and whose strong cell reads `manual test`; a rule reading `not audited` or `weak`, a rule with no test and a rule whose level is `passed` are never in it, and it is empty under the gate `passed`
- RULE-30: Each queue row carries exactly `feature`, `owner`, `rule`, `text`, `level`, `need`, `word`, `reasons` and `command`; a hand check carries the strong cell's word and reasons and the command `purlin:sign <feature> <RULE-N> --note "<what you saw>"`, and a signature carries the signed cell's word and reasons and the command `purlin:sign <feature> <RULE-N>`
- RULE-31: The queue reads by feature, then by rule number, and names each rule once under the feature that owns it
- RULE-32: The dashboard's data file is written as `const PURLIN_DATA = ` followed by the payload and a trailing semicolon, and reads back as the payload that was written
- RULE-34: Every section in the payload's `evidence` map, keyed by feature, source and operating system, carries the result of the run it names, `fail` where any proof it observed failed and `pass` otherwise, beside its commit, its time, whether it is current and its path
- RULE-35: The tests a rule's test hash binds for a proof are the ones the feature's current sections list, every operating system and both sources together, so every checkout and CI read the same hash; where no section is current every section's list answers, so a code change alone does not move the hash, and a runtime proof file this checkout wrote moves nothing
- RULE-36: The status table is one row per spec under the columns Spec, Rules, Proofs and Tests, where a project at the gate `passed` that writes no proof line is shown neither the Proofs column nor a count of proof lines, with Strong added at the gate `strong` and Signed added at `signed`; `Proofs` reads `<n>` and appends `· <k> without a test`, `Tests` reads `<passed> of <rules>` and appends `· <k> partial` and `· <k> failing`, `Strong` reads `<n> of <rules> · <strength>` and a feature with no audit shows `n/a`, and `Signed` reads `<n> of <rules>`
- RULE-49: The status table and the dashboard render one spec's row from one module, so a cell reads the same characters wherever it is printed
- RULE-37: The status report's summary opens `<met> of <rules> rules meet the gate <gate>`, then counts the buckets the gate reaches in the tiles' own words and order, then names a test strength or a signature rule only at the gate that asks for one
- RULE-38: The report ends with exactly one `Next:` line, computed from the lowest cell blocking the project rather than from what the caller asked for
- RULE-58: The `Next:` line for rules with no current run to read names `purlin:audit` at `strong` and at `signed`, because evidence either source wrote counts at both and the audit runs the tests too, and names `purlin:test --remote` instead where the project's `trust` is `remote`, which is the one setting that asks for a `ci` run; the `Queue:` line beside it reads the one sentence every surface says a person is owed in, so one rule reads `1 rule needs a person`
- RULE-39: A project with no specs under `specs/` says what to run instead of printing an empty table [level: passed]
- RULE-40: The report carries no emoji: the only characters above U+2000 it prints are the arrow, the two triangles and the horizontal rule the design system allows
- RULE-41: A config carrying a key 0.9.5 wrote that this release does not read prints the line `Run: purlin:init --update` above the next step
- RULE-50: A rule's level is the lower of its `[level: ...]` tag and the gate, because the gate is the ceiling, and the gate where it names none; the rule entry carries `level`, the effective one, and `level_marked`, the tag as the spec wrote it or null
- RULE-52: A rule meets the gate when its passed cell is met, its strong cell is met if its level is `strong` or `signed`, and its signed cell is met if its level is `signed`; a cell above the rule's level is still computed and shown, and does not block it
- RULE-53: The rollup and the summary carry `queue`, how many of their rules are in the queue, and `hand_checks`, how many of those need a hand check
- RULE-54: At the gate `signed` the queue also holds, with the need `signature`, every rule whose level is `signed`, whose passed and strong cells are met and whose signed cell is not; a rule that needs a hand check and a signature is one row, `hand check`
- RULE-55: At the gate `strong` and above the status report prints `Queue: <n> rules. <h> hand checks, <s> signatures.` and, where the queue is not empty, `→ Queue: <n> rules need a person. Run purlin:sign.`; at the gate `passed` it prints neither [level: passed]
- RULE-60: Where a rule is marked above the gate the status report prints `<n> rules are marked above the gate and are read as <gate>.`, and `1 rule is marked above the gate and is read as <gate>.` for one; where none is, it prints neither
- RULE-59: At the gate `signed`, `tag` names the `signed/*` tag pointing at HEAD as `{name, commit}`, and is null where none does, so a surface that shows one commit's standing can say whether that commit is marked; where several point at HEAD the newest version wins, read as numbers where the name is numeric. Below `signed` `tag` is null, even where such a tag points at HEAD, because only a project at `signed` is ever tagged
- RULE-61: Every rule carries `audit`, at every gate: the `verdict` and `findings` of the audit entry for its current hashes, the feature's test strength, the `model` that answered or `unknown`, `at`, `commit` and the evidence file under `path`, or null where no entry answers
- RULE-62: A feature spec with no `> Scope:` line, or whose scope reaches no tracked file, carries `incomplete: true` and `incomplete_reason`, `no > Scope: line` or `> Scope: names nothing that exists`, its rollup carries `incomplete: true`, and `summary.incomplete` counts such specs; a spec whose scope reaches a file carries `incomplete: false` and a null reason; an anchor is never incomplete; its rules' passed and strong cells read as any other spec's
- RULE-63: At the gate `signed` only, a rule of an incomplete spec reads `unsigned` in its signed cell with the reason `the spec names no files in > Scope:, so a signature cannot be tied to the code it governs`, whatever signature it has, does not meet the gate where its level is `signed`, and is not in the queue; below `signed` it meets the gate as it would with its files named
- RULE-64: The status report prints `1 spec names no files, so its tests run every time: <name>.`, or `<n> specs name no files, so their tests run every time: <names>.`, at every gate, and nothing of the kind when every spec names its files; at the gate `signed`, with nothing else outstanding, its next step reads `→ Next: run purlin:spec <name>. It names no files in > Scope:, so its rules cannot be signed.`
- RULE-65: A rule no proof line names whose test is marked with the rule's own id reads its passed cell from that test, as a proof's test is read: `passed` where it passed in a current section and `failed` where it failed
- RULE-66: Proofs are optional at the gate `passed` and required above it: at `strong` and `signed`, a rule whose passed cell reads `passed` and that has no proof reads `no proof` in its strong cell with the reason `the rule has a test and no proof`, and does not meet the gate unless its level is `passed`
- RULE-67: The status report's summary counts the rules whose passed cell reads `out of date`, `<n> rules out of date` and `1 rule out of date` for one, and nothing where there are none; where those rules are what blocks a project at the gate `passed`, its `Next:` line reads `→ Next: run purlin:test. <n> rules are out of date.`, and `1 rule is out of date.` for one
- RULE-68: Every `Next:` line that counts rules reads singular for one rule, `1 rule has` and `1 rule is`, and plural for any other count
- RULE-69: At the gate `passed`, where proofs are optional, a rule with neither a proof nor a test sends the reader to `purlin:build` with `<n> rules have no test.`, and the report names no proof
- RULE-70: The three sample payloads the dashboard is built and photographed against, one per gate, carry together exactly the key paths the builder writes, at every depth, and no other [level: passed]
