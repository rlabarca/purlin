# Feature: sync_status

> Requires: schema_spec_format, schema_proof_format, security_no_dangerous_patterns
> Scope: scripts/mcp/purlin_server.py
> Stack: python/stdlib, json, glob, re, hashlib
> Description: Rule coverage reporting tool. Scans specs and proof files, computes per-feature coverage including own, required, and global anchor rules. Reports actionable directives and computes verification hashes.

## Rules

- RULE-1: Scans `specs/**/*.md` for RULE-N lines, reads `*.proofs-*.json`, and reports per-feature coverage including own rules, required rules (from `> Requires:`), and global anchor rules, with actionable directives
- RULE-2: Status is determined by proof coverage: VERIFIED (all rules proved + passing + non-stale receipt exists), PASSING (all rules proved + passing + no current receipt), PARTIAL (some but not all rules proved, none failing), FAILING (any proof has status FAIL), UNTESTED (zero proofs). Partial coverage never earns PASSING — every rule must have a passing proof
- RULE-3: Warns about unnumbered lines under `## Rules` and missing `## Rules` sections
- RULE-4: Required rules from `> Requires:` specs count toward a feature's coverage total (X/total) with `(required)` label; proofs are looked up under the source spec's feature name
- RULE-5: A `@manual(email, date, sha)` stamp on one of the feature's own rules counts that rule as proved, exactly as a passing proof entry does, for as long as `git log <sha>..HEAD -- <the spec's Scope paths>` is empty. One commit touching a scope path takes the rule back out of the count and its detail line reads `MANUAL PROOF STALE` with the re-verify directive, so a feature at 2/2 drops to 1/2 and PASSING drops to PARTIAL. The same function answers both questions, `_scope_changed_since(project_root, scope, sha)`, because a stamp that reads PASS in the detail while the counter refuses it is a report arguing with itself. A spec with no `> Scope:` has nothing to compare the sha against, so its stamps can never be shown to be out of date and none of them count: the advisory says so in the same line that says staleness cannot be detected. An executed proof wins for display: a rule with a failing test reads FAIL and leaves the feature FAILING whatever a stamp beside it says. A counted stamp is a human's word that a human checked something, recorded with an email and a date; it is coverage, not a signature
- RULE-6: `vhash` is `sha256` over `\x00`-joined segments truncated to 8 hex, and the first segment is the literal version tag `purlin-vhash/2`. After it come `["R", rule_key, sha256(" ".join(rule_text.split()))[:16]]` for every active rule key in sorted order, where a required or global key is `<source>/RULE-N` and its text comes from the source feature's spec; then `["P", feature, id, rule, status, tier, platform or "", test_file, test_name]` for every relevant proof entry, sorted by `(feature, id, rule, tier, platform or "", test_file, test_name)`; then `["M", feature, proof_id, rule, email, date, sha]` for every counted manual stamp. Each clause exists for a failure it prevents: hashing the rule text and not only the key means a reworded rule stales the receipt, and normalising whitespace first means a reflow of the same words does not; binding `test_file` and `test_name` means a rewritten or renamed test stales it, where before a test could be gutted without moving the hash; binding `feature` on every proof segment ends the collision where the same `PROOF-3` under a feature and under a required anchor hashed identically; binding `tier` and `platform` means a result that moves between them is a different hash, while an undeclared platform result (RULE-53) never enters the input at all. The separator is `\x00`, which no field can contain, so no value can forge a field boundary the way a `:` or `,` join allowed. The version tag is first so a version 1 and a version 2 hash of the same state can never collide. The hash is a change detector, not a token: it is not a signature, and it binds nothing about the source code under test
- RULE-7: All proofs count equally toward coverage regardless of proof type (grep-based, behavioral, etc.). Proof quality (STRONG/WEAK/HOLLOW) is assessed by the auditor, not the coverage system
- RULE-8: Detects `> Global: true` metadata on anchor specs and sets the `is_global` flag
- RULE-9: Global anchor rules auto-apply to all non-anchor feature specs without needing `> Requires:`; they appear in coverage with `(global)` label
- RULE-10: Displays rule labels: `(own)` for the feature's own rules, `(required)` for `> Requires:` rules, `(global)` for global anchor rules
- RULE-11: Shows a scope overlap advisory when an anchor's `> Scope:` overlaps a feature's scope but is not in `> Requires:`
- RULE-12: Warns when a `> Requires:` target does not match any known spec name
- RULE-13: Warns when a spec has manual proofs but no `> Scope:` metadata
- RULE-14: Prefers proof files adjacent to their spec over proof files in the specs/ root directory
- RULE-15: Explains receipt staleness cause: distinguishes own rule changes from required/global anchor rule changes
- RULE-16: Warns when `specs/` contains uncommitted changes to `.md` or `.proofs-*.json` files, listing the affected files and recommending a commit before drift or verify
- RULE-17: All proofs are displayed uniformly — grep-based and behavioral proofs both show PASS/FAIL status with no visual distinction in coverage reporting
- RULE-18: sync_status output begins with a summary table showing feature name, coverage fraction, status (VERIFIED/PASSING/FAILING/PARTIAL/UNTESTED), Proof Design and Proof Integrity for all features, sorted by status priority (FAILING, PARTIAL, PASSING, VERIFIED, UNTESTED). Each gauge cell shows a percentage, `not audited` when the feature has no assessments or only a subset, or the unscorable word from that gauge's own vocabulary when every proof is assessed and none is gradeable: `structural` for Design and `excluded` for Integrity. Tokens match the dashboard's exactly so the two surfaces cannot disagree. A feature held at PASSING by a platform that has not run carries a `*` after its status token, those rows lead their status group, and one legend line under the box reads `* proved here, awaiting a declared platform. VERIFIED needs every declared platform proved and receipted`. One legend line for the project and none when no row is marked: a PASSING row beside another PASSING row otherwise says nothing about which one is waiting on a runner, and repeating the explanation per row would cost more lines than the table
- RULE-19: sync_status appends an integrity summary after the features VERIFIED line showing the integrity percentage and relative time since last purlin:audit, sourced from the audit cache; when no cache exists, shows a prompt to run purlin:audit
- RULE-20: Reports UNTESTED when a feature has zero behavioral proofs — this replaces the em-dash display for features with no proofs
- RULE-21: Reports PARTIAL (not PASSING) when a feature has some rules proved and passing but not all rules are covered — partial coverage never earns PASSING status
- RULE-22: Anchor detail shows Source URL, Path (if present), and Pinned value (SHA truncated to 7 chars) for anchors with `> Source:` metadata
- RULE-23: Shows unpinned warning for anchors with `> Source:` but no `> Pinned:`
- RULE-24: report-data.js feature entries include `pinned` and `source_path` fields when the anchor spec has `> Pinned:` and `> Path:` metadata
- RULE-25: A gauge is stale when the newest assessment in its own cache is older than 24 hours, computed per gauge and never shared between them. A stale gauge is marked in the summary line; what the mark says is RULE-45's concern
- RULE-26: report-data.js includes audit_summary with integrity, assessment counts, last_audit, last_audit_relative, and stale fields when cache exists; audit_summary is null when no cache exists
- RULE-27: report-data.js per-feature audit data is populated from cache entries matching the feature name
- RULE-28: When the audit cache already contains entries without a `feature` field, written before the writer-side check existed or hand-edited since, the reader does not crash on them and does not attribute them to a feature. It cannot count them either: an entry with no feature names no proof, so its key can never be recomputed and RULE-61 reports it as invalidated. Rejecting such an entry outright is still the writer's job (`static_checks` RULE-33); the reader's job is to leave it out of every number rather than to fail
- RULE-29: Per-feature integrity = (STRONG + MANUAL) / (STRONG + WEAK + HOLLOW + MANUAL) — measures proof quality only; NONE rules do not affect the integrity denominator
- RULE-30: Per-feature integrity counts only proofs cached under that feature name — required/global anchor proofs are counted under the anchor's own feature, not the consuming feature
- RULE-31: Global integrity (project-wide) = (STRONG + MANUAL) / (STRONG + WEAK + HOLLOW + MANUAL) across all features — NONE rules do not affect the denominator. That is the assessed score, over the proofs the audit cache actually holds; RULE-46 defines the coverage-weighted figure the surfaces report from it
- RULE-32: sync_status CLI integrity percentage matches the audit_summary.integrity value in report-data.js
- RULE-33: The integrity formula `(STRONG + MANUAL) / (STRONG + WEAK + HOLLOW + MANUAL)` is consistent across `references/audit_criteria.md`, `skills/audit/SKILL.md`, and this spec; none of these files include NONE in the integrity formula denominator
- RULE-34: Integrity is computed by exactly one function (`_compute_integrity`) — both `_read_audit_summary` and `_build_feature_audit` delegate to it; no other function in purlin_server.py contains the integrity formula
- RULE-35: Feature status is determined by exactly one function (`_determine_status(proved, active_total, has_fail, has_current_receipt, platform_complete)`) — all call sites in purlin_server.py delegate to it; no other function contains the status determination logic, and in particular `_report_feature` no longer decides its own header with a receipt ternary. `platform_complete` is false when some proof declares a platform with no result there, and it turns VERIFIED into PASSING and nothing else: a feature that is proved here cannot claim it was verified everywhere it says it runs, and an awaiting platform warns rather than demotes, so it never produces PARTIAL or FAILING. A header that decided VERIFIED for itself is how a feature printed VERIFIED over a platform that had never run
- RULE-36: `_scan_specs` parses `> Stack:` metadata from spec files and includes it in feature info; report-data.js includes `stack` field when present
- RULE-37: Does NOT warn about rule count — rule count scales with feature complexity per `references/spec_quality_guide.md` ("Coverage dimensions")
- RULE-38: When the project's `.mcp.json` defines a `purlin` server whose command or args path points into the Claude plugin cache (`.claude/plugins/cache/`), sync_status reports it as the `legacy-mcp` entry of the pending-migrations advisory (RULE-55), naming the pinned path and closing with that advisory's `→ Run: purlin:init --update` directive rather than a `--mcp` directive of its own: a project that has not been updated usually carries several migrations, and one directive that fixes all of them is what a reader can act on (`--mcp` remains the name of that single step). No entry when `.mcp.json` is absent, has no `purlin` entry, or the `purlin` entry points elsewhere (e.g., a dev checkout)
- RULE-39: sync_status reports both quality gauges. When a design cache exists it prints `Proof Design: N%`, where N is the coverage-weighted figure of RULE-46 computed from the assessed score PROVABLE / (PROVABLE + LOOSE + UNPROVABLE), excluding STRUCTURAL from both numerator and denominator; when none exists it prints `Proof Design: not measured` rather than omitting the gauge, so a project that has never graded its descriptions is distinguishable from one where the reporter forgot. When no audit cache exists it distinguishes two states: a project where no proof has executed reads `Proof Integrity: no tests yet`, while one with executed proofs reads `No audit data` — reporting them identically made a deliberate spec-first project look neglected. Each printed percentage is followed by a parenthetical carrying its measurement coverage as `N of M measured`, the unweighted assessed score as `P% of those assessed` whenever coverage is incomplete, and that gauge's own relative age, because a score over a thin slice of the project is not a project-wide score, a weighted figure is unreadable without the assessed one it came from, and the two caches age independently
- RULE-40: The coverage table renders every status without breaking its borders — the status column is sized from the longest token actually rendered, not from the status vocabulary, so `UNTESTED` and `VERIFIED` (8 characters) and a marked token such as `UNTESTED*` (9) each fit. Every rendered line has identical width. Ruling the column from the vocabulary is what let the 8-character words overflow a 7-wide column, and the RULE-18 marker makes a token wider than any word in that vocabulary
- RULE-41: A rule with no executed proof reports the PROOF ids and descriptions the spec already declares for it, and the suggested `@pytest.mark.proof` marker names the real declared PROOF id rather than the literal placeholder `PROOF-N`
- RULE-42: The next-step directive is chosen from observable state: a rule with no proof whose feature has no existing `> Scope:` files routes to `purlin:build <name>`, while one whose scope files exist routes to `purlin:test`. A feature emits exactly one directive per uncovered rule, never a duplicate
- RULE-43: The design formula `PROVABLE / (PROVABLE + LOOSE + UNPROVABLE)` is consistent across `references/audit_criteria.md`, `skills/audit/SKILL.md`, and this spec, the same three files RULE-33 pins for the integrity formula; none of them include STRUCTURAL in the design denominator
- RULE-44: A fully covered feature whose quality gauges show findings emits a gauge-driven directive rather than `No action needed.` Design findings route to `purlin:spec <name>` because the proof description is the artifact at fault, Integrity WEAK or HOLLOW findings route to `purlin:build <name>` because only test code moves them, and a gauge in state `unmeasured` routes to `purlin:audit`. Design is reported before Integrity, since a high Integrity score over LOOSE descriptions measures an unfalsifiable spec rather than good tests. These directives are additional to the per-rule coverage directives and never replace or duplicate them
- RULE-45: Each gauge's freshness is reported from its own cache timestamp, never from the other's. A stale gauge's directive names the narrowest refresh command (`purlin:audit --design`, `purlin:audit --integrity`, or bare `purlin:audit` when both are stale), because Design grading is deterministic and free while Integrity grading needs test code and costs LLM calls
- RULE-46: Every project-wide gauge figure a surface reports is weighted by measurement coverage as `passing / (gradeable + unmeasured)`, where `unmeasured` is that gauge's population minus what its cache has assessed. An unassessed item is unknown, not passing, so it counts in the denominator; an item excluded from scoring (STRUCTURAL for Design, EXCLUDED for Integrity) counts in neither, being a correct terminal state rather than an unknown. At full coverage the weighted figure equals the assessed score of RULE-29/31/43 exactly, so the gauge does not change meaning as coverage fills in. The assessed score remains available and is reported alongside, because a weighted 2% caused by thin coverage and a 2% caused by bad proofs need different fixes. Per-feature gauges report the assessed score directly, since RULE-18 makes a partially assessed feature read `not audited` rather than a number
- RULE-47: A proof declaring `@on(<platforms>)` that has no result satisfying one of those platforms is reported as awaiting a runner on that platform, naming the platform and the proof ids in the line grammar of RULE-58. A result satisfies a declared platform D when it comes from a proof file scoped to R (`<feature>.proofs-<tier>@<R>.json`, or the legacy `proofs-windows.json` read as `unit@windows`) and either R equals D, or D is a family id (`windows`, `macos`, `linux`) and the registry entry for R has `os` equal to D; nothing else satisfies, so a family result never satisfies a specific id, an unregistered id satisfies nothing but itself, and an agnostic result satisfies no platform. When several files satisfy the same platform a failing result wins. This is distinct from `NO PROOF`, which means nobody wrote it. It warns and never blocks: the awaiting proofs do not count against coverage, and a rule leaves the coverage denominator, the way a DEFERRED rule does, only when every declared proof for it is awaiting on every platform it declares; a rule with any satisfying result stays in and counts what that result proves, so a proof declared on two platforms and proved on one keeps its rule in the denominator with the other platform reported as awaiting. A required anchor rule is never excluded this way, because it is proved under the anchor's own feature name. The directive names `purlin:test` as the way to close the gap, because that skill owns the remote path that dispatches a runner and pulls back the proofs it commits; it must not describe the work as something the reader has to arrange by hand. A feature with anything awaiting is reported as PASSING at most, however current its receipt is (RULE-35): the receipt is still issued and still true about the platforms it names, and the status is where the incompleteness is stated
- RULE-48: When a declared platform has a satisfying result, sync_status reports on that platform's RULE-58 line when it was last proved and by which runner, read per scoped proof file from `git log -1` on that file and the commit's `Purlin-Runner:` trailer, with the commit's `Purlin-Platform:` trailer cross-checked against the platform id in the filename: a trailer naming a different id is reported as `trailer says <id>` after the runner rather than trusted or hidden. Proof entries carry no timestamp and gain none, because that absence is what makes a CI commit-back idempotent; a missing trailer reports the date with the runner unrecorded rather than omitting the line. One `git log` per file per report run, memoized, so a feature proved on several platforms does not re-read the same commit
- RULE-49: sync_status reports the project's declared `remote_verification` mode (`required`, `optional`, `off`) on its own line after the summary line, and states in the same breath that the field is a declaration and the enforcement is branch protection. The field lives in a file the agent can edit, so presenting it as a gate would misreport where the trust boundary is. The line is printed whenever the mode is not `off` or some proof is actually awaiting a runner, and is silent only for an `off` project with nothing waiting, because a project that never opted in has nothing to report. The `off` branch keys on awaiting rather than on declared: a project whose runner-gated proofs were already proved elsewhere has nothing stuck, so telling it those proofs will stay awaiting would be false. When something is waiting it is told how many and pointed at `purlin:test`. A value outside the three is reported as unrecognized and named, never silently treated as `off`: a typo in the mode would otherwise disable the declaration invisibly
- RULE-50: The platform ids a spec's `@on(...)` tags name resolve against a registry built from three built-in family entries (`windows`, `macos`, `linux`, each carrying only its `os`) overlaid by the optional `platforms` object in `.purlin/config.json`, where a config entry of the same id replaces the built-in so a project can attach a runner to a family id. Each config entry is validated: the id matches `[a-z0-9][a-z0-9-]*`; `os` is required and one of `windows`, `macos`, `linux`, with `ios` and `android` rejected as "not yet supported" so the extension point is named; `version` is optional and either `N[.N...]` or `>=N[.N...]`; `distro` is optional and valid only when `os` is `linux`; `arch` is optional and normalised to `x86_64` or `arm64` (accepting `AMD64`, `amd64`, `x64`, `aarch64`); `runner` is an optional object whose `provider` is required and whose only other keys are `runs_on` and `workflow`; `label` is optional; any other key is an error, so a typo cannot vanish into an entry that matches every host of its family. A malformed entry is dropped and reported in the sync_status preamble naming the id and the problem, never silently, and a built-in it would have replaced stays. A proof naming an id that is neither registered nor a family id gets a per-feature advisory naming the proof, the id and the fix (register it, or use a family id); advisories change no verdict
- RULE-51: The host is described by `_detect_host_platform` as `{os, version, distro, arch, id}`: `os` maps `platform.system()` to the family (`Darwin` to `macos`, `Windows` to `windows`, `Linux` to `linux`, anything else lower-cased); `version` is `mac_ver()[0]` on macOS, `win32_ver()[1]` on Windows and the os-release `VERSION_ID` on Linux; `distro` is the os-release `ID` on Linux and empty elsewhere or when os-release is unreadable; `arch` is `machine()` through the same normaliser as the registry; `id` is `PURLIN_PLATFORM` when set, else None. A registry entry is satisfied by the host when `PURLIN_PLATFORM` equals the entry's id, and otherwise only when `os` matches, `distro` matches whenever the entry names one, `arch` matches whenever the entry names one, and the version constraint holds: no constraint always holds, any constraint fails against an unknown host version, `N[.N...]` matches when the host's leading components equal it (`14` matches `14.7.1`, `14.7` does not match `14.8`), and `>=N[.N...]` compares component by component with the shorter side padded with zeros. A family entry carrying only `os` is therefore satisfied by any host of that family
- RULE-52: When any proof in the project declares a platform, sync_status prints a `Platforms:` block after the remote-verification line and before the feature detail: a host line (`Platforms: host <os> <version> <arch>`, plus the `PURLIN_PLATFORM` id when set), then one `local:` line per declared id this host satisfies (RULE-51) naming the proof count and `run with PURLIN_PLATFORM=<id>`, and one `runner:` line per declared id it does not, naming the proof count and how a runner reaches it: `github workflow <name>` from the registry entry's runner block, `no runner configured` when the entry has none, `runner provider <x> is not one purlin:test can dispatch` for any other provider, and `unregistered` for an id that is neither registered nor a family id. Every declared id lands on exactly one line and registry errors keep printing in the preamble (RULE-50), so a platform the project names is never silently dropped. A project with no `@on` prints no `Platforms:` line at all
- RULE-53: A scoped proof file whose platform satisfies none of the platforms its proof declares is an undeclared result: sync_status reports it as `Undeclared platform result`, naming the file and the proof id, and it counts toward nothing. It satisfies no declared platform, so the proof stays awaiting a runner there; it moves no rule to PASS or FAIL; it enters no vhash; and the payload lists it under `undeclared` beside `awaiting_runner` rather than mixing the two. A proof that declares no platform never produces an undeclared result, and an agnostic result is never undeclared, because it is not a platform result at all. Silence here would make a file that was ignored look like a file that was never produced
- RULE-54: Every surface that states a feature's verdict reads it from exactly one function, `_feature_verdict(name, info, all_features, all_proofs, global_anchors, project_root, registry)`, which returns the rule entries, the active entries, the proof lookup, the relevant proofs, the active rules' text, the counted manual stamps, `proved`, `has_fail`, the vhash, the awaiting and undeclared lists, the per-platform results, the receipt on disk and whether that receipt is current. The detail report, the summary table, the dashboard payload, the drift snapshot and `dev/issue_receipts.py` all call it and none recomputes any part of it, so `_compute_vhash` and `_active_rule_entries` are each called from exactly one place in `scripts/mcp/purlin_server.py` and that place is this function. Duplication here is not a tidiness question: the issuer built its own active rule set and skipped as unproved every feature whose only uncovered rule was awaiting a runner, while sync_status read the same feature PASSING, and the summary table rebuilt the rule entries a second time inside the loop that had just printed them. A receipt that disagrees with the report that sent you to write it is worse than no receipt
- RULE-55: sync_status opens with a pending-migrations advisory when the project still carries artifacts an older plugin wrote: one line per migration id with its count, a summary and the files it counted, closed by a single `→ Run: purlin:init --update`. The ids are `legacy-tier-windows`, `legacy-proof-file`, `legacy-marker`, `plugin-copies-stale`, `config-fields-missing`, `receipt-v1` and `legacy-mcp`. Detection is content-based and never version-based, because a project may have been initialized by any version, edited by hand, or half-migrated already, so what is on disk is the only honest input. A project with no readable `.purlin/config.json` reports no `config-fields-missing` entry: an absent config is not a config missing fields, and bringing one into existence is `purlin:init`'s work rather than the update's. A receipt written under the version 1 vhash formula mismatches for that reason alone, so the stale block for such a feature reads `Receipt is version 1; the vhash formula changed; run purlin:verify` rather than the generic explanations, which would all be wrong about why
- RULE-56: Proof Integrity splits per platform and Proof Design never does. A platform's Integrity population is every executed proof entry read from a file scoped to it, plus every agnostic entry when the platform is the host id, because a test that names no platform still ran somewhere and that somewhere is here. `measured` is how many of those entries the audit cache holds a grade for, and the reported figure is weighted by that coverage exactly as RULE-46 weights the project figure, so a platform reads `Integrity W% (M of T measured)` and never a bare percentage. A grade describes the test and not the machine, so the split reports measurement coverage per platform rather than claiming the same proof is stronger on one host than another; splitting Proof Design would be meaningless, since a description is graded from its text and has no platform at all. The host id is `PURLIN_PLATFORM` when set, else a registry id the host satisfies preferring a project-registered id over its family, else the literal `unregistered`
- RULE-57: When any proof declares a platform, sync_status prints exactly one `Platforms (host: <id>): <segment> | <segment>` line, after the summary line and before the remote-verification line. `<id>` is `PURLIN_PLATFORM` when set, else a registry id the host satisfies preferring a project-registered id over its family, else the literal `unregistered`. A segment is one platform some proof declares: its id, ` (host)` when it is this machine, `<verified>/<features> verified`, then at most five clauses in this order, each omitted when its count is zero or its figure is unavailable: `<n> passing`, `<n> failing`, `<n> proofs awaiting runner`, `Integrity <W>% (<M> of <T> measured)` when the platform has executed proofs, and `proved <relative time> (<runner>)`. Segments are joined by ` | ` and clauses by `, `. One line for the whole project and no line at all when nothing declares a platform: `purlin:status` is read in a terminal above forty feature rows, the per-platform breakdown belongs to the dashboard modal and to the RULE-58 lines, and it sits below the summary line so that line, which `skills/status/SKILL.md` prints verbatim, keeps one job
- RULE-58: A feature's detail carries one line per platform its proofs declare, host platforms first and the rest by id, in exactly four forms: `✓ <id> (host): <proved>/<declared> proved` when this host satisfies the id, `✓ <id>: <proved>/<declared> proved remotely <relative time> (<runner>)` when a runner proved it (with `runner not recorded` when the commit carries no trailer and `(trailer says <x>)` appended when the commit's `Purlin-Platform:` disagrees), `⚠ <id>: awaiting runner, <n> proofs (<ids>)` when a declared proof has no result there, and `✗ <id>: <proved>/<declared> proved, <n> failing (<ids>)` when one failed. Beside them at most three further lines, each only when something is awaiting: the count of rules that left the coverage denominator, the `purlin:test` directive, and `⚠ Receipt is platform-partial: verified here, not on <ids>` when the feature holds a current receipt that does not cover every declared platform. A feature declaring no platform prints none of it. The bound is the point: one line per platform rather than one per proof, per file or per group, because the previous shape printed an awaiting block, a denominator note, a directive and one provenance line per satisfying file, and a reader scanning forty features could not see the shape repeat
- RULE-59: Every counted manual stamp enters the verification hash as an `M` segment of `[feature, proof_id, rule, email, date, sha]` (RULE-6), so re-stamping a rule with a new email, date or sha moves the feature's vhash and stales the receipt issued against the old stamp. Without the segment a re-stamp is invisible to every downstream gate: the receipt still matches, the dashboard still reads VERIFIED, and nothing records that the human behind the coverage changed or that the claim was made again on a later day. The issuer writes the same list into the receipt's `manual` array, omitted when there are none, so a reader can see which rules were proved by a person rather than by a test without re-deriving it from the spec
- RULE-60: A VERIFIED feature with a `> Scope:` whose scope has been committed to since the tests behind its receipt ran says so, in two lines: `⚠ EVIDENCE OLDER THAN CODE: scope changed in <n> commits since the tests behind this receipt ran (<sha7>)` and the directive `→ Run: purlin:test <name>`. `<n>` is `git rev-list --count --end-of-options <sha>..HEAD -- <the spec's Scope paths>` and `<sha>` is `evidence.test_run.commit` from the receipt, falling back to `receipt.commit` for a receipt issued before that field existed. The `--` is what makes the count about the scope rather than about the project, and `--end-of-options` keeps a scope path beginning with `-` from being read as a flag. It warns and never blocks: the status stays VERIFIED, no gate reads it, and the payload carries it as `evidence_stale` (`report_data` RULE-38) for the dashboard to render. What is compared is the recorded run and never the proof files' own git dates: a re-executed test file whose bytes do not change gets no new commit, so a proof-file date says when the file was last edited and would fire falsely on almost every feature that had just been re-run. A feature with no `> Scope:`, no receipt, or a status below VERIFIED prints nothing
- RULE-61: A cached quality grade is believed only while its key still recomputes from project state. `_read_audit_summary`, `_read_design_summary` and `_read_audit_cache_by_feature` recompute every deduplicated entry's key through `static_checks.cache_key_for` and drop the ones that no longer match, reporting the count as `invalidated`. An invalidated grade counts as unmeasured and never as passing, so the coverage-weighted headline falls instead of holding on stale evidence, and the Proof Integrity line names the count and directs the reader to `purlin:audit`. A MANUAL grade is a human's claim rather than a measurement, so it is valid only while the `@manual` stamp behind it is current at read time, judged by the same `_manual_ok_keys` the coverage count uses. When `static_checks` cannot be imported no key can be checked at all, so every entry is invalidated: an unverifiable cache is not a valid one
- RULE-62: When `audit_llm` is configured and cannot run, `sync_status` warns and never blocks. It warns when the first token of `shlex.split(audit_llm)` does not resolve on `PATH`, and when the command carries no `{prompt}` placeholder, so the criteria and the test code would never reach it. `audit_llm_name` set with no `audit_llm` warns for the same reason: every grade would be stamped with an auditor that never ran. Each line names the offending value, the advisory carries one directive naming `.purlin/config.json`, and it states that it is a warning and that grades already cached are unaffected. A gate here would stop a build over a tool the project installs on another machine
