# Feature: static_checks

> Scope: scripts/audit/static_checks.py
> Description: Deterministic pre-filter that catches structural test problems without any LLM. Every language Purlin ships a proof plugin for has a checker here, seven of them: Python (`ast`), JavaScript/TypeScript (`.js` `.jsx` `.mjs` `.cjs` `.ts` `.tsx`, brace-balancing tokenizer), Shell (regex), C# (`.cs`), PHP (`.php`), SQL (`.sql`) and C (`.c` `.h`). Which checker reads which extension is decided in one extension table. It also runs language-agnostic proof-file checks (proof ID collisions, orphan rules) that operate on JSON regardless of source language. `deterministic_sweep` runs those checkers and the proof-description grader over a whole project at once, reading no cache and writing nothing, so a CI job can recompute the same verdict from a clean checkout. Runs before the LLM audit pass so that structural issues like `assert True` are always caught regardless of which LLM performs the semantic evaluation.

## Rules

- RULE-1: Detects assert True / tautological assertions in Python test functions
- RULE-2: Detects test functions with no assertion statements
- RULE-3: Detects bare except:pass around code under test
- RULE-4: Detects logic mirroring (expected value from same function as SUT)
- RULE-5: Detects mock target matching the function being tested (requires --spec-path)
- RULE-6: Returns JSON with proof_id, rule_id, test_name, status, reason for each proof
- RULE-7: Always exits 0 for completed analysis; defects are reported via JSON output status=fail, not exit codes. Non-zero exits (2) are reserved for real errors (bad args, missing files)
- RULE-8: check_spec_coverage returns rule_count and proof_count for the spec
- RULE-10: compute_proof_hash returns a deterministic 16-char hex hash from (rule text, proof description, test code)
- RULE-11: read_audit_cache returns an empty dict when no cache file exists and parses valid JSON when it does
- RULE-12: write_audit_cache writes atomically via tmp + os.replace
- RULE-13: Shell if/else proof pairs (same proof_id and rule_id with one pass and one fail branch) are recognized as a single conditional proof where the if-condition is the assertion, not flagged as hardcoded pass
- RULE-14: Python assert_true results include a literal field (true for assert True/assertTrue(True), false for heuristic patterns like assert x is not None)
- RULE-15: Proof ID collisions within a feature are detected — same PROOF-N targeting different RULE-N values in a proof JSON file
- RULE-16: Proof entries referencing non-existent rules in the spec are flagged as orphans
- RULE-17: Each audit cache entry contains all required fields: assessment, criterion, why, fix, feature, proof_id, rule_id, priority, cached_at
- RULE-18: clear_audit_cache atomically replaces the cache file with an empty dict {}
- RULE-19: write_audit_cache stamps the real current UTC time on the entries the caller supplies, overwriting any caller-provided cached_at so a stamp cannot be backdated. Entries carried forward from the existing cache on disk keep their original cached_at — re-stamping them would make every surviving entry look freshly audited, leaving `last_audit` permanently reading "now" and the 24h staleness check unable to fire
- RULE-21: load_criteria returns built-in criteria always, appends cached additional criteria from `.purlin/cache/additional_criteria.md` if present, appends extra path if provided; no other function in static_checks.py assembles criteria text
- RULE-22: prune_audit_cache removes all cache entries whose hash key is not in the provided live_keys set, preserving entries whose key IS in live_keys with all fields intact
- RULE-23: prune_audit_cache with an empty live_keys set on a non-empty cache produces an empty cache (full sweep), and with all keys live produces an identical cache (no false pruning)
- RULE-24: write_audit_cache merges new entries into the existing cache on disk — entries from prior writes for different features are preserved, not overwritten. Entries for the same (feature, proof_id) are deduplicated by keeping the latest cached_at
- RULE-25: Every operation that mutates the audit cache — write_audit_cache, prune_audit_cache and clear_audit_cache — protects its entire read→modify→write cycle with an exclusive OS file lock on `audit_cache.json.lock` (`fcntl.flock` on POSIX, `msvcrt.locking` on Windows), so concurrent subagent writers and a following prune serialize correctly and no entries are lost
- RULE-26: `--write-cache` CLI flag reads a JSON dict of cache entries from stdin and merges them into the existing audit cache via write_audit_cache, printing a JSON status response with `status: "merged"` and entry count
- RULE-27: check_js detects tautological assertions (`expect(true).toBe(true)`) and JS/TS test bodies with no `expect()` calls, returning the same JSON shape (proof_id, rule_id, test_name, status, reason) as check_python
- RULE-28: check_js parses JS/TS test files with a brace-balancing tokenizer that (a) matches test titles containing apostrophes regardless of quote style, and (b) captures full test bodies containing nested braces — options objects, destructured parameters, type assertions — without truncating at the first inner `}`
- RULE-29: static_checks.py imports and runs on Windows as well as POSIX — no Unix-only module is imported unconditionally at module load. `fcntl` is imported under `try/except ImportError` and a module-level flag (`_HAS_FCNTL`) selects between `fcntl.flock` and an `msvcrt.locking` fallback, so write_audit_cache acquires and releases its exclusive lock through that flag and the Windows lock path is exercisable without `fcntl`. The native lock path is verified for real on a `windows-latest` GitHub Actions runner (where `_HAS_FCNTL` is genuinely False and `msvcrt` is real), not only by host simulation
- RULE-30: static_checks.py performs all text I/O as UTF-8 regardless of the OS locale: every text-mode `open()` specifies `encoding='utf-8'`, and stdout/stderr are reconfigured to UTF-8 at startup, so the tool's own UTF-8 specs/proofs/criteria/config/cache files both parse (read) and print (stdout) correctly even when the platform codec is cp1252/ASCII (e.g. on Windows). Without this, `--load-criteria` raises `UnicodeDecodeError` reading `audit_criteria.md` and `UnicodeEncodeError` printing its glyphs. This is verified for real under the native Windows console codec on a `windows-latest` GitHub Actions runner, not only by host locale simulation
- RULE-32: resolve_test_file_from_name locates a test's source file from its fully-qualified test_name (e.g. `Ns.Sub.AuthLogicTests.Evaluate_NullRow`) when the proof's test_file is empty — deriving the declaring type (the segment before the final `.method`) and searching the project's source files (skipping bin/obj/node_modules/.git and other build/vendored dirs) for its `class`/`struct`/`record`/`interface` declaration. Returns the repo-relative POSIX path of the best match (preferring a file whose stem equals the type name) or `''` if none. Exposed via the `--resolve-source <test_name> [--project-root P] [--ext .cs]` CLI flag (printing JSON `{test_name, test_file}`), so purlin:audit can reach C# Pass-1/Pass-2 even when the xUnit logger emits an empty test_file (TestCase.CodeFilePath is null under `dotnet test` without source info)
- RULE-31: For `.cs` test files, Pass 1 parses `[Trait("PurlinProof", "feature:PROOF-N:RULE-N:tier")]` traits, associates each with its `[Fact]`/`[Theory]` method body, and applies assert-true and no-assertion detection — returning the same JSON shape (proof_id, rule_id, test_name, status, reason) as check_python/check_js. xUnit `Assert.*`, NUnit `Assert.That`, MSTest `Assert.*`, FluentAssertions `.Should()`, and Playwright fluent assertions — `Expect(...)`/`Assertions.Expect(...)` chained to a `To*Async()` matcher (`ToBeVisibleAsync`, `ToHaveTextAsync`, `ToContainTextAsync`, …) — all count as assertions. A bare `Expect(x)` with no matcher chain is not an assertion (still flagged no_assertions)
- RULE-33: write_audit_cache rejects any entry missing `feature` or `proof_id` — the deduplication key — by raising ValueError naming every offending cache key, before touching the filesystem, so the cache on disk is unchanged. `--write-cache` surfaces it as a JSON `error` object with exit 2, and likewise rejects stdin that is not a JSON object rather than raising an unhandled exception
- RULE-34: The CLI help text and the module docstring stay in step with the dispatch chain: every `--flag` that `main()` dispatches on appears in the `_USAGE` tuple printed on a bad invocation, and the docstring states the RULE-7 exit convention (0 for any completed analysis, 2 for real errors) rather than contradicting it
- RULE-35: check_proof_design grades every proof description in a spec as PROVABLE, LOOSE, UNPROVABLE or STRUCTURAL from the rule text and description alone — no test file and no proof JSON — and is exposed as `--check-proof-design --spec-path <path>`. A description whose only action reads an existing artifact is STRUCTURAL (nothing ran to produce what is asserted on); one whose entire assertion is existence is UNPROVABLE; an assertion of absence is a FORBIDDEN-pattern proof and is not treated as UNPROVABLE
- RULE-36: audit_scope reports, per feature, the rule count, declared proof count, executed proof count, how many `> Scope:` files exist on disk, and how many distinct test files back the executed proofs, plus a `recommended_mode` of `design` when no proof has executed anywhere and `both` otherwise. Exposed as `--audit-scope`. `scope_files_exist` is what distinguishes a spec with nothing built from code that has no tests yet
- RULE-37: Proof Design results are cached in `.purlin/cache/design_cache.json`, keyed by `compute_design_hash` over the proof's identity and description with test code deliberately excluded, so a design grade survives test edits. It uses the same entry shape, the same required-field validation and the same exclusive lock as the audit cache, via `--read-design-cache` and `--write-design-cache`
- RULE-38: `resolve_proof_inputs(project_root, feature, proof_id)` reads the rule text, the proof description and the graded test function's source out of the project, and it is the only source of a cache key. `--cache-key --feature <name> --proof-id PROOF-N` prints that key and the flag it replaced, `--compute-proof-hash`, is gone. The proof's own identity, `<feature>\0<proof_id>`, is hashed in alongside the three inputs, so `(feature, proof_id)` to key is injective: without it two features whose rule text and proof description are byte-identical share one key and one grade silently overwrites the other while the deduplication key still says they are two proofs. `write_audit_cache` discards whatever key a caller supplied and re-keys every entry through that one function, so a stored key always describes project state instead of the text a caller happened to paste. An entry naming a `(feature, proof_id)` that does not resolve is rejected the way a missing deduplication field is (RULE-33): ValueError naming every offender, raised before the filesystem is touched, surfaced by `--write-cache` as a JSON `error` with exit 2
- RULE-39: Every entry `write_audit_cache` stores carries `auditor` as `{name, command}` read from `.purlin/config.json` at write time: `audit_llm_name` or `claude` when nothing is configured, and the literal `audit_llm` command or null. Every entry also carries `inputs.test_verifiable`, false when no test source entered the key, whether because none could be extracted for that proof or because the key is a design-cache key, which excludes test code by RULE-37 and so never opens the test file; that is how a reader tells an entry that a test edit cannot invalidate from one that it can. Without the stamp a reader cannot see that a whole gauge was produced by one unnamed tool
- RULE-40: `cache_key_for` is deterministic in the three resolved inputs and nothing else, which is what lets a reader treat a stored key that no longer recomputes as an invalidated grade rather than a cache miss: re-keying an already re-keyed batch changes no key, editing one character inside the graded test function changes the key, and editing a different test function in the same file does not
- RULE-41: `load_criteria` never grades against criteria it cannot name. A plugin root it cannot find, or a missing built-in `references/audit_criteria.md`, raises `CriteriaError` instead of returning an empty string. When `audit_criteria` is set in config, `.purlin/cache/additional_criteria.md` must exist and must begin with `<!-- purlin-criteria-sha: <sha> -->` whose sha equals `audit_criteria_pinned`; a missing cache, a missing header line or a different sha raises `CriteriaError` naming what was found and what was pinned, and `--load-criteria` prints it on stderr and exits 2. There is no silent fall back to the built-in criteria, which would grade a regulated project against the wrong standard and report a number that looks like every other number
- RULE-42: `run_scope()` is the one memoization the key resolver has. Inside one scope each spec file is read once, each feature's proof files are loaded once, and each test file is parsed once (one `ast.parse` and one line split per Python file) however many features or proofs it carries and whether the caller is the cache-key resolver or a Pass 1 check, and every function's source is sliced from that single split, never through `ast.get_source_segment`, which re-splits the whole file on every call. A key computed inside a scope is byte-identical to the key computed outside one. Outside a scope nothing is memoized, so RULE-40's edit-then-recompute contract holds for a caller that never opens one. The scope is explicit rather than keyed on file mtimes because a same-size edit inside one second, exactly what PROOF-65 performs, is invisible to a clock-resolution key, and a key that depends on the clock is not deterministic in the three inputs alone. Validating this repository's own caches went from 1333 parses of 45 files and over a minute to one parse per file and under a second
- RULE-43: A failed `os.replace` in `write_audit_cache` leaves no temporary file behind: the `<cache>.tmp` it was renaming is removed (a temp file already gone is not itself an error) and the original exception propagates to the caller unchanged, with the existing cache file byte-identical to what it was before the call. Swallowing the error would report a write that never landed, and leaving the fragment makes `.purlin/cache/` accumulate one `<cache>.tmp` per failed write, which a reader listing the directory cannot tell apart from a live cache. This covers the design cache too, since `cache_name` selects which file the same writer renames onto
- RULE-44: `analyze_test_file` dispatches from one module-level extension table — `_JS_EXTENSIONS` (`.js` `.jsx` `.mjs` `.cjs` `.ts` `.tsx`), `_C_EXTENSIONS` (`.c` `.h`), and `.py` `.sh` `.cs` `.php` `.sql` — with no fallback branch: an extension the table does not name returns `[]` rather than reaching whichever checker an if-chain happened to end on. `_TEST_CODE_EXTENSIONS` is derived from that same table minus `.sh` rather than listed again, and `_test_bodies` carries one explicit branch per language with `else: None`, so no extension can reach Pass 1 while the extractor silently hands it to the JS scanner, which is how `.mjs` and `.cjs` went unchecked and `.php`/`.sql`/`.c` were scanned for `it(...)`. Shell is the one checked language with no extractor, by design
- RULE-45: For `.php` test files, Pass 1 reads the `@purlin feature PROOF-N RULE-N` docblocks with the marker regex `scripts/proof/phpunit_purlin.php` itself uses (its `(?:public\s+)?function` form included, so the function audited is the function the plugin executed), locates each marked function's `{ ... }` body treating both `//` and `#` as line comments, and flags as `assert_true` a body containing `assertTrue(true)`, `assertFalse(false)`, `assert(true)`, `assertSame`/`assertEquals` of two identical literals, or a constant `if` guard on a `throw`. A body with no `assert*`, `expect*` or `throw` call is `no_assertions`. Comments are stripped before either check so a `// no throw = pass` note is not read as an assertion and a `// never assert(true)` note is not read as a tautology. `test_name` is the function name. Known limit, shared with C#: a test that delegates every assertion to a helper method reads as `no_assertions`
- RULE-46: For `.sql` test files, Pass 1 delimits proof blocks exactly as `scripts/proof/sql_purlin.sh` does (marker to next marker or end of file) and takes `test_name` from the block's `-- Test:` line, else the proof id. It flags as `assert_true` a block whose first `'PASS'` producer is an unconditional `SELECT 'PASS'` statement or a `CASE WHEN … THEN 'PASS'` whose predicate names no identifier outside `and or not is null in like glob between true false escape`, so `1 = 1` and `'alice' = 'alice'` are caught while `changes() = 1`, a column comparison and any subquery are not. Only the first producer is judged, because sqlite3 prints rows in statement order and the plugin reads the first line. `no_assertions` fires only when the executable block runs no `SELECT` at all
- RULE-47: For `.c` and `.h` test files, Pass 1 finds `purlin_proof(` and `purlin_proof_on(` calls, reads the balanced argument list with strings, chars and comments skipped, splits it on depth-0 commas, and keeps only calls of seven or more arguments whose first argument is this feature's name as a string literal — which is what keeps the header's own forwarding declaration and another feature's calls out. It makes exactly one check, deliberately: the fourth argument, `passed`, is `assert_true` when it is a constant expression, because the harness records whatever that argument evaluates to and a constant one cannot depend on the code under test. A variable or a call there is an assertion computed before the call and passes, and there is no no-assertion check because a C test that asserts nothing is one whose `passed` is constant. `test_name` comes from the fifth argument when it is a string literal
- RULE-48: PHP, SQL and C test code enters the cache key like Python, JS/TS and C# code: `.php` keys on the marked function's body, `.sql` on the raw block between markers, and `.c`/`.h` on the enclosing top-level `{ ... }` block, which over-invalidates every proof that block carries whenever any line in it moves — the safe direction, since a grade is recomputed rather than wrongly reused. An entry for one of these records `inputs.test_verifiable: true`, so a reader can tell it apart from a shell proof, the one checked language whose grade a test edit cannot move
- RULE-49: `deterministic_sweep(project_root)` runs both model-free passes over a whole project inside one `run_scope()`: Pass D1 (`check_proof_design`) over every proof description declared in `specs/**/*.md`, and Pass 1 over every executed backing of every proof. A backing is a `(test_file, test_name)` pair from `_proof_backings`, which collects every record across the feature's proof files and deduplicates them by `(test_file, proof_id)`, and each `(test file, feature)` pair is analysed exactly once, so a file carrying two features is still parsed once. A backing Pass 1 cannot measure is `unmeasurable` and never a failure: `no_checker` for an extension outside `_CHECKER_EXTENSIONS`, `missing_file` for a path that is not on disk (an empty `test_file`, which the xUnit logger records when the runner surfaces no source info, is first resolved through `resolve_test_file_from_name`), and `marker_not_found` for a file whose checker finds no marker for that proof. Across several backings `fail` beats `unmeasurable` beats `pass`, because a proof is only as good as its weakest backing and one hollow test among two is a defect rather than a measurement gap. An anchor under `specs/_anchors/` is swept like any other feature, its proofs having executed like any other. A proof stamped `@manual(...)` has no test to grade, so it is graded by Pass D1, appears under `design`, and is neither hollow nor unmeasurable: counting a human stamp as unmeasurable would park every manual proof in a gate's could-not-measure column forever, and counting it as measured would claim a machine checked it. The return is `{project_root, features: {name: {spec, design: {pid: {rule_id, level, check, reason}}, integrity: {pid: {rule_id, status, check, reason, test_file, test_name, backings}}}}, hollow, unprovable, unmeasurable, counts}`, where `backings` counts the proof's executed backings and `test_file`/`test_name` name the one whose verdict was taken, and the three lists are sorted by `(feature, proof_id, test_file)`. It opens nothing for writing: no cache is read or written and no runtime file is created, which is what lets a CI job recompute the same verdict from a clean checkout instead of trusting a grade somebody once stored
- RULE-50: `--deterministic-sweep [--project-root <path>]` prints `deterministic_sweep`'s JSON on stdout and exits 0, and the mode is carried in `_USAGE` and the module docstring like every other one (RULE-34). The command is read-only end to end: running it over a checkout leaves every tracked file and every file under `.purlin/` byte-identical, so a job may run it on the very tree it is about to gate without changing what it gates
- RULE-51: Inside one `run_scope()` every file is read from disk once, keyed by path. `_file_text` is that one reader and `_RunCache.texts` holds what it read: the three spec readers (`_read_rule_descriptions`, `_read_proof_descriptions`, `_read_proof_tags`) and every Pass 1 checker come through it. Those readers take a path rather than a feature, so they never reach the feature-keyed `_spec_inputs` memo and each spec was opened once per reader that wanted it: `deterministic_sweep` over this repository opened its 46 specs 184 times, and opened one test file once per feature declaring a proof in it, twelve times for `dev/test_skill_specs.py`. The memo is keyed on the path and on nothing else, never on an mtime or a size, for RULE-42's reason: a same-size edit inside one clock tick is invisible to a stat-based key and a key that depends on the clock is not deterministic in its inputs. Outside a scope nothing is memoized, so a caller that never opens one always reads what is on disk. The sweep's totals and its per-proof verdicts are unchanged; only the open count moves, from 366 to 180, one per file on disk
- RULE-52: The five brace-body checkers share one driver. `check_js`, `check_csharp`, `check_php`, `check_sql` and `check_c` are one-line wrappers over `_run_body_checks(filepath, feature_name, lang)`, and everything a language differs in sits in its row of the `_BODY_CHECKS` table: the body iterator, the strip applied before judging, the tautology predicate and the reason it returns, the assertion predicate and its reason (None for C, whose constant-`passed` check is the only check it makes), and the shaping of the test name. The five bodies had been the same shape written out five times: read the file, walk the marked bodies, fail the first one that is tautological, fail the next that asserts nothing, pass the rest, emitting the same three result dicts. The wrappers keep their names because the extension table dispatches to them and because PROOF-42 through PROOF-79 call them by name. Every reason string is byte-identical to what it was, since those proofs assert the strings themselves. A sixth brace language is a row in the table rather than a sixth copy of the shape
