# Feature: purlin_report

> Description: The board: one HTML file that shows where every rule stands.
>   It opens from disk, reads `.purlin/report-data.js`
>   beside it, and carries two screens: the board and one rule.
>   `purlin:status`, `purlin:test`, `purlin:audit` and `purlin:sign`
>   write that data file as they finish, and nothing writes it in the
>   background. It is assembled from the parts under `scripts/report/src/`
>   by `dev/build_report.py`, which inlines the design tokens so every colour on
>   the page resolves to one block and both themes ship in the same file.
> Scope: scripts/report/src/page.html, scripts/report/src/styles.css, scripts/report/src/theme.js, scripts/report/src/board.js, scripts/report/src/rule.js, scripts/report/src/app.js, scripts/report/purlin-report.html, scripts/mcp/purlin/report_data.py, dev/build_report.py
> Stack: html/css/javascript, no framework and no build-time dependency, design tokens inlined by a python assembler
> Highest-Rule: 80
> Highest-Proof: 255

## Rules

- RULE-2: The build writes one page and copies it to the project root, where the data file resolves beside it
- RULE-3: The page keeps to the design system on its own: every colour it uses is written inside the one inlined token block, it carries no shadow and no gradient, and its only affordances are the glyphs `▶`, `▼`, `▲`, `→`, `◐` and `◑`, with no icon set and no emoji
- RULE-5: The page asks nothing of anything outside itself: no stylesheet link, no style import, no fetch, and no source or link address on another host
- RULE-7: The top bar holds two boxes, one for each fact, as the payload gives them: `Tests`, reading `met` where every rule's tests pass on the committed evidence and `not met` otherwise, and `Sign-off`, reading `signed <version> at <commit>`, `signed <version>, <n> commits since` or `not signed`. The sign-off's box and its words are in the pass tone at the signed commit, the warn tone once commits have followed it, and the page's secondary text colour, no tone, where nothing is signed
- RULE-8: The boxes count the project's rules from the payload: `No proof`, wherever the project writes at least one proof line, counting the rules of the kind `no_proof`; `Passing`, counting the rules whose tests pass, with the project's rule count beneath it as `<n> RULES TOTAL`, in the pass tone once every rule passes or reads `checked at sign-off`; and `Strong`, wherever a rule has an audit entry, counting the rules it found strong, in the pass tone once every rule the audit could read that is not an anchor's is strong, its hover the audit's counts, one to a line, then `Last audit: <date>`. A count is in the pass tone once it is complete, `No proof` at zero, and the warn tone until then
- RULE-9: A column exists only where the project reaches it: `Spec`, `Rules` and `Tests` always, `Proofs` wherever the project writes at least one proof line, and `Strong` last wherever a rule has an audit entry. Each count cell names what it counts beside the number: `Proofs` the proof total, then `<k> no test`, a `@manual` proof counting as no gap; `Tests` `<passed> of <rules>`, then `<k> by hand`, `<k> partial` and `<k> failing`; a feature's `Strong` `<s> of <n>`, `<n>` the spec's rules that pass their tests and have a tested proof
- RULE-10: A spec row opens to its `> Description:` and the rules it owns and closes again on the next click, and a rule's screen carries one link, `Back to the board`, which returns to the board
- RULE-12: Both themes ship in the page and it opens dark; the theme button, `◐` named `Light theme` in the dark theme and `◑` named `Dark theme` in the light, swaps the ground, the ink and the mark to the other theme, and the theme chosen is the one the page opens in after a reload
- RULE-15: The rule screen states the rule text, the row of its passed cell and, wherever a rule has an audit entry, the row of its strong cell, each carrying that cell's word and its reasons, the passed cell's row also its platform boxes; and each proof with its `@manual`, `@slow` and `@env` tags where it carries them and the tests that carry it. A rule with no proof reads `no test` with the reason `no proof written`, except in a project that writes no proof line, where the screen shows neither its proofs nor that reason; and a rule whose evidence is older than its spec, its code or its tests reads `out of date` with the reason naming what changed
- RULE-17: A rule's screen shows where its tests ran: its passed row carries one box per operating system a counting run covered, `Win`, `Mac` or `Lin`, in the pass tone where the rule passed there and the fail tone where it failed, its hover naming the system, the result and the run's source and age, and its last run line the newest run's source and age. A rule whose proof names an operating system no counting run came from reads `not run` and names that system
- RULE-20: With no data file, or one written for another schema version, the page shows one notice naming the command that writes it, and draws no boxes and no table rather than fields it cannot read
- RULE-22: The board draws the notice that the working tree has uncommitted changes, `The working tree has uncommitted changes, so what is on this board is not what a commit would carry.`, then each warning the data carries as a notice of its own, whole, above the boxes; a rule's screen draws neither
- RULE-36: Specs stand in bands by category, each naming the category, how many specs it holds and `<passing> of <rules> rules pass`. A band counts the rules of its own specs, so the bands and the anchors' rules add up to the project's rules; the whole band folds its group with a click, Enter or Space and tells a screen reader whether it is open
- RULE-37: Every hover is a `title` attribute, so a page opened from disk needs no script to show it, and gives the detail behind its cell: the `Proofs` cell names the proofs no test runs, the `Tests` cell reads one line per operating system a counting run covered with its newest run's source, age and results, and the `Strong` cell the newest audit's source and age. A hover with nothing to show says so in one sentence
- RULE-39: Wherever a rule has an audit entry, the rule screen carries an `Audit` panel that reads what the audit found: `No audit has read this rule yet.` where it has none; otherwise `Strong. It found nothing.`, `Weak.` followed by each finding, or `Spot-checked.` followed by `The spot tests found nothing.` and each `no_bug` sentence, then the model's explanation; an entry out of date opens the panel with `Out of date:` and the cell's reasons
- RULE-41: `purlin:status`, `purlin:test`, `purlin:audit` and `purlin:sign` each write the page's data file as they finish, and nothing else writes it: an edit made with no Purlin command leaves the file's bytes and modification time as they were, and a directory with no Purlin settings file gets no data file at all
- RULE-44: In a project no audit has read, no text the page shows uses `strong` or `audit` at any casing: no box, column, hover, empty state or rule screen does, nor uses `proof` where the project writes no proof line, and a rule shows its text, its tests and one status out of `passed`, `failed`, `partial`, `no test`, `not run`, `out of date` and `checked at sign-off`
- RULE-46: On a rule's screen each proof reads its id, its words in full, its own result, `passed`, `failed`, `no test`, `not run` or `checked at sign-off`, the operating system its `@env` names, and each of its tests as `<file> :: <name>` behind a dot in the colour of the result that test's run gave it, the result's word in the dot's hover and no badge on the line; a rule with no proof shows the tests marked with its own id the same way
- RULE-47: Every spec in the payload has a row listing its own rules, its `Rules` cell reading their count. A rule is addressed by its owner and its id together, so a rule's screen opens and names the rule of that owner wherever it was clicked
- RULE-55: A rule's row on the board carries a badge for each count the boxes put it in, `PASSED` where its tests pass and `STRONG` where the audit found it strong, and `FAILED` where a test of the rule failed on any operating system; a count the rule is not in draws no badge
- RULE-63: The anchors stand in a section of their own between the boxes and the spec table, headed `Anchors` in the small capitals of the section labels, one row per anchor in the spec table's columns, row format, hovers and opening, with no band; the spec table holds no anchor. Where the project has no anchor the section is absent
- RULE-68: A rule of a spec to repair says on its screen why its tests' result does not count
- RULE-71: A `@manual` proof no test carries reads `checked at sign-off` under its tests on the rule's screen, and beneath it the note of the newest sign-off that holds one, `noted at the sign-off of <version> by <signer>, <since>: <note>`, `<since>` reading `at this commit`, `1 commit since` or `<n> commits since`, and above that note, where the rule's or the proof's wording changed since it, `the rule's wording changed since its last note` or `the proof's wording changed since its last note`
- RULE-74: An anchor's rule whose proof found nothing to check reads `passed`, and its screen's passed row carries the reason the test gave, as `<PROOF-N>: <reason>`, so a reader sees the rule was not exercised
- RULE-75: The page reads on every screen from 390 to 1500 pixels wide, in both themes, on the board and a rule's screen: the page never scrolls sideways, no count, label, box or rule id breaks onto two lines, and every text drawn, in any colour, measures at least 7:1 by the WCAG contrast formula against the ground beneath it, read through every translucent layer, in both themes, but the dark theme's fail red and accent copper, which measure at least 4.5:1

- RULE-76: Whenever a Purlin command writes the page's data file, it also writes the page itself where the project's copy differs from the plugin's, so the page and its data always come from the same version of Purlin
- RULE-77: The top bar names the checkout state its data describes and when it was written, as `<branch> at <commit>, written <hh:mm> <zone>`, as in `main at a1b2c3d, written 06:42 EDT`: the branch and the first 7 characters of the commit the writing command ran on, and the time, 24-hour, in the timezone of the person looking at the page, named by the browser's short name for it or, where it has none, by its offset, as in `GMT+5:30`. Its hover gives the date and time in full in that zone, then the UTC time, as in `2026-10-01 06:42 EDT (10:42 UTC)`. The data keeps its stamp in UTC, and the line is unchanged while the page is open
- RULE-78: Where the audit read a rule, its `Audit` panel shows the model's explanation after the findings, each sentence on its own line, whatever the audit found; then each planted bug the rule's tests missed, as `<PROOF-N>: its tests missed a bug planted at <file>:<line>.` with the lines before the bug under `Before` and the lines after it under `After`. A planted bug the tests caught is not shown
- RULE-79: The theme button stands at the right end of the top bar's first line, the line the mark is on, at every width from 390 to 1500 pixels; where the two boxes do not both fit on that line they both stand on the line below the mark, and the button stays where it is
- RULE-80: An anchor's `Strong` cell reads one word and never `<s> of <n>`, counting the anchor's rules that pass their tests and have a tested proof: `weak`, in the warn tone, where the audit found any of them weak, else `out of date` where the audit entry of any is out of date, else `spot-checked` where the audit found every one of them spot-checked, else nothing. Its hover reads `No bug is planted for an anchor's rule.` on its first line, then the newest audit's source and age
