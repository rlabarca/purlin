# Feature: purlin_report

> Description: The board: one HTML file that shows where every rule stands.
>   It opens from disk, reads `.purlin/report-data.js`
>   beside it, and carries two screens: the board and one rule.
>   `purlin:status`, `purlin:test`, `purlin:audit` and `purlin:sign`
>   write that data file as they finish, and nothing writes it in the
>   background. It is assembled from the parts under `scripts/report/src/`
>   by `dev/build_report.py`, which inlines the design tokens so every colour on
>   the page resolves to one block and both themes ship in the same file. The
>   screenshots the docs embed are captured from the same fixture payloads the
>   tests render.
> Scope: scripts/report/src/page.html, scripts/report/src/styles.css, scripts/report/src/theme.js, scripts/report/src/filters.js, scripts/report/src/board.js, scripts/report/src/rule.js, scripts/report/src/app.js, scripts/report/purlin-report.html, scripts/mcp/purlin/report_data.py, dev/build_report.py, dev/capture_doc_screenshots.py
> Stack: html/css/javascript, no framework and no build-time dependency, design tokens inlined by a python assembler

## Rules

- RULE-1: The build is a pure function of its parts: two runs over unchanged sources write the same bytes
- RULE-2: The build writes one file of at most 1200 lines and copies it to the project root, where the data file resolves beside it
- RULE-3: Every colour the page uses is written inside the one inlined token block, and no colour literal appears anywhere else in the file
- RULE-4: The page carries no shadow, no gradient and no emoji
- RULE-5: The page asks nothing of anything outside itself: no stylesheet link, no style import, no fetch, and no source or link address on another host
- RULE-6: Affordances are unicode glyphs and the page draws no icon set
- RULE-7: The board opens on the strip of boxes. The top bar states the gate as one chip, `gate: <gate>`, and how old the data is, and every spec in the payload has a row
- RULE-8: The strip above the table carries one box per step the gate reaches, `Passing` at every gate, `Strong` at `strong` and above and `Signed` at `signed`, each reading the payload's count of the rules that reached that step, in the pass tone once every rule has reached it and the warn tone until then; every label is set in capitals and every step box carries a hover. Under the boxes `Left to do` lists the payload's lines of what is left, in the payload's order, each its text and then its command, and where nothing is left the payload's last line stands in the list's place
- RULE-9: A column exists only where the gate reaches it, and the board has exactly these: `Spec`, `Rules` and `Tests` at every gate, `Proofs` between `Rules` and `Tests` at `strong` and above and at `passed` only where the project writes at least one proof line, `Strong` at `strong` and above, `Signed` at `signed`, in that order; every when, who and platform detail is in a cell's hover. Every count cell names what it counts beside the number, one labelled part per word in that word's tone: the first part is always drawn, and a later part only where it is above zero. `Proofs` reads the rollup's proof total, then the rollup's count of proofs no test runs as `<k> no test` in the warn tone, a `@manual` proof counting as no gap; `Tests` reads `<passed> of <rules>`, then `<k> partial` in the warn tone and `<k> failing` in the fail tone; `Strong` reads `<n> of <rules>`, `<n>` counting the rules whose strong cell reads `strong`, and the audit's test strength, `n/a` where nothing measured it; `Signed` reads `<n> of <rules>`, `<n>` counting the rules whose signed cell reads `signed`
- RULE-10: A spec row opens to the rules it owns and closes again on the next click
- RULE-12: Both themes ship in the page. It sets no surface override, so it opens dark on the brand navy ground, and the toggle swaps the ground, the ink and the mark to the other theme, and swaps back
- RULE-13: From `strong` up the board offers three filters, in this order: `No proof`, which accepts a rule the payload gives the kind `no_proof`; `Weak`, which accepts a strong cell reading `weak`; and `Not audited`, which accepts a strong cell reading `not audited`, so a pill counts the rules whose status is the word on it and never a rule whose strong cell reads `waiting`. Each pill carries the number of rules it accepts, counted over the rules every spec owns, and each narrows the table to those rules. At `passed` the board offers no filter
- RULE-14: Filters compose: a rule shows only where every set filter accepts it, a combination nothing matches says so in place of the table, and unsetting them restores every row
- RULE-15: The rule screen states the rule text, one row per cell the gate reaches, carrying that cell's word, its reasons, and what the word leaves out: the passed cell's platform boxes and the signed cell's signer and date, the signer named once and not again in the cell's own `by <signer>` reason; and each proof with its `@manual` and `@env` tags where it carries them and the tests that carry it. A rule with no proof reads `no test` with the reason `no proof written`, except at `passed` in a project that writes no proof line, where the screen shows neither its proofs nor that reason; and a rule whose evidence is older than its spec, its code or its tests reads `out of date` with the reason naming what changed
- RULE-16: Where the payload names a git host the page can address, the spec file, the evidence file and each signature file are links to that host at the payload's commit; where it names no remote the same paths stay plain text and nothing on the screen is a link
- RULE-17: A rule whose proof names an operating system that no counting run came from says so on its screen, naming that system, rather than reading as proved
- RULE-20: A payload written for another schema version shows one notice naming the command that rewrites it, and no tiles, no table and no tabs, rather than rendering fields it cannot read
- RULE-21: With no data file at all the page names the command that writes one
- RULE-22: The notice that the working tree has uncommitted changes belongs to the board and appears on no other screen
- RULE-23: The docs embed two screenshots, the board and one rule, each captured from a fixture payload the tests render rather than from whatever the checkout holds, and they land in `docs/images/`
- RULE-24: The tabs read Board, then the open rule, and the open rule's tab stays clickable while its screen is showing
- RULE-25: The rule screen carries one link back at its top, reading `← Board`, which closes the rule and returns to the board
- RULE-26: At the `signed` gate a rule that is not signed carries a panel headed `Hand check` where a proof of the rule is `@manual` and nobody has checked it, and `Signature` otherwise, naming the command that answers it, `purlin:sign <feature> <RULE-N>`, set in the monospace face, and saying that the page shows the signature once it is committed; a signed rule's panel names who signed it by name and email, the date and minute in UTC, the key it was made with as `the key ending ...<last 4>`, and for each operating system the machine the tests ran on. Below the `signed` gate the panel is absent
- RULE-27: Coming back to a tab whose data is more than 60 seconds old reloads the page, and the screen and the open rule survive that reload
- RULE-28: The freshness line in the top bar is a button carrying that same age text, styled as the theme button is, and pressing it reloads the page
- RULE-29: The age in the top bar recomputes every 60 seconds from the stamp the payload already carries, reading the data file zero further times
- RULE-31: The rule screen's passed cell row carries one box per operating system a counting run covered, labelled with the payload's short word for that system, `Win`, `Mac` or `Lin`, in the pass tone where the rule passed there, the fail tone where it failed and grey otherwise, each carrying as a hover the system's word, `Windows`, `macOS` or `Linux/Unix`, the result, the source of its newest run and that run's age. Its last run line reads the newest run's source and age, linked to the evidence file on the git host, or `—` where the spec has no evidence. The board draws no such box
- RULE-33: Every column heading of the spec table starts where its column's cells start in every row, so a wide cell never pushes its row's columns out of line with the headings
- RULE-34: No text the board draws is set smaller than 13 pixels, in either theme
- RULE-35: A value never breaks inside itself: a count cell such as `42 · 2 no test`, `21 of 21` or `15 (+6 shared)` is one line at every width, and each value column of the spec table is at least as wide as its widest value, the same in every row, while the spec's name is the one text cut short, with its path in the hover. Every heading and every cell starts at its column's left edge; nothing on the table is aligned right, because two bare number columns twelve pixels apart read as one number. From 1024 pixels wide up every column the gate reaches is on screen, the table scrolls sideways zero pixels and the page does too
- RULE-36: The band over each category is one row with two ends: at the left the open or closed glyph, the category's name, the strongest text in the band, and how many specs it holds in the muted colour, `6 specs` or `1 spec`, at least 16 pixels apart and with no `·` between them; at the right, at the table's right edge, `<passing> of <rules> rules pass`, `1 of 1 rule passes` for one, then a bar of one width in every band. A band counts each rule once, under the spec that owns it, so a shared rule is counted in its anchor's band and the bands add up to the project's rules. Under 1024 pixels the right end sits beneath the left, left-aligned. The whole band is the control that folds its group, pressed with a click, Enter or Space, and tells a screen reader whether it is open
- RULE-37: Every hover on the board is a `title` attribute, one item to a line and the parts of an item separated by a middot, so a page opened from disk needs no script to show it. The `Spec` cell's hover is the spec's path; the `Proofs` cell's hover names the proofs no test runs; the `Tests` cell's hover reads one line per operating system a counting run covered, newest run first, naming that system by the payload's word for it, `Windows`, `macOS` or `Linux/Unix`, then the source of its newest run, that run's age and how its rules came out; the `Strong` cell's hover names the newest audit's source and age and the minimum strength; the `Signed` cell's hover names each signer with the date of their newest signature. The `Passing`, `Strong` and `Signed` boxes carry the same three hovers read over every spec, and the `No proof` box, where it counts a rule, names each spec with how many of its rules have no proof
- RULE-39: At `strong` and above the rule screen carries an `Audit` panel that reads what the audit found: `Strong. It found nothing.`, `Weak.` or `Undecided.` with the reason the rule reads weak, then each finding on a line of its own in the sentence the audit wrote, then the test strength beside the minimum or `no mutation score measured`, then the model that read the rule and the date and minute it did; a rule no audit has read says so in place of the answer
- RULE-40: At the gate `signed` the top bar states the signed tag the payload names, its name and the first seven characters of the commit it points at, and reads `no signed tag` where the payload names none; below `signed` the top bar shows no tag at all
- RULE-41: `purlin:status`, `purlin:test`, `purlin:audit` and `purlin:sign` each write the page's data file as they finish, so the page shows what the last of them saw
- RULE-42: Nothing writes the data file in the background: an edit to a spec or to code made with no Purlin command leaves the file's bytes and its modification time as they were, and a directory with no Purlin settings file gets no data file at all
- RULE-43: A spec that names no files reads `<name> · no scope` on the board at every gate, and the hover on `no scope` gives the reason the payload carries
- RULE-44: At the gate `passed` no text the page shows, in any tab, box, column, hover, empty state or rule screen, uses a word of a higher level: none of `strong`, `signed`, `audit`, `signature` and `hand check` appears at any casing, nor `proof` where the project writes no proof line, and a rule shows its text, its tests and one status out of `passed`, `failed`, `partial`, `no test`, `not run` and `out of date`
- RULE-45: In both themes, on the board and a rule screen, every text the page draws in a neutral colour, any colour but the four state colours and the accent, measures at least 7:1 by the WCAG contrast formula against the ground it sits on, read through every translucent layer beneath it; text on a solid badge filled with a state colour is the badge's and is not held to it
- RULE-46: Under an open spec, each rule's row carries a button that opens that rule's proofs beneath the row and closes them again, reading `▶` closed and `▼` open and telling a screen reader whether it is open; every rule's proofs are closed when the page loads and when its spec is opened, and opening one rule's proofs leaves every other rule's as it was. Closed, the button reads how many proofs the rule has, `<n> proofs` or `1 proof`, in the warn tone when one of them reads `failed` or `no test`, and `no proof` where it has none; at `passed` in a project that writes no proof line it reads the tests marked with the rule's own id, `<n> tests` or `1 test`, and is absent where there are none. Open, each proof reads its id, its words in full, its own result, `passed`, `failed`, `no test`, `not run` or `hand check`, the operating system its `@env` names, and each of its tests as `<file> :: <name>` with the result that test's run gave it; a rule with no proof shows the tests marked with its own id the same way. A filter that hides a rule hides its proofs, and the rule screen draws each proof with the same words and results
- RULE-47: A spec's rows list the rules it owns. A rule a feature proves from an anchor it requires or from a global anchor is listed once, under the anchor that owns it, and still counts toward the feature: the feature's `Rules` cell reads `<own> (+<k> shared)` with a hover naming each anchor the shared rules come from and how many, `<anchor> · <k>`, and its `Proofs`, `Tests`, `Strong` and `Signed` cells count them; a spec that proves no shared rule reads its own count alone. The boxes, the filters and the bands count each rule once, under the spec that owns it. A rule is addressed by its owner and its id together, so the rule screen, its heading and its tab open and name the rule of that owner wherever it was clicked
- RULE-49: The page works on every screen from 390 to 1500 pixels wide, in both themes, on the board and a rule's screen: the page never scrolls sideways, text keeps its size, and no value breaks inside itself. Under 1024 pixels the spec table has no heading row: each spec is a block with its name on the first line and its values beneath as labelled pairs, `Rules 15 (+6 shared)`, `Proofs 42`, `Tests 21 of 21`, `Strong 0 of 12`, `Signed 0 of 12`, each pair on one line and the pairs wrapping whole; a rule in an open spec reads its id and its badges first, its words beneath at full width and its proofs control beneath them; a rule's screen and a proof beneath a rule put each label above its value. The boxes wrap as rows of equal width, four to a row under 1024 pixels and two to a row under 600; the filters and the top bar's chips wrap as whole pills and chips
- RULE-50: A cell reading `waiting` is drawn in the neutral state colour, teal, on the board and on the rule screen, and the rule screen carries its reason, `waiting for its tests to pass` for the strong cell and `waiting for the audit` for the signed cell
- RULE-51: From `strong` up a `No proof` box follows the step boxes, counting the rules the payload gives the kind `no_proof`, in the warn tone above zero and the pass tone at zero, and the `No proof` filter narrows the table to those rules
- RULE-52: A spec's `> Description:` shows beneath its row when the row is opened, above its rules, and a spec that writes none shows nothing there
- RULE-53: Each line of `Left to do` shows the command that clears it in the monospace face, and the list says each command is typed in Claude Code; nothing on the list is a control: no line carries a checkbox or a button, and pressing a line changes nothing on the page
