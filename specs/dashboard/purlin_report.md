# Feature: purlin_report

> Description: The board: one HTML file that shows where every rule stands.
>   It opens from disk, reads `.purlin/report-data.js`
>   beside it, and carries four screens: the board, one rule, the Review tab
>   and the Sign tab. It is assembled from the parts under `scripts/report/src/`
>   by `dev/build_report.py`, which inlines the design tokens so every colour on
>   the page resolves to one block and both themes ship in the same file. The
>   screenshots the docs embed are captured from the same fixture payloads the
>   tests render.
> Scope: scripts/report/src/page.html, scripts/report/src/styles.css, scripts/report/src/theme.js, scripts/report/src/filters.js, scripts/report/src/board.js, scripts/report/src/rule.js, scripts/report/src/review.js, scripts/report/src/app.js, scripts/report/purlin-report.html, dev/build_report.py, dev/capture_doc_screenshots.py
> Stack: html/css/javascript, no framework and no build-time dependency, design tokens inlined by a python assembler

## Rules

- RULE-1: The build is a pure function of its parts: two runs over unchanged sources write the same bytes [bar: passed]
- RULE-2: The build writes one file of at most 1200 lines and copies it to the project root, where the data file resolves beside it [bar: passed]
- RULE-3: Every colour the page uses is written inside the one inlined token block, and no colour literal appears anywhere else in the file [bar: strong]
- RULE-4: The page carries no shadow, no gradient and no emoji [bar: strong]
- RULE-5: The page asks nothing of anything outside itself: no stylesheet link, no style import, no fetch, and no source or link address on another host [bar: strong]
- RULE-6: Affordances are unicode glyphs and the page draws no icon set [bar: passed]
- RULE-7: The board heading's first line states how many rules pass their tests out of how many there are, then the failing count, the partial count and the untested count; its second line, in the secondary tone, reads the sentence `scripts/mcp/purlin/board.py` renders for a status table's summary, `<met> of <rules> rules meet the gate <gate>.`, word for word and with its full stop. The top bar states the gate and how old the data is, and every spec in the payload has a row [bar: strong]
- RULE-8: The strip above the table carries one tile per bucket the gate reaches, `Untested`, `Failing`, `Partial` and `Passing` at every gate, `Strong` at `strong` and `Signed` at `signed`. The three level tiles are cumulative: each counts the rules that reached its level or any level above it, added up in the page from the payload's exclusive buckets; `Untested`, `Failing` and `Partial` count their own bucket alone. Every label is set in capitals, every tile carries a hover, and at `signed` a `To sign` flag card and a `Stale` flag card sit beside the tiles, in that order [bar: strong]
- RULE-9: A column exists only where the gate reaches it: `Spec`, `Rules`, `Proofs` and `Tests` at every gate, `Strong` at `strong`, `Signable` and `Signed` at `signed`, in that order. The board carries no `Spec status` column, no `Strength` column, no `Last run` column and no grid of rules by bucket at any gate: every when, who and platform detail is in a cell's hover instead. Every count cell names what it counts beside the number, one labelled part per word in that word's tone: the first part is always drawn, and a later part only where it is above zero. `Proofs` reads the rollup's proof total, then the rollup's count of proofs no tagged test runs as `<k> without a test` in the warn tone, a `@manual` proof counting as no gap; `Tests` reads `<passed> of <rules>`, then `<k> partial` in the warn tone and `<k> failing` in the fail tone; `Strong` reads `<n> of <rules>` and the newest record's test strength, `n/a` where nothing measured it; `Signable` reads `<n> of <rules>`, the rollup's own count of the rules a signer can act on now; `Signed` reads `<n> of <rules>` [bar: strong]
- RULE-10: A spec row opens to the rules it owns and closes again on the next click [bar: passed]
- RULE-12: Both themes ship in the page. It sets no surface override, so it opens dark on the brand navy ground, and the toggle swaps the ground, the ink and the mark to the other theme, and swaps back [bar: strong]
- RULE-13: The board offers one filter per bucket it shows and one per kind of work beyond the tests, in the order the tiles and the columns read: `Untested`, `Failing` and `Partial` at every gate, `Weak` and `To review` at `strong` and above, `To sign` and `Stale` at `signed`. `Untested`, `Failing` and `Partial` accept the rules of their own bucket and read the tile's label; `Weak` accepts a strong cell reading `weak` or `not audited`, the two words the audit itself leaves; `To review` accepts a strong cell reading `manual test`, `unsettled` or `held`, the three that wait for a person; `To sign` accepts a rule the payload marks signable; `Stale` accepts a rule flagged stale. Each pill carries the number of rules it accepts, counted over the rules every spec owns, and each narrows the table to those rules [bar: strong]
- RULE-14: Filters compose: a rule shows only where every set filter accepts it, a combination nothing matches says so in place of the table, and unsetting them restores every row [bar: strong]
- RULE-15: The rule screen states the rule text, the spec status, one row per cell the gate reaches carrying that cell's word, its reasons, and what the word leaves out: the passed cell's platform boxes and the signed cell's signer and date, the signer named once and not again in the cell's own `by <signer>` reason, and each proof with its `@manual` and `@env` tags where it carries them and the test file and test name that carry the proof marker; at `strong` and above it carries a `Bar` row reading the rule's bar and where it came from, `from the tag` or `from the gate`; at `strong` and above a Brief panel gives the test strength beside the minimum, each of the audit's observations as the sentence the audit wrote, and whether the audit settled [bar: strong]
- RULE-16: Where the payload names a git host the page can address, the spec file, the record and each signature file are links to that host at the payload's commit; where it names no remote the same paths stay plain text and nothing on the screen is a link [bar: strong]
- RULE-17: A rule whose proof names an operating system that no counting record came from says so on its screen, naming that system, rather than reading as proved [bar: strong]
- RULE-18: The Review tab names how many rules need a person and groups its rows by what the strong cell reads, `manual test`, `unsettled` then `held`, with a count per group; every row carries the feature, the rule id, the rule's text cut to one line, the rule's bar, the strong cell's word as the pill the board draws, and opens the rule screen when clicked. Both tabs name their six columns in a heading row. Under the `passed` gate the Review tab is not offered at all, and under `strong` the Sign tab is not [bar: strong]
- RULE-19: An empty Review tab says what puts a rule on it instead of showing nothing [bar: passed]
- RULE-20: A payload written for another schema version shows one notice naming the command that rewrites it, and no tiles, no table and no tabs, rather than rendering fields it cannot read [bar: strong]
- RULE-21: With no data file at all the page names the command that writes one [bar: passed]
- RULE-22: The notice that the working tree has uncommitted changes belongs to the board and appears on no other screen [bar: strong]
- RULE-23: The screenshots the docs embed are captured from the fixture payloads the tests render, not from whatever the checkout holds, and land in `docs/images/` [bar: passed]
- RULE-24: The tabs read Board, then `Review (<n>)` at `strong` and above, then `Sign (<n>)` at `signed`, then the open rule last, and the open rule's tab stays clickable while its screen is showing [bar: passed]
- RULE-25: The rule screen carries one link back at its top which closes the rule and returns to the screen the rule was opened from, reading `← Review` from the Review tab, `← Sign` from the Sign tab and `← Board` from the board [bar: passed]
- RULE-26: A rule that is not signed names the command that signs it, `purlin:sign <feature> <RULE-N>`, set in the monospace face, and states that a signature is a signed commit this page can only read back; a signed rule names who signed it instead, and a rule that needs no signature says so, naming its bar and the rules this project signs. Below the `signed` gate the panel is absent [bar: passed]
- RULE-27: Coming back to a tab whose data is more than 60 seconds old reloads the page, and the screen and the open rule survive that reload [bar: passed]
- RULE-28: The freshness line in the top bar is a button carrying that same age text, styled as the theme button is, and pressing it reloads the page [bar: passed]
- RULE-29: The age in the top bar recomputes every 60 seconds from the stamp the payload already carries, reading the data file zero further times [bar: passed]
- RULE-30: A Review row states the strong cell's word and that cell's reasons as the payload writes them; where the cell carries no reason of its own, the row reads that word as a sentence instead [bar: passed]
- RULE-31: The rule screen's passed cell row carries one box per operating system a counting run covered, labelled by that system's first three letters, in the pass tone where the rule passed there, the fail tone where it failed and grey otherwise, each carrying that system's word, the source of its newest run and that run's age as a hover. Its last run line reads the newest record's source and age, linked to the file on the git host, or `—` where the spec has no record. The board draws no such box [bar: passed]
- RULE-32: At the `signed` gate the board shows two flag cards beside the six tiles: `To sign`, carrying the summary's signable count in the warn tone when it is above zero and a hover naming each spec with how many of its rules are waiting, and `Stale`, carrying the summary's stale count in the fail tone when it is above zero. The heading line names the summary's failing count as `<N> failing`. The `Signed` column states no stale count of its own; its hover carries the spec's [bar: strong]
- RULE-33: Every column heading of the spec table starts where its column's cells start in every row, so a wide cell never pushes its row's columns out of line with the headings [bar: strong]
- RULE-34: No text the board draws is set smaller than 13 pixels, in either theme [bar: strong]
- RULE-35: Every column of the spec table holds a minimum width, and under the sum of those minima the table scrolls sideways rather than squeezing a column past one, so a heading and its cells stay inside their own column at every window width. Every heading and every cell starts at its column's left edge; nothing on the table is aligned right, because two bare number columns twelve pixels apart read as one number. Those minima sum to less than a 1024-wide window gives the table, so at 1024 every column the gate reaches is on screen with no sideways scroll, and at 1280 and above every count cell holds its first two parts on one line [bar: strong]
- RULE-36: The band over each category names the category, how many specs it holds, and how many of their rules pass their tests, reading `<category> · <n> specs · <passing> of <rules> pass` with the share bar after it and `1 spec` where it holds one [bar: passed]
- RULE-37: Every hover on the board is a `title` attribute, one item to a line and the parts of an item separated by a middot, so a page opened from disk needs no script to show it. The `Spec` cell's hover is the spec's path; the `Proofs` cell's hover names the proofs no tagged test runs; the `Tests` cell's hover reads one line per operating system a counting run covered, newest run first, naming that system, the source of its newest run, that run's age and how its rules came out; the `Strong` cell's hover names the newest record's source and age and the minimum strength; the `Signable` cell's hover names those rules, or says no rule there is waiting for a signature; the `Signed` cell's hover names each signer with the date of their newest signature and then the stale count. The `Passing`, `Strong` and `Signed` tiles carry the same three hovers read over every spec, and the `Untested`, `Failing` and `Partial` tiles each say in one sentence what they count [bar: strong]
- RULE-39: The Brief panel names no check: it reads the test strength beside the minimum, then each of the audit's observations as the sentence the audit wrote, then whether the audit settled. No proof panel carries a findings row, and no free-check name is drawn anywhere on the page [bar: strong]
- RULE-40: The top bar states the signed tag the payload names, its name and the first seven characters of the commit it points at, and reads `no signed tag` where the payload names none [bar: strong]
- RULE-38: At the `signed` gate the Sign tab lists the rules the payload marks signable, naming how many there are; every row carries the feature, the rule id, the rule's text cut to one line, the rule's bar, the signed cell's word and the command `purlin:sign <feature> <RULE-N>`, and opens the rule screen when clicked. An empty Sign tab says what puts a rule on it [bar: strong]
