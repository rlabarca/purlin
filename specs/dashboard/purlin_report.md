# Feature: purlin_report

> Requires: dashboard_visual
> Scope: scripts/report/purlin-report.html
> Stack: html/css/javascript
> Description: Static HTML dashboard that renders Purlin coverage data from `.purlin/report-data.js`. Opens via `file://` in any browser with no server or build step.

## Rules

- RULE-1: HTML loads `.purlin/report-data.js` via a script tag before rendering, with a cache-busting `?t=` query, inside a throwaway same-origin iframe rather than the page's own head: the file declares a `const`, which one window cannot declare twice, and the page re-reads the file while it is open (RULE-48). The frame stays in the document until the next load replaces it, so the script that was loaded is inspectable, and `srcdoc` inherits the page's base URL and origin so the relative path resolves on `file://` exactly as it did from the head
- RULE-2: When PURLIN_DATA is undefined, dashboard shows a no-data message with instructions
- RULE-3: Summary strip shows total features, verified, passing, incomplete (partial + untested combined), failing counts from PURLIN_DATA.summary; the incomplete card shows a subtitle breakdown when both partial and untested are nonzero. When the payload reports `platform_testing`, the Verified and Passing headline numbers stay the all-platform figures and gain a sub-label instead: Verified reads `<verified_here> on host, <n> on <platform>` naming the platform binding the count when `held_by_platform` is above zero and `every declared platform` otherwise, and Passing reads `<held_by_platform> awaiting a platform` when any feature is held. Changing the headline would make a Verified count that fell because a runner has not run yet indistinguishable from a regression, and leaving the drop unlabelled would make it inexplicable
- RULE-4: Feature table renders one row per feature with name, coverage fraction, status badge, design, integrity, and verified columns. Design and Integrity are separate columns because they are separate measurements: one grades the proof description, the other the test behind it. A feature whose payload carries platform records renders a chip strip under its status badge, one chip per declared platform carrying a label and a mark for its record status, with the full record in the chip's tooltip. The strip is centered under the badge and every chip is the same shape: a minimum width so a short label does not look like a different kind of thing, a maximum width with an ellipsis so a long id cannot widen the status column, and the full id always in the tooltip. The label is the family abbreviation (`win`, `mac`, `linux`) for a bare family id; an id named after its family keeps its suffix (`windows-2022` reads `win-2022`, `macos-14` reads `mac-14`), so two ids of one family never collapse into one word; any other id is itself, an environment id included (RULE-47). No new column: seven columns of table already compete for the width, and the chips belong to the status the badge is already stating
- RULE-5: Clicking a feature row expands it to show per-rule detail
- RULE-6: Expanded detail shows each rule with id, description, source (blank for own rules, "required" or "global" for others), status, and proof column; when a rule has multiple proofs, all proofs are stacked vertically in a single cell separated by a thin divider, not split across rowspan rows
- RULE-7: Toggling dark/light mode persists the preference to localStorage
- RULE-8: Staleness indicator shows amber warning when data is older than 1 hour
- RULE-9: Staleness indicator shows red warning when data is older than 24 hours
- RULE-10: Anchor features display a type pill (anchor or global) next to their name
- RULE-11: Anchors with source_url display an external link icon with the URL as tooltip
- RULE-12: Feature table columns are sortable by clicking column headers
- RULE-13: Footer docs link uses docs_url from PURLIN_DATA, not a hardcoded URL
- RULE-14: Summary strip shows integrity percentage from audit_summary with color coding, or dash with "run purlin:audit" when null. When `platform_testing` is true the card also opens the per-platform Integrity modal, because a single project figure cannot say which platform was measured and which was not
- RULE-15: The header shows one freshness label per quality gauge, each naming its own gauge and carrying its own relative time and staleness class, sourced from `audit_summary.stale` and `design_summary.stale` independently. A single combined `audit` label is forbidden: the two caches have independent timestamps, so one label reported the Integrity cache's age as though it were the project's, and a repo graded for Design an hour ago read as 78 days stale
- RULE-16: Status column is centered in both the feature table and the expanded rules sub-table at all viewport widths
- RULE-17: Dashboard uses full available width up to 2400px and is responsive down to 1100px
- RULE-18: Coverage bar fill width matches the proved/total fraction — a feature with 2/6 coverage has a bar fill at ~33%, not 100%
- RULE-19: Features are grouped by category with collapsible section headers showing rolled-up summaries (total count, coverage fraction, and status breakdown); category coverage bar is amber when any feature is untested or coverage is incomplete, red when any feature is failing, green only when all features are passing or verified; this grouping applies independently within both the Specs and Anchors sections
- RULE-20: Category sections are expanded by default; a category renders collapsed only when localStorage explicitly records it as collapsed
- RULE-21: Category and feature open/closed state is persisted to localStorage and restored on reload
- RULE-22: Proof audit tags (STRONG/WEAK/HOLLOW) only appear when audit_summary has data; when audit_summary is null (integrity card shows dash), no audit tags render on any proof
- RULE-23: Expanded detail view shows a status-colored action banner above the rules table: PARTIAL shows how many rules need proofs, FAILING shows how many tests are failing, PASSING shows "run purlin:verify", UNTESTED shows "write tests to begin coverage", VERIFIED shows no banner of its own. When the payload's `migrations` list is non-empty the same banner area also shows a pending-migrations banner naming the count, the ids and `purlin:init --update`, in every status including VERIFIED: pending migrations are project state rather than feature state, and a feature verified against a legacy alias is verified against a reading the next release drops. It carries the same directive `sync_status` prints, so the dashboard and the CLI cannot send a reader to different commands
- RULE-24: Rules with NONE status display with an amber left border, visually distinguishing uncovered rules from proved ones
- RULE-25: Rules with FAIL status display with a red left border, visually distinguishing failing rules from passing ones
- RULE-26: Expanded detail view for anchors with source_url shows an "External Reference" info block above the rules table, displaying Source URL (as clickable link), Path (if present, in code font), and Pinned version (a hex-only git SHA truncated to its first 7 chars, a Figma ISO 8601 timestamp shown in full); unpinned anchors show amber "Unpinned" text
- RULE-27: External link icon tooltip includes Source URL, Path (if present), and Pinned value (truncated)
- RULE-28: Anchors with `ext_status` of "stale" or "unpinned" display an amber outline "STALE" badge next to the external link icon, with tooltip "Run purlin:anchor sync to update"; anchors with "current" or null ext_status show no badge
- RULE-29: When `uncommitted` array in PURLIN_DATA is non-empty, an expandable "uncommitted work" section appears between the summary strip and the feature table, showing the file count when collapsed and the file list when expanded; when the array is empty or absent, no section appears
- RULE-30: Expanded detail view shows the spec's `> Description:` content as a description block (`.desc-block`) using the full width of the detail container, positioned between the external reference block (or action banner if no external reference) and the "Rules & Proofs" header; the block is only rendered when the feature has a non-null, non-empty description
- RULE-31: Proofs whose description matches structural patterns (grep, file exists, section present, verify contains) display a green "Structural" tag (solid green background, white text) next to the proof ID; structural tags render independently of audit data and are not counted in the integrity score
- RULE-32: Anchor features render in a separate "Anchors" section below the Specs section, with its own section label and table; the Specs section contains only non-anchor features
- RULE-33: Planned proofs (proof entries with status "planned") render in the rule's proof cell greyed with a "not run" indicator, visually distinct from executed proofs and from the bare em dash shown when a rule has no proofs at all; planned proofs never show an audit tag
- RULE-34: The summary strip renders a Proof Design card beside Proof Integrity, reading `design_summary.design` with the same 80/50 colour bands and CSS classes as the integrity card, and a sub-label of per-level counts. When `design_summary` is null it shows `—`. The integrity card's null sub-label distinguishes a project where every feature is UNTESTED (`no tests yet`) from one that simply has not been audited (`run purlin:audit`)
- RULE-35: Every quality cell in the feature table renders a value, never an em dash: a percentage when the gauge is `measured`, `not audited` when it is `unmeasured`, and when it is `excluded` the word from that gauge's own vocabulary: `structural` for Proof Design, whose unscorable level is STRUCTURAL, and `excluded` for Proof Integrity, whose unscorable level is EXCLUDED. The two vocabularies never mix, so a Design cell must never read `excluded`. Each cell carries a `title` tooltip naming the reason and stating the feature's measurement coverage, and is coloured by its meaning rather than greyed out. Tokens are whole words, not abbreviations
- RULE-36: Each gauge card headlines the coverage-weighted figure rather than the assessed score, so a high score over a small measured subset cannot read as a green project-wide result, and the card's colour band follows that headline with no override. Beneath it a sub-label reads `<measured> of <total> measured`, coloured by the measured/total fraction through the same colour-band helper as the headline, so how much was measured is legible at a glance rather than dim grey text under a large number. The card's tooltip carries the per-level counts and the unweighted assessed score, because a low headline caused by thin coverage and one caused by bad proofs need different fixes. `gaugeCard` takes a fifth `attrs` argument carrying the modal attributes of RULE-42, empty for a project declaring no platform, so one helper still builds both cards and neither grows a second definition to drift from
- RULE-37: A stale or unmeasured gauge's refresh directive is carried in the `title` tooltip of that gauge's freshness label, worded `Run ` plus the command, and never in the label text, which stays `<Gauge>: <relative time>`; a fresh gauge carries no tooltip, so a tooltip being present is itself the signal that something needs running. The directive names the narrowest command that refreshes that gauge: `purlin:audit --design` when only Design needs it, `purlin:audit --integrity` when only Integrity does, and bare `purlin:audit` only when both do. Design grading is deterministic and needs no tests, while Integrity grading needs test code and costs LLM calls, so directing someone to a full audit to refresh Design alone spends budget for nothing
- RULE-38: At every breakpoint of 900px or wider, the summary strip tiles its cards into completely filled rows. A column count that leaves empty cells in the last row reads as a rendering failure rather than a layout, so the narrower desktop breakpoint spans the five status cards and the two gauge cards into two exactly-filled rows instead of wrapping seven cards into four columns. Below 900px a trailing gap is ordinary responsive wrapping and is allowed. The modal overlay is `position: fixed` outside the strip's grid, so opening it adds no grid item and the card count stays seven at every breakpoint: a dialog that tiled as an eighth card would break the exactly-filled rows this rule exists to guarantee
- RULE-39: A feature whose payload carries platform records renders a Platforms block in its expanded detail, one line per declared platform with the host first and badged, each naming the proved fraction, the failing and awaiting proof ids when there are any, and when the platform was last proved and by which runner. A feature whose records are empty but whose `awaiting_runner` list is not falls back to the tier-grouped Awaiting Runner block, which is what a payload written before platform records existed carries. Either block carries no status badge change and no red: the coverage fraction on that row already excludes those rules, so the block exists to explain an exclusion the row would otherwise make silently. A feature with neither renders no block at all
- RULE-40: The header renders a remote chip beside the two gauge-freshness labels whenever the payload's `remote_verification` is not `"off"`, and its words are the data's, not the config's: from the payload's `remote_status` (`report_data` RULE-44) it reads `Remote: none declared` when no proof declares a platform, `Remote: proved` in green when every platform proof has a result, `Remote: <n> awaiting` in amber, or `Remote: <n> failing` in red, the colours being `dashboard_visual` RULE-3's; `· required` is appended when the mode is required, because that is the one mode that changes an outcome. The chip carries `data-rv-mode` and `data-rv-state`, and its tooltip names the proved-of-declared count, the platforms holding things back, the mode, and the declaration/enforcement split: the config field declares the mode and branch protection enforces it. An `"off"` project renders no chip, so the header gains nothing for a project that never opted in. Mode and state are read from the payload and never recomputed here, for the same reason the gauges are: two surfaces computing one figure is how they come to disagree
- RULE-41: The dashboard has exactly one modal helper, `openModal(title, bodyHtml, footHtml)` with `closeModal()` and `onModalKey`, and every dialog on the page goes through it. The overlay is appended to `document.body` and never to `#app`, because `render()` rewrites `#app` wholesale and a dialog mounted inside it would be destroyed mid-interaction by any sort, expand or theme toggle; `render()` itself begins with `closeModal()`, so no dialog outlives the content it described. The dialog carries `role="dialog"` and `aria-modal="true"` and is labelled by its own heading. Escape, a click on the backdrop and the close button each close it; Tab is trapped inside it; focus moves to the close button on open and returns to the element that opened it on close; and a second open replaces the first rather than stacking two dialogs
- RULE-42: When and only when the payload reports `platform_testing`, the Verified, Passing and Proof Integrity cards, and the Failing card when some platform has a failing feature, carry `role="button"`, `tabindex="0"`, `aria-haspopup="dialog"` and a `data-modal` naming which modal they open, and open it on click and on Enter or Space. The three modals are the counts table (Platform, Features, Verified, Passing, Awaiting, Failing, Last proved), the Integrity table (Platform, Executed, Measured, Integrity, Assessed, S / W / H) and the failing table (Platform, Failing features, Proofs), each with the host row first and badged and each closed by a footer stating what the numbers above it do and do not claim. With `platform_testing` false no card carries any of those attributes and every card is inert exactly as it was before platforms existed, because a card that opens an empty table is worse than one that does not open
- RULE-43: Platform colour is colour by meaning, taken from the RULE-3 status colours of `dashboard_visual`: green for proved, amber for awaiting a runner, red for failing. The chip strip never alters the feature's status badge and carries no click handler of its own, so the row click that expands the detail keeps working; a PASSING badge held by an awaiting platform gains a tooltip naming that platform and nothing else. A badge that changed colour because a platform had not run yet would be reporting a failure that has not happened
- RULE-44: A feature whose payload entry carries `evidence_stale` true renders two things and nothing else: a `title` on its row saying the evidence is older than the code and naming `purlin:test <name>`, and one amber chip reading `stale evidence` in the status cell, carrying the same sentence as its own tooltip. The status badge keeps the class its status alone dictates, because the receipt is still true about the commit it names and a badge that changed colour would be reporting a failure that has not happened. A feature with `evidence_stale` false renders neither the title nor the chip, so a project whose evidence is current gets the row it had before the field existed
- RULE-45: The Proof Integrity card tells the reader when its number is built on grades that no longer describe anything. When `audit_summary.invalidated` is non-zero the card's sub-label tooltip carries `N grades invalidated, re-run purlin:audit` and the per-platform Integrity modal repeats it as an amber note under the table. When `audit_summary.auditors` names any auditor other than `claude`, the sub-label appends `by <names>` and the tooltip carries each auditor with its count. The default auditor is never named, because a label every project carries is one nobody reads
- RULE-46: The row the RULE-42 modals put first is the `platforms.summary` row whose id equals `platforms.host_id`, and when that row carries `host` true it is the one covering the results that name no platform. Both platform modals label it with its id, or with the words `this host` when the id is the literal `unregistered`, because `unregistered` in a Platform column reads as a broken lookup rather than as this machine. The Integrity modal reports that row's Executed column as the number of agnostic proof entries and its Integrity percentage as the figure computed over exactly those entries, and its footnote says the host row covers the results that name no platform because they ran here, beside the existing sentence that a grade describes the test and not the platform. A `host` true row is read as a platform nowhere else: the Verified card's held-by sub-label and the Failing card's clickability are both computed from the declared rows alone, because a sub-label reading `held by` the host would name the machine the report was written on, and a Failing card that opened on an agnostic failure would open a per-platform table with no row in it
- RULE-47: The dashboard names an environment as an environment wherever a platform id appears. A chip for an id whose `platforms.registry` entry reads `platform_kind` `environment` (`report_data` RULE-42) shows that id verbatim and never an OS abbreviation, followed by a `span.env-badge` reading `env` and styled as `.host-badge` is; the first column of the counts table, the Integrity table and the failing table is headed `Platform / environment`, which the modal table style renders upper case, and its cell for such an id carries the same badge after any host badge; and both the chip's `title` and that cell's `title` carry `environment: satisfied only by a hand run with PURLIN_PLATFORM=<id> on a host that has it`. An id carrying an `os` is unchanged: its chip keeps the three-letter abbreviation `win`, `mac` or `linux`, its cell carries no `env-badge`, and neither gets that sentence. A chip reading `mac` for `figma-mcp` would claim the row is about this machine's operating system, and a reader who cannot tell the two kinds apart cannot tell which gaps a runner will close from which need a person at a keyboard
- RULE-48: The page re-reads `.purlin/report-data.js` when its tab regains focus or becomes visible, and at no other time: no interval, no polling, nothing while nobody is looking. It re-renders only when the new payload's `timestamp` differs from the one rendered, so a re-read that found the same data costs nothing visible, and it leaves an open modal alone (the next focus retries). Sort column and direction, theme, expanded rows and open categories live outside `render()` and survive the reload. The 30-second tick that relabels the age text is started once, outside `render()`, and relabels only; the previous per-render timer accumulated one more copy on every sort, theme toggle and reload
- RULE-49: The header's freshness label reads `Data: <relative time>` followed by the producer in parentheses when the payload carries `generated_by` (`report_data` RULE-43): `(purlin:status)` for `sync_status`, `(pre-commit)` for the commit hook, `(auto)` for the refresh hook, and no suffix for a payload written before the field existed. `Data: none` when there is no payload. The RULE-8 and RULE-9 age bands and their `run purlin:status to refresh` hint are unchanged: with the refresh hook installed an hour without a write means an hour without a change or a session, and the hint is still the right one. The label's tooltip says the file is re-read on focus, so a reader knows why the number moved without a reload
- RULE-50: A proof the recorded run skipped on this host renders as inherited, never as an ordinary pass. In the proof cell a proof object carrying `inherited: true` (`report_data` RULE-45) draws one `span.pchip.pchip-wait` whose text is `inherited`, amber like the awaiting chip because something is missing here and it is not a failure, carrying its `inherited_reason` as the `title` and `no reason recorded` when that reason is null. A proof object with no `inherited` key draws no such chip, so the chip is evidence rather than decoration. The dashboard reads those two payload keys alone and never opens `.purlin/runtime/test_run.json`: a second reader of the marker would be a second chance to disagree with the text report about which evidence this host produced. Without the chip a green row says a rule is proved and nothing on the page says the commit that proved it was months ago on a machine that had the toolchain
