# Feature: purlin_report

> Description: The board: one HTML file that shows where every rule stands.
>   It opens from disk, reads `.purlin/report-data.js`
>   beside it, and carries three screens: the board, one rule and the Queue
>   tab. `purlin:status`, `purlin:test`, `purlin:audit` and `purlin:sign`
>   write that data file as they finish, and nothing writes it in the
>   background. It is assembled from the parts under `scripts/report/src/`
>   by `dev/build_report.py`, which inlines the design tokens so every colour on
>   the page resolves to one block and both themes ship in the same file. The
>   screenshots the docs embed are captured from the same fixture payloads the
>   tests render.
> Scope: scripts/report/src/page.html, scripts/report/src/styles.css, scripts/report/src/theme.js, scripts/report/src/filters.js, scripts/report/src/board.js, scripts/report/src/rule.js, scripts/report/src/queue.js, scripts/report/src/app.js, scripts/report/purlin-report.html, scripts/mcp/purlin/report_data.py, dev/build_report.py, dev/capture_doc_screenshots.py
> Stack: html/css/javascript, no framework and no build-time dependency, design tokens inlined by a python assembler

## Rules

- RULE-1: The build is a pure function of its parts: two runs over unchanged sources write the same bytes [level: passed]
- RULE-2: The build writes one file of at most 1200 lines and copies it to the project root, where the data file resolves beside it [level: passed]
- RULE-3: Every colour the page uses is written inside the one inlined token block, and no colour literal appears anywhere else in the file [level: passed]
- RULE-4: The page carries no shadow, no gradient and no emoji [level: passed]
- RULE-5: The page asks nothing of anything outside itself: no stylesheet link, no style import, no fetch, and no source or link address on another host [level: passed]
- RULE-6: Affordances are unicode glyphs and the page draws no icon set [level: passed]
- RULE-7: The board opens on the strip of tiles. The top bar states the gate and how many rules meet it, as `gate: <gate> · <met> of <rules>` from the payload's summary, and how old the data is, and every spec in the payload has a row [level: passed]
- RULE-8: The strip above the table carries one tile per bucket the gate reaches, `Untested`, `Failing`, `Partial` and `Passing` at every gate, `Strong` at `strong` and `Signed` at `signed`. The three level tiles are cumulative: each counts the rules that reached its level or any level above it, added up in the page from the payload's exclusive buckets; `Untested`, `Failing` and `Partial` count their own bucket alone. Every label is set in capitals, every tile carries a hover, and at `signed` a `Queue` flag card and a `Stale` flag card sit beside the tiles, in that order [level: passed]
- RULE-9: A column exists only where the gate reaches it, and the board has exactly these: `Spec`, `Rules` and `Tests` at every gate, `Proofs` between `Rules` and `Tests` at `strong` and above and at `passed` only where the project writes at least one proof line, `Strong` at `strong` and above, `Signed` at `signed`, in that order; every when, who and platform detail is in a cell's hover. Every count cell names what it counts beside the number, one labelled part per word in that word's tone: the first part is always drawn, and a later part only where it is above zero. `Proofs` reads the rollup's proof total, then the rollup's count of proofs no test runs as `<k> without a test` in the warn tone, a `@manual` proof counting as no gap; `Tests` reads `<passed> of <rules>`, then `<k> partial` in the warn tone and `<k> failing` in the fail tone; `Strong` reads `<n> of <rules>` and the audit's test strength, `n/a` where nothing measured it; `Signed` reads `<n> of <rules>` [level: passed]
- RULE-10: A spec row opens to the rules it owns and closes again on the next click [level: passed]
- RULE-12: Both themes ship in the page. It sets no surface override, so it opens dark on the brand navy ground, and the toggle swaps the ground, the ink and the mark to the other theme, and swaps back [level: passed]
- RULE-13: The board offers one filter per bucket it shows and one per kind of work beyond the tests, in the order the tiles and the columns read: `Untested`, `Failing` and `Partial` at every gate, `Weak` and `Queue` at `strong` and above, `Stale` at `signed`. `Untested`, `Failing` and `Partial` accept the rules of their own bucket and read the tile's label; `Weak` accepts a strong cell reading `weak` or `not audited`, the two words the audit itself leaves; `Queue` accepts a rule the payload's queue names, the rules that wait for a person; `Stale` accepts a rule flagged stale. Each pill carries the number of rules it accepts, counted over the rules every spec owns, and each narrows the table to those rules [level: passed]
- RULE-14: Filters compose: a rule shows only where every set filter accepts it, a combination nothing matches says so in place of the table, and unsetting them restores every row [level: passed]
- RULE-15: The rule screen states the rule text, one row per cell the gate reaches carrying that cell's word, its reasons, and what the word leaves out: the passed cell's platform boxes and the signed cell's signer and date, the signer named once and not again in the cell's own `by <signer>` reason; and each proof with its `@manual` and `@env` tags where it carries them and the tests that carry it. A rule with no proof reads `no test` with the reason `no proof written`, except at `passed` in a project that writes no proof line, where the screen shows neither its proofs nor that reason; and a rule whose evidence is older than its spec, its code or its tests reads `out of date` with the reason naming what changed. At `strong` and above a `Level` row reads the rule's level and where it came from, `<level> (marked)`, `<level> (the gate)` or `<level> (marked <mark>; the gate is the ceiling)` [level: passed]
- RULE-16: Where the payload names a git host the page can address, the spec file, the evidence file and each signature file are links to that host at the payload's commit; where it names no remote the same paths stay plain text and nothing on the screen is a link [level: passed]
- RULE-17: A rule whose proof names an operating system that no counting run came from says so on its screen, naming that system, rather than reading as proved [level: passed]
- RULE-18: The Queue tab names how many rules need a person, with the subline `Hand checks <h> · Signatures <s>`, and lists the payload's queue in its own order; every row carries the feature, the rule id, the rule's text cut to one line, the rule's level, what it needs and the command that answers it, and opens the rule screen when clicked. The tab names its six columns in a heading row. Under the `passed` gate the Queue tab is not offered at all [level: passed]
- RULE-19: An empty Queue tab says what puts a rule on it at the project's gate: at `strong`, a rule whose level is `strong` and whose proof is `@manual`; at `signed`, that or a rule whose level is `signed` and that has passed its tests and its audit [level: passed]
- RULE-20: A payload written for another schema version shows one notice naming the command that rewrites it, and no tiles, no table and no tabs, rather than rendering fields it cannot read [level: passed]
- RULE-21: With no data file at all the page names the command that writes one [level: passed]
- RULE-22: The notice that the working tree has uncommitted changes belongs to the board and appears on no other screen [level: passed]
- RULE-23: The docs embed three screenshots, the board, the Queue tab and one rule, each captured from a fixture payload the tests render rather than from whatever the checkout holds, and they land in `docs/images/` [level: passed]
- RULE-24: The tabs read Board, then `Queue (<n>)` at `strong` and above, then the open rule last, and the open rule's tab stays clickable while its screen is showing [level: passed]
- RULE-25: The rule screen carries one link back at its top which closes the rule and returns to the screen the rule was opened from, reading `← Queue` from the Queue tab and `← Board` from the board [level: passed]
- RULE-26: At the `signed` gate a rule that is not signed carries a panel headed with what the queue calls its need, `Hand check` or `Signature`, naming the command that answers it set in the monospace face, `purlin:sign <feature> <RULE-N>` with `--note "<what you saw>"` for a hand check, and stating that a signature is a signed commit this page can only read back; a signed rule's panel names who signed it, the date and minute in UTC, and the machine and the operating system it was signed on; a rule whose level is below `signed` says it asks for no signature, naming its level. Below the `signed` gate the panel is absent [level: passed]
- RULE-27: Coming back to a tab whose data is more than 60 seconds old reloads the page, and the screen and the open rule survive that reload [level: passed]
- RULE-28: The freshness line in the top bar is a button carrying that same age text, styled as the theme button is, and pressing it reloads the page [level: passed]

- RULE-30: A Queue row states the rule's level, what it needs, `hand check` or `signature`, with the queue row's word and reasons in that cell's hover, and the command the row carries [level: passed]
- RULE-31: The rule screen's passed cell row carries one box per operating system a counting run covered, labelled by that system's first three letters, in the pass tone where the rule passed there, the fail tone where it failed and grey otherwise, each carrying that system's word, the source of its newest run and that run's age as a hover. Its last run line reads the newest run's source and age, linked to the evidence file on the git host, or `—` where the spec has no evidence. The board draws no such box [level: passed]
- RULE-32: At the `signed` gate the board shows two flag cards beside the six tiles: `Queue`, carrying the summary's queue count in the warn tone when it is above zero and a hover naming each spec with how many of its rules are waiting, and `Stale`, carrying the summary's stale count in the fail tone when it is above zero. The `Signed` column states no stale count of its own; its hover carries the spec's [level: passed]
- RULE-33: Every column heading of the spec table starts where its column's cells start in every row, so a wide cell never pushes its row's columns out of line with the headings [level: passed]
- RULE-34: No text the board draws is set smaller than 13 pixels, in either theme [level: passed]
- RULE-35: Every column of the spec table holds a minimum width, and under the sum of those minima the table scrolls sideways rather than squeezing a column past one, so a heading and its cells stay inside their own column at every window width. Every heading and every cell starts at its column's left edge; nothing on the table is aligned right, because two bare number columns twelve pixels apart read as one number. Those minima sum to less than a 1024-wide window gives the table, so at 1024 every column the gate reaches is on screen with no sideways scroll, and at 1280 and above every count cell holds its first two parts on one line [level: passed]
- RULE-36: The band over each category names the category, how many specs it holds, and how many of their rules pass their tests, reading `<category> · <n> specs · <passing> of <rules> pass` with the share bar after it and `1 spec` where it holds one [level: passed]
- RULE-37: Every hover on the board is a `title` attribute, one item to a line and the parts of an item separated by a middot, so a page opened from disk needs no script to show it. The `Spec` cell's hover is the spec's path; the `Proofs` cell's hover names the proofs no test runs; the `Tests` cell's hover reads one line per operating system a counting run covered, newest run first, naming that system, the source of its newest run, that run's age and how its rules came out; the `Strong` cell's hover names the newest audit's source and age and the minimum strength; the `Signed` cell's hover names each signer with the date of their newest signature and then the stale count. The `Passing`, `Strong` and `Signed` tiles carry the same three hovers read over every spec, and the `Untested`, `Failing` and `Partial` tiles each say in one sentence what they count [level: passed]
- RULE-39: At `strong` and above the rule screen carries an `Audit` panel that reads what the audit found: `Strong. It found nothing.`, `Weak.` or `Undecided.` with the reason the rule reads weak, then each finding on a line of its own in the sentence the audit wrote, then the test strength beside the minimum or `no mutation score measured`, then the model that read the rule and the date and minute it did; a rule no audit has read says so in place of the answer [level: passed]
- RULE-40: At the gate `signed` the top bar states the signed tag the payload names, its name and the first seven characters of the commit it points at, and reads `no signed tag` where the payload names none; below `signed` the top bar shows no tag at all [level: passed]
- RULE-41: `purlin:status`, `purlin:test`, `purlin:audit` and `purlin:sign` each write the page's data file as they finish, so the page shows what the last of them saw [level: passed]
- RULE-42: Nothing writes the data file in the background: an edit to a spec or to code made with no Purlin command leaves the file's bytes and its modification time as they were, and a directory with no Purlin settings file gets no data file at all [level: passed]
- RULE-43: A spec that names no files reads `<name> · no scope` on the board at every gate, and the hover on `no scope` gives the reason the payload carries [level: passed]
- RULE-44: At the gate `passed` no text the page shows, in any tab, tile, column, filter, hover, empty state or rule screen, uses a word of a higher level: none of `strong`, `signed`, `audit`, `queue`, `signature`, `level` and `hand check` appears at any casing, nor `proof` where the project writes no proof line, and a rule shows its text, its tests and one status out of `passed`, `failed`, `partial`, `no test`, `not run` and `out of date` [level: passed]
