# Feature: pre_push_hook

> Requires: security_no_dangerous_patterns
> Scope: scripts/hooks/pre-push.sh, scripts/hooks/pre_push_gate.py
> Stack: shell/bash, python3 (status payload, config parsing)
> Description: Pre-push git hook that blocks pushes when the evidence does not support them. The shell half runs the unit-tier tests and resolves paths; `pre_push_gate.py` reads the structured status payload and decides. Three modes: warn (default) blocks only on FAILING, strict blocks anything not VERIFIED, off disables the hook.

## Rules

- RULE-1: Blocks push with exit 1 when any feature has status FAILING in sync_status output
- RULE-2: Allows push with exit 0 and prints a warning when any feature is PARTIAL (some behavioral rules proved, none failing)
- RULE-3: Allows push with exit 0 silently when no specs directory exists or specs directory contains no .md files
- RULE-4: Allows push with exit 0 when all features are PASSING or VERIFIED (all behavioral rules proved, no failures)
- RULE-5: Reads `test_framework` from `.purlin/config.json` as a comma-separated list: split, trimmed, deduplicated, order preserved. `auto` expands in place to every framework detected in `references/supported_frameworks.md` detection order (pytest, vitest, jest, c, php, sql, and shell when nothing else matches). The names the gate accepts are `KNOWN_FRAMEWORKS` in `scripts/hooks/pre_push_gate.py`, and that tuple equals the id set of the framework registry `references/supported_frameworks.md`, taken over both of its plugin tables, where a framework's id is the first word of its **Display name** cell: pytest, vitest, jest, c, php, sql, shell and xunit. A name outside that set is named on stderr and dropped; a registered name the shell half has no runner arm for (c, php, sql, xunit) is kept and reported as unrun rather than dropped
- RULE-6: Runs only unit-tier tests, one runner arm per resolved framework with no `|| true` on any arm: pytest with `-m "not integration and not e2e"` where exit code 5 (nothing collected) counts as success, jest with `--testPathPattern=unit --passWithNoTests`, vitest with `run --passWithNoTests`, shell with `*.test.sh`. The pytest expression names both slow tiers and selects anything at all only because proof_plugins_pytest RULE-5 adds each proof marker's tier to its test as a pytest marker; before that rule the arm called itself unit-tier and ran every tier in the project. Any other non-zero exit from a runner blocks the push in both warn and strict mode, naming the runner and its exit code
- RULE-7: Produces output showing which features passed, which have partial coverage, and which are blocked with FAIL proofs
- RULE-8: In strict mode (`"pre_push": "strict"` in config), blocks push with exit 1 when any non-anchor feature is not VERIFIED, which includes PASSING features (full coverage but no receipt) and PARTIAL features (incomplete behavioral rule coverage); allows push only when every non-anchor feature is VERIFIED. A proof declared `@on(<platform>)` with no result on that platform is reported as one advisory line and never blocks, in either mode. That extends to the feature it holds: a non-anchor feature reading PASSING only because a declared platform has no result there, while its receipt is current, is listed with its reason and is not blocked, because a gate that refused it would be blocking on the awaiting platform by another route
- RULE-9: After `purlin:init`, the hook git runs is a three-line delegator in the repository's hooks directory that `exec`s `.purlin/hooks/pre-push`, the tracked shim, which `exec`s the installed plugin's `scripts/hooks/pre-push.sh` (`skill_init` RULE-67 and RULE-77). Every file in that chain exists and is executable, and a push carrying a FAIL proof is blocked through the whole of it. Nothing in the chain is a symlink into the plugin, because the only path a plugin install can offer is version-pinned and dangles on the next update
- RULE-10: The verdict is computed by `scripts/hooks/pre_push_gate.py` from `purlin_server.read_report_payload`, never from the rendered summary table. Neither hook file contains a box-drawing character (U+2500 to U+257F) and the shell half matches no status word, so no change to the table's columns or glyphs can change what a push is allowed to do
- RULE-11: With `"pre_push": "off"` the hook prints exactly one line naming the mode and exits 0, running no test runner and reading no proof file
- RULE-12: A `pre_push` value that is not warn, strict or off blocks the push with exit 1 and a message naming the offending value together with all three valid modes, rather than falling back to warn
- RULE-13: Specs are discovered recursively under the spec directory with no depth limit, so a spec nested at any depth is checked
- RULE-14: The plugin root is the directory this script was run out of, `$(cd "$(dirname "$0")/../.." && pwd)`, and nothing here searches for it. The shim at `.purlin/hooks/pre-push` resolved it and exec'd this script out of it (`skill_init` RULE-77), so the script is inside the plugin by construction, and a second resolution order in a second file is a second answer the day one of them is edited. The shim steps over a candidate carrying no `scripts/hooks/pre-push.sh` rather than ending the search, and when no candidate carries it, it keeps this hook's own contract without reaching this file: it prints a WARNING naming every path it searched, then exits 0 in `warn` and `off` and 1 in any other mode, blocking rather than passing a push it could not check
- RULE-15: No command in the hook has its stderr redirected to `/dev/null`. Only the gate's stdout is captured, for its `mode=` and `frameworks=` lines, so every diagnostic the gate writes reaches the developer running `git push`
- RULE-16: Feature names are matched whole, never by substring, so a feature whose whole name occurs inside another feature's name still gets its own `purlin:test <feature>` recovery line
- RULE-17: Every Python this hook starts is the one `scripts/purlin_python.sh` resolved, run as `"$PURLIN_PY"`, and `scripts/hooks/pre-push.sh` names no interpreter in command position: the resolver is sourced out of the plugin root the shim exec'd this script from, and its order (`$PURLIN_PYTHON`, `python3`, `python` at major version 3, `py -3`) is the same order the MCP launcher and the pre-commit hook get. When it finds none, the resolver names all four on stderr, the hook says the coverage check did not run, and it exits 0 in `warn` and `off` and 1 in `strict`, the same division RULE-14 gives the shim and for the same reason: those two modes would have let this push through anyway, and a check that could not run is not a pass. Strict is read from the config text by a single grep for that one mode rather than by a second parser, because the gate that owns config reading is the thing that needs the missing interpreter. The same holds of every other place a consumer's Purlin starts a Python process: `scripts/hooks/pre-commit.sh`, both shims `scripts/init/scaffold.py` generates, `hooks/hooks.json` and `.claude-plugin/plugin.json` name no interpreter in command position either, since one entry point fixed and the rest left is the same outage moved
