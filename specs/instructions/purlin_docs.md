# Feature: purlin_docs

> Requires: schema_spec_format
> Scope: docs/index.md, docs/lifecycle-guide.md, docs/testing-workflow-guide.md, docs/installation-guide.md, docs/collaboration-guide.md, docs/dashboard-guide.md, docs/regulated-environments.md, docs/anchors-guide.md, docs/spec-from-code-guide.md, docs/examples/figma-web-app.md, docs/images, README.md, references/hard_gates.md, references/remote_verification.md, assets/src, .gitignore
> Stack: markdown (user-facing documentation)
> Description: The user-facing documentation set, held to what the code actually does. Three classes of defect had accumulated and none of them was visible to any existing proof: prose that promised cryptographic properties the framework has never had, an enforcement model told three different ways in three files, and CI examples that no runner could execute. The rules here are grep-shaped on purpose. They cannot judge whether a guide is well written; they can keep it from claiming something untrue, from carrying a second copy of a model that then drifts, and from shipping a workflow example that is not a workflow.

## Rules

- RULE-1: FORBIDDEN: the strings `signed verification`, `tamper-evident`, `The vhash proves`, `(signed off)` and `signed off` do not appear in any git-tracked file under `docs/`, `references/`, `skills/`, `tools/` or `agents/`, or in `README.md`. The only permitted occurrences are inside `docs/regulated-environments.md`'s "What Purlin Is NOT" list, where each is a negation stating that Purlin does not do the thing. Nothing Purlin writes is signed and nothing it writes is tamper-evident, so prose that says otherwise is a claim the mechanism cannot support. Separately, the bare tag token `@windows` (not the `@windows-<id>` of a platform id and not a `...@windows.json` filename) appears only in a paragraph that also names it as legacy or shows its `@unit @on(...)` rewrite: `windows` is a platform, never a tier, and a reader who meets the token with no such paragraph around it will write it as one. `RELEASE_NOTES.md` and `dev/plans/` are historical records of what was once true and are out of scope
- RULE-2: `docs/regulated-environments.md` states what the receipt hash binds and what it does not, in two sections headed "What the vhash binds" and "What it does not bind". The first names every version 2 segment: the rule text, the feature, the proof id, the rule, the status, the tier, the platform, the test file, the test name, and the manual stamps. The second names the five things it cannot reach: the content of the test code, who ran it, when it ran, that the test is meaningful, and the runner's honesty. The file names no `.test-lock.json`, because no such file exists in the framework or is read by it; it describes `audit_llm` as executable configuration the compliance team pins rather than as a label; it describes the criteria pin as a check that is enforced on every audit rather than as a plan; and it carries the sentence `Pass D1 is deterministic; Pass D2 is an LLM pass`, which `references/remote_verification.md` states the same way. A compliance reader takes "deterministic" as a property they can rely on, so saying it of the whole of Proof Design overstates by exactly one pass
- RULE-3: `docs/index.md` is the entry point and carries four things a reader arriving cold needs: a Guides table row linking remote verification and platforms, a Guides table row linking the hard-gates reference, a summary line naming the enforcement layers and pointing at that one reference, both gauge names (`Proof Design` and `Proof Integrity`) inside the key-skills list, and `purlin:init --update` named as the command that migrates a project after the plugin moves under it. An index that omits a subsystem is how a reader concludes the subsystem does not exist
- RULE-4: Exactly one enforcement-layer table exists in the repository, in `references/hard_gates.md` under a `## Enforcement Layers` heading, and it is reached by counting table rows whose first cell is a bold `Layer` or `Not a layer` label. That heading is not a `## Gate N` heading, so the one-gate count of `purlin_references` RULE-6 is unaffected. The table has a row for Layer 0 (skill logic, the one gate), Layer 1 (the pre-push hook, its three modes and the plugin-resolution caveat), Layer 2 (the project's own CI test run), Layer 3 (`scripts/ci/verify_gate.py --check` made required by branch protection, with `remote_verification` named as the declaration rather than the enforcement) and a row stating that `purlin:verify --recheck` is not a layer. `docs/regulated-environments.md`, `docs/lifecycle-guide.md` and `docs/testing-workflow-guide.md` each keep at most two sentences on the subject and a link to that reference. Three copies is how the repository came to say the hook has two modes in one file and three in another
- RULE-5: FORBIDDEN: no fenced `yaml` block under `docs/` contains `run: purlin:` or `on: deploy`. A workflow cannot invoke a Claude Code skill and `deploy` is not a GitHub Actions event, so such a block is an example that fails on first paste. Every fenced `yaml` block under `docs/` that runs the verification gate runs a real test command first, then `python3 "$PURLIN_PLUGIN_ROOT/scripts/ci/verify_gate.py" --check`, and its job checks out with `fetch-depth: 0` and installs the tooling by cloning the plugin at a pinned tag. The test command is what regenerates the proof files, so without it the gate re-reads what the developer committed instead of what the code proves; `fetch-depth: 0` is what gives the gate the `git log` history it reads per proof file
- RULE-6: Every `assets/lifecycle-*.svg` has a Mermaid source of the same stem under `assets/src/`, and `.gitignore` carries a `!assets/src/*.mmd` negation after its `*.mmd` line so those sources stay tracked. `assets/purlin-logo.svg` is hand-authored, has no Mermaid source and is exempt by name. The SVG node positions and edge paths are computed by Mermaid's layout engine and are not hand-editable, so an SVG with no source is a diagram nobody can change
- RULE-7: The three dashboard screenshots `docs/images/dashboard-summary.png`, `docs/images/dashboard-categories.png` and `docs/images/dashboard-platforms.png` exist on disk, are non-empty, and each is referenced by at least one markdown file under `docs/`. An image nothing references is one nobody notices going stale, and a reference to an image that is not there renders as a broken box
