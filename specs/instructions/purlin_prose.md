# Feature: purlin_prose

> Requires: schema_spec_format
> Scope: dev/prose_lint.py, docs/*.md, docs/examples/*.md, docs/images, README.md, references/*.md, references/formats/*.md, skills/*/SKILL.md, agents/*.md, tools/*/*.md, .claude-plugin/plugin.json, .claude-plugin/marketplace.json, assets/src, .gitignore
> Stack: markdown (user-facing documentation), python (dev/prose_lint.py)
> Description: The repository's prose, held to what the code actually does, by one module rather than by a hand-written list per defect. `dev/prose_lint.py` carries five lints and their tables. Four are stated here: `banned_strings` (a string this repository forbids, with the sections that may still carry it), `paths_exist` (a backticked path that resolves, and a skill flag that its `## Usage` block declares), `structure` (the shape a skill or agent definition must have) and `single_home` (a subject documented in exactly one file). The fifth, `banned_paths`, is stated by the two specs that own the surfaces it reads, `purlin_skills` RULE-19 and `purlin_references` RULE-35. Each table states the file set it covers today, so widening a lint is an edit to a row and to the rule that names the set, never a new rule and never a second module. The remaining rules are grep-shaped on purpose: they cannot judge whether a guide is well written; they can keep it from claiming something untrue, from carrying a second copy of a model that then drifts, and from shipping a workflow example that is not a workflow. RULE-1, RULE-4, RULE-10 and RULE-11 were hand-written lists of exactly these four shapes and retired into the tables; their numbers stay vacant.

## Rules

- RULE-2: `docs/regulated-environments.md` states what the receipt hash binds and what it does not, in two sections headed "What the vhash binds" and "What it does not bind". The first names every version 2 segment: the rule text, the feature, the proof id, the rule, the status, the tier, the platform, the test file, the test name, and the manual stamps. The second names the five things it cannot reach: the content of the test code, who ran it, when it ran, that the test is meaningful, and the runner's honesty. The file names no `.test-lock.json`, because no such file exists in the framework or is read by it; it describes `audit_llm` as executable configuration the compliance team pins rather than as a label; it describes the criteria pin as a check that is enforced on every audit rather than as a plan; and it carries the sentence `Pass D1 is deterministic; Pass D2 is an LLM pass`, which `references/remote_verification.md` states the same way. A compliance reader takes "deterministic" as a property they can rely on, so saying it of the whole of Proof Design overstates by exactly one pass
- RULE-3: `docs/index.md` is the entry point and carries four things a reader arriving cold needs: a Guides table row linking remote verification and platforms, a Guides table row linking the hard-gates reference, a summary line naming the enforcement layers and pointing at that one reference, both gauge names (`Proof Design` and `Proof Integrity`) inside the key-skills list, and `purlin:init --update` named as the command that migrates a project after the plugin moves under it. An index that omits a subsystem is how a reader concludes the subsystem does not exist
- RULE-5: FORBIDDEN: no fenced `yaml` block under `docs/` contains `run: purlin:` or `on: deploy`. A workflow cannot invoke a Claude Code skill and `deploy` is not a GitHub Actions event, so such a block is an example that fails on first paste. The same holds one fence down: no fenced `bash` block under `docs/` contains a line whose first token begins `purlin:`, because a skill is no more a shell command than it is a workflow step, and a reader who pastes such a block into a script or a CI step gets `command not found` with no clue that the line was never meant for a shell. A skill call belongs in the prose beside the block, naming the session it runs in. At least one fenced `bash` block under `docs/` is scanned, so that sweep cannot pass by finding none. Every fenced `yaml` block under `docs/` that runs the verification gate runs a real test command first, then `python3 "$PURLIN_PLUGIN_ROOT/scripts/ci/verify_gate.py" --check`, and its job checks out with `fetch-depth: 0` and installs the tooling by cloning the plugin at a pinned tag. The test command is what regenerates the proof files, so without it the gate re-reads what the developer committed instead of what the code proves; `fetch-depth: 0` is what gives the gate the `git log` history it reads per proof file. Separately, no trigger `paths:` filter in any fenced `yaml` block under `docs/` names a path under `scripts/`: a consumer checkout holds specs, proofs, receipts and `.purlin/` and no Purlin `scripts/`, so a filter copied from this repository's own gate job would skip the run a spec or config change should have triggered, and the workflow would look configured while never firing. At least one such block carries a filter, so the requirement is read from a real example rather than from none

- RULE-9: Every `##` section of `docs/regulated-environments.md` names at least one mechanism a reader can act on. A mechanism name is one of five fixed shapes: a script path under `scripts/`, written in backticks; a rule id, written as a backticked spec or feature name immediately followed by `RULE-N`; a config field, backticked, from the closed set `audit_llm`, `audit_llm_name`, `audit_criteria`, `audit_criteria_pinned`, `mutation_checks`, `platforms`, `remote_verification`, `quality_gate`, `pre_push`, `digest`, `report`, `test_framework`, `version` and `skipped_proofs`; a skill command, backticked, of the form `purlin:<name>` with any flags; or a format or spec file path under `references/` or `specs/`, backticked. - RULE-12: `dev/prose_lint.py`'s `banned_strings` table is the one home of every string this repository forbids in its own prose. A row is `(name, unit, pattern, scope, min_files, allowlist, note)`. The pattern is searched a line at a time or a paragraph at a time, never inside a fenced code block where the text may be quoted output; a `.json` file in scope is searched in its decoded `description` values rather than in its raw bytes, because the plugin manifests carry their dashes as `\u2014` escapes and a byte sweep reads them as clean; the scope must resolve to at least `min_files` files, so no row can pass by scanning nothing; and every `(path, section)` pair in the allowlist both exempts a hit there and must itself still be hit, so an exemption that outlives the text it covers fails as loudly as a new occurrence. Nine rows are enforced today. `em-dash`: U+2014 and U+2013 over `docs/**.md`, `README.md`, `references/remote_verification.md`, `references/spec_quality_guide.md`, `references/hard_gates.md`, `references/audit_criteria.md`, `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `skills/**.md`, `agents/**.md`, `references/**.md`, `tools/**.md`, `CLAUDE.md` and `specs/**.md`, because a dash of either kind is a joint the writer did not have to name: the sentence it produces carries two ideas and no stated relation, and a colon, a comma or a full stop always states one. Its allowlist holds three pairs of sections, and every one of them is a quotation of something a program emits or parses rather than prose. `skills/spec/SKILL.md`'s `Step 5: Rule Extraction Heuristics` and `references/formats/spec_format.md`'s `Rule Tags` spell the `(assumed - <context>)` rule tag, which `scripts/mcp/purlin_server.py` matches with an em dash. `specs/mcp/sync_status.md`'s `Rules` and `Proof` quote the anchor header line the same file prints, character for character, which is what makes RULE-67 and PROOF-106 checkable at all. `specs/skills/skill_init.md`'s `Rules` and `Proof` are the one exemption that is not a literal: the file is held by the lane landing the hook and `--update` work, its five dashes are a follow-up, and naming it here is what let `specs/**.md` be widened without waiting. Retiring the two separators is an edit to `scripts/`, and the third exemption goes when that lane lands; each pair fails the day its text changes. `em-dash-comment`: the same two characters over the comment lines of `scripts/**` in the nine languages `COMMENT_LINE_MARKERS` and `COMMENT_BLOCK_MARKERS` cover, because a comment is prose written next to code and drifts the same way. Only comment lines are read: a whole-line `#`, `//` or `--` comment, and everything from a `/*` or `<!--` opener to its closer. A string literal is never read, so what a program prints stays the program's own business, which is why the box-drawn separator rules of `scripts/mcp/purlin_server.py` are untouched by this row. `promise`: `signed verification`, `tamper-evident`, `The vhash proves`, `(signed off)` and `signed off` over `docs/`, `references/`, `skills/`, `tools/`, `agents/` and `README.md`, allowed only in `docs/regulated-environments.md`'s "What Purlin Is NOT" section, because nothing Purlin writes is signed and nothing it writes is tamper-evident. `windows-tier`: the bare token `@windows` (not the `@windows-<id>` of a platform id and not a `...@windows.json` filename) over the same set, allowed only in the nine sections of the migration documentation that state the one-release legacy alias and its `@unit @on(<platform-id>)` rewrite, because `windows` is a platform and never a tier, and a reader who meets the token outside a section about the migration will write it as one; the word `legacy` in the same paragraph exempts nothing. `approval`: `compliance status`, `sign-off`, `signs off` and `certified` in `docs/regulated-environments.md`, because they are approval vocabulary for something Purlin never does. `retired-format`: the literal `3-section format`, and a heading line at any depth whose whole text is `What it does`, over every prose tree, `docs/**`, `references/**`, `skills/**`, `tools/**`, `agents/**` and `README.md`, because a spec and an anchor carry two sections and the third retired from both format contracts; the heading arm is anchored at both ends so `#### What it does not bind`, a live heading of `docs/regulated-environments.md` that RULE-2 requires, is not read as the retired section. `anchor-home`: `specs/schema/` in any form and the bare category token `` `schema/` `` over `docs/**`, `references/**`, `skills/**` and `agents/**`, because `sync_status` reads anchors from `specs/_anchors/` and from no other directory, so a routing list that sends a cross-cutting contract to a `schema/` category writes the spec to a path nothing loads; `skills/` is inside this row's tuple although the older rows stop short of it, because the two skills that pick a category for a new spec are where the wrong home is chosen. `slash-prefix`: the literal `/purlin:` over `docs/**`, `references/**`, `skills/**`, `agents/**`, `specs/**.md` and the two hook scripts `scripts/hooks/pre_push_gate.py` and `scripts/hooks/pre-push.sh`, because a skill is invoked as `purlin:<name>` everywhere except the pages and the recovery messages that wrote it with a leading slash, and a reader who copies one spelling from a guide and the other from a hook cannot tell which one works. The `## Rules` section of this file is the row's one allowlisted section, because the rule that states a banned literal has to quote it; the allowlist half of RULE-12 makes that exemption fail the day the quotation goes. `last-gate`: the phrasings `last gate`, `final gate` and `the last check` over `docs/**`, because `purlin:verify` is Layer 0 and the first of the four enforcement layers `references/hard_gates.md` records, the CI gate job is Layer 3, and a guide that calls either of them the last gate tells a reader the reverse of what the one enforcement-layer table says; the three phrasings are one row rather than three because they are one claim said three ways, which is how the `promise` row carries its five. Widening a row is an edit to its scope tuple and to this rule, not a new rule
- RULE-13: Every backticked token containing a `/` in the file set `paths_exist` covers resolves on disk relative to the repository root, and a `<file>.md#<fragment>` token resolves to a heading of that file under its GitHub-style slug. The set today is `docs/**.md`, `README.md`, the four references the `em-dash` row names, `skills/**.md` and `agents/**.md`. The skills and the agent definitions are in it because they are where the plugin-relative paths live: a skill names `references/purlin_commands.md` bare and the reader resolves it against the plugin root, which is safe exactly as long as something checks that the file is there. A token is read as a repository path only when its first segment names something at the repository root: a token beginning `src/`, `tests/` or `utils/` is a path in someone else's project, which these guides use to show a shape. Tokens carrying `<`, `>`, `*`, `$`, a space, a pipe, a brace or `::`, and tokens beginning with `/`, are placeholders, globs, command lines, table boundaries, templates, language-scoped names and absolute paths rather than links, and are skipped; so are the tokens `RUNTIME_PATHS` covers: `.purlin/report-stamp.js` and everything under `.purlin/cache/`, `.purlin/runtime/` and `.claude/`, an entry ending in `/` covering everything beneath it. That state is generated at run time and gitignored, and the documentation names it on purpose, so a fresh clone and a fresh worktree carry none of it while the pages that name it are correct for every reader who has run a build; a lint that reported those tokens would fail on every checkout before its first build rather than on a broken link. `PATH_ALLOWLIST` holds the illustrative paths that remain. Every entry of both tables must still appear somewhere in the scanned set or the lint reports that exemption or skip as stale, so a token the documentation has stopped naming is deleted from the table rather than left to cover a path that later returns as a real one. Separately, every `purlin:<skill> --<flag>` token in the same set resolves to a `--<flag>` in the `## Usage` block of `skills/<skill>/SKILL.md`, the placeholders `--flag` and `--option` excepted, because a flag a guide teaches and the skill does not accept is an instruction that fails on first use. The reverse direction, a `## Usage` flag absent from `references/purlin_commands.md`, is printed as a note rather than as an offender while the count is above five: it is a backlog to drive down, not a gate. A path in backticks reads as a link, and a reader who follows one that resolves to nothing concludes the subsystem was deleted
