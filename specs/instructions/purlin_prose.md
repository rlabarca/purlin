# Feature: purlin_prose

> Requires: schema_spec_format
> Scope: dev/prose_lint.py, docs/*.md, docs/examples/*.md, docs/images, README.md, references/*.md, references/formats/*.md, skills/*/SKILL.md, agents/*.md, tools/*/*.md, .claude-plugin/plugin.json, .claude-plugin/marketplace.json, assets/src, .gitignore
> Stack: markdown (user-facing documentation), python (dev/prose_lint.py)
> Description: The repository's prose, held to what the code actually does, by one module rather than by a hand-written list per defect. `dev/prose_lint.py` carries four lints and their tables: `banned_strings` (a string this repository forbids, with the sections that may still carry it), `paths_exist` (a backticked path that resolves, and a skill flag that its `## Usage` block declares), `structure` (the shape a skill or agent definition must have) and `single_home` (a subject documented in exactly one file). Each table states the file set it covers today, so widening a lint is an edit to a row and to the rule that names the set, never a new rule and never a second module. The remaining rules are grep-shaped on purpose: they cannot judge whether a guide is well written; they can keep it from claiming something untrue, from carrying a second copy of a model that then drifts, and from shipping a workflow example that is not a workflow. RULE-1, RULE-4, RULE-10 and RULE-11 were hand-written lists of exactly these four shapes and retired into the tables; their numbers stay vacant.

## Rules

- RULE-2: `docs/regulated-environments.md` states what the receipt hash binds and what it does not, in two sections headed "What the vhash binds" and "What it does not bind". The first names every version 2 segment: the rule text, the feature, the proof id, the rule, the status, the tier, the platform, the test file, the test name, and the manual stamps. The second names the five things it cannot reach: the content of the test code, who ran it, when it ran, that the test is meaningful, and the runner's honesty. The file names no `.test-lock.json`, because no such file exists in the framework or is read by it; it describes `audit_llm` as executable configuration the compliance team pins rather than as a label; it describes the criteria pin as a check that is enforced on every audit rather than as a plan; and it carries the sentence `Pass D1 is deterministic; Pass D2 is an LLM pass`, which `references/remote_verification.md` states the same way. A compliance reader takes "deterministic" as a property they can rely on, so saying it of the whole of Proof Design overstates by exactly one pass
- RULE-3: `docs/index.md` is the entry point and carries four things a reader arriving cold needs: a Guides table row linking remote verification and platforms, a Guides table row linking the hard-gates reference, a summary line naming the enforcement layers and pointing at that one reference, both gauge names (`Proof Design` and `Proof Integrity`) inside the key-skills list, and `purlin:init --update` named as the command that migrates a project after the plugin moves under it. An index that omits a subsystem is how a reader concludes the subsystem does not exist
- RULE-5: FORBIDDEN: no fenced `yaml` block under `docs/` contains `run: purlin:` or `on: deploy`. A workflow cannot invoke a Claude Code skill and `deploy` is not a GitHub Actions event, so such a block is an example that fails on first paste. Every fenced `yaml` block under `docs/` that runs the verification gate runs a real test command first, then `python3 "$PURLIN_PLUGIN_ROOT/scripts/ci/verify_gate.py" --check`, and its job checks out with `fetch-depth: 0` and installs the tooling by cloning the plugin at a pinned tag. The test command is what regenerates the proof files, so without it the gate re-reads what the developer committed instead of what the code proves; `fetch-depth: 0` is what gives the gate the `git log` history it reads per proof file. Separately, no trigger `paths:` filter in any fenced `yaml` block under `docs/` names a path under `scripts/`: a consumer checkout holds specs, proofs, receipts and `.purlin/` and no Purlin `scripts/`, so a filter copied from this repository's own gate job would skip the run a spec or config change should have triggered, and the workflow would look configured while never firing. At least one such block carries a filter, so the requirement is read from a real example rather than from none
- RULE-6: Every `assets/lifecycle-*.svg` has a Mermaid source of the same stem under `assets/src/`, and `.gitignore` carries a `!assets/src/*.mmd` negation after its `*.mmd` line so those sources stay tracked. `assets/purlin-logo.svg` is hand-authored, has no Mermaid source and is exempt by name. The SVG node positions and edge paths are computed by Mermaid's layout engine and are not hand-editable, so an SVG with no source is a diagram nobody can change
- RULE-7: The three dashboard screenshots `docs/images/dashboard-summary.png`, `docs/images/dashboard-categories.png` and `docs/images/dashboard-platforms.png` exist on disk, are non-empty, and each is referenced by at least one markdown file under `docs/`. An image nothing references is one nobody notices going stale, and a reference to an image that is not there renders as a broken box
- RULE-8: `docs/regulated-environments.md` states the two things a regulated installation is qualified against, in one section headed `Pinned Plugin Version and Interpreter` under `## Integration Points (not extensions)`, each with the literal mechanism a reader can act on. The pinning statement says a regulated deployment `pins the plugin by tag` and `never installs it from a branch head`, and names the places that resolve the plugin: the marketplace entry `claude plugin marketplace add` and the `.claude/settings.json` it is stored in, the `version` field of `.claude-plugin/plugin.json` that reads the installed release back, and the CI install `git clone --depth 1 --branch v<VERSION>`. No ref field is invented for either the marketplace entry or `plugin.json`, because neither carries one. The interpreter statement says the deployment runs `Python 3.11 or newer` and calls that the `tested floor`, naming `python-version: '3.11'` as what this repository's own workflows pin, so the higher floor is evidence about where the proofs ran rather than a syntax claim. A deployment that installs from a branch head cannot say which plugin produced a proof result, and a floor no document states is one a validation record cannot cite
- RULE-9: Every `##` section of `docs/regulated-environments.md` names at least one mechanism a reader can act on. A mechanism name is one of five fixed shapes: a script path under `scripts/`, written in backticks; a rule id, written as a backticked spec or feature name immediately followed by `RULE-N`; a config field, backticked, from the closed set `audit_llm`, `audit_llm_name`, `audit_criteria`, `audit_criteria_pinned`, `mutation_checks`, `platforms`, `remote_verification`, `quality_gate`, `pre_push`, `digest`, `report`, `test_framework`, `version` and `skipped_proofs`; a skill command, backticked, of the form `purlin:<name>` with any flags; or a format or spec file path under `references/` or `specs/`, backticked. The page is read by compliance teams who cite it in a validation record, so a paragraph that asserts a property with no named mechanism is a claim they cannot check. The four approval phrases the page must never use are a `banned_strings` row under RULE-12, not a clause here
- RULE-12: `dev/prose_lint.py`'s `banned_strings` table is the one home of every string this repository forbids in its own prose. A row is `(name, unit, pattern, scope, min_files, allowlist, note)`. The pattern is searched a line at a time or a paragraph at a time, never inside a fenced code block where the text may be quoted output; a `.json` file in scope is searched in its decoded `description` values rather than in its raw bytes, because the plugin manifests carry their dashes as `\u2014` escapes and a byte sweep reads them as clean; the scope must resolve to at least `min_files` files, so no row can pass by scanning nothing; and every `(path, section)` pair in the allowlist both exempts a hit there and must itself still be hit, so an exemption that outlives the text it covers fails as loudly as a new occurrence. Four rows are enforced today. `em-dash`: U+2014 and U+2013 over `docs/**.md`, `README.md`, `references/remote_verification.md`, `references/spec_quality_guide.md`, `references/hard_gates.md`, `references/audit_criteria.md`, `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`, because a dash of either kind is a joint the writer did not have to name: the sentence it produces carries two ideas and no stated relation, and a colon, a comma or a full stop always states one. `promise`: `signed verification`, `tamper-evident`, `The vhash proves`, `(signed off)` and `signed off` over `docs/`, `references/`, `skills/`, `tools/`, `agents/` and `README.md`, allowed only in `docs/regulated-environments.md`'s "What Purlin Is NOT" section, because nothing Purlin writes is signed and nothing it writes is tamper-evident. `windows-tier`: the bare token `@windows` (not the `@windows-<id>` of a platform id and not a `...@windows.json` filename) over the same set, allowed only in the nine sections of the migration documentation that state the one-release legacy alias and its `@unit @on(<platform-id>)` rewrite, because `windows` is a platform and never a tier, and a reader who meets the token outside a section about the migration will write it as one; the word `legacy` in the same paragraph exempts nothing. `approval`: `compliance status`, `sign-off`, `signs off` and `certified` in `docs/regulated-environments.md`, because they are approval vocabulary for something Purlin never does. `RELEASE_NOTES.md` and `dev/` are out of scope by name: the notes are a historical record of what was once true, and the lint and its proofs carry the banned literals themselves. Widening a row is an edit to its scope tuple and to this rule, not a new rule
- RULE-13: Every backticked token containing a `/` in the file set `paths_exist` covers resolves on disk relative to the repository root, and a `<file>.md#<fragment>` token resolves to a heading of that file under its GitHub-style slug. The set today is `docs/**.md`, `README.md` and the four references the `em-dash` row names. A token is read as a repository path only when its first segment names something at the repository root: a token beginning `src/`, `tests/` or `utils/` is a path in someone else's project, which these guides use to show a shape. Tokens carrying `<`, `>`, `*`, `$`, a space, a pipe, a brace or `::`, and tokens beginning with `/`, are placeholders, globs, command lines, table boundaries, templates, language-scoped names and absolute paths rather than links, and are skipped; so are tokens under `.purlin/cache/`, `.purlin/runtime/` and `.claude/`, which name runtime and user-local state a checkout is not expected to carry. `PATH_ALLOWLIST` holds the illustrative paths that remain, each of which must still appear somewhere in the scanned set or the lint reports the exemption as stale. Separately, every `purlin:<skill> --<flag>` token in the same set resolves to a `--<flag>` in the `## Usage` block of `skills/<skill>/SKILL.md`, the placeholders `--flag` and `--option` excepted, because a flag a guide teaches and the skill does not accept is an instruction that fails on first use. The reverse direction, a `## Usage` flag absent from `references/purlin_commands.md`, is printed as a note rather than as an offender while the count is above five: it is a backlog to drive down, not a gate. A path in backticks reads as a link, and a reader who follows one that resolves to nothing concludes the subsystem was deleted
- RULE-14: Every `skills/*/SKILL.md` carries a YAML frontmatter block whose `name` equals its own directory and whose `description` is present, and a `## Usage` section. Every `agents/*.md` carries frontmatter with both `name` and `description`. The loader resolves a skill by its directory and shows the description wherever the skill is offered, so a `name` that disagrees with the directory is a skill that cannot be invoked by the name it prints, and a missing description is a skill nobody chooses; the `## Usage` block is where a skill declares the flags `references/purlin_commands.md`, the guides and RULE-13 all read back. The lint refuses to run against fewer than ten skills or fewer than one agent, so it cannot pass by reading an empty tree
- RULE-15: `dev/prose_lint.py`'s `HOMES` table names each subject that has exactly one home. A row is `(name, unit, pattern, home, scope, min_hits, pointer, note)`: the pattern must occur in `home` at least `min_hits` times and in no other file of `scope`, and where a `pointer` is given, a hit elsewhere that carries it is a link back to the home rather than a second copy. The scope today is `docs/**.md`, `references/**.md`, `skills/**.md`, `agents/**.md` and `README.md`, and a home that lies outside that scope is read for its own count regardless, so `min_hits` cannot fail on the home's absence. Six rows are enforced: the enforcement-layer table, reached by the row pattern `^\|\s*\*\*(Layer \d|Not a layer)`, lives only in `references/hard_gates.md` and has five rows there, because three copies is how the repository came to say the pre-push hook has two modes in one file and three in another; the three membership questions of `references/remote_verification.md`'s "Platforms, environments and prerequisites" section live only there, because a second copy is a second answer the day one of the two is edited; a paragraph naming all three of `platform`, `environment` and `prerequisite` is either in that same home or carries a link to it, because a doc that names the three categories without the link leaves a reader with three words and nowhere to resolve them; and the text of a `proof_common` rule lives only in `specs/_anchors/proof_common.md`, the row's pattern being the alternation of that anchor's own `- RULE-N:` lines with `min_hits` 25, because `references/proof_plugin_contract.md` promises in its opening paragraph to cite those rules and never restate them and carried a paraphrase of all 25 for four releases. A subject with two homes drifts at the first edit that reaches only one of them
- RULE-16: The project root is documented in two places and named in both. `docs/installation-guide.md` carries a section headed `A workspace in a subdirectory` that states the resolution order as a numbered list of three, `PURLIN_PROJECT_ROOT` first, then the climb to a `.purlin/` marker, then the working directory, and shows both ways to point the server at a workspace that is not at the repository root: the variable set under `env` in `.claude/settings.json`, and the `project_root` argument the tools take. `references/drift_criteria.md` carries a section headed `Project Root Ownership` naming the same variable and saying why no config field answers the question. The variable was called the primary mechanism in `scripts/mcp/config_engine.py` for four releases and appeared in no document, so the monorepo case, a workspace initialized one directory down and a session opened at the repository root, had no written fix at all
- RULE-17: The `## Prerequisites` section of `docs/installation-guide.md` names every name Purlin will try for an interpreter and the one override, in the order `scripts/purlin_python.sh` tries them: `python3`, then `python`, then `py`, with `PURLIN_PYTHON` named as what is tried before all three. It also names `sh`, which every git hook and the MCP server are launched through, and Git for Windows as what supplies it on the platform that does not ship one. Prerequisites that list only `Python 3.8+` leave the reader whose host carries `python` and no `python3` with a working installation and no way to know why nothing starts, which is the one failure a prerequisites list exists to prevent
