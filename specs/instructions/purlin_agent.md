# Feature: purlin_agent

> Requires: schema_spec_format
> Scope: agents/purlin.md
> Stack: markdown (agent definition)
> Description: Defines the Purlin Agent persona and behavior for Claude Code — the primary instruction document that shapes how Claude operates in spec-driven mode. Covers the core development loop, proof marker syntax, coverage gates, and routing between skills.

## Rules

- RULE-1: The agent definition's YAML frontmatter carries `name` and `description` and **no** `model` field. A shipped agent that pins a model overrides the choice of every host that installs the plugin, goes stale the moment the named model is superseded, and, on the auditor, quietly reframes independence as a model difference when it is a context difference. The host chooses; this repository's own choice, if it makes one, belongs in `.claude/settings.json`
- RULE-2: The `## Core Loop` section defines exactly 4 numbered steps: do the work, call sync_status, follow directives, ship with verify
- RULE-3: The `## Specs` section includes the 2-section format template with `> Description:`, `## Rules`, `## Proof`
- RULE-4: The `## Proof Markers` section documents marker syntax for all 3 frameworks: pytest, Jest, and shell
- RULE-5: The `## Hard Gates` section defines exactly 1 gate: proof coverage
- RULE-6: The `## Implicit Routing` section maps user intents to actions including role-based priority handling (test/build/fix → read spec + build, status → sync_status, drift → purlin:drift, spec → purlin:spec, verify → purlin:verify with independent audit, engineer items → drift + build/test, QA items → drift + verify)
- RULE-7: Every row of the `## Skills` table names a skill that exists on disk as `skills/<name>/SKILL.md`, and every shipped skill has a row, each with a non-empty purpose. The table is proved by that correspondence and not by a row count: a count passes while naming a skill that was deleted, and the previous count of 12 passed only because a thirteenth row, `purlin:init --update`, was a flag the row regex could not see. Flags belong in the row of the skill they belong to
- RULE-8: Every row of the `## References` table that names a repository path names one that exists on disk, and every row carries a non-empty topic. The table is a reading list, not an inventory, so it is proved by every row leading somewhere rather than by a count: a count freezes the table at a number, says nothing about whether a reader following a row arrives anywhere, and has to be edited by hand every time the list changes
- RULE-9: The agent instructions present the three questions (provable / proven / passes now) mapped to Proof Design, Proof Integrity and `purlin:verify`, and state that `purlin:verify` alone owns pass/fail
- RULE-10: The Core Loop states there is no fixed order, enumerates the observable states with the next step for each, and names all three supported pathways — specs-and-proofs-first, specs-then-code-and-tests, and specs-then-code-then-tests-then-verify. It contains no instruction to build code first when a spec exists without code
- RULE-11: Implicit routing includes design-intent triggers ("are my proofs any good", "before we build") routed to `purlin:audit --design`, and an integrity-target trigger that requires answering the ceiling arithmetic before starting work. The agent routes to that arithmetic by name, in `references/audit_criteria.md` (“Reaching a target Integrity score”), and carries no copy of the formula: this file is read on every turn, so a formula here costs tokens every turn and is the copy that goes stale when the denominator's definition changes
- RULE-12: The agent definition links the two shared sections rather than restating them: `references/spec_quality_guide.md#mutation-check` in the core loop, so the practice that catches a proof passing against broken code is one click away when a proof is written, and `references/purlin_commands.md#pending-migrations`, so a pending migration is handled before anything else. The reference table's `spec_quality_guide.md` row names the mutation check among what that file covers
- RULE-13: The `--no-verify` entry of the NEVER list says what the pre-push hook actually is: Layer 1 of the four enforcement layers, with `references/hard_gates.md` named as where the layers are recorded, and a mode the project chooses and may set to `off`. The entry carries none of `safety gate`, `no legitimate reason` and `defeats proof enforcement`. `hard_gates.md` states that Layer 1 blocks nothing in `off`, that the developer picks the mode with `purlin:init --pre-push` and can bypass any mode with `--no-verify`, and this repository's own config runs `pre_push: off`; an agent told the hook is a safety gate that no one has a legitimate reason to skip has been told the opposite of the reference it is pointed at, and has not been told the thing that actually holds: the mode is the project's decision and a push is not where an agent overturns it
