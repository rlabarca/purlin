Show model routing, or turn it on or off. Each Purlin skill names its tier, `fast`, `balanced` or
`performance`, in its own front matter; this skill gives each tier a model for the project, in
`.purlin/routing.json`, writes one project skill per Purlin skill that runs it on that model, and
sets the project's sessions to start as the Purlin agent. `references/formats/routing_format.md`
is the one home of the tables, the file, the project skills and the hand-off.

**Paths in this skill:** every `references/` and `agents/` path below is relative to the plugin
root; see `references/purlin_commands.md#path-resolution`.

A line marked **Stop and ask** is a question for the person: print it, end your turn, and act
only on their answer. Never answer it yourself.

## Usage

```
purlin:route            Show the tier and model of each skill
purlin:route on         Write or change the routing file, the project skills and the session settings
purlin:route off        Run every skill on the session's model again
```

`purlin:route` itself runs on the session's model, whatever the file says.

## Show

Read `.purlin/routing.json`, and the `tiers` of `.purlin/routing.local.json` over it. Print one
line per skill: its name, its tier and that tier's model, the tier from the file's `skills` entry
or else the skill's own `tier:`, as the format gives them, and the command that runs it on that
model, `/<skill>`.

With no file, print `Routing is not set up. Run purlin:route on.` With `"enabled": false`,
print `Routing is off. Run purlin:route on to turn it on.` Write nothing either way.

## On

Progress:
- [ ] The person has answered the question in step 3
- [ ] `.purlin/routing.json` written
- [ ] The project skills written
- [ ] `.claude/settings.json` merged
- [ ] Every check in step 7 passes
- [ ] Committed as `chore: model routing`

1. Read `.purlin/routing.json` where it exists, and keep each setting the person does not change.
2. Name the models this harness can start, as it names them. In Claude Code these are the three
   slots `haiku`, `sonnet` and `opus`, which a gateway may fill with another provider's models.
   Where the harness names none, ask the person to name them. Read the format's part "The two
   tables" and show each skill's tier from it.
3. **Stop and ask** the person to confirm the model each tier gets, and any skill whose tier in
   this project differs from its own. Ask too whether the models are the team's or theirs alone.
4. Read the format's part "The file". Write `.purlin/routing.json` with
   `"schema": "purlin-routing/1"`, `"enabled": true`, the `tiers` and any `skills` confirmed, in
   that shape. Where the models are the person's alone, write the tiers to
   `.purlin/routing.local.json` instead, and leave the team's as they are.
   `.purlin/routing.local.json` holds `tiers` alone, and git ignores it: add the line
   `.purlin/routing.local.json` to `.gitignore` where no line covers it.
5. Read the format's parts "The project skills" and "The hand-off message". For each skill that
   names a tier but `init`, write `.claude/skills/<skill>/SKILL.md` as the format's part "The
   project skills" gives it: the hand-off form for `spec`, `spec-from-code` and `sign`, the model
   form for the rest. Copy each template exactly, changing only `<skill>`, `<tier>` and `<model>`
   and filling in the hand-off message's lines; leave no `<` placeholder in a file. `purlin:route on`
   never writes over a file there whose description does not open on `Generated by purlin:route`: name
   each such skill, and say it runs on the session's model.
6. Merge `"agent": "purlin:purlin"` and `"model": "<the balanced model>"` into
   `.claude/settings.json`, keeping every other setting, or into `.claude/settings.local.json`
   where the models are the person's alone.
7. Check what you wrote before you commit: each project skill's `model:`, or the model its hand-off
   message names, is its tier's model in the table; there is no project skill for `init`; no file
   holds a `<` placeholder; `.claude/settings.json` holds the agent and the balanced model and
   every setting it held before. Fix what fails and check again until every check passes.
8. Commit `.purlin/routing.json`, `.claude/settings.json` and `.claude/skills/`, with `.gitignore`
   where step 4 changed it, and nothing else, as `chore: model routing`. The commit takes the
   `chore:` prefix of `references/commit_conventions.md`. Show the table as "Show" says. Tell the
   person that routing works in this session now, that new sessions start as the Purlin agent on
   the balanced model, and to type `/<skill>`, not /purlin:<skill>, since `/purlin:<skill>` and
   requests in plain words run on the session's model.

## Off

Set `"enabled": false` in `.purlin/routing.json` and keep every other setting. Off removes each
file under `.claude/skills/` whose description opens on `Generated by purlin:route`, and no other.
Off then takes out of `.claude/settings.json`, or `.claude/settings.local.json`, the `agent` where
it is `purlin:purlin` and the `model` where it is the `balanced` model, keeping every other
setting. Commit `.purlin/routing.json`, `.claude/settings.json` and `.claude/skills/` alone as
`chore: model routing off`. Every skill then runs on the session's model, sessions start as they
did before routing, and `purlin:route on` turns routing on again with the settings kept.

## Gotchas

- Write nothing until the person answers the **Stop and ask**: a session that ends at the question
  leaves routing unset.
- `/purlin:<skill>` always runs Purlin's own skill on the session's model; only `/<skill>` carries
  the tier's model.
- A skill another skill runs, and a request in plain words, use the model already running.
- Routing works in this session at once, and this session keeps its own model; the settings make
  new sessions start on the `balanced` model.
- `purlin:route on` starts no model, so a model the harness does not know fails at the first skill that
  names it. Run `purlin:route on` again to change it.
