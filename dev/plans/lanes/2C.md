## The interfaces lane 2A calls (write exactly these; 2A's run script imports them lazily)

```python
# scripts/run/records.py
write_record(project_root, record, runner, os_name=None) -> str   # path written; prune applied
commit_records(project_root, paths, identity, message) -> str     # identity 'developer' | 'ci'; the sha
tag_validated(project_root, name, record_paths) -> None
load_records(project_root, ref=None) -> dict      # delegate to scripts/mcp/purlin/records.py
record_label(project_root, path) -> str           # delegate to the same
# scripts/run/ci.py
post_pr_comment(project_root, text) -> bool       # GitHub through the REST API with GITHUB_TOKEN; ADO with System.AccessToken; False with a printed reason otherwise
publish_dashboard(project_root, out_dir) -> str   # copies the dashboard page and data into out_dir for the workflow's upload step
# scripts/run/remote.py
run_remote(project_root, args) -> int             # push the branch, watch, pull, print the table
# scripts/run/workflow.py
render_workflow(host, env_tags, purlin_ref, upstream_check=False) -> str   # the workflow text phase 5's init writes
```

The `record` dict arrives from 2A in the `purlin-record/1` shape B3 lists; this lane names
the file, prunes, writes, commits and labels. C3 fixes the file name:
`<YYYYMMDDTHHMMSSZ>-<commit7>-<runner>[-<os>].json`, runner `ci` or the developer's git
email local part lowercased with non-alphanumerics as `-`.
