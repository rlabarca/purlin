## What you produce

1. **A findings file**, `dev/plans/lanes/tl-13-findings.md`, in four sections, each a list of
   findings with the file and line, one sentence saying what is wrong, and one saying the
   fix:
   - **Logic.** Read `states.py`, `gate.py`, `records.py`, `signatures.py`, `payload.py`,
     `board.py`, `sign.py`, `brief.py`, `gate_check.py`, `purlin_run.py`, `results.py`,
     `remote.py`, `scaffold.py`, `update.py`, `pre-push.sh`, the workflow templates. For each
     gate, walk one rule through the chain by hand (bar `passed` and bar `strong`; sources
     `local` and `ci`; a partial run; an unsettled brief; a hold; a stale signature; `sign_at`
     `strong` and `all`) and confirm the code gives the answer decisions 23 to 30 give. Every
     disagreement is a finding. A case the decisions do not cover is a question for the user,
     listed under "Questions", not decided.
   - **Terms.** One vocabulary across `references/glossary.md`, every reference, every skill,
     `agents/purlin.md`, every docs page, `README.md`, the specs' prose, the CLI strings in
     the code, the board's strings and the deck text in `dev/plans/lanes/tl-12B-slides.md`.
     Each place a concept has two names, or a name has two meanings, is a finding. Run
     `dev/test_vocabulary.py`'s collapsed scan and a scan of your own for the live words used
     loosely (`record`, `result`, `run`, `audit`, `review`, `sign`, `bar`, `level`, `gate`,
     `source`, `platform`).
   - **Elegance.** Duplicated logic across modules; a function that decides what another
     module already decided; dead code left by the retired model (risk, ai_review_at,
     developer source, the old review list, `needs a person`, `manual audit`, `not required`,
     `verify`); names that no longer say what the thing is; a spec rule that pins an
     implementation detail rather than a behaviour. Each is a finding with the fix.
   - **Clarity.** Read every docs page as a developer who has never seen Purlin, in the
     order `docs/index.md` gives. Each place you had to read twice, or a term appeared before
     its definition, or a page said something the code does not do, is a finding.
2. **The fixes** you can make without a user decision, committed one logical change at a
   time, each with its test where behaviour changed, the sweep green at the end. Name every
   file you touched in the report.
3. **Questions for the user**, in `tl-13-findings.md` under "Questions", each one sentence
   with the two or three answers it could take and what each would change. The orchestrator
   puts them to the user before anything else moves.
