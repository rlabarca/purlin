## What phase 9 is

Purlin dogfoods at `gate: recorded`. The 37 frozen specs describe the old code; each phase 9
lane writes the specs for one part of the new surface, tags the existing `dev/` tests with
proof markers so the runtime proofs prove them, and deletes the frozen specs its group
replaces in the same commit. The orchestrator then runs `purlin:init --update` on this
repository, the three hand-run CLI checks, verify locally, and the user pushes so
`purlin.yml` runs.

## Inputs every phase 9 lane reads

- `dev/plans/evidence-workflow.md` in full; `references/formats/spec_format.md`
  (Format-Version 11: rule tags, proof tiers, `@env`, `@manual`, `> Scope:`, `> Requires:`);
  `references/spec_quality_guide.md`; `references/rule_examples.md`;
  `references/formats/proofs_format.md` and `references/proof_plugin_contract.md` (the
  marker syntax per framework: `@pytest.mark.proof("<feature>", "PROOF-N", "RULE-N")` for
  pytest, the shell plugin's function for shell suites); `references/review_criteria.md`
  (what a proof must state: trigger, expected value, negative case).
- The frozen specs your group replaces (read them for the rules still true; most of their
  rules describe retired mechanisms and are dropped).
- The code and tests your group covers, listed in your brief.
- `scripts/run/purlin_run.py --help` and `scripts/mcp/purlin/status.py`: after tagging,
  `python3 scripts/run/purlin_run.py --feature <name> --quick --project-root .` must show
  every rule of your specs at Tested.

## Rules every phase 9 lane follows

- A spec is `specs/<category>/<feature>.md` in Format-Version 11: `> Scope:` naming the
  code files, rules that are observable claims (one line each, `[risk: ...]` where the
  claim is more than low risk, `[origin: eng]` may be omitted since it is the default),
  one proof per rule at least, each proof stating trigger and expected value, tiers `@unit`
  for pytest, `@e2e` for the shell suites, `@manual` only where no test can exist. Rule
  counts per spec: what the code does, not what the old spec had; the plan's estimate is
  about 150 rules across the set.
- Proof markers go on existing tests. Add a test only where a rule has none; keep such
  additions small and in the file that already covers the module. Every marker names a
  proof that exists in the spec; every proof names a test that carries its marker (the run
  script's two loud failures check this).
- Delete the frozen specs your brief lists with `git rm`, in the same commit as their
  replacements. Never delete another lane's.
- `specs/_anchors/` is lane 9G's; the other lanes may add `> Requires: proof_common` and
  the schema anchors but do not edit them.
- The one `@env(windows)` proof this repository keeps is the file-locking check in
  `scripts/review/static_checks.py` (lane 9C). No other `@env` tag in this repository.
- No retired vocabulary (`sys.platform` excepted), no emoji, no `dev/` path in a spec's
  prose beyond the `> Scope:` and proof lines that name test files (those are allowed:
  this repository's specs describe this repository).
- Before committing: `git clean -f specs/` is no longer needed (proofs are runtime), but
  `git status` must be clean of `.purlin/runtime/`.
- Worktree `/Users/richlabarca/LocalCode/purlin-wt/9G`, branch `lane/9G` from
  `evidence-workflow`; `/Users/richlabarca/LocalCode/purlin/.venv/bin` and
  `/opt/homebrew/opt/dotnet@8/bin` first on PATH; commit prefixes `spec(<name>):` and
  `test(<name>):`; the two attribution lines; `PURLIN_SKIP_DIGEST=1`; end with the DONE
  note, listing every spec written with its rule count and every frozen spec deleted.
