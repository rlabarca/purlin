the gate, and a test that fails on Windows for a portability reason is telling the truth
about the code or about itself. Fix them.

## How

- The Windows job log: `gh run view --job 103864548612 --log` (the pytest arm's own output
  is not in it: the run script captures it). Reproduce on this Mac by reading the tests:
  the usual causes are `/` versus `\` in path assertions (`os.path.join`, `pathlib`), `#!`
  shebangs and `chmod +x` (no execute bit on Windows), `bash` spawned by name, `sh -c`,
  `os.getuid`, symlinks, `fcntl`, `\n` versus `\r\n` in text comparisons, `tempfile` paths
  with spaces, `git` core.autocrlf, and hard-coded `python3`. Where a test needs a shell that
  Windows lacks, the honest fix is a skip with a reason on Windows (`sys.platform` is the
  one permitted read) and, when the rule itself is about shell behaviour, an `@env(linux)`
  tag on the proof so the Windows record says `needs linux`. Where the code under test is
  wrong on Windows (a path built with `/`, a hook written without the right line endings,
  a subprocess that assumes `bash` on PATH), fix the code: that is what the Windows job is
  for.
- The heaviest files: `dev/test_init_scaffold.py` (77), `dev/test_upstream.py` (21),
  `dev/test_run_script.py` (11), `dev/test_security.py` (5), `dev/test_drift.py` (5),
  `dev/test_proof_stress.py` (4), `dev/test_proof_plugins_missing.py` (3),
  `dev/test_purlin_version.py` (3), `dev/test_skills.py` (3), then singles.
- You cannot run Windows here. Read each failing test, decide the cause, make the change,
  and keep every test green on this Mac. The orchestrator pushes after you land and the
  Windows job is the check; expect one round of follow-up from its log.
