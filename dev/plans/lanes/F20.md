## Change

- `_commit_github`: build the tree in one request. The trees endpoint accepts each entry as
  `{"path", "mode": "100644", "type": "blob", "content": "<utf-8 text>"}` and creates the
  blob itself; every file this commit carries is UTF-8 JSON, so no separate blob request
  is needed. Keep the deletion entries (`sha: null`) as they are. Keep `POST /blobs` only
  for a file that is not valid UTF-8 (`decode` fails), which none of ours is; a test covers
  the branch with one binary file.
- `_api`: on 403 or 429, read `Retry-After` (seconds) or `x-ratelimit-reset` (epoch) and
  wait that long, capped at 120 s, then retry, up to three times; print one line per wait
  (`git host asked for a pause of N s`). Keep the existing 422 retry on the ref update.
- If the tree request itself is refused for size (GitHub answers 422 with a message about
  the tree), split the entries into batches of 200 built as successive trees with
  `base_tree` chained, and say so in a comment; do not implement batching if one request
  is accepted for 600 entries (it is: the documented limit is on the request body, and
  600 small JSON files are well under it).
- Tests in `dev/test_records.py` with the HTTP boundary mocked as the file already does:
  the tree request carries `content` and no blob request is made for text files; a 403
  with `Retry-After: 1` is retried once and succeeds; a fourth 403 raises with the
  status in the message. Proof markers on `specs/run/records.md` RULE-5 (edit its text to
  say the commit is one tree request; keep the number) and a new rule for the pause
  (`[risk: medium] [origin: eng]`).
- `references/formats/record_format.md` and `docs/running-and-records.md`: correct any
  sentence that describes blob-by-blob commits.
